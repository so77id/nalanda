# Estructuras de Datos · Listas Enlazadas

El TDA Sequence no dice dónde viven los elementos de la colección, y esa
libertad admite dos decisiones opuestas. El arreglo los guarda juntos, y eso
le fija los costos: llegar a una posición es una cuenta, abrir un hueco
obliga a correr todo lo que sigue. Esta clase estudia la estructura que toma
la decisión contraria —cada elemento por su lado, guardando dónde está el
siguiente— y cumple el mismo contrato con los costos casi invertidos.

Presentamos la lista simplemente enlazada con todas sus operaciones, sus
cuatro variantes, la comparación completa contra el arreglo y los cuatro
ejercicios que la vuelven una herramienta de trabajo.

<Slide title="El TDA Sequence">

**dónde se insertó cada uno**, y no su valor. El contrato que estudiamos en
[[edd-introduccion|Estructuras de Datos · Introducción]] es este:

El contrato fija qué se le puede pedir a la colección y qué significa cada
pedido. No dice **cómo** se cumple, y esa libertad es la que permite que dos
estructuras muy distintas lo cumplan igual de bien.

</Slide>

<Slide title="El precio de tener los elementos juntos">
El arreglo cumple el contrato guardando los elementos en un **bloque
consecutivo**: casillas del mismo tamaño, una al lado de la otra.

Las direcciones suben de cuatro en cuatro, así que la posición `i` está
siempre en `base + i × 4`. Esa cuenta es lo que hace que `getAt(i)` cueste
$$\Theta(1)$$: no hay que buscar, hay que calcular.

Y esa misma cuenta cobra su precio. Para que valga **no puede haber huecos**,
así que insertar al principio obliga a correr los $$N$$ elementos una casilla
a la derecha antes de escribir nada.

</Slide>

**Tenemos un elemento en la mano y no hay manera de llegar al siguiente.** Ni
siquiera sabemos cuál es: los cuatro valores están ahí, pero como colección
ya no existen.

Con esa referencia guardada, los cuatro valores vuelven a formar una
secuencia aunque estén desperdigados: desde el primero se llega al segundo,
del segundo al tercero, y así hasta el último. El orden ya no lo da la
posición en memoria, lo da el enlace.

Y ahí está lo que ganamos. Cambiar el orden, o meter un elemento entre dos,
pasa a ser cambiar a quién apunta un enlace: nada se mueve de lugar, porque
el lugar dejó de importar.

Esa referencia al siguiente se llama **`next`**.

```java
class Node {
    int value;
    Node next;

    Node(int value) {
        this.value = value;
        this.next = null;
    }
}
```

El campo `next` no es una copia del siguiente nodo: es una **referencia** a
él. Un nodo recién creado tiene `next` en `null`, que es la manera de decir
«después de mí no hay nadie».

Nada obliga a que dos nodos consecutivos estén cerca en memoria. Pueden
haberse creado en momentos distintos y quedar en direcciones sin relación
entre sí. Lo único que los mantiene en orden es el enlace.

</Slide>

Una sola referencia, `head`, alcanza para tener la cadena entera: desde ella
se llega al primero, y de cada uno al que sigue. El último no apunta a
ninguno, y ese `null` es lo que dice dónde termina.

</Slide>

<Slide title="La estructura en código">
Con el nodo definido, la lista completa se sostiene con dos atributos:

```java
public class LinkedList {
    private Node head;
    private int size;

    public LinkedList() {
        this.head = null;
        this.size = 0;
    }
}
```

`head` es la puerta de entrada: desde ahí se llega a todos los demás nodos
siguiendo enlaces. Una lista vacía es exactamente `head == null`.

`size` no es indispensable —se podría contar la cadena cada vez— pero
contarla cuesta recorrerla entera. Guardar el número y mantenerlo al día en
cada inserción y cada eliminación convierte `len()` en una lectura.

</Slide>

<Slide title="Las invariantes de la lista enlazada">
Tres propiedades tienen que valer antes y después de cada operación. Si
alguna se rompe, las demás operaciones dejan de funcionar aunque su código
sea correcto.

1. **`head` apunta al primer nodo, o a `null` si la lista está vacía.** Es el
   único punto de entrada a la cadena. Si `head` queda apuntando a un nodo
   del medio, todo lo anterior se vuelve inalcanzable: sigue en memoria y no
   hay manera de llegar.

2. **Desde `head`, siguiendo `next`, se llega a todos los nodos y se termina
   en `null`.** La cadena no tiene cortes ni ciclos. Un corte pierde la cola;
   un ciclo hace que cualquier recorrido no termine nunca.

3. **`size` es la cantidad de nodos de esa cadena.** Cada operación que
   agrega o saca un nodo lo actualiza. Un `size` desfasado convierte en
   válidos índices que no existen.

La segunda es la que fija los dos costos de la estructura, el barato y el
caro, y por eso conviene tenerla a mano. Gracias a ella insertar al principio
es cambiar un enlace, sin tocar ningún otro nodo. Y por ella misma, llegar a
la posición `i` obliga a dar `i` saltos: la única forma de avanzar en la
cadena es preguntarle a cada nodo por el siguiente.

</Slide>

## Las operaciones de la lista enlazada

<Slide title="build · crear la lista">
Crear una lista es dejarla en su estado inicial: sin ningún nodo.

```java
public LinkedList() {
    this.head = null;
    this.size = 0;
}
```

Los dos valores no son arbitrarios: son lo que las invariantes exigen cuando
no hay nodos. `head` en `null` dice que no hay primer nodo, y `size` en cero
dice que la cadena que arranca ahí tiene largo cero. Ambas cosas son ciertas,
y la lista queda en un estado válido antes de que nadie la use.

Ese es el trabajo del constructor y todo su trabajo: dos asignaciones que no
dependen de nada, así que crear una lista cuesta $$\Theta(1)$$.

</Slide>

<Slide title="La lista vacía y el largo">
Dos operaciones que no recorren nada:

```java
public boolean isEmpty() {
    return head == null;
}

public int len() {
    return size;
}
```

`isEmpty()` lee la primera invariante directamente: una lista está vacía
exactamente cuando `head` es `null`. No hace falta contar.

`len()` es $$\Theta(1)$$ porque `size` se mantiene al día en cada inserción y
cada eliminación. Ese es el trato: pagamos una suma o una resta en cada
operación que cambia la cadena, y a cambio preguntar el largo nunca cuesta
recorrerla.

</Slide>

<Slide title="getAt · el dato de la posición $$i$$">
Pedir el elemento de una posición no es una cuenta: es un recorrido.

```java
int getAt(int i) {
    if (i < 0 || i >= size) {
        throw new IndexOutOfBoundsException();
    }
    Node current = head;
    for (int j = 0; j < i; j++) {
        current = current.next;
    }
    return current.value;
}
```

Cada paso del recorrido es un salto, y hay que darlos todos: no existe forma
de adelantarse. Llegar a la posición `i` cuesta `i` saltos, y en el peor caso
—el último nodo— son $$N - 1$$, así que la operación es $$\Theta(N)$$.

Es exactamente la operación que el arreglo resuelve con una multiplicación y
una suma. Aquí no hay ninguna cuenta posible, porque las direcciones de los
nodos no guardan relación entre sí.

</Slide>

  index={[0, 3, 6]}

La misma llamada, tres posiciones: ninguna, tres y seis saltos. El costo de
`getAt` no es un número, es la posición que se pide.

</Slide>

<Slide title="buscar · el recorrido hasta el valor">
Buscar un valor recorre la cadena preguntando nodo por nodo.

```java
int search(int x) {
    Node current = head;
    for (int i = 0; current != null; i++) {
        if (current.value == x) {
            return i;
        }
        current = current.next;
    }
    return -1;
}
```

El peor caso visita los $$N$$ nodos, y llega por dos caminos: que el valor
esté al final, o que no esté. En los dos hay que preguntarle a todos antes de
poder responder, así que la operación es $$\Theta(N)$$. Un arreglo
desordenado cuesta lo mismo, y por una vez las dos estructuras empatan.

El empate se rompe cuando los datos están ordenados. Sobre un arreglo
ordenado la búsqueda binaria baja a $$\Theta(\log N)$$ porque puede saltar
al elemento del medio con una cuenta. Sobre una lista ordenada no puede: para
llegar al nodo del medio hay que caminar hasta él, y entonces ya se recorrió
media cadena. La lista se queda en $$\Theta(N)$$ aunque esté ordenada.

</Slide>

  target={[7, 8, 4]}

Los tres casos que importan, en orden: el valor que está adelante y corta al
primer nodo, el que está al final y obliga a recorrerlo todo, y el que no
está —que también obliga a recorrerlo todo, porque solo al llegar a `null` se
puede afirmar que no está.

</Slide>

<Slide title="insertFirst · insertar al comienzo">
Insertar al principio se resuelve con tres asignaciones, y ninguna de las tres
depende de cuántos elementos haya en la lista.

```java
void insertFirst(int x) {
    Node fresh = new Node(x);
    fresh.next = head;
    head = fresh;
    size++;
}
```

El nodo nuevo toma el enlace que tenía `head`, y recién entonces `head` pasa a
apuntar al nodo nuevo. El orden importa: al revés se pierde la referencia al
resto de la cadena.

Los demás nodos no se enteran. Ninguno cambia de lugar ni de contenido, y por
eso el costo no crece con el largo: la operación es $$\Theta(1)$$. La
invariante que restaura es la primera —`head` apunta al primer nodo— y
restaurarla cuesta esas tres asignaciones, haya cero elementos o un millón.

</Slide>

<Slide title="insertFirst">
<SequenceStepper

La cadena creció cuatro veces y ningún nodo se movió de su sitio. En un
arreglo, cada una de esas cuatro inserciones habría corrido todos los
elementos una casilla a la derecha para abrir el hueco: $$\Theta(N)$$ cada
vez. Aquí no hay hueco que abrir, porque los nodos no están obligados a ser
vecinos, y por eso la lista gana en $$\Theta(1)$$ — el mismo pedido, y el
costo dejó de depender del largo.

</Slide>

<Slide title="insertLast · insertar al final">
Insertar al final invierte la comparación anterior.

```java
void insertLast(int x) {
    Node fresh = new Node(x);
    if (head == null) {
        head = fresh;
    } else {
        Node current = head;
        while (current.next != null) {
            current = current.next;
        }
        current.next = fresh;
    }
    size++;
}
```

Enlazar el nodo nuevo cuesta una asignación, igual que antes. Lo caro es
llegar: el único nodo autorizado a apuntar al nuevo es el último, y la única
forma de saber cuál es consiste en recorrer la cadena hasta encontrar al que
tiene `next == null`. Son $$N - 1$$ saltos, y el total queda en
$$\Theta(N)$$.

La cadena vacía es un caso aparte, y por eso el método pregunta primero: sin
nodos no hay un último al que enlazarse, así que lo que la inserción asigna
es `head`.

</Slide>

En el arreglo esta misma operación era la barata —escribir en `data[size]`, sin
recorrer nada— así que aquí la comparación se da vuelta: la lista paga
$$\Theta(N)$$ por llegar al final justamente porque nadie guarda dónde está.

</Slide>

<Slide title="insertAt · encontrar al previo">
Insertar en una posición cualquiera se hace en dos tiempos: primero llegar,
después enlazar.

```java
void insertAt(int i, int x) {
    if (i < 0 || i > size) {
        throw new IndexOutOfBoundsException();
    }
    if (i == 0) {
        insertFirst(x);
        return;
    }
    Node fresh = new Node(x);
    Node prev = head;
    for (int j = 0; j < i - 1; j++) {
        prev = prev.next;
    }
    fresh.next = prev.next;
    prev.next = fresh;
    size++;
}
```

El nodo que hay que modificar no es el de la posición `i`, sino el de la
posición `i - 1`: es el que tiene que dejar de apuntar a su siguiente para
apuntar al nodo nuevo. Por eso el recorrido se detiene un paso antes. Y en la
posición 0 no existe ese previo, así que ahí el trabajo es el de
`insertFirst`.

El orden de las dos asignaciones no es libre. Primero el nodo nuevo toma el
enlace del previo, y solo después el previo apunta al nuevo. Al revés se
pierde la referencia al resto de la cadena y todo lo que venía después queda
inalcanzable.

</Slide>

<Slide title="deleteFirst · eliminar el primero">
Eliminar el primer nodo es el reflejo de insertarlo.

```java
int deleteFirst() {
    if (head == null) {
        throw new NoSuchElementException();
    }
    Node old = head;
    head = head.next;
    size--;
    return old.value;
}
```

`head` pasa a apuntar al segundo nodo y la cadena queda completa desde ahí.
El nodo que salió ya no es alcanzable desde ninguna parte, y el recolector de
basura de Java se encarga del resto.

Son dos asignaciones y ningún recorrido, haya dos nodos o dos millones: la
operación es $$\Theta(1)$$.

Sobre un arreglo la misma operación cuesta $$\Theta(N)$$: eliminar la
posición 0 deja un hueco que la memoria consecutiva no admite, así que hay
que copiar todo lo demás una casilla a la izquierda. Es el mismo intercambio
que en `insertFirst`, en el otro sentido.

</Slide>

<Slide title="deleteLast · eliminar el último">
Eliminar el último nodo es la operación que mejor muestra qué le falta a esta
estructura.

```java
int deleteLast() {
    if (head == null) {
        throw new NoSuchElementException();
    }
    Node old;
    if (head.next == null) {
        old = head;
        head = null;
    } else {
        Node prev = head;
        while (prev.next.next != null) {
            prev = prev.next;
        }
        old = prev.next;
        prev.next = null;
    }
    size--;
    return old.value;
}
```

El nodo que hay que modificar es el **anteúltimo**: es quien debe pasar a
apuntar a `null` para que la cadena vuelva a terminar bien. Y un nodo no
guarda quién lo apunta, solo a quién apunta: desde el último no hay manera de
retroceder un paso. La única salida es volver a `head` y recorrer.

Con un solo nodo no hay anteúltimo a quien pedirle nada, y `prev.next.next`
reventaría contra `null`. Por eso el método pregunta antes: ahí el que
cambia es `head`.

Ese recorrido es lo que se paga: $$N - 2$$ saltos para llegar al anteúltimo,
y después una sola asignación. La operación es $$\Theta(N)$$, y lo es por
llegar, no por borrar.

Sobre un arreglo esta operación es $$\Theta(1)$$ —basta con restar uno a
`size`—, exactamente al revés que `insertFirst`.

</Slide>

El recorrido se acorta con la cadena, pero nunca desaparece: cada borrado
vuelve a partir de `head` porque el último nodo no sabe quién lo apunta.

</Slide>

<Slide title="deleteAt · eliminar una posición">
Eliminar una posición cualquiera repite el patrón: llegar al previo, y
después una sola asignación.

```java
int deleteAt(int i) {
    if (i < 0 || i >= size) {
        throw new IndexOutOfBoundsException();
    }
    if (i == 0) {
        return deleteFirst();
    }
    Node prev = head;
    for (int j = 0; j < i - 1; j++) {
        prev = prev.next;
    }
    Node old = prev.next;
    prev.next = old.next;
    size--;
    return old.value;
}
```

El previo pasa a apuntar al siguiente del nodo que sale, que queda fuera de
la cadena sin haber movido ningún otro dato. La invariante que se restaura es
la segunda: desde `head` se sigue llegando a todos los nodos y se sigue
terminando en `null`.

Las dos estructuras cuestan $$\Theta(N)$$ aquí, pero no gastan ese
$$\Theta(N)$$ en lo mismo, y conviene ver en qué.

- **El arreglo** hace $$N$$ **escrituras**: corre cada elemento posterior una
  casilla a la izquierda para tapar el hueco. Toca la memoria $$N$$ veces.
- **La lista** hace $$N$$ **lecturas** y una sola escritura: sigue $$N$$
  enlaces para encontrar al previo, y recién ahí cambia un puntero.

Leer es más barato que escribir, así que la lista suele ganar en el reloj
aunque empate en la notación. Y la diferencia crece cuando el elemento es
grande: mover un objeto de cien bytes cien veces no cuesta lo mismo que
seguir cien punteros.

</Slide>

<Slide title="Los casos de borde">
Todos los métodos de esta clase empiezan preguntando algo antes de trabajar.
No es prolijidad: cada `if` del principio tapa un caso en el que el cuerpo
general del método **no funciona**.

| El caso | Qué pasa si el método no pregunta | El `if` que lo evita |
| --- | --- | --- |
| La cadena está vacía y le pedimos sacar un nodo | `head` es `null` y el método lo sigue igual | `if (head == null) throw new NoSuchElementException();` |
| La cadena está vacía y le insertamos al final | no hay último al que enlazarse | `if (head == null) { head = fresh; }` |
| Queda un solo nodo y borramos el último | no hay anteúltimo: `prev.next.next` revienta | `if (head.next == null) { old = head; head = null; }` |
| La posición es 0 en `insertAt` o `deleteAt` | no hay nodo previo, y se termina modificando el nodo equivocado | `if (i == 0)`, que delega en la operación del frente |

Notemos qué tienen en común: **los cuatro son el extremo de la cadena**, que
es donde vive `head`. El cuerpo general de cada método supone que hay un nodo
antes del que le interesa, y en los extremos ese nodo no existe.

</Slide>

<Slide title="Operaciones y sus costos">
| Molde | Operación | Peor caso | Invariante que restaura |
|---|---|---|---|
| crear | `build()` | $$\Theta(1)$$ | Deja las invariantes en su caso base: `head` en `null`, `size` en cero |
| consultar | `len()` | $$\Theta(1)$$ | Ninguna: `size` ya guarda el dato |
| consultar | `getAt(i)` | $$\Theta(N)$$ | Ninguna: no cambia la cadena |
| consultar | `search(x)` | $$\Theta(N)$$ | Ninguna: no cambia la cadena |
| modificar | `setAt(i, x)` | $$\Theta(N)$$ | Ninguna: cambia un valor, no la forma |
| modificar | <code style={{ color: 'var(--color-keep)' }}>insertFirst(x)</code> | <span style={{ color: 'var(--color-keep)', fontWeight: 700 }}>$$\Theta(1)$$</span> | `head` apunta al primero: el nodo nuevo enlaza al que lo era |
| modificar | `insertLast(x)` | $$\Theta(N)$$ | La cadena termina en `null`: hay que encontrar quién lo hace |
| modificar | `insertAt(i, x)` | $$\Theta(N)$$ | La cadena queda completa: el previo enlaza al nuevo, el nuevo al que seguía |
| modificar | <code style={{ color: 'var(--color-keep)' }}>deleteFirst()</code> | <span style={{ color: 'var(--color-keep)', fontWeight: 700 }}>$$\Theta(1)$$</span> | `head` apunta al primero: pasa a ser el segundo |
| modificar | `deleteLast()` | $$\Theta(N)$$ | La cadena termina en `null`: el nuevo último debe apuntar ahí |
| modificar | `deleteAt(i)` | $$\Theta(N)$$ | La cadena no se corta: el previo salta al siguiente |

Las dos destacadas son las únicas de costo constante, y las dos operan sobre
el mismo lugar: el principio de la cadena. Es el único punto al que se llega
sin caminar, porque `head` ya está ahí.

</Slide>

<Slide title="Dónde vive el costo">
Todo lo que cuesta $$\Theta(N)$$ en esta tabla lo cuesta por la misma razón, y
no es la operación en sí: es **llegar** al lugar donde hay que operar.

Enlazar un nodo cuesta lo mismo en cualquier parte de la cadena —una
asignación—, pero para enlazarlo en la posición `i` primero hay que tener en
la mano el nodo `i - 1`, y para tenerlo hay que dar `i - 1` saltos desde
`head`.

De ahí sale una regla para leer la tabla entera sin memorizarla:
**preguntemos dónde ocurre la operación, y contemos los saltos que hacen
falta para llegar ahí**.

- Si ocurre en el primer nodo, no hay saltos: `head` ya lo tiene en la mano.
  $$\Theta(1)$$.
- Si ocurre en cualquier otro lado, hay que caminar desde `head` hasta ahí, y
  en el peor caso eso es toda la cadena. $$\Theta(N)$$.

No hace falta recordar once costos: alcanza con saber dónde empieza el único
camino que la lista ofrece.

</Slide>

## Las variantes de la lista enlazada

<Slide title="La lista con tail · un puntero más">
La primera variante agrega un solo atributo:

```java
public class LinkedList {
    private Node head;
    private Node tail;
    private int size;
}
```

`tail` guarda una referencia al último nodo. Con eso aparece una cuarta
invariante, y mantenerla es trabajo de cada operación:

4. **`tail` apunta al último nodo de la cadena, o a `null` si está vacía.**
   Si queda apuntando a un nodo que ya salió de la lista, insertar al final
   enlaza contra un nodo inalcanzable y lo insertado se pierde.

Las tres invariantes anteriores no cambian. Lo único nuevo es esta, y todo lo
que sigue se explica por ella.

</Slide>

<Slide title="insertLast con tail · llegar sin caminar">
<SequenceStepper
  eda="linked-list-singly"
  operation="insert-last"
  values={[7, 3, 1, 5]}
  value={9}
  tail
/>

El recorrido desapareció. `tail` ya tiene en la mano el nodo que hay que
modificar, así que enlazar el nodo nuevo y actualizar `tail` son dos
asignaciones: la operación baja de $$\Theta(N)$$ a $$\Theta(1)$$.

Es el patrón que se repite en toda la unidad: guardar un dato de más
—un puntero— convierte un recorrido en una lectura.

</Slide>

<Slide title="deleteLast con tail · el que no baja">
La simetría invita a esperar que eliminar al final también baje a
$$\Theta(1)$$. No lo hace.

<SequenceStepper eda="linked-list-singly" operation="remove-last" values={[7, 3, 1, 5]} tail />

`tail` entrega el último nodo de inmediato, pero el nodo que hay que
modificar es el **anteúltimo**: alguien tiene que pasar a apuntar a `null`, y
ese alguien no es el que sale. Después de eliminar, además, `tail` tiene que
apuntar al anteúltimo, así que hace falta igual.

Un enlace apunta en una sola dirección. Desde el último nodo no se puede
retroceder, y `tail` da acceso al final, no al camino de vuelta. La operación
sigue costando $$\Theta(N)$$.

</Slide>

<Slide title="La lista doblemente enlazada · el enlace de vuelta">
La segunda variante ataca exactamente esa carencia. Cada nodo gana un
segundo enlace:

```java
class Node {
    int value;
    Node next;
    Node prev;
}
```

Con eso aparece la invariante que le da sentido:

5. **Si `a.next` es `b`, entonces `b.prev` es `a`.** Los dos enlaces
   describen la misma cadena en sentidos opuestos. Si se desincronizan,
   recorrer hacia adelante y hacia atrás da dos listas distintas, y las dos
   parecen correctas por separado.

El primer nodo tiene `prev == null` y el último `next == null`, igual que
antes.

</Slide>

<Slide title="deleteLast en la doblemente enlazada">
<SequenceStepper eda="linked-list-doubly" operation="remove-last" values={[7, 3, 1, 5]} tail />

Ahora sí. `tail` da el último nodo y `tail.prev` da el anteúltimo sin
recorrer nada: la operación baja a $$\Theta(1)$$.

Lo mismo vale para eliminar cualquier nodo que ya tengamos en la mano. En una
lista simplemente enlazada, tener el nodo no alcanza —hay que buscar quién lo
apunta—; en una doblemente enlazada, `nodo.prev` y `nodo.next` son
suficientes para sacarlo de la cadena con dos asignaciones.

</Slide>

<Slide title="El precio del enlace de vuelta">
Nada de esto es gratis, y el costo se paga en dos monedas.

- **Memoria.** Cada nodo guarda una referencia más. Sobre $$N$$ nodos son
  $$N$$ referencias extra, así que el espacio adicional es $$\Theta(N)$$.
- **Trabajo en cada modificación.** Toda operación que cambia la cadena tiene
  que dejar consistentes los dos enlaces. Donde antes había una asignación
  ahora hay dos, y olvidar una rompe la quinta invariante sin que nada avise
  en el momento.

El orden asintótico de las operaciones no empeora: siguen siendo las mismas
constantes o los mismos recorridos. Lo que crece es el trabajo por paso y la
cantidad de casos que hay que escribir bien.

</Slide>

<Slide title="La lista ordenada · una invariante en vez de un puntero">
La tercera variante no agrega ningún campo. Agrega una promesa:

6. **Recorriendo la cadena desde `head`, los valores no decrecen.** El orden
   de la lista deja de ser el orden en que se insertó cada elemento y pasa a
   ser el orden de los valores.

Es la primera variante que cambia el **contrato** y no la representación. Una
lista ordenada ya no cumple el TDA Sequence: `insertAt(i, x)` permitiría
poner cualquier valor en cualquier posición, que es justamente lo que esta
invariante prohíbe. La operación de inserción pasa a ser una sola, y no
recibe posición.

</Slide>

<Slide title="insertOrdenado · la posición la decide el valor">
<SequenceStepper
  eda="linked-list-singly"
  operation="insert-ordered"
  values={[1, 3, 7, 9]}
  target={5}
/>

El recorrido avanza mientras el valor del nodo siguiente sea menor que el que
insertamos, y se detiene en cuanto deja de serlo: ahí está el lugar. Enlazar
es lo de siempre, dos asignaciones.

El costo es $$\Theta(N)$$ en el peor caso —el valor va al final—, igual que
`insertAt`. La diferencia no está en el costo sino en quién elige la
posición: aquí la elige el valor, y por eso la invariante se mantiene sola.

</Slide>

<Slide title="Qué gana la lista ordenada">
La ganancia aparece en las búsquedas que **fracasan**.

Sobre una lista sin ordenar, buscar un valor que no está obliga a recorrer
los $$N$$ nodos: hasta el último no se puede descartar. Sobre una lista
ordenada, el recorrido puede abandonar apenas encuentra un valor mayor que el
buscado, porque todo lo que sigue es todavía mayor.

En el peor caso sigue siendo $$\Theta(N)$$ —el valor buscado podría ser mayor
que todos—, y esa es la parte que conviene no perder de vista: el orden
mejora el promedio, no la cota. Lo que la lista ordenada **no** consigue es
la búsqueda binaria, porque llegar al nodo del medio sigue costando recorrer
media cadena.

</Slide>

<Slide title="La lista circular · el último vuelve al primero">
La cuarta variante cambia una sola referencia: la del último nodo, que en
vez de `null` apunta a `head`.

<SequenceStepper
  eda="linked-list-circular"
  operation="insert-first"
  values={[7, 3, 1, 5]}
  value={9}
/>

La invariante de terminación se reemplaza:

7. **El `next` del último nodo apunta a `head`.** Ningún nodo tiene `next` en
   `null`. Desde cualquier nodo se llega a todos los demás.

Es un cambio pequeño con una consecuencia grande: **ningún recorrido termina
solo**. Un `while (current != null)` sobre una lista circular no se detiene
nunca. La condición de corte pasa a ser haber vuelto al punto de partida,
`current.next != head`, y hay que escribirla a propósito en cada recorrido.

</Slide>

<Slide title="Dónde sirve que no haya final">
La lista circular resuelve un problema concreto: recorrer una colección de
manera indefinida sin tratar el final como un caso especial.

- **Turnos rotativos.** Un planificador que reparte tiempo entre procesos
  avanza un nodo por turno; cuando se acaban, ya está en el primero otra vez
  sin ninguna comprobación.
- **Listas de reproducción en repetición.** El siguiente del último tema es
  el primero, y esa regla vive en la estructura en vez de en el código que la
  usa.
- **Buffers circulares.** Un espacio fijo donde lo nuevo sobrescribe lo más
  viejo, como el registro de los últimos eventos de un sistema.

En los tres, la alternativa sería preguntar «¿llegué al final?» en cada paso.
La estructura hace que la pregunta no exista.

</Slide>

<Slide title="Las piezas se combinan">
Las cuatro variantes son independientes y se acumulan. Lo habitual es
encontrarlas juntas:

- **Doblemente enlazada con tail** es la combinación más frecuente, y es la
  que usa `LinkedList` de Java. Con ella, insertar y eliminar en cualquiera
  de los dos extremos cuesta $$\Theta(1)$$.
- **Circular y doblemente enlazada** permite recorrer en los dos sentidos sin
  final, que es lo que quiere un carrusel.
- **Ordenada con tail** deja insertar el máximo sin recorrer, y es útil
  cuando los valores tienden a llegar en orden.

Cada pieza se paga por separado: `tail` cuesta una referencia por lista,
`prev` cuesta una por nodo, el orden cuesta perder `insertAt`, y el ciclo
cuesta escribir cada recorrido con su corte explícito.

</Slide>

<Slide title="Insertar, por variante">
| Operación | Simple | Con tail | Doble con tail | Ordenada |
|---|---|---|---|---|
| `insertFirst(x)` | $$\Theta(1)$$ | $$\Theta(1)$$ | $$\Theta(1)$$ | no aplica |
| `insertLast(x)` | $$\Theta(N)$$ | <span style={{ color: 'var(--color-keep)', fontWeight: 700 }}>$$\Theta(1)$$</span> | <span style={{ color: 'var(--color-keep)', fontWeight: 700 }}>$$\Theta(1)$$</span> | no aplica |
| `insertAt(i, x)` | $$\Theta(N)$$ | $$\Theta(N)$$ | $$\Theta(N)$$ | no aplica |
| `insertOrdered(x)` | — | — | — | $$\Theta(N)$$ |

La única fila que se mueve al agregar `tail` es `insertLast`, y se mueve
porque `tail` es exactamente el nodo que esa operación necesitaba encontrar.
`insertAt` no mejora en ninguna variante: el nodo previo a una posición
arbitraria no lo guarda nadie.

</Slide>

<Slide title="Eliminar y buscar, por variante">
| Operación | Simple | Con tail | Doble con tail | Ordenada |
|---|---|---|---|---|
| `deleteFirst()` | $$\Theta(1)$$ | $$\Theta(1)$$ | $$\Theta(1)$$ | $$\Theta(1)$$ |
| `deleteLast()` | $$\Theta(N)$$ | $$\Theta(N)$$ | <span style={{ color: 'var(--color-keep)', fontWeight: 700 }}>$$\Theta(1)$$</span> | $$\Theta(N)$$ |
| `deleteAt(i)` | $$\Theta(N)$$ | $$\Theta(N)$$ | $$\Theta(N)$$ | $$\Theta(N)$$ |
| `search(x)` | $$\Theta(N)$$ | $$\Theta(N)$$ | $$\Theta(N)$$ | $$\Theta(N)$$ |

`deleteLast` es la fila que distingue las variantes entre sí. Con `tail` no
baja, porque lo que falta es el nodo anterior; con `prev` sí baja, porque es
justamente el nodo anterior lo que `prev` guarda. Es la mejor prueba de que
la pieza que hay que agregar se deduce de qué nodo necesita la operación, y
no de dónde ocurre.

</Slide>

## El arreglo y la lista enlazada

<Slide title="Arreglo y lista enlazada · la tabla completa">
| Operación | Arreglo | Arreglo dinámico | Lista simple | Lista doble con tail |
|---|---|---|---|---|
| `getAt(i)` · `setAt(i, x)` | <span style={{ color: 'var(--color-keep)', fontWeight: 700 }}>$$\Theta(1)$$</span> | <span style={{ color: 'var(--color-keep)', fontWeight: 700 }}>$$\Theta(1)$$</span> | $$\Theta(N)$$ | $$\Theta(N)$$ |
| `insertFirst(x)` · `deleteFirst()` | $$\Theta(N)$$ | $$\Theta(N)$$ | <span style={{ color: 'var(--color-keep)', fontWeight: 700 }}>$$\Theta(1)$$</span> | <span style={{ color: 'var(--color-keep)', fontWeight: 700 }}>$$\Theta(1)$$</span> |
| `insertLast(x)` | $$\Theta(1)$$ | $$\Theta(1)$$ amortizado | $$\Theta(N)$$ | $$\Theta(1)$$ |
| `deleteLast()` | $$\Theta(1)$$ | $$\Theta(1)$$ amortizado | $$\Theta(N)$$ | $$\Theta(1)$$ |
| `insertAt(i, x)` · `deleteAt(i)` | $$\Theta(N)$$ | $$\Theta(N)$$ | $$\Theta(N)$$ | $$\Theta(N)$$ |
| `search(x)` | $$\Theta(N)$$ | $$\Theta(N)$$ | $$\Theta(N)$$ | $$\Theta(N)$$ |
| Capacidad | fija | crece | crece | crece |

La primera fila y la segunda son la imagen espejo, y resumen toda la
comparación: el arreglo llega a cualquier posición con una cuenta y paga por
abrir hueco al principio; la lista abre hueco al principio con una asignación
y paga por llegar a cualquier posición.

</Slide>

<Slide title="Cuándo conviene cada una">
La elección no se hace por la estructura sino por la mezcla de operaciones
que el programa va a pedir.

**Conviene un arreglo** cuando se lee mucho por posición y se modifica poco
la forma: una tabla que se llena una vez y después se consulta, cualquier
recorrido por índice, cualquier algoritmo que compare `data[i]` con
`data[j]`. La búsqueda binaria y los algoritmos de ordenamiento sobre
arreglos viven de esta propiedad.

**Conviene una lista** cuando se inserta y se elimina seguido en los
extremos, y casi nunca se pide una posición arbitraria: una cola de tareas
por atender, un historial al que se le agrega adelante, cualquier colección
que crece y se achica todo el tiempo por los bordes.

Cuando el programa pide de las dos cosas, la respuesta suele ser el arreglo
dinámico: pierde solo en las inserciones al principio, y gana en todo lo que
se lee por posición.

</Slide>

<Slide title="Lo que la tabla no dice">
Dos cosas quedan fuera de una tabla de complejidades y a veces deciden la
elección.

**La memoria que se gasta de más.** Un arreglo guarda los datos y nada más,
aunque reserve casillas de sobra. Una lista guarda, por cada dato, una
referencia al siguiente —y dos en la doblemente enlazada—, más el costo de
cada objeto en sí. Para elementos chicos, como enteros, la estructura puede
ocupar varias veces lo que ocupan los datos.

**Dónde caen los datos en memoria.** Los elementos de un arreglo están
juntos, y los procesadores están construidos para eso: leer una posición
trae también a sus vecinas. Los nodos de una lista pueden estar dispersos, y
cada salto puede caer lejos del anterior. Dos recorridos que la tabla llama
igual, ambos $$\Theta(N)$$, pueden medir tiempos muy distintos.

Ninguna de las dos contradice la tabla: las constantes que el orden
asintótico deja fuera son reales, y se notan cuando $$N$$ es chico o cuando
las dos opciones tienen el mismo orden.

</Slide>

<Slide title="Un método, dos estructuras">
El contrato compartido es lo que permite escribir código que no elige.

```java
public static int sumar(Sequence s) {
    int total = 0;
    for (int i = 0; i < s.len(); i++) {
        total += s.getAt(i);
    }
    return total;
}
```

Este método funciona con un arreglo y con una lista, sin cambiar una línea y
sin saber cuál recibió. Eso es el TDA cumpliendo su promesa.

También muestra el otro lado. Sobre un arreglo el recorrido cuesta
$$\Theta(N)$$; sobre una lista, cada `getAt(i)` vuelve a caminar desde
`head`, así que el mismo código cuesta $$\Theta(N^2)$$. El contrato garantiza
que compila y que da el resultado correcto, y no garantiza nada sobre el
tiempo: por eso conviene recorrer una lista siguiendo sus enlaces una sola
vez, en lugar de pedirle posiciones.

</Slide>

## Los ejercicios canónicos

<Slide title="Invertir la lista · dar vuelta cada enlace">
Invertir una lista no mueve datos: da vuelta el sentido de cada enlace. El
recorrido necesita tres referencias al mismo tiempo.

```java
Node reverse(Node head) {
    Node prev = null;
    Node current = head;
    while (current != null) {
        Node nextNode = current.next;
        current.next = prev;
        prev = current;
        current = nextNode;
    }
    return prev;
}
```

`nextNode` es la que hace posible el resto: en cuanto `current.next` cambia,
el acceso al resto de la cadena se pierde, así que hay que guardarlo antes.

Una pasada, $$\Theta(N)$$ tiempo y $$\Theta(1)$$ espacio adicional. Al
terminar, `current` es `null` y `prev` es la nueva cabeza.

</Slide>

<Slide title="Invertir con recursión">
La misma operación admite una escritura recursiva, sobre la idea de que
invertir una lista es invertir su cola y después enganchar la cabeza al
final.

```java
Node reverse(Node head) {
    if (head == null || head.next == null) {
        return head;
    }
    Node newHead = reverse(head.next);
    head.next.next = head;
    head.next = null;
    return newHead;
}
```

El caso base son las listas de cero y de un nodo, que ya están invertidas.
La línea `head.next.next = head` es el paso: el que era el siguiente pasa a
apuntar de vuelta.

El tiempo sigue siendo $$\Theta(N)$$, pero el espacio ya no es constante: hay
$$N$$ llamadas anidadas en la pila antes de que la primera termine, así que
el espacio adicional es $$\Theta(N)$$. El análisis de ese costo está en
[[complejidad-recursion|Complejidad y recursión]].

</Slide>

<Slide title="Detectar un ciclo · dos velocidades">
Una cadena que en vez de terminar en `null` vuelve sobre sí misma hace que
cualquier recorrido no termine. Detectarlo con dos punteros que avanzan a
distinta velocidad se conoce como algoritmo de la liebre y la tortuga, y se
atribuye a Robert W. Floyd.

```java
boolean hasCycle(Node head) {
    Node slow = head;
    Node fast = head;
    while (fast != null && fast.next != null) {
        slow = slow.next;
        fast = fast.next.next;
        if (slow == fast) {
            return true;
        }
    }
    return false;
}
```

Si la lista termina, el rápido llega al final y el ciclo del `while` corta.
Si no termina, los dos quedan girando dentro del ciclo, y como el rápido se
acerca al lento un nodo por vuelta, alcanzarlo es cuestión de tiempo.

Comparamos `slow == fast`, que pregunta si son **el mismo nodo**, y no
`slow.value == fast.value`, que preguntaría si guardan el mismo número.

</Slide>

<Slide title="El nodo del medio en una pasada">
La misma idea de dos velocidades resuelve un problema distinto: encontrar el
nodo del medio sin saber cuántos hay.

```java
Node middle(Node head) {
    Node slow = head;
    Node fast = head;
    while (fast != null && fast.next != null) {
        slow = slow.next;
        fast = fast.next.next;
    }
    return slow;
}
```

Cuando el rápido llega al final, ha avanzado el doble que el lento, así que
el lento está a mitad de camino.

La alternativa obvia —recorrer una vez para contar y otra hasta `size / 2`—
también es $$\Theta(N)$$ y también es correcta. Esta versión hace una sola
pasada, que es lo que importa cuando los datos llegan de a uno y no se pueden
volver a leer.

</Slide>

<Slide title="Fusionar dos listas ordenadas">
Dadas dos listas ordenadas, producir una sola ordenada con todos los
elementos es el mismo procedimiento que combina las mitades en el
ordenamiento por mezcla.

```java
Node merge(Node a, Node b) {
    Node dummy = new Node(0);
    Node tail = dummy;
    while (a != null && b != null) {
        if (a.value <= b.value) {
            tail.next = a;
            a = a.next;
        } else {
            tail.next = b;
            b = b.next;
        }
        tail = tail.next;
    }
    tail.next = (a != null) ? a : b;
    return dummy.next;
}
```

En cada paso se compara la cabeza de cada lista y se engancha la menor. El
`nodo dummy` es un nodo de mentira que evita escribir aparte el caso del
primer elemento; al final se devuelve el que le sigue.

Sobre listas la fusión no necesita memoria adicional para los datos: reordena
enlaces. Sobre arreglos, la misma operación necesita un arreglo auxiliar.

</Slide>

<Slide title="El precio de pedir cualquier posición">
Las dos estructuras de esta unidad comparten una debilidad, y es la misma
fila de la tabla: `insertAt`, `deleteAt` y —en la lista— `getAt` cuestan
$$\Theta(N)$$ en todas las variantes. La causa es distinta en cada una
—correr elementos en el arreglo, caminar enlaces en la lista— y ninguna
variante la arregla, porque el contrato exige poder operar en cualquier
posición.

**¿Y si un programa no necesita el medio?**

Muchos no lo necesitan: una pila de platos solo toca el de arriba, una fila
de espera solo toca los extremos. Un contrato que prometa menos —solo los
bordes— se puede cumplir en $$\Theta(1)$$ **sobre las dos estructuras a la
vez**, cada una usando justamente la punta donde es rápida.

El precio es perder el acceso por posición: lo que se gana en costo se paga
en lo que ya no se puede pedir. Esos contratos más chicos son los TDA Stack,
Queue y Deque.

</Slide>

## Lo que sigue

La próxima clase estudia tres contratos más chicos que Sequence —los TDA
**Stack**, **Queue** y **Deque**—, que renuncian al acceso por posición y a
cambio se cumplen en tiempo constante. Cada uno se construye sobre un arreglo
y sobre una lista, y la comparación entre ambas implementaciones es la otra
mitad del principio que abre la unidad: si aquí un mismo contrato admitió dos
estructuras, allá una misma estructura cumplirá varios contratos.
