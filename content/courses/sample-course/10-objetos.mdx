# Clases y Objetos

Hasta aquí has programado con los tipos que Java trae de fábrica. Este
documento te convierte en autor de tipos: defines tus propias clases, creas
objetos a partir de ellas y decides qué significa que dos objetos «tuyos»
sean iguales. El documento cierra con un bug real que aparece cuando ese
trabajo se hace a medias: un `HashSet` que no encuentra lo que tú mismo le
metiste.

## Clase: atributos y métodos

<Slide title="¿Qué es una clase? ¿Qué es un objeto?">
Una **clase** es una definición: dice qué datos guarda algo y qué puede
hacer. Piensa en la clase `Persona`: tiene un nombre y un RUT (los datos) y
sabe presentarse (el comportamiento). Es una plantilla — por sí sola no *es*
nadie.

Un **objeto** es una pieza concreta construida a partir de esa definición:
`new Persona("Ana", 12345)` crea una persona real en memoria, con su propio
nombre y su propio RUT. **Instancia** y **objeto** son dos nombres para lo
mismo: cada `new` produce una instancia de la clase.

La clase es la definición; el objeto es lo que usas para interactuar. Todo
lo que sigue es, en el fondo, ese ciclo: definir una clase, crear objetos
con `new` y llamar sus métodos.
</Slide>

<Slide title="Clases en C++">
En C++ ya escribiste clases: atributos, constructor, métodos, con la
separación en `.h` y `.cpp`. La `Pair` con la que vas a trabajar en este
documento:

```cpp
class Pair {
 public:
  Pair(int a, int b) : first_(a), second_(b) {}
  int first() const  { return first_; }
  int second() const { return second_; }
 private:
  int first_, second_;
};
```

El delta con Java es cosmético: no hay `.h` ni `.cpp`, no hay `::`, y todo va
junto en un archivo. La idea — datos y comportamiento en una misma caja — es
la misma.
</Slide>

<Slide title="Clases en Java">
Una clase Java lleva atributos, uno o más constructores y métodos, todo en el
mismo archivo. La misma `Pair`:

```java
public class Pair {
  private int first;
  private int second;

  public Pair(int first, int second) {
    this.first = first;
    this.second = second;
  }

  public int first()  { return first; }
  public int second() { return second; }
}
```

- **Atributos `private`** — los datos de la clase. `private` significa que
  solo los métodos de la propia clase pueden tocarlos: desde fuera, los datos
  de un objeto cambian únicamente a través de sus métodos.
- **El constructor** — el método que corre cuando creas un objeto con `new`.
  Se llama exactamente como la clase, no declara tipo de retorno, y su
  trabajo es dejar el objeto listo para usarse: aquí, guardar en los
  atributos los dos números que recibió. `this.first = first` se lee «el
  atributo `first` de este objeto recibe el parámetro `first`» — `this` es
  el objeto que se está construyendo.
- **Getters** — métodos de lectura. `first()` devuelve el valor del atributo
  `first`; el atributo queda privado y el resto del programa lo lee por esta
  puerta. **Setters** serían lo simétrico — métodos que cambian el valor — y
  no toda clase los necesita: escribir `setX` para cada campo no es una
  regla, es una decisión.
</Slide>

<Slide title="Instancia y usa">
`new Pair(3, 7)` es el momento en que la definición se vuelve algo real:
reserva memoria, corre el constructor con esos dos argumentos y devuelve una
**instancia** — un objeto `Pair` concreto, con sus propios `first` y
`second`. La variable `p` guarda una referencia a esa instancia, y a través
de ella llamas sus métodos:

<CodeEditor
  language="java"
  defaultValue={`// La clase provista — en tus programas futuros viviría en su propio archivo

confirma que `p` no es los números — es la caja que los guarda.
</Slide>

<Slide title="this">
Dentro de un método, `this` es una referencia al objeto sobre el que se llamó
ese método. Sirve para desambiguar cuando un parámetro tiene el mismo nombre
que un atributo:

```java
public class Punto {
  private int x, y;

  public void mover(int x, int y) {
    this.x = x;   // el atributo x recibe el parámetro x
    this.y = y;
  }
}
```

Sin el `this.`, el parámetro `x` le tapa al atributo — el compilador te deja
escribirlo, no siempre te avisa, y el bug es callado. Corre la versión con
`this.` y después bórralos para ver la diferencia:

<CodeEditor
  language="java"
  defaultValue={`class Punto {

    public void mover(int x, int y) {
        this.x = x;
        this.y = y;
    }

    // toString: «cómo se imprime este objeto»
    public String toString() {
        return "x=" + x + ", y=" + y;
    }
}

    public static void main(String[] args) {

/>

Borra los `this.` y corre de nuevo: `p` queda en `x=0, y=0`. El parámetro
ganó el nombre y el atributo nunca se tocó — el programa compila, corre e
imprime un resultado silenciosamente equivocado.
</Slide>

## Visibilidad

<Slide title="Visibilidad en C++">
En C++ la visibilidad se declara en bloque: `public:` y `private:` son
etiquetas que cambian todo lo que viene después.

```cpp
class Cuenta {
 private:
  int saldo;
 public:
  int ver() const { return saldo; }
};
```

Java usa el mismo modelo con otra sintaxis — la diferencia está en la
próxima slide.
</Slide>

<Slide title="public / private en Java">
Java pone la visibilidad **por miembro**, no en bloque, y el compilador te
detiene si intentas leer un `private` desde fuera:

```java
public class Cuenta {
  private int saldo;

  public int getSaldo()        { return saldo; }
  public void depositar(int m) { saldo += m; }
}
```

- `private int saldo` — solo los métodos de `Cuenta` lo ven.
- Getters y setters son la fachada para no exponer el campo. **No los generes
  por reflejo**: cada uno abre una puerta, y a veces la puerta correcta es no
  tenerla. `Cuenta` no tiene `setSaldo` — el saldo solo se mueve con
  `depositar`.
</Slide>

<Slide title="La trampa: acceso desde afuera">
<PredictOutput title="El saldo es privado">

¿Compila? ¿Qué imprime?

```java predict
class Cuenta { private int saldo = 100; }
class Uso {
    public static void main(String[] args) {
        System.out.println(new Cuenta().saldo);
    }
}
```

</PredictOutput>

El compilador no discute intenciones: `saldo` es `private` y `Uso` está
afuera. El error — `The field Cuenta.saldo is not visible` — es la puerta
funcionando, y es el mensaje real que el editor te muestra al correr, letra
por letra. C++ rechaza el mismo descuido en compilación, igual que aquí: la
visibilidad se hace cumplir en ambos lenguajes. Lo que cambia es la sintaxis
— por miembro en vez de en bloque — y que en Java el mensaje te llega en el
mismo panel donde corre el código.
</Slide>

## Herencia

<Slide title="Herencia · para qué sirve">
La herencia captura una relación **«es-un»**: un `Auto` **es un** `Vehiculo`.
Sirve para dos cosas:

1. **No repetir código** — lo que todos los vehículos tienen en común (una
   marca, un método `describir`) vive una vez, en `Vehiculo`.
2. **Tratar variedad como una sola cosa** — cuando el resto del programa
   recibe `Vehiculo`, funciona con `Auto`, `Camion`, o lo que venga después.

Un curso de estructuras de datos usa herencia poco, pero tiene que **leerla**
en el JDK todo el rato (`ArrayList extends AbstractList`, y así con media
biblioteca). Vas a escribir dos o tres jerarquías tuyas y a leer muchas.
</Slide>

<Slide title="Herencia en el JDK · ejemplo real">
Ya usaste una jerarquía real sin darte cuenta. Los tipos numéricos «boxed»
heredan todos de una misma clase, `Number`, que vive en `java.lang`:

- `Number` — la clase madre, abstracta.
  - `Integer`, `Long`, `Double`, `Float`
  - `BigInteger`, `BigDecimal`, …

Un método declarado sobre el padre acepta cualquiera de los hijos:

```java
public static double sumar(Number a, Number b) {
  return a.doubleValue() + b.doubleValue();
}

System.out.println(sumar(42, 3.14));   // 45.14
// el 42 entra como Integer, el 3.14 como Double,
// y sumar() no cambia una línea
```

Es lo que la herencia te compra en la práctica: escribes **una** vez, y te
sirve para toda la familia — la de hoy y la que agreguen mañana.
</Slide>

<Slide title="extends, super, @Override">
La mecánica completa, en una jerarquía de vehículos:

```java
public class Vehiculo {
  protected String marca;

  public Vehiculo(String marca) { this.marca = marca; }
  public String describir() { return "vehículo " + marca; }
}

public class Auto extends Vehiculo {
  public Auto(String marca) { super(marca); }

  @Override
  public String describir() { return "auto " + marca; }
}
```

- **`extends`** — `Auto` hereda todo lo de `Vehiculo`. Y en Java heredas de
  **una sola** clase: nada de herencia múltiple como en C++. Si un tipo
  necesita cumplir varios contratos a la vez, las **interfaces** lo
  resuelven.
- **`super(marca)`** — llama al constructor del padre, para que la parte
  «vehículo» se inicialice con la marca.
- **`protected`** — visible para las subclases, invisible desde fuera: el
  punto medio entre `public` y `private`.
- **`@Override`** — una anotación que le pide al compilador **verificar** que
  realmente estás sobrescribiendo algo. Un typo en el nombre pasa de bug
  silencioso a error de build. Escríbela siempre.
</Slide>

<Slide title="La trampa del @Override">
`@Override` no cambia lo que corre — le pide al compilador que revise. Mira
qué pasa sin ella, con un typo de una letra:

<PredictOutput title="saluar en vez de saludar">

¿Qué imprime? Ojo con `saluar`:

```java predict
class A { void saludar() { System.out.println("hola"); } }
class B extends A { void saluar() { System.out.println("chao"); } }

public class Main {
    public static void main(String[] args) {
        A x = new B();
        x.saludar();
    }
}
```

</PredictOutput>

Imprime `hola`: `saluar` no sobrescribe nada — es un método nuevo con otro
nombre, y `B` hereda el `saludar` original de `A`. El bug es silencioso: el
programa compila, corre, e imprime lo contrario de lo que querías. Con
`@Override` encima de `saluar`, el compilador lo habría atajado en build:
«el método no sobrescribe nada del padre».
</Slide>

**Nota:** Java tiene además `abstract class` — una clase que no se instancia,
solo se hereda, y que puede mezclar métodos con y sin implementación. La vas
a leer mucho en el JDK (Collections está lleno de ellas), aunque escribas
pocas.

## Interfaces

<Slide title="Interfaces · para qué sirven">
Una interfaz dice **qué métodos hay** sin decir cómo se hacen. Es un
**contrato**: cualquier clase que la implementa se compromete a ofrecer esos
métodos, cada una a su manera.

Sirven para que un mismo verbo — `comparar`, `ejecutar`, `imprimir` — lo
puedan cumplir clases muy distintas, y el resto del programa las trate igual.
Media biblioteca estándar de Java funciona así: `Comparable`, `Iterable`,
`Runnable`, `Iterator`… — todas son interfaces.
</Slide>

<Slide title="Una interfaz, una clase que la cumple">
```java
public interface Formal {
  String tratarDe();
}

public class Persona implements Formal {
  @Override
  public String tratarDe() { return "usted"; }
}
```

La interfaz declara el método; `implements` obliga a la clase a definirlo.
Un `Persona` es ahora **también** un `Formal` — puede ir a cualquier parte
que pida un `Formal`.
</Slide>

<Slide title="La misma clase, varias interfaces">
Una clase puede cumplir **varios** contratos a la vez, separados por coma:

```java
public interface Serializable { String aString(); }

public class Persona implements Formal, Serializable {
  @Override public String tratarDe() { return "usted"; }
  @Override public String aString()  { return "persona"; }
}
```

`Persona` puede pasar por cualquier lugar que pida un `Formal` **o** un
`Serializable`. Esto es lo que las estructuras de datos de Java explotan
constantemente — `TreeSet` acepta cualquier cosa que sea `Comparable`, y así
con media biblioteca.
</Slide>

<Slide title="Una interfaz del sistema: Comparable">
Los mismos `Integer`/`Long`/`Double` que vimos como `Number`, acá se miran
desde otro lado: **también** implementan `Comparable` (por interfaz). Un
mismo objeto vive las dos vidas.

`Comparable` vive en `java.lang` y define UN método: «cuando te comparen
contigo, ¿cómo respondes?». El contrato de `compareTo` es simple: devuelve
**negativo** si `this` va antes que el argumento, **cero** si son iguales en
el orden, **positivo** si va después. Cada clase decide qué significa
«antes» para ella:

```java
Integer.valueOf(3).compareTo(5);              // -1: 3 va antes que 5
"pera".compareTo("manzana");                  // > 0: "pera" va después, por orden alfabético
LocalDate.now().compareTo(LocalDate.now());   // 0: misma fecha
```

`Integer` compara valores numéricos, `String` compara en orden alfabético,
`LocalDate` compara fechas — y quien las use no necesita saber cómo lo
calcula cada una. El mismo `Integer`, dos vidas:

```java
Integer x = 3;
double s = x.doubleValue();   // la vida heredada de Number
int c    = x.compareTo(5);    // la vida contratada con Comparable → -1
```
</Slide>

<Slide title="Tu clase se une al club">
Tu propia clase puede implementar `Comparable` y ordenarse igual que las de
fábrica:

```java
public class Fecha implements Comparable<Fecha> {
  int año, mes, dia;

  @Override
  public int compareTo(Fecha o) {
    // negativo si this < o, 0 si igual, positivo si this > o
    if (año != o.año) return año - o.año;
    if (mes != o.mes) return mes - o.mes;
    return dia - o.dia;
  }
}
```

Compara año contra año; si empatan, mes contra mes; si empatan, día contra
día — por eso los `return` devuelven la diferencia. Con esto solo,
`TreeSet<Fecha>` y `Collections.sort(listaDeFechas)` ya saben ordenarla, sin
cambiar una línea del código de esas estructuras. (El `<Fecha>` entre
ángulos declara con qué tipo se compara.)
</Slide>

<Slide title="La trampa: implements sin cumplir">
<PredictOutput title="El contrato no se negocia">

¿Compila?

```java predict
interface Formal { String tratarDe(); }

class Persona implements Formal {
    public String saludar() { return "hola"; }
}
```

</PredictOutput>

No compila. `implements` es un contrato: el compilador exige el método
`tratarDe()`, y `saludar()` no lo cumple. El error —
`The type Persona must implement the inherited abstract method Formal.tratarDe()` —
te dice exactamente qué falta y dónde. («abstract» es la palabra que usa el
mensaje para decir «la clase no terminó de cumplir su contrato» — se lee «no
cumpliste el contrato».)
</Slide>

## Polimorfismo

<Slide title="Polimorfismo · qué es y para qué">
**La palabra**: «polimorfismo» = «muchas formas». **La idea**: una misma
operación — «describir», «comparar», «imprimir» — que responde distinto
según **quién es** el objeto que la recibe.

**Para qué sirve**: para escribir código **una vez** que funcione sobre
muchos tipos distintos, sin `switch` ni `if instanceof`. La estructura de
datos que trate `Comparable` funciona con `Integer`, con `String`, con tu
propia clase — sin cambiar una línea del código de la estructura.

**Cómo pensarlo**: cuando escribas «recorrer una colección y aplicar algo a
cada elemento», el «algo» normalmente **es** un método polimórfico. No
pienses «qué tipo es cada uno»; piensa «qué verbo necesito de todos ellos».

Ya viste este juego moviéndose: un mismo método `sumar` aceptaba un
`Integer` y un `Double` sin cambiar una línea, y un mismo `Integer`
respondía como número y como comparable. Esas dos maneras — heredar e
implementar — se llaman ambas polimorfismo, y se usan exactamente igual. Es
lo que muestran los dos ejemplos a continuación.
</Slide>

<Slide title="Dos maneras, un mismo verbo">

`tratarDe()`.
Ambos son polimorfismo; los usas igual.
</Slide>

<Slide title="Polimorfismo por herencia — Vehiculo[]">
Un arreglo declarado `Vehiculo[]` acepta cualquier subtipo. El método que
corre es el del objeto real, no el del tipo declarado:

<CodeEditor

— y sin embargo imprime `auto Toyota`, `camión Kenworth`, `auto Fiat`. El
tipo de la variable dice qué métodos puedes llamar; **el objeto real decide
cuál corre**. Agrega un `Camión` más a la flota: el `for-each` no cambia una
línea.
</Slide>

<Slide title="Polimorfismo por interfaz — Comparable[]">
Muchos tipos de la biblioteca estándar implementan `Comparable`. Un arreglo
`Comparable[]` los mezcla libremente:

<CodeEditor
  language="java"
  defaultValue={`public class Main {

Imprime `3`, `pera`, `1` — en orden de inserción, cada uno respondiendo por
sí mismo a `println`. El `Integer` se imprime como número, el `String` como
texto: la misma línea `System.out.println(c)` hace dos trabajos distintos
según quién es `c`. Es la misma máquina, llegando por la otra vía —
interfaz en vez de herencia.
</Slide>

## toString, equals, hashCode

<Slide title="Los métodos que toda clase hereda">
En el ejemplo anterior, `println` imprimió un `Integer` y un `String` sin que
nadie le dijera cómo: cada objeto trae su propia forma de presentarse. Esa
forma no es magia — es un método que **todos** los objetos tienen, porque
toda clase en Java desciende de una clase base llamada `Object`.

`Object` define tres métodos que tus clases heredan desde el primer día:

- `toString()` — cómo se presenta el objeto cuando se imprime.
- `equals()` — cuándo dos objetos son «el mismo» para ti.
- `hashCode()` — un número que identifica al objeto para las estructuras que
  agrupan por valor.

Heredarlos es gratis; el problema es lo que traen **por defecto**. `toString`
imprime `Persona@1b6d3586` (tipo + dirección de memoria — inútil para leer);
`equals` compara si dos variables apuntan a la misma instancia (no si dos
personas tienen el mismo RUT); `hashCode` devuelve un número derivado de la
identidad del objeto, no de sus datos. Y Java no permite redefinir `==` para
tus tipos, así que «iguales en contenido» siempre pasa por métodos.

Por eso se **sobrescriben**: `@Override` reemplaza la versión heredada por la
tuya. Una clase que define cómo presentarse, cómo igualarse y cómo agruparse
es una clase que se integra con todo el lenguaje — desde `println` hasta las
colecciones.
</Slide>

<Slide title="toString">
Sobrescribe `toString` cuando quieras que el objeto se imprima legible.
`System.out.println(p)` lo llama automáticamente:

```java
public class Persona {
  private String nombre;
  private int rut;

  @Override
  public String toString() {
    return nombre + " (" + rut + ")";
  }
}
```

Sin el override: `Persona@1b6d3586`. Con el override: `Ana (12345)`. Es el
método que `println` viene llamando en silencio cada vez que le pasas un
objeto.
</Slide>

<Slide title="equals y hashCode: qué son y cómo se usan">
**`equals`: cuándo dos objetos son el mismo.** Lo escribes tú porque solo tú
sabes qué hace iguales a dos personas en tu dominio: ¿el RUT? ¿nombre y
apellido? Tu `equals` responde esa pregunta, y `HashSet`, `HashMap` y
cualquier comparación de contenido la usan.

**`hashCode`: el número que agrupa.** Las estructuras hash reparten los
objetos en grupos usando un número, y ese número es `hashCode`. Para que dos
objetos que `equals` declara iguales caigan en el mismo grupo, su `hashCode`
debe coincidir. Por eso la regla operativa:

> Si sobrescribes `equals`, sobrescribes `hashCode`. Siempre. Juntos.

**Cómo se usan**: al guardar objetos en un `HashSet` (o como llave de un
`HashMap`), los dos trabajan en equipo — `hashCode` elige el grupo, `equals`
confirma dentro del grupo. Si el orden de recorrido importa y tu clase sabe
compararse, `TreeSet`/`TreeMap` ordenan con `compareTo` en vez de agrupar
por hash.

El teorema completo del contrato (reflexivo, simétrico, transitivo) lo
enseña el material de algoritmos y estructuras; aquí alcanza con la regla:
**los dos, juntos**.
</Slide>

<Slide title="El bug del HashSet">
`Persona` tiene `equals` (compara por RUT) pero **no** `hashCode`. Predice
cuántos elementos tiene el `HashSet` al final:

<Slide title="La corrección">
Ahora `Persona` sobrescribe **los dos**, con ayuda de `java.util.Objects`:

<CodeEditor
  language="java"
  defaultValue={`import java.util.HashSet;
import java.util.Objects;

class Persona {
    private String nombre;
    private int rut;

    public Persona(String nombre, int rut) {
        this.nombre = nombre;
        this.rut = rut;
    }

    @Override
    public boolean equals(Object o) {
        if (!(o instanceof Persona)) return false;
        Persona p = (Persona) o;
        return rut == p.rut;

    @Override

        return Objects.hash(rut);
    }
}

objetos caen al mismo bucket, `HashSet` pregunta por `equals`, y `Anita`
(mismo RUT) se descarta como duplicada. En la práctica los generas con el IDE
(«Generate equals() and hashCode()»); aquí van a mano para que veas de qué
están hechos.
</Slide>
