# Estructuras de Datos Avanzadas · Árboles II

Un registro de estudiantes recibe números de matrícula de a uno, y en
cualquier momento hay que responder si un número ya está. Un registro de
fechas, o de folios, pide lo mismo: guardar un conjunto de valores que crece,
y buscar e insertar en él todo el tiempo. Para eso hacen falta dos
operaciones rápidas a la vez.

export function SortedRow({ values, hot = -1, out = [], caption, label }) {
  const box = 44;
  const pad = 12;
  // A caption wider than the row widens the canvas, and the row is centred in it.
  const rowW = 2 * pad + values.length * box;
  const width = Math.max(rowW, caption ? caption.length * 6.6 + 24 : 0);
  const left = (width - rowW) / 2 + pad;
  const height = 2 * pad + box + 18 + (caption ? 22 : 0);
  return (
    <svg viewBox={`0 0 ${width} ${height}`} style={{ width: '100%', maxWidth: `${Math.round(width * 1.3)}px`, height: 'auto', display: 'block', margin: '0.4rem auto' }} role="img" aria-label={label}>
      {values.map((v, i) => {
        const set = out.includes(i);
        const isHot = i === hot;
        return (
          <g key={i} opacity={set ? 0.45 : undefined}>
            <rect x={left + i * box} y={pad} width={box} height={box} rx="3" style={{ fill: 'var(--color-surface)', stroke: isHot ? 'var(--color-focus)' : set ? 'var(--color-rule)' : 'var(--color-rule-strong)' }} strokeWidth={isHot ? 2.6 : 1.2} strokeDasharray={set ? '4 3' : undefined} />
            <text x={left + i * box + box / 2} y={pad + box / 2 + 5} textAnchor="middle" fontSize="15" fontWeight="600" style={{ fill: 'var(--color-ink)' }}>{v}</text>
            <text x={left + i * box + box / 2} y={pad + box + 14} textAnchor="middle" fontSize="10" style={{ fill: 'var(--color-ink-faint)' }}>{i}</text>
          </g>
        );
      })}
      {caption ? (
        <text x={width / 2} y={height - 6} textAnchor="middle" fontSize="12" style={{ fill: 'var(--color-ink-soft)' }}>{caption}</text>
      ) : null}
    </svg>
  );
}

<Slide title="Un dilema entre buscar e insertar">
Las estructuras que guardan sus elementos en fila no resuelven bien las dos
operaciones a la vez: buscar e insertar.

- **Sin orden**, un valor nuevo entra al final de un arreglo, o al principio
  de una lista, sin mirar a los demás. Pero buscar obliga a revisar los
  valores uno por uno: nada dice dónde está el buscado.
- **Un arreglo ordenado** se busca con la búsqueda binaria, que descarta la
  mitad de lo que queda en cada comparación. Pero un valor nuevo tiene que
  entrar en su lugar, y todos los mayores se corren una casilla.
- **Una lista ordenada** no gana nada con el orden: la búsqueda binaria
  necesita llegar al elemento del medio en un paso, y en una lista llegar al
  medio es recorrer la mitad. Buscar sigue siendo recorrer, y para insertar
  también hay que recorrer hasta el lugar del valor nuevo, aunque enlazarlo
  ahí no corra a nadie.

| Estructura               | Buscar             | Insertar                 |
| ------------------------ | ------------------ | ------------------------ |
| Arreglo sin orden        | $$\Theta(n)$$      | $$\Theta(1)$$ amortizado |
| Lista enlazada sin orden | $$\Theta(n)$$      | $$\Theta(1)$$            |
| Arreglo ordenado         | $$\Theta(\log n)$$ | $$\Theta(n)$$            |
| Lista enlazada ordenada  | $$\Theta(n)$$      | $$\Theta(n)$$            |
| **Lo que buscamos**      | $$O(\log n)$$      | $$O(\log n)$$            |

Ninguna de las cuatro logra las dos cosas a la vez. **El objetivo** es una
estructura que mantenga los valores en orden, que busque como la búsqueda
binaria, en tiempo logarítmico, y que inserte también en tiempo logarítmico,
sin correr a nadie para hacerle lugar al valor nuevo.

</Slide>

<Slide title="La búsqueda binaria">
En un arreglo ordenado, la búsqueda binaria compara el valor buscado con el
elemento del medio. Si son iguales, lo encontró. Si el buscado es menor, no
puede estar en la mitad derecha, y la búsqueda sigue en la izquierda; si es
mayor, al revés. Cada comparación descarta la mitad de lo que quedaba, así que
bastan $$\lfloor \log_2 n \rfloor + 1$$ comparaciones. Se escribe con
recursión, una llamada por rango, o con un ciclo que achica el rango: las dos
comparan los mismos valores en el mismo orden.

<SequenceStepper eda="dynamic-array" operation="binary-search" values={[2, 4, 6, 8, 10, 12, 14]} target={6} iterative />

</Slide>

<Slide title="Las decisiones de la búsqueda binaria">
Las comparaciones de una búsqueda binaria siguen siempre el mismo patrón. La
primera es con el elemento del medio. Si el buscado es menor, la segunda es
con el medio de la mitad izquierda; si es mayor, con el medio de la derecha;
y así. Dibujadas, esas decisiones forman un **árbol binario**: el elemento del
medio es la raíz, y cada mitad, un subárbol armado con la misma regla.

<BinaryPicture tree={EVENS} splits label="El árbol de decisiones de una búsqueda binaria sobre el arreglo 2, 4, 6, 8, 10, 12, 14. La raíz es 8; a la izquierda, 4, con hijos 2 y 6; a la derecha, 12, con hijos 10 y 14. Cada nivel del árbol tiene un color, y debajo, en una fila por nivel, el arreglo partido como lo parte la búsqueda: entero, con el 8 en el medio; en dos mitades, 2, 4, 6 con el 4 en el medio y 10, 12, 14 con el 12; y en valores sueltos, el 2, el 6, el 10 y el 14. Cada valor queda bajo su nodo, y cada tramo, del color de su nodo." caption="cada nodo es el medio de su tramo; sus hijos, los medios de las dos mitades" />

Cada búsqueda es un camino desde la raíz hacia abajo, una comparación por
nivel. Debajo del árbol, cada fila es un nivel: los tramos del arreglo que la
búsqueda puede estar revisando en ese momento, cada uno con su elemento del
medio marcado, que es el nodo de ese nivel. Por eso cada nodo queda en la
misma columna que su valor en el arreglo, y los nodos, leídos de izquierda a
derecha, repiten el arreglo ordenado.

</Slide>

<Slide title="Las decisiones guardadas en nodos">
Si esas decisiones se guardan como **nodos enlazados** en lugar de un
arreglo, buscar sigue siendo lo mismo: comparar y bajar por un lado. Y un
valor que no está termina su búsqueda en un subárbol vacío, que es justo
donde tiene que ir.

## El árbol binario de búsqueda

<Slide title="La definición del árbol binario de búsqueda">
Un **árbol binario de búsqueda** —en inglés, *binary search tree*, o
**BST**— es un árbol binario que guarda sus valores en el orden de las
decisiones de una búsqueda binaria: los menores que un nodo, a su izquierda;
los mayores, a su derecha. Sus nodos son los del árbol binario: un valor y dos
referencias, `left` y `right`.

<BinaryPicture tree={EVENS} tones={{ 8: 'accent', 4: 'focus', 2: 'focus', 6: 'focus', 12: 'keep', 10: 'keep', 14: 'keep' }} label="Un árbol binario de búsqueda: 8 en la raíz, 4 y 12 debajo, 2, 6, 10 y 14 en el último nivel. El subárbol izquierdo del 8, con el 4, el 2 y el 6, tiene el color de los menores; el derecho, con el 12, el 10 y el 14, el de los mayores." caption="a la izquierda del 8, los menores; a su derecha, los mayores" />

Con esa forma, buscar e insertar recorren un solo camino desde la raíz:
ninguna operación revisa todos los valores ni corre a nadie. Lo que cuesta ese
camino depende de la altura del árbol.

</Slide>

<Slide title="La invariante de orden">
Lo que hace que un árbol binario sea de búsqueda es esta **invariante**:

> **para cada nodo, todos los valores de su subárbol izquierdo son menores
> que el suyo, y todos los de su subárbol derecho son mayores.**

<OrderSides label="Un nodo x con sus dos subárboles dibujados como triángulos: el izquierdo, en un color, guarda solo valores menores que x; el derecho, en otro color, guarda solo valores mayores que x." />

</div>

La palabra que importa es **todos**. No basta con que cada hijo esté del lado
correcto de su padre: un valor tiene que estar del lado correcto de **cada**
nodo por encima de él.

</Slide>

<Slide title="Las invariantes del árbol de búsqueda">
Un árbol de búsqueda cumple tres invariantes. Las dos primeras son las del
árbol binario, sin cambios; la tercera es la que lo hace de búsqueda.

1. **Cada nodo tiene a lo más dos hijos, y cada uno es el izquierdo o el
   derecho.**
2. **Cada nodo, salvo la raíz, tiene exactamente un padre.**
3. **Todo nodo del subárbol izquierdo es menor que la raíz, y todo nodo del
   subárbol derecho es mayor que la raíz.** Vale para el árbol entero y para
   cada uno de sus subárboles, porque cada nodo es la raíz del suyo. En
   particular, ningún valor se repite: un valor igual no estaría ni a un lado
   ni al otro.

La tercera decide los costos: por ella, cada comparación descarta un subárbol
entero, y cada inserción y cada eliminación tienen que dejar a cada valor del
lado correcto de cada uno de sus ancestros.

</Slide>

<Slide title="El nodo y la clase BST">
Las operaciones se escriben sobre dos clases. El árbol de búsqueda usa el
mismo nodo del árbol binario: un valor y una referencia a cada hijo. La clase
del árbol guarda solo la raíz, privada, y un árbol vacío la tiene en `null`.

```java
class Node<T> {
    T value;
    Node<T> left;
    Node<T> right;

    Node(T value) {
        this.value = value;
    }
}

class BST<T extends Comparable<T>> {
    private Node<T> root;
}
```

Lo nuevo es `T extends Comparable<T>`. Para elegir entre la izquierda y la
derecha hay que comparar valores, y `compareTo` responde un número negativo,
cero o positivo según el valor sea menor, igual o mayor que el otro: el tipo
de los valores tiene que saber compararse. El nodo no lleva esa condición:
solo guarda valores, y quien los compara es el árbol.

</Slide>

<Slide title="Buscar en un árbol de búsqueda">
**Buscar** responde si un valor está en el árbol: recibe el valor, responde sí
o no, y no cambia nada. En cada nodo hay tres respuestas posibles: el valor
buscado es el del nodo, es menor o es mayor. Si es menor, la invariante
garantiza que no está en el subárbol derecho, y la búsqueda sigue solo por la
izquierda; si es mayor, al revés. La búsqueda termina en el valor, o en un
subárbol vacío, y entonces el valor no está.

<Slide title="El código de la búsqueda">
Quien usa el árbol llama al método público, `contains`, que recibe solo el
valor: no tiene nodos. Ese método llama al privado con la raíz y devuelve su
respuesta. El privado busca en un subárbol: si está vacío, el valor no está;
si su raíz tiene el valor, está; si no, sigue por el lado que dice la
comparación. La versión iterativa no necesita método privado: una variable
baja desde la raíz y toma las mismas decisiones. Las dos bajan por un solo
camino: $$O(h)$$, se encuentre o no el valor.

<SequenceStepper eda="bst" operation="search" values={[8, 4, 12, 2, 6, 10, 14]} target={10} iterative />

</Slide>

<Slide title="Insertar en un árbol de búsqueda">
**Insertar** agrega un valor sin romper la invariante: recibe el valor y no
devuelve nada. Primero se busca. Si el valor ya está, no se hace nada, porque
el árbol no guarda repetidos. Si no está, la búsqueda termina en un subárbol
vacío, y ahí se cuelga el valor nuevo como una **hoja**: queda del lado que
eligió cada comparación, y ningún otro nodo se mueve.

<Slide title="El código de la inserción">
El método público, `insert`, llama al privado con la raíz y guarda en `root`
lo que este devuelve. La versión iterativa, al lado, es el método público
mismo. Las dos bajan por un solo camino, como la búsqueda: $$O(h)$$.

<SequenceStepper eda="bst" operation="insert" values={[8, 4, 12, 2, 6, 10, 14]} value={7} iterative />

</Slide>

<Slide title="La raíz que devuelve insert y su envoltorio">
El método recursivo recibe la raíz de un subárbol y devuelve la raíz de ese
mismo subárbol después de insertar. Casi siempre es el nodo que recibió; la
excepción es el subárbol vacío, donde devuelve el nodo nuevo. Por eso cada
llamada guarda lo que le devuelve la siguiente en `node.left` o `node.right`:
así la hoja nueva queda enlazada a su padre.

Quien usa el árbol no tiene nodos, solo valores. El método público es un
**envoltorio** del recursivo: recibe el valor, llama al recursivo con la raíz
y guarda en `root` lo que devuelve. Por eso, insertar en un árbol vacío crea
la raíz.

El ciclo no necesita envoltorio, porque ya es el método público. Como no
vuelve por el camino, baja recordando el padre, y al final cuelga la hoja de
él.

</Slide>

<Slide title="El inorden de un árbol de búsqueda">
Un árbol armado con inserciones guarda sus valores en orden, y hay un
recorrido que los entrega así: **el inorden de un árbol binario de búsqueda
entrega sus valores ordenados de menor a mayor.** El inorden visita cada nodo
entre sus dos subárboles: primero el izquierdo, después el nodo, después el
derecho.

<OrderRule parts={['izquierda', 'raíz', 'derecha']} tone="accent" label="La regla del inorden: el subárbol izquierdo, después la raíz, después el derecho." />

<BinaryPicture tree={EVENS} visits="in" strip label="El árbol de búsqueda con 8 en la raíz, 4 y 12 debajo, y 2, 6, 10 y 14 en el último nivel, recorrido en inorden: cada nodo numerado en el orden en que se visita, con una flecha de cada visita a la siguiente. Se visitan el 2, el 4, el 6, el 8, el 10, el 12 y el 14, y la fila de abajo los muestra en ese orden, cada uno bajo su nodo." caption="el inorden: 2, 4, 6, 8, 10, 12, 14, ordenado" />

La razón es la invariante: todo lo de la izquierda de un nodo es menor que él
y todo lo de la derecha es mayor. Si cada subárbol, más pequeño, ya sale
ordenado, el nodo queda exactamente entre los dos, y el total sale ordenado.

</Slide>

<Slide title="El código del inorden">
El método público, `inorder`, llama al privado con la raíz. El privado es el
recorrido del árbol binario: la visita va entre las dos llamadas, así que cada
nodo se imprime después de todo su subárbol izquierdo y antes de todo el
derecho. Visita cada nodo una vez: $$\Theta(n)$$.

</Slide>

<Slide title="Eliminar en un árbol de búsqueda">
**Eliminar** saca un valor del árbol sin romper la invariante. Primero se busca
el nodo que lo guarda; si el valor no está, no se hace nada. Si está, lo que se
hace depende de cuántos hijos tiene ese nodo: **ninguno**, **uno** o **dos**.

El 2 es una hoja, el 6 tiene un solo hijo y el 8 tiene dos: los tres casos de la eliminación." caption="los tres casos: una hoja, un hijo, dos hijos" />

</Slide>

<Slide title="Eliminar una hoja">
Una **hoja** no tiene hijos, así que nadie cuelga de ella. Basta con que su
padre deje de apuntarle, y en ese lado queda el árbol vacío.

<BinaryPicture tree={EVENS} tones={{ 2: 'hidden' }} holes={[4]} label="El mismo árbol sin el 2: el hijo izquierdo del 4 es ahora el árbol vacío." caption="el 4 apunta a null por la izquierda" />
</div>

</Slide>

<Slide title="Eliminar un nodo con un hijo">
Cuando el nodo tiene **un solo hijo**, a la izquierda o a la derecha, su padre
pasa a apuntar a ese hijo, y el subárbol del hijo sube un nivel, entero. La
invariante se mantiene, porque todo ese subárbol ya estaba del mismo lado del
padre que el nodo eliminado.

<BinaryPicture tree={EVENS_WITH_7} tones={{ 6: 'mark' }} minColumns={8} label="El árbol de búsqueda con el 7 colgando del 6. El 6 está marcado: tiene un solo hijo, el 7, a la derecha." caption="eliminar 6, que tiene un solo hijo" />

</div>

</Slide>

<Slide title="Eliminar un nodo con dos hijos">
Un nodo con **dos hijos** no se puede sacar: dejaría dos subárboles colgando,
y su padre tiene lugar para uno solo. Por eso el nodo se queda, y lo que
cambia es su valor:

1. Se busca su **sucesor**, el valor que le sigue en orden: el menor de su
   subárbol derecho. Se baja una vez a la derecha, y después a la izquierda
   mientras haya hijo izquierdo.
2. El nodo toma el valor del sucesor.
3. Se elimina el sucesor de abajo.

<div style={{ display: 'grid', gridTemplateColumns: 'repeat(auto-fit, minmax(240px, 1fr))', gap: '1rem 2rem', alignItems: 'end' }}>
<BinaryPicture tree={EVENS} tones={{ 8: 'mark', 10: 'focus' }} notes={{ 10: 'sucesor' }} holes={[]} label="El árbol de búsqueda con el 8 marcado: tiene dos hijos. Su sucesor, el mínimo de su subárbol derecho, es el 10." caption="eliminar 8: su sucesor es 10" />
<BinaryPicture tree={{ v: 10, l: { v: 4, l: { v: 2 }, r: { v: 6 } }, r: { v: 12, r: { v: 14 } } }} tones={{ 10: 'mark' }} holes={[12]} minColumns={7} label="El árbol después: la raíz tomó el valor 10, y el nodo del 10 que estaba abajo se eliminó; el 12 ya no tiene hijo izquierdo." caption="la raíz toma el 10, y el 10 de abajo se elimina" />
</div>

El sucesor cabe justo en ese lugar. Es mayor que todo el subárbol izquierdo
del nodo, porque ese subárbol era menor que el valor eliminado; y es menor que
todo lo que queda en el derecho, porque era el menor de ese lado.

</Slide>

<Slide title="El sucesor tiene a lo más un hijo">
El sucesor **nunca tiene hijo izquierdo**. Si lo tuviera, ese hijo estaría en el
mismo subárbol derecho y sería menor que él, y entonces el sucesor sería ese
hijo. Por eso, eliminar el sucesor de abajo nunca vuelve a ser el caso de dos
hijos, sino uno de los dos primeros:

- si es una **hoja**, su padre deja de apuntarle;
- si tiene **un hijo**, ese hijo está a la derecha, y su padre pasa a apuntar
  a él.

</div>

</Slide>

<Slide title="Eliminar la raíz">
La raíz se elimina con los mismos casos. Lo único distinto es que no tiene
padre: quien la apunta es el árbol, con `root`. Por eso, lo que en los otros
casos hacía el padre, aquí lo hace `root`:

- si la raíz es una **hoja**, `root` pasa a ser `null`, y el árbol queda vacío;
- si tiene **un hijo**, `root` pasa a apuntar a ese hijo, que es la nueva raíz;
- si tiene **dos**, la raíz se queda y toma el valor de su sucesor, como
  cualquier otro nodo.

<BinaryPicture tree={{ v: 8, l: { v: 4, l: { v: 2 }, r: { v: 6 } } }} tones={{ 8: 'mark' }} compact minColumns={3} label="Un árbol con el 8 en la raíz y un solo hijo, el 4, que tiene al 2 y al 6 debajo." caption="eliminar 8, raíz con un hijo" />
<BinaryPicture tree={{ v: 4, l: { v: 2 }, r: { v: 6 } }} tones={{ 4: 'mark' }} compact minColumns={3} label="El árbol después de eliminar el 8: el 4 es la nueva raíz, con el 2 y el 6 debajo." caption="root apunta al 4, la nueva raíz" />
</div>

</Slide>

<Slide title="El código de la eliminación">
El método público, `remove`, llama al privado con la raíz y guarda en `root`
lo que este devuelve, como `insert`. El privado devuelve lo que queda en el
lugar del nodo: `null`, su único hijo, o el mismo nodo con el valor de su
sucesor. Baja dos veces por un camino, hasta el nodo y hasta su sucesor:
$$O(h)$$.

<SequenceStepper eda="bst" operation="remove" values={[8, 4, 12, 2, 6, 10, 14]} target={8} />

</Slide>

<Slide title="Costos del árbol de búsqueda">
Cada operación baja por un camino desde la raíz, así que todas cuestan lo
mismo: la altura.

| Molde     | Operación           | Peor caso | Invariante que restaura                                              |
| --------- | ------------------- | --------- | -------------------------------------------------------------------- |
| Consultar | `contains`          | $$O(h)$$  | Ninguna: no cambia el árbol                                          |
| Modificar | `insert`            | $$O(h)$$  | La de orden: la hoja nueva queda del lado que eligió cada comparación |
| Modificar | `remove`            | $$O(h)$$  | La de orden: el sucesor cabe justo en el lugar que deja              |

La altura de un árbol binario de $$n$$ nodos está entre
$$\lfloor \log_2 n \rfloor$$ y $$n - 1$$.

</Slide>

<Slide title="Altura mínima: un árbol balanceado">
La forma de un árbol de búsqueda la decide el orden en que se insertan sus
valores. Si cada valor nuevo cae en un nivel que todavía tiene lugar, los
niveles se llenan de arriba hacia abajo, y el árbol queda con la **altura
mínima**, $$\lfloor \log_2 n \rfloor$$. Un árbol así está **balanceado**: en
cada nodo, el subárbol izquierdo y el derecho tienen alturas parecidas.

<SequenceStepper eda="bst" operation="insert" values={[]} value={[8, 4, 12, 2, 6, 10, 14]} program />

</Slide>

<Slide title="Altura máxima: un árbol desbalanceado">
Si los mismos valores se insertan de menor a mayor, cada uno es mayor que
todos los anteriores: siempre baja por la derecha y se cuelga al final. El
árbol queda como una cadena, con la **altura máxima**, $$n - 1$$. Está
**desbalanceado**: en cada nodo, todo lo que sigue cuelga a la derecha.

<SequenceStepper eda="bst" operation="insert" values={[]} value={[2, 4, 6, 8, 10, 12, 14]} program />

Buscar el mayor compara con todos los nodos, como en una lista enlazada.

</Slide>

<Slide title="Altura intermedia: un árbol en parte desbalanceado">
En un orden cualquiera, ni por niveles ni de menor a mayor, el árbol queda
entre los dos extremos: algunas ramas se alargan más que otras, y la altura
queda entre la mínima y la máxima.

<Slide title="El caso esperado y el peor caso">
El costo de un árbol de búsqueda depende de un orden que el árbol no elige: el
orden en que llegan sus valores.

- **En el caso esperado**, el árbol se arma insertando los valores en un
  orden al azar, con todos los órdenes igual de probables. Se demuestra que
  su altura esperada es $$O(\log n)$$.
- **En el peor caso**, los valores llegan ordenados, y la altura es $$n - 1$$.

| Operación  | Caso esperado | Peor caso     |
| ---------- | ------------- | ------------- |
| `contains` | $$O(\log n)$$ | $$\Theta(n)$$ |
| `insert`   | $$O(\log n)$$ | $$\Theta(n)$$ |
| `remove`   | $$O(\log n)$$ | $$\Theta(n)$$ |

En el peor caso, un árbol de búsqueda no es mejor que una lista enlazada
ordenada.

</Slide>

<Slide title="El desbalance con datos reales">
El peor caso no es raro. Los números de matrícula se asignan en orden
creciente; los registros de un sistema llegan ordenados por fecha; un archivo
de palabras suele venir en orden alfabético. Cargar cualquiera de ellos en un
árbol de búsqueda lo deja como una cadena, con la altura máxima.

El caso esperado supone que los valores llegan al azar, y los datos reales no
lo garantizan. Por eso un árbol de búsqueda, por sí solo, no puede asegurar
que buscar, insertar y eliminar cuesten $$O(\log n)$$.

</Slide>

<Slide title="El árbol de búsqueda balanceado">
La invariante de orden dice de qué lado de cada nodo va cada valor, pero no
dice nada sobre la forma del árbol: nada impide que se desbalancee.

Un **árbol de búsqueda balanceado** agrega lo que falta. Después de cada
inserción y de cada eliminación, revisa la forma y la arregla donde quedó
desbalanceada, sin romper la invariante de orden. Su altura queda en
$$O(\log n)$$ en el peor caso, sin importar el orden en que lleguen los
valores, y con ella el costo de todas las operaciones. El precio es más trabajo en cada inserción y en cada
eliminación.

Arreglar la forma sin romper el orden es posible porque los mismos valores
caben en muchas formas que cumplen la invariante. La herramienta que pasa de
una forma a otra es la **rotación**.

<Slide title="La rotación a la derecha">
Una **rotación** cambia la forma de un árbol de búsqueda sin romper la
invariante de orden. La **rotación a la derecha** en un nodo `p` que tiene
hijo izquierdo `q` hace subir a `q` al lugar de `p`: `p` baja a ser el hijo
derecho de `q`, y el subárbol derecho de `q` pasa a ser el subárbol izquierdo
de `p`. Los otros dos subárboles siguen colgados del mismo nodo que antes.

Una flecha curva, en el sentido de las agujas del reloj, sobre la arista entre p y q." caption="antes: A, más alto, carga la izquierda" />
<BinaryPicture tree={ROTATION_AFTER} subtrees={['A', 'B', 'C']} tall={['A']} tones={{ p: 'accent', q: 'accent', B: 'mark' }} label="Después de rotar a la derecha en p: q arriba, con el subárbol A a su izquierda y p a su derecha; p tiene a B a la izquierda y a C a la derecha. A subió un nivel, C bajó uno, y el árbol quedó parejo." caption="después: A sube un nivel, C baja uno" />
</div>

</Slide>

<Slide title="Por qué la rotación a la derecha conserva el orden">
Antes de rotar, los valores de B estaban en el subárbol derecho de `q` y en el
izquierdo de `p`: eran mayores que `q` y menores que `p`. Después siguen
siendo las dos cosas, porque B quedó a la izquierda de `p`, y `p` quedó a la
derecha de `q`. A sigue a la izquierda de `q`, y C a la derecha de `p`.
Ningún valor cambia de lado respecto de ningún nodo: **la invariante de orden
se mantiene**.

<div style={{ display: 'grid', gridTemplateColumns: 'repeat(auto-fit, minmax(240px, 1fr))', gap: '1rem 2rem', alignItems: 'end' }}>
<BinaryPicture tree={ROTATION_BEFORE} subtrees={['A', 'B', 'C']} tall={['A']} strip label="Antes de rotar, con el inorden debajo: A, q, B, p, C." caption="inorden antes: A, q, B, p, C" />
<BinaryPicture tree={ROTATION_AFTER} subtrees={['A', 'B', 'C']} tall={['A']} strip label="Después de rotar, con el inorden debajo: A, q, B, p, C, el mismo de antes." caption="inorden después: el mismo" />

Cada nodo y cada subárbol está dibujado en la columna de su lugar en el
inorden: al rotar, nada cambia de columna. Los nodos solo suben o bajan.

</Slide>

<Slide title="El código de la rotación a la derecha">
Tres referencias cambian, una por línea. El método devuelve `q`, el nodo que
subió, y quien lo llamó lo guarda donde estaba `p`: en `root`, o en el hijo
del padre de `p`. Mientras tanto, por un momento, un subárbol tiene dos
padres, y `q` apunta hacia arriba sin que nadie le apunte.

</Slide>

<Slide title="La rotación a la izquierda">

baja a ser el hijo izquierdo de `q`, y el subárbol izquierdo de `q` pasa a ser
el subárbol derecho de `p`. Los otros dos subárboles siguen colgados del mismo
nodo que antes.

<Slide title="Por qué la rotación a la izquierda conserva el orden">
Antes de rotar, los valores de B estaban en el subárbol izquierdo de `q` y en
el derecho de `p`: eran mayores que `p` y menores que `q`. Después siguen
siendo las dos cosas, porque B quedó a la derecha de `p`, y `p` quedó a la
izquierda de `q`. A sigue a la izquierda de `p`, y C a la derecha de `q`.
Ningún valor cambia de lado respecto de ningún nodo: **la invariante de orden
se mantiene**.

Como en la rotación a la derecha, nada cambia de columna: los nodos solo suben

Las mismas tres referencias, del lado contrario: `p` toma como hijo derecho al
subárbol izquierdo de `q`, y `q` toma a `p` como hijo izquierdo. El método
devuelve `q`, y quien lo llamó lo guarda donde estaba `p`.

<Slide title="Lo que una rotación hace con la altura">

se queda en el suyo; al rotar a la izquierda es al revés: C sube y A baja. Si
A era el subárbol más alto, el árbol queda más parejo: la rotación pasa altura
de un lado al otro, sin tocar el orden.

<Slide title="Cuando una rotación simple no alcanza">
Las rotaciones a la derecha y a la izquierda se llaman **simples**. Al rotar a
la derecha en `p`, lo que cuelga a la izquierda de `q` sube un nivel, y lo que
cuelga a su derecha cambia de padre sin cambiar de nivel. Por eso una rotación
simple empareja el árbol o no según dónde esté lo que lo carga:

- **por fuera**, a la izquierda de `q`: sube, y el árbol queda parejo;
- **por dentro**, a la derecha de `q`, bajo `r`: no sube, solo pasa al otro
  lado, y el árbol queda cargado igual de fuerte, pero hacia la derecha.

<Slide title="La rotación doble a la derecha">
La **rotación doble a la derecha** empareja un árbol cargado a la izquierda con
el peso por dentro, bajo `r`, con dos rotaciones simples:

1. una **rotación a la izquierda en `q`**: sube `r`, y el peso queda por
   fuera;
2. una **rotación a la derecha en `p`**, que ahora sí empareja: `r` queda
   arriba, con `q` y `p` como hijos.

En inglés se llama *left-right*: el peso está en el hijo izquierdo y, dentro de
él, a la derecha.

## El árbol AVL

{/* A tree that keeps the balance invariant, and one that breaks it at a single node, the 8. */}

export const NOT_AVL = { v: 8, l: { v: 4, l: { v: 2 }, r: { v: 6, r: { v: 7 } } }, r: { v: 12 } };

<Slide title="Un árbol de búsqueda que cuida su forma">
El primer árbol de búsqueda balanceado lo publicaron Georgy Adelson-Velsky y
Evgenii Landis en 1962, y lleva sus iniciales: el **árbol AVL**. Es un árbol
binario de búsqueda cuyas inserciones y eliminaciones, al terminar, revisan
el camino que recorrieron y **rotan** donde el árbol quedó desbalanceado.

<div style={{ display: 'grid', gridTemplateColumns: 'repeat(auto-fit, minmax(240px, 1fr))', gap: '1rem 2rem', alignItems: 'end' }}>
<BinaryPicture tree={EVENS_CHAIN} ruler="h = 6" compact label="Los valores 2 a 14 insertados de menor a mayor en un árbol de búsqueda: una cadena de altura 6." caption="de menor a mayor, en un árbol de búsqueda: altura 6" />
<BinaryPicture tree={EVENS} ruler="h = 2" compact minColumns={7} label="Los mismos valores insertados de menor a mayor en un árbol AVL: un árbol lleno de altura 2." caption="los mismos, en un AVL: altura 2" />
</div>

Los valores pueden llegar en el peor orden: la forma la cuida el árbol.

</Slide>

<Slide title="La invariante de balance">
Las tres invariantes del árbol de búsqueda siguen en pie, sin cambios. El AVL
agrega una cuarta:

4. **En cada nodo, las alturas de sus dos subárboles difieren a lo más en
   1.** Ningún lado puede ser dos niveles más alto que el otro, en ningún
   nodo.

<div style={{ display: 'grid', gridTemplateColumns: 'repeat(auto-fit, minmax(240px, 1fr))', gap: '1rem 2rem', alignItems: 'end' }}>
<BinaryPicture tree={EVENS_SHUFFLED} minColumns={7} label="Un árbol AVL: 10 en la raíz, con 4 y 14 debajo; el 4 con 2 y 8, el 8 con 6, y el 14 con 12. En cada nodo, las alturas de los dos subárboles difieren a lo más en 1." caption="cumple la invariante de balance en cada nodo" />
<BinaryPicture tree={NOT_AVL} minColumns={7} tones={{ 8: 'mark' }} notes={{ 8: 'izq. 2, der. 0' }} label="Un árbol de búsqueda que no es AVL: en el 8, el subárbol izquierdo tiene altura 2 y el derecho, el 12, altura 0." caption="en el 8, la izquierda es dos niveles más alta" />
</div>

Mantener esta invariante tiene un costo: después de cada inserción y de cada
eliminación hay que revisar los nodos del camino recorrido y, donde alguno
quedó desbalanceado, rotar. A cambio, la altura del árbol queda en
$$O(\log n)$$, y con ella el costo de buscar, insertar y eliminar.

</Slide>

<Slide title="El factor de balance">
El **factor de balance** de un nodo es la altura de su subárbol derecho menos
la de su subárbol izquierdo, contando $$-1$$ como la altura del árbol vacío.
La invariante de balance dice que todo factor es $$-1$$, $$0$$ o $$+1$$. Un
factor negativo dice que el nodo está **cargado a la izquierda**; uno
positivo, **a la derecha**; y un $$-2$$ o un $$+2$$ dice que ahí la invariante
se rompió.

<BinaryPicture tree={NOT_AVL} minColumns={7} tones={{ 8: 'mark' }} badges={{ 8: '−2', 4: '+1', 2: '0', 6: '+1', 7: '0', 12: '0' }} label="El árbol que no es AVL con sus factores: 8, menos 2; 4, más 1; 2, 0; 6, más 1; 7, 0; 12, 0." caption="el −2 del 8 rompe la invariante" />
</div>

</Slide>

<Slide title="La altura de un árbol AVL">
La invariante de balance basta para que la altura quede en $$O(\log n)$$. El
árbol AVL **más flaco** de cada altura, el que tiene menos nodos, es una
raíz sobre los más flacos de las dos alturas anteriores. Sus tamaños crecen
como los números de Fibonacci: 1, 2, 4, 7, 12, 20, 33… y eso es crecer de
forma exponencial. Al revés, la altura de un AVL de $$n$$ nodos crece como
$$\log n$$: Adelson-Velsky y Landis demostraron que es menor que
$$1{,}45 \cdot \log_2(n + 2)$$.

<Slide title="Dónde se rompe la invariante">
Una inserción o una eliminación solo cambia las alturas de los nodos de su
camino, así que solo ahí puede romperse la invariante de balance. Por eso, al
volver de la operación, se revisa el factor de cada nodo del camino, de abajo
hacia arriba, y el que llega a $$-2$$ o $$+2$$ se arregla con una rotación.

<Slide title="Los cuatro casos de desbalance">
Cuando un nodo queda con factor $$-2$$ o $$+2$$, la rotación que lo arregla
depende de dos cosas: hacia qué lado está cargado el nodo, y hacia qué lado
está cargado su hijo de ese lado. Si el hijo está cargado hacia el **mismo
lado**, lo que carga está por fuera, y basta una **rotación simple** en el
nodo; si está cargado hacia el **lado contrario**, está por dentro, y hace
falta una **rotación doble**. En inglés, los cuatro casos se llaman
*left-left*, *left-right*, *right-right* y *right-left*.

<Slide title="La regla para elegir la rotación">
La rotación sale del factor del nodo y del factor de su hijo del lado
cargado:

| Factor del nodo | Factor del hijo del lado cargado | Rotación                 |
| --------------- | -------------------------------- | ------------------------ |
| $$-2$$          | $$-1$$ o $$0$$                   | simple a la derecha      |
| $$-2$$          | $$+1$$                           | doble a la derecha       |
| $$+2$$          | $$+1$$ o $$0$$                   | simple a la izquierda    |
| $$+2$$          | $$-1$$                           | doble a la izquierda     |

Dicho en una frase: si el hijo está cargado hacia el lado contrario, doble; si
no, simple. Un hijo con factor 0 nunca aparece al insertar; aparece al
eliminar, y ahí basta la rotación simple.

</Slide>

<Slide title="El nodo que guarda su altura">
Calcular la altura de un subárbol recorriéndolo cuesta $$\Theta(n)$$, y el
AVL la necesita en cada nodo de cada camino. Por eso cada nodo **guarda su
altura**: es el nodo del árbol de búsqueda con un campo más, `height`. Un
nodo nuevo es una hoja, y su altura empieza en 0.

```java
class Node<T> {
    T value;
    Node<T> left;
    Node<T> right;
    int height;

    Node(T value) {
        this.value = value;
    }
}
```

</Slide>

<Slide title="La clase AVL y la altura de un subárbol">
La clase guarda la raíz, como el árbol de búsqueda. `height` lee la altura de
un subárbol en tiempo constante, con $$-1$$ para el árbol vacío;
`updateHeight` la vuelve a calcular a partir de las de sus dos hijos, y hay
que llamarla cada vez que un nodo cambia de hijos; `factor` es el factor de
balance.

```java
class AVL<T extends Comparable<T>> {
    Node<T> root;

    int height(Node<T> node) {
        return node == null ? -1 : node.height;
    }

    void updateHeight(Node<T> node) {
        node.height = 1 + Math.max(height(node.left),
                                   height(node.right));
    }

    int factor(Node<T> node) {
        return height(node.right) - height(node.left);
    }
}
```

</Slide>

<Slide title="Las rotaciones actualizan las alturas">
Una rotación cambia los hijos de dos nodos, así que las dos rotaciones
agregan dos líneas antes de devolver `q`: primero se actualiza `p`, que quedó
abajo, y después `q`, cuya altura depende de la de `p`. Los subárboles que se
movieron enteros no cambian de altura.

```java
Node<T> rotateRight(Node<T> p) {
    Node<T> q = p.left;
    p.left = q.right;
    q.right = p;
    updateHeight(p);
    updateHeight(q);
    return q;
}
```

`rotateLeft` agrega las mismas dos líneas, en el mismo orden. Las dobles no
cambian: sus dos llamadas son a las simples, que ya actualizan las alturas.

</Slide>

<Slide title="El código de balance">
`balance` actualiza la altura del nodo, calcula su factor y, si la invariante
se rompió, hace la rotación de la regla: la doble si el hijo del lado cargado
está cargado hacia el lado contrario, y la simple si no. Devuelve la raíz del
subárbol que queda: el mismo nodo, o el que subió al rotar.

```java
Node<T> balance(Node<T> node) {
    updateHeight(node);
    int b = factor(node);
    if (b < -1) {
        if (factor(node.left) > 0)
            return rotateLeftRight(node);
        return rotateRight(node);
    }
    if (b > 1) {
        if (factor(node.right) < 0)
            return rotateRightLeft(node);
        return rotateLeft(node);
    }
    return node;
}
```

</Slide>

pasa por `balance`, que rota el primero que quedó con $$\pm 2$$: el privado
devuelve `balance(node)` en vez de `node`. Baja y vuelve por un camino de
altura $$O(\log n)$$: $$O(\log n)$$.

<Slide title="Eliminar en un árbol AVL">
Eliminar en un árbol AVL también se hace en dos partes:

1. **Se elimina como en el árbol de búsqueda**: el nodo se busca y se saca
   según su caso, hoja, un hijo o dos hijos.
2. **Se rebalancea al volver**: igual que al insertar, cada nodo del camino de
   vuelta revisa su factor, y el que quedó con $$-2$$ o $$+2$$ rota.

Eliminar acorta un lado, y el que queda cargado es el otro. Ahí aparece un
caso que insertar nunca produce: el hijo del lado cargado con factor 0, con
sus dos subárboles igual de altos. Basta una rotación simple: lo de fuera
sube, y lo de dentro, que pesa lo mismo, pasa al otro lado sin romper la
invariante.

<Slide title="Costos del árbol AVL">
Las operaciones son las del árbol de búsqueda, y cuestan la altura; la

llegue.

| Molde     | Operación           | Peor caso       | Invariante que restaura                                         |
| --------- | ------------------- | --------------- | --------------------------------------------------------------- |
| Consultar | `contains`          | $$O(\log n)$$   | Ninguna: no cambia el árbol                                     |
| Modificar | `insert`            | $$O(\log n)$$   | La de orden, y la de balance con a lo más una rotación          |
| Modificar | `remove`            | $$O(\log n)$$   | La de orden, y la de balance con a lo más una rotación por nivel |

</Slide>

<Slide title="El precio del balance">
El árbol AVL garantiza $$O(\log n)$$ en todas sus operaciones, y lo paga de
tres maneras. Cada nodo guarda un entero más, su altura. Cada inserción y cada
eliminación recorren de vuelta todo su camino, actualizando alturas y
revisando factores, aunque no haya nada que rotar. Y el código es más largo:
cuatro casos de rotación y una invariante más que mantener en cada
modificación.

Cuando hay muchas más búsquedas que modificaciones, lo que se paga al
modificar se recupera en cada búsqueda.

</Slide>

## Otros árboles de búsqueda

<Slide title="Árboles balanceados de otras formas">
El AVL no es la única manera de acotar la altura. Otros árboles de búsqueda
balanceados cuidan la forma con otras reglas, y cada uno cambia un poco de
trabajo por otra ventaja.

| Árbol         | Qué cuida                                                                              | Para qué se usa                                                                                 |
| ------------- | -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Rojo-negro    | Cada nodo es rojo o negro, ningún rojo tiene un hijo rojo, y todos los caminos hacia abajo tienen la misma cantidad de negros | Al eliminar rota a lo más tres veces, contra $$O(\log n)$$ del AVL; es el que usan `TreeMap` y `TreeSet` de Java |
| Árbol 2-3     | Nodos de uno o dos valores, y todas las hojas en el mismo nivel                         | Casi no se programa tal cual: es la idea detrás del rojo-negro, que lo escribe con nodos binarios, y del árbol B, que lo generaliza |
| Árbol B       | Generaliza el 2-3: nodos con muchos valores, cientos, y todas las hojas en el mismo nivel | Los índices de las bases de datos: cada nodo es una página del disco, y tres o cuatro niveles alcanzan para millones de valores |
| *Splay*       | Nada fijo: cada búsqueda sube el nodo encontrado hasta la raíz                          | Datos donde unos pocos valores se buscan una y otra vez                                         |

</Slide>

<Slide title="Árboles para otras preguntas">
Otros árboles no buscan un valor por comparación, sino que responden otras
preguntas rápido.

| Árbol                | Qué responde rápido                                           | Dónde se usa                                   |
| -------------------- | ------------------------------------------------------------- | ---------------------------------------------- |
| *Trie*               | Qué palabras empiezan con un prefijo: cada nivel es una letra | Autocompletar, diccionarios, rutas de red      |
| Árbol de segmentos   | La suma o el mínimo de un tramo de un arreglo que cambia      | Consultas por rango en datos que se actualizan |
| *Treap*              | Un árbol de búsqueda balanceado en promedio, con prioridades al azar | Una alternativa simple al AVL y al rojo-negro |
| *Quadtree*           | Qué puntos de un plano caen en una región                     | Mapas, geolocalización, colisiones en juegos   |
| Árbol de decisión    | Qué respuesta dar según una serie de preguntas                | Clasificadores en aprendizaje automático       |
| *Heap*               | Cuál es el mayor, o el menor, de todos: siempre está en la raíz | Colas de prioridad: urgencias, planificadores de tareas |

</Slide>

<Slide title="Recorrer un árbol con un for">
En Java, `for (int x : lista)` recorre cualquier objeto que implemente
`Iterable`: le pide un **iterador**, un objeto con dos métodos. `hasNext`
responde si quedan valores, y `next` entrega el siguiente, o lanza
`NoSuchElementException` si no queda ninguno. Para que un árbol de búsqueda se
recorra con un `for`, de menor a mayor, hace falta su iterador.

<BinaryPicture tree={EVENS} visits="in" sequence label="El árbol de búsqueda con 8 en la raíz, recorrido de menor a mayor: el iterador entrega 2, 4, 6, 8, 10, 12 y 14, en ese orden." caption="cada next entrega el siguiente: 2, 4, 6, 8, 10, 12, 14" />

El iterador recibe la raíz del árbol, que puede estar vacío, y entrega sus
valores en orden; en un árbol vacío, `hasNext` responde `false` desde el
principio. Llamamos $$n$$ a la cantidad de valores y $$h$$ a la altura: el
iterador puede pedir memoria $$O(h)$$, pero no $$\Theta(n)$$.

```java
class InorderIterator<T> implements Iterator<T> {
    InorderIterator(Node<T> root)
    public boolean hasNext()
    public T next()
}
```

</Slide>

<Slide title="Copiar el inorden a una lista">
La primera idea es recorrer el árbol en inorden al crear el iterador, guardar
los valores en una lista y entregarlos de a uno. Funciona, pero copia el árbol
entero: la memoria es $$\Theta(n)$$, no $$O(h)$$. Y hace todo el trabajo antes
de entregar el primer valor, aunque el `for` se detenga en el segundo.

<SortedRow values={[2, 4, 6, 8, 10, 12, 14]} label="La copia del inorden en una lista: 2, 4, 6, 8, 10, 12 y 14, los siete valores del árbol, guardados antes de entregar el primero." caption="la copia: los siete valores, guardados antes de entregar el primero" />

El inorden recursivo tampoco sirve tal cual: una recursión no se puede pausar
a la mitad. Entrega todos los valores de una vez, y un iterador tiene que
entregar uno y esperar.

</Slide>

<Slide title="Pausar el inorden">
El inorden visita un nodo recién cuando termina su subárbol izquierdo. Por
eso, al bajar por la izquierda desde la raíz, cada nodo del camino queda
**pendiente**, esperando a los de más abajo, y el primero en entregarse es el
último del camino. Después de entregar un nodo, el inorden sigue con su
subárbol derecho, que empieza igual: bajando por la izquierda desde el hijo
derecho, y dejando pendientes los nodos de ese camino.

El próximo en entregarse es siempre el último pendiente que entró. Los
pendientes forman una **pila**, y su cima es el próximo valor.

<Slide title="Iterador · el árbol en un for">
El `for` pide un iterador a lo que recorre. Para eso, la clase del árbol
implementa `Iterable`, cuyo único método, `iterator`, crea un iterador que
parte de la raíz. Cada `for` pide el suyo, así que dos recorridos del mismo
árbol no se estorban.

```java
class BST<T extends Comparable<T>> implements Iterable<T> {
    Node<T> root;

    public Iterator<T> iterator() {
        return new InorderIterator<>(root);
    }
}
```

Con eso, un `BST<Integer>` llamado `tree` se recorre de menor a mayor como
cualquier colección:

```java
for (int x : tree) {
    System.out.println(x);
}
```

</Slide>

<Slide title="El árbol vacío y el costo de next">
Con el árbol vacío, el constructor no deja nada pendiente: `hasNext` responde
`false` desde el principio, y `next` lanza la excepción, como pide el contrato
de `Iterator`. Lo mismo pasa con un `next` pedido después del último valor.

**Tiempo.** Un solo `next` puede bajar por un camino entero, $$O(h)$$. Pero
cada nodo entra a la pila una vez y sale una vez, así que recorrer los $$n$$
valores cuesta $$\Theta(n)$$ en total: $$\Theta(1)$$ amortizado por `next`.
**Memoria.** La pila guarda solo nodos de un mismo camino desde la raíz:
$$O(h)$$.

</Slide>

```java starter
import java.util.ArrayDeque;
import java.util.Deque;
import java.util.Iterator;
import java.util.NoSuchElementException;

class Node<T> {
    T value;
    Node<T> left;
    Node<T> right;
    Node(T value) { this.value = value; }
}

class InorderIterator<T> implements Iterator<T> {
    private final Deque<Node<T>> pending =
            new ArrayDeque<>();

    private void pushLeft(Node<T> node) {
        while (node != null) {
            pending.push(node);
            node = node.left;
        }
    }

    InorderIterator(Node<T> root) {
        pushLeft(root);
    }

    public boolean hasNext() {
        return !pending.isEmpty();
    }

    public T next() {
        if (pending.isEmpty()) {
            throw new NoSuchElementException();
        }
        Node<T> node = pending.pop();
        pushLeft(node.right);
        return node.value;
    }
}

class BST<T extends Comparable<T>> implements Iterable<T> {
    Node<T> root;

    public Iterator<T> iterator() {
        return new InorderIterator<>(root);
    }
}
```

<Slide title="Un árbol vacío y el costo de la intersección">
Si un árbol está vacío, su iterador no entrega nada, `x` o `y` empieza en
`null`, y el ciclo no corre: la respuesta es la lista vacía. Si los árboles no
tienen valores en común, el ciclo avanza hasta acabar uno de los dos sin
agregar nada.

**Tiempo.** Cada vuelta del ciclo saca al menos un valor de un iterador, y
cada nodo entra y sale de su pila una sola vez: $$O(n + m)$$. Puede ser menos,
porque el ciclo termina en cuanto un árbol se acaba. **Memoria.** Las dos
pilas guardan un camino cada una: $$O(h_1 + h_2)$$, aparte de la respuesta.
Si los dos son árboles AVL, eso es $$O(\log n + \log m)$$.

```java starter
import java.util.ArrayDeque;
import java.util.ArrayList;
import java.util.Deque;
import java.util.Iterator;
import java.util.List;
import java.util.NoSuchElementException;

class Node<T> {
    T value;
    Node<T> left;
    Node<T> right;
    Node(T value) { this.value = value; }
}

class InorderIterator<T> implements Iterator<T> {
    private final Deque<Node<T>> pending =
            new ArrayDeque<>();

    private void pushLeft(Node<T> node) {
        while (node != null) {
            pending.push(node);
            node = node.left;
        }
    }

    InorderIterator(Node<T> root) {
        pushLeft(root);
    }

    public boolean hasNext() {
        return !pending.isEmpty();
    }

    public T next() {
        if (pending.isEmpty()) {
            throw new NoSuchElementException();
        }
        Node<T> node = pending.pop();
        pushLeft(node.right);
        return node.value;
    }
}

class Solution {
    static List<Integer> intersection(Node<Integer> a,
            Node<Integer> b) {
        List<Integer> both = new ArrayList<>();
        Iterator<Integer> ia = new InorderIterator<>(a);
        Iterator<Integer> ib = new InorderIterator<>(b);
        Integer x = ia.hasNext() ? ia.next() : null;
        Integer y = ib.hasNext() ? ib.next() : null;
        while (x != null && y != null) {
            int c = x.compareTo(y);
            if (c == 0) both.add(x);
            if (c <= 0) x = ia.hasNext() ? ia.next() : null;
            if (c >= 0) y = ib.hasNext() ? ib.next() : null;
        }
        return both;
    }
}
```

<Exercise title="Un árbol de búsqueda de altura mínima">

Un arreglo trae valores distintos, ordenados de menor a mayor, y hay que
guardarlos en un árbol binario de búsqueda lo más bajo posible: con $$n$$
valores, de altura $$\lfloor \log_2 n \rfloor$$. Escribamos `build`, que
recibe el arreglo, que puede estar vacío, y devuelve la raíz del árbol, o
`null` si no hay valores.

Con los valores del 1 al 7, la raíz es el 4, con el 2 y el 6 debajo, y el árbol
tiene altura 2. Con los valores del 1 al 4, la raíz puede ser el 2 o el 3, y la
altura es 2. Con un solo valor, el árbol es una hoja.

los anteriores, y el arreglo ordenado es justo el peor orden de llegada. La
raíz tiene que dejar la mitad de los valores a cada lado, y cada mitad se arma
con la misma regla.

```java solution
class Node<T> {
    T value;
    Node<T> left;
    Node<T> right;
    Node(T value) { this.value = value; }
}

class Solution {
    static Node<Integer> build(int[] sorted, int lo, int hi) {
        if (lo > hi) return null;
        int mid = (lo + hi) / 2;
        Node<Integer> node = new Node<>(sorted[mid]);
        node.left = build(sorted, lo, mid - 1);
        node.right = build(sorted, mid + 1, hi);
        return node;
    }

    static Node<Integer> build(int[] sorted) {
        return build(sorted, 0, sorted.length - 1);
    }
}
```

<Exercise title="Verificación de un árbol de búsqueda">

Un árbol binario dice ser un árbol de búsqueda. Escribamos `isBST`, que recibe
su raíz y responde si cumple la invariante de orden: para cada nodo, **todos**
los valores de su subárbol izquierdo son menores que el suyo, y **todos** los
de su subárbol derecho son mayores. El árbol vacío la cumple.

El árbol con el 8 en la raíz, el 4 y el 12 debajo, y el 2, el 6, el 10 y el 14
en el último nivel, la cumple. El mismo árbol con un 10 en lugar del 6 no la
cumple: el 10 está bien con su padre, el 4, pero está a la izquierda del 8.

Revisar cada nodo solo con sus hijos no alcanza, y ese es el ejemplo que lo
muestra. Cada subárbol tiene un rango de valores permitidos, que se angosta al
bajar: bajar con ese rango revisa cada nodo contra todos sus ancestros a la
vez.

```java solution
class Node<T> {
    T value;
    Node<T> left;
    Node<T> right;
    Node(T value) { this.value = value; }
}

class Solution {
    static boolean isBST(Node<Integer> root) {
        return isBST(root, Long.MIN_VALUE, Long.MAX_VALUE);
    }

    static boolean isBST(Node<Integer> node, long min, long max) {
        if (node == null) return true;
        if (node.value <= min || node.value >= max) return false;
        return isBST(node.left, min, node.value)
            && isBST(node.right, node.value, max);
    }
}
```

<Exercise title="El problema de Josefo con saltos grandes">

En el problema de Josefo, $$n$$ personas numeradas de 1 a $$n$$ forman un
círculo. Se cuenta desde la primera, y la $$k$$-ésima sale del círculo; se
sigue contando desde la siguiente, y la $$k$$-ésima sale; y así, hasta que no
queda nadie. Escribamos `josephus`, que recibe $$n$$ y $$k$$, los dos mayores
que cero, y devuelve el orden en que salen.

Con siete personas y saltos de tres, salen en el orden 3, 6, 2, 7, 5, 1, 4. Con
una sola persona, sale ella; con saltos de uno, salen en orden, de 1 a $$n$$; y
un salto puede ser más largo que el círculo: con cuatro personas y saltos de
diez, salen 2, 3, 1, 4.

Con una cola, cada salida hace avanzar a $$k - 1$$ personas, y el total es
$$\Theta(n \cdot k)$$: con saltos de mil millones, no termina. La dificultad es
llegar a la $$k$$-ésima persona sin contar de a una. Guardemos a las $$n$$
personas en un árbol de búsqueda de altura mínima en el que cada nodo sabe
cuántas personas de su subárbol siguen en el círculo: con esas cuentas se baja
directo a la persona número $$r$$ entre las que quedan, y sacarla corrige las
cuentas de un solo camino. Cada salida cuesta $$O(\log n)$$, y todas juntas,
$$O(n \log n)$$, sea cual sea $$k$$.

```java starter

import java.util.List;

class Solution {
    static List<Integer> josephus(int n, int k) {
        return new ArrayList<>();
    }
}
```

```java solution
import java.util.ArrayList;
import java.util.List;

class Solution {
    // Una persona del círculo, en un árbol de búsqueda de altura
    // mínima sobre 1..n; alive cuenta cuántas personas de su
    // subárbol siguen en el círculo.
    static class Seat {
        int value;
        int alive;
        boolean here = true;
        Seat left;
        Seat right;
    }

    static Seat build(int lo, int hi) {
        if (lo > hi) return null;
        int mid = (lo + hi) / 2;
        Seat seat = new Seat();
        seat.value = mid;
        seat.alive = hi - lo + 1;
        seat.left = build(lo, mid - 1);
        seat.right = build(mid + 1, hi);
        return seat;
    }

    static int alive(Seat seat) {
        return seat == null ? 0 : seat.alive;
    }

    // Saca a la persona en la posición rank, desde 0, entre las que
    // siguen en el círculo; cada nodo del camino pierde una.
    static int removeAt(Seat seat, int rank) {
        seat.alive--;
        int left = alive(seat.left);
        if (rank < left) return removeAt(seat.left, rank);
        if (seat.here && rank == left) {
            seat.here = false;
            return seat.value;
        }
        int skipped = left + (seat.here ? 1 : 0);
        return removeAt(seat.right, rank - skipped);
    }

    static List<Integer> josephus(int n, int k) {
        List<Integer> order = new ArrayList<>();
        Seat root = build(1, n);
        int position = 0;
        for (int left = n; left > 0; left--) {
            position = (position + k - 1) % left;
            order.add(removeAt(root, position));
        }
        return order;
    }
}
```
