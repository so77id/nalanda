# Estructuras de Datos Avanzadas · Árboles II

Un registro de estudiantes recibe números de matrícula de a uno, y en
cualquier momento hay que responder si un número ya está. Un registro de
fechas, o de folios, pide lo mismo: guardar un conjunto de valores que crece,
y buscar e insertar en él todo el tiempo. Para eso hacen falta dos
operaciones rápidas a la vez.

<Slide title="Un dilema entre buscar e insertar">
Las estructuras que guardan sus elementos en fila resuelven bien una de las dos
operaciones y mal la otra.

- **Sin orden**, un valor nuevo entra al principio de una lista, o al final de
  un arreglo, sin mirar a los demás. Pero buscar obliga a revisar los valores
  uno por uno: nada dice dónde está el buscado.
- **Ordenado**, un arreglo se busca con la búsqueda binaria, que descarta la
  mitad de lo que queda en cada comparación. Pero un valor nuevo tiene que
  entrar en su lugar, y todos los mayores se corren una casilla.

| Estructura            | Buscar             | Insertar      |
| --------------------- | ------------------ | ------------- |
| Lista enlazada        | $$\Theta(n)$$      | $$\Theta(1)$$ |
| Arreglo ordenado      | $$\Theta(\log n)$$ | $$\Theta(n)$$ |

Una sirve para insertar y la otra para buscar. Lo que hace falta es una
estructura que no tenga que elegir.

</Slide>

<Slide title="La búsqueda binaria">
En un arreglo ordenado, la búsqueda binaria compara el valor buscado con el
elemento del medio. Si son iguales, lo encontró. Si el buscado es menor, no
puede estar en la mitad derecha, y la búsqueda sigue en la izquierda; si es
mayor, al revés. Cada comparación descarta la mitad de lo que quedaba, así que
bastan $$\lfloor \log_2 n \rfloor + 1$$ comparaciones.

<BinarySearchOnArray values={[2, 4, 6, 8, 10, 12, 14]} target={12} />

</Slide>

<Slide title="Insertar en un arreglo ordenado">
La búsqueda binaria también dice dónde va un valor nuevo: en la posición
donde la búsqueda terminó sin encontrarlo. Pero para abrirle esa casilla,
cada valor mayor se corre un lugar a la derecha, empezando por el último. En
el peor caso se corren todos: $$\Theta(n)$$.

<SequenceStepper eda="dynamic-array" operation="insert-at" values={[2, 4, 6, 8, 10, 12, 14]} value={7} index={3} capacity={8} />

</Slide>

<Slide title="Las decisiones de la búsqueda binaria">
Las comparaciones de una búsqueda binaria siguen siempre el mismo patrón. La
primera es con el elemento del medio. Si el buscado es menor, la segunda es
con el medio de la mitad izquierda; si es mayor, con el medio de la derecha;
y así. Dibujadas, esas decisiones forman un **árbol binario**: el elemento del
medio es la raíz, y cada mitad, un subárbol armado con la misma regla.

<BinaryPicture tree={EVENS} strip label="El árbol de decisiones de una búsqueda binaria sobre el arreglo 2, 4, 6, 8, 10, 12, 14. La raíz es 8; a la izquierda, 4, con hijos 2 y 6; a la derecha, 12, con hijos 10 y 14. Debajo, el arreglo ordenado, con cada valor exactamente bajo su nodo." caption="el arreglo ordenado es el inorden del árbol" />

Cada búsqueda es un camino desde la raíz hacia abajo, y el arreglo ordenado
es el inorden del árbol: cada valor queda debajo de su nodo.

</Slide>

<Slide title="Las decisiones guardadas en nodos">
Si esas decisiones se guardan como **nodos enlazados** en lugar de un
arreglo, buscar sigue siendo lo mismo: comparar y bajar por un lado. Y un
valor que no está termina su búsqueda en un subárbol vacío, que es justo
donde tiene que ir.

El 7 no está." caption="buscar 7: 8, 4, 6, y a la derecha de 6 no hay nada" />
<BinaryPicture tree={EVENS_WITH_7} fresh={7} tones={{ 7: 'mark' }} holes={[]} minColumns={8} label="El 7 colgado como hijo derecho del 6: una hoja nueva, sin que ningún otro nodo se mueva." caption="el 7 se cuelga ahí, como hoja: nada se corre" />
</div>

Insertar ya no corre nada: el valor nuevo se cuelga como una **hoja** en el
lugar donde su búsqueda terminó.

</Slide>

<Slide title="La invariante de orden">
Un **árbol binario de búsqueda** —en inglés, *binary search tree*, o
**BST**— es un árbol binario que cumple esta **invariante**:

> **para cada nodo, todos los valores de su subárbol izquierdo son menores
> que el suyo, y todos los de su subárbol derecho son mayores.**

La palabra que importa es **todos**. No basta con que cada hijo esté del lado
correcto de su padre: un valor tiene que estar del lado correcto de **cada**
nodo por encima de él.

<div style={{ display: 'grid', gridTemplateColumns: 'repeat(auto-fit, minmax(220px, 1fr))', gap: '1rem', alignItems: 'end' }}>
<BinaryPicture tree={EVENS} minColumns={7} compact label="Un árbol de búsqueda: 8 en la raíz, 4 y 12 debajo, 2, 6, 10 y 14 en el último nivel. Todo lo que está a la izquierda de cada nodo es menor que él, y todo lo de la derecha, mayor." caption="cumple la invariante en cada nodo" />
<BinaryPicture tree={{ v: 8, l: { v: 4, l: { v: 2 }, r: { v: 10 } }, r: { v: 12 } }} minColumns={7} compact tones={{ 10: 'mark' }} notes={{ 10: '10 > 8' }} label="Un árbol que no es de búsqueda: 8 en la raíz, con 4 y 12 debajo; el 4 tiene hijos 2 y 10. El 10 está bien con su padre, el 4, pero está en el subárbol izquierdo del 8 y es mayor que 8." caption="10 está bien con su padre, 4, pero no con el 8" />
</div>

</Slide>

<Slide title="Las invariantes del árbol de búsqueda">
Las dos invariantes del árbol binario siguen en pie, sin cambios: cada nodo
tiene a lo más dos hijos, el izquierdo y el derecho, y cada nodo salvo la raíz
tiene exactamente un padre. El árbol de búsqueda agrega una tercera:

3. **Para cada nodo, todo su subárbol izquierdo es menor que él, y todo su
   subárbol derecho es mayor.** En particular, ningún valor se repite: un
   valor igual no estaría ni a un lado ni al otro.

Es la invariante que decide los costos. Por ella, cada comparación descarta
un subárbol entero, y por ella cada inserción y cada eliminación tienen que
dejar a cada valor del lado correcto de cada uno de sus ancestros.

</Slide>

<Slide title="El inorden de un árbol de búsqueda">
**El inorden de un árbol binario de búsqueda entrega sus valores ordenados de
menor a mayor.**

La razón es la definición recursiva del inorden: primero el subárbol
izquierdo, después el nodo, después el subárbol derecho. Por la invariante,
todo lo de la izquierda es menor que el nodo y todo lo de la derecha es mayor.
Si cada subárbol, más pequeño, ya sale ordenado, el nodo queda exactamente
entre los dos, y el total sale ordenado.

<SequenceStepper eda="binary-tree" operation="inorder" values={[8, 4, 12, 2, 6, 10, 14]} />

</Slide>

## Las operaciones del árbol de búsqueda

<Slide title="Buscar en un árbol de búsqueda">
En cada nodo hay tres respuestas posibles: el valor buscado es el del nodo, es
menor o es mayor. Si es menor, la invariante garantiza que no está en el
subárbol derecho, y la búsqueda sigue solo por la izquierda; si es mayor, al
revés. Cada comparación descarta un subárbol entero.

<div style={{ display: 'grid', gridTemplateColumns: 'repeat(auto-fit, minmax(240px, 1fr))', gap: '1rem 2rem', alignItems: 'end' }}>
<BinaryPicture tree={EVENS} path={[8, 12, 10]} seek={10} tones={{ 10: 'keep', 4: 'faint', 2: 'faint', 6: 'faint', 14: 'faint' }} holes={[]} label="Buscar el 10: se compara con el 8 y se baja a la derecha, con el 12 y se baja a la izquierda, y el 10 es el buscado. El subárbol izquierdo del 8 y el 14 quedan descartados, atenuados." caption="buscar 10: 8, 12, 10; el resto queda descartado" />
<BinaryPicture tree={EVENS} path={[8, 4, 6]} seek={7} probe={{ at: 6, side: 'r' }} tones={{ 6: 'focus', 2: 'faint', 12: 'faint', 10: 'faint', 14: 'faint' }} holes={[]} label="Buscar el 7: se compara con el 8, el 4 y el 6, y a la derecha del 6 está el árbol vacío. El 7 no está. El 2 y el subárbol derecho del 8 quedan descartados." caption="buscar 7: 8, 4, 6, y a la derecha de 6 no hay nada" />
</div>

La búsqueda baja por **un solo camino**, y termina en el valor o en un
subárbol vacío. Un camino desde la raíz tiene a lo más $$h + 1$$ nodos, así
que buscar cuesta $$O(h)$$, se encuentre o no el valor.

</Slide>

<Slide title="La clase BST">
La clase guarda la raíz y ofrece un método público que delega en uno
recursivo, que recibe la raíz de un subárbol. Los nodos son los `Node<T>` del
árbol binario.

```java
class BST<T extends Comparable<T>> {
    Node<T> root;

    boolean contains(T value) {
        return contains(root, value);
    }
}
```

Para comparar se usa `compareTo`, que responde un número negativo, cero o
positivo: por eso el tipo de los valores tiene que ser comparable, `T extends
Comparable<T>`.

</Slide>

<Slide title="El código de la búsqueda">
Cada caso de la regla es una línea del método recursivo: el subárbol vacío,
el valor encontrado, y un lado o el otro según la comparación.

<SequenceStepper eda="bst" operation="search" values={[8, 4, 12, 2, 6, 10, 14]} target={[10, 7]} />

</Slide>

<Slide title="Insertar en un árbol de búsqueda">
Para insertar, se busca el valor. Si aparece, no se hace nada: el árbol no
guarda repetidos. Si la búsqueda termina en un subárbol vacío, ahí se cuelga
el valor nuevo como una **hoja**.

<SequenceStepper eda="bst" operation="insert" values={[8, 4, 12, 2, 6, 10, 14]} value={7} />

La invariante queda en pie: la hoja nueva quedó del lado que eligió cada
comparación, que es el lado correcto de cada nodo por encima de ella. Ningún
otro nodo se mueve, y el costo es el de la búsqueda: $$O(h)$$.

</Slide>

<Slide title="La raíz que devuelve insert">
El método recursivo devuelve la raíz del subárbol en que insertó. Casi siempre
es el mismo nodo que recibió; la excepción es el subárbol vacío, donde
devuelve el nodo nuevo. Por eso cada llamada guarda lo que devuelve la
siguiente en `node.left` o `node.right`, y el método público lo guarda en
`root`: así, insertar en un árbol vacío crea la raíz.

```java
void insert(T value) {
    root = insert(root, value);
}
```

<SequenceStepper eda="bst" operation="insert" values={[]} value={[8, 4, 12]} />

</Slide>

<Slide title="El mínimo y el máximo">
Por la invariante, todo lo menor que un nodo está a su izquierda. El
**mínimo** es entonces el nodo de más a la izquierda: se baja por la izquierda
hasta un nodo que no tenga hijo izquierdo. El **máximo** es el simétrico: se
baja por la derecha.

<SequenceStepper eda="bst" operation="minimum" values={[8, 4, 12, 2, 6, 10, 14]} />

Los dos bajan por un solo camino: $$O(h)$$. En un árbol vacío no hay mínimo,
y el método lanza una excepción.

</Slide>

<Slide title="El sucesor y el predecesor">
El **sucesor** de un valor es el menor valor del árbol que es mayor que él.
Se encuentra con una sola bajada desde la raíz que guarda un candidato: en
cada nodo mayor que el valor, ese nodo es el mejor candidato hasta ahí, y uno
mejor solo puede estar a su izquierda; en cada nodo menor o igual, el sucesor
solo puede estar a su derecha. Cuando la bajada llega a un subárbol vacío, el
último candidato es el sucesor.

<SequenceStepper eda="bst" operation="successor" values={[8, 4, 12, 2, 6, 10, 14]} target={[6, 8]} />

El **predecesor**, el mayor valor menor que él, es el simétrico. Los dos
cuestan $$O(h)$$.

</Slide>

<Slide title="Eliminar una hoja">
Para eliminar, primero se busca el valor. Cuando el nodo que lo guarda es una
**hoja**, basta con que su padre deje de apuntarle: en ese lado queda el árbol
vacío.

<div style={{ display: 'grid', gridTemplateColumns: 'repeat(auto-fit, minmax(240px, 1fr))', gap: '1rem 2rem', alignItems: 'end' }}>
<BinaryPicture tree={EVENS} tones={{ 2: 'mark' }} holes={[]} label="El árbol de búsqueda con el 2 marcado: es una hoja, hijo izquierdo del 4." caption="eliminar 2, una hoja" />
<BinaryPicture tree={EVENS} tones={{ 2: 'hidden' }} holes={[4]} label="El mismo árbol sin el 2: el hijo izquierdo del 4 es ahora el árbol vacío." caption="el 4 apunta a null por la izquierda" />
</div>

</Slide>

<Slide title="Eliminar un nodo con un hijo">
Cuando el nodo tiene **un solo hijo**, su padre pasa a apuntar a ese hijo. La
invariante se mantiene: todo el subárbol del hijo estaba del mismo lado del
padre que el nodo eliminado.

<div style={{ display: 'grid', gridTemplateColumns: 'repeat(auto-fit, minmax(240px, 1fr))', gap: '1rem 2rem', alignItems: 'end' }}>
<BinaryPicture tree={EVENS_WITH_7} tones={{ 6: 'mark' }} minColumns={8} label="El árbol de búsqueda con el 7 colgando del 6. El 6 está marcado: tiene un solo hijo, el 7, a la derecha." caption="eliminar 6, que tiene un solo hijo" />
<BinaryPicture tree={{ v: 8, l: { v: 4, l: { v: 2 }, r: { v: 7 } }, r: { v: 12, l: { v: 10 }, r: { v: 14 } } }} fresh={7} minColumns={8} label="El árbol sin el 6: el 4 apunta ahora directamente al 7, que quedó como su hijo derecho." caption="el 4 pasa a apuntar al 7" />
</div>

</Slide>

<Slide title="Eliminar un nodo con dos hijos">
Un nodo con **dos hijos** no se puede sacar: dejaría dos subárboles colgando,
y su padre tiene lugar para uno solo. Por eso el nodo se queda y cambia de
valor: toma el de su **sucesor**, el mínimo de su subárbol derecho, y después
se elimina el sucesor.

<div style={{ display: 'grid', gridTemplateColumns: 'repeat(auto-fit, minmax(240px, 1fr))', gap: '1rem 2rem', alignItems: 'end' }}>
<BinaryPicture tree={EVENS} tones={{ 8: 'mark', 10: 'focus' }} notes={{ 10: 'sucesor' }} holes={[]} label="El árbol de búsqueda con el 8 marcado: tiene dos hijos. Su sucesor, el mínimo de su subárbol derecho, es el 10." caption="eliminar 8: su sucesor es 10" />
<BinaryPicture tree={{ v: 10, l: { v: 4, l: { v: 2 }, r: { v: 6 } }, r: { v: 12, r: { v: 14 } } }} tones={{ 10: 'mark' }} holes={[12]} minColumns={7} label="El árbol después: la raíz tomó el valor 10, y el nodo del 10 que estaba abajo se eliminó; el 12 ya no tiene hijo izquierdo." caption="la raíz toma el 10, y el 10 de abajo se elimina" />
</div>

El sucesor es mayor que todo lo de la izquierda y menor que todo lo demás de
la derecha: cabe exactamente en el lugar que deja el valor eliminado. Y como
es un mínimo, no tiene hijo izquierdo, así que eliminarlo es uno de los dos
casos anteriores.

</Slide>

<Slide title="El código de la eliminación">
Cada caso es una rama del método recursivo, que devuelve la raíz del subárbol
que queda.

<SequenceStepper eda="bst" operation="remove" values={[8, 4, 12, 2, 6, 10, 14, 7]} target={[2, 6, 8]} />

</Slide>

Como `insert`, cada llamada guarda lo que devuelve la siguiente donde estaba
el nodo. Una hoja devuelve `null`, un nodo con un hijo devuelve ese hijo, y
uno con dos hijos copia el valor de su sucesor y lo elimina de su derecha.
Todo el trabajo es bajar dos veces por un camino, una hasta el nodo y otra
hasta su sucesor: el costo sigue siendo $$O(h)$$.

<Slide title="Costos del árbol de búsqueda">
Cada operación baja por un camino desde la raíz, así que todas cuestan lo
mismo: la altura.

| Molde     | Operación           | Peor caso | Invariante que restaura                                              |
| --------- | ------------------- | --------- | -------------------------------------------------------------------- |
| Consultar | `contains`          | $$O(h)$$  | Ninguna: no cambia el árbol                                          |
| Consultar | mínimo, máximo      | $$O(h)$$  | Ninguna: no cambia el árbol                                          |
| Consultar | sucesor, predecesor | $$O(h)$$  | Ninguna: no cambia el árbol                                          |
| Modificar | `insert`            | $$O(h)$$  | La de orden: la hoja nueva queda del lado que eligió cada comparación |
| Modificar | `remove`            | $$O(h)$$  | La de orden: el sucesor cabe justo en el lugar que deja              |

La altura de un árbol binario de $$n$$ nodos está entre
$$\lfloor \log_2 n \rfloor$$ y $$n - 1$$.

</Slide>

## La altura según el orden de llegada

<Slide title="Un orden de llegada que llena el árbol">
La forma de un árbol de búsqueda la decide el orden en que llegan sus valores.
Si cada valor nuevo cae en un nivel que todavía tiene lugar, los niveles se
llenan de arriba hacia abajo, y el árbol queda con la altura más baja posible.

<Slide title="Valores que llegan ordenados">
Si los mismos valores llegan de menor a mayor, cada uno es mayor que todos
los anteriores: siempre baja por la derecha y se cuelga al final. El árbol
queda como una cadena, con la altura más alta posible.

<Slide title="Datos que llegan en orden">
El orden de menor a mayor no es un caso raro. Los números de matrícula se
asignan en orden creciente; los registros de un sistema llegan ordenados por
fecha; un archivo de palabras suele venir en orden alfabético. Cargar
cualquiera de ellos en un árbol de búsqueda lo deja como una cadena: el peor
caso es el caso de todos los días.

Cuando los valores llegan en un orden al azar, en cambio, la altura esperada
crece como $$O(\log n)$$. Es un resultado conocido, que aquí se cita sin
demostrar. Pero nadie garantiza que los datos lleguen al azar.

</Slide>

<Slide title="Una altura acotada a cambio de cuidar la forma">
Todas las operaciones del árbol de búsqueda cuestan $$O(h)$$, y cuando los
valores llegan ordenados, $$h$$ es $$n - 1$$: cada operación cuesta
$$\Theta(n)$$, lo mismo que en una lista.

La causa es la invariante de orden: dice de qué lado de cada nodo va cada
valor, y no dice nada sobre la forma del árbol. Nadie impide que el árbol se
cargue hacia un lado.

¿Y si cada inserción y cada eliminación cuidaran también la forma,
reacomodando el árbol cuando se carga hacia un lado, sin romper la invariante
de orden? La altura quedaría acotada por $$O(\log n)$$, y con ella todas las
operaciones. El precio sería más trabajo en cada inserción y en cada
eliminación. Ese es el intercambio de un **árbol de búsqueda balanceado**.

</Slide>

## Las rotaciones

{/* The generic right rotation: p over q and C, q over A and B; after it, q over A and p, p over B and C. A, B and C are whole subtrees, drawn as triangles. */}

export const ROTATION_BEFORE = { v: 'p', l: { v: 'q', l: { v: 'A' }, r: { v: 'B' } }, r: { v: 'C' } };

export const ROTATION_AFTER = { v: 'q', l: { v: 'A' }, r: { v: 'p', l: { v: 'B' }, r: { v: 'C' } } };

<Slide title="La rotación a la derecha">
Una **rotación** cambia la forma de un árbol de búsqueda sin romper la
invariante de orden. La **rotación a la derecha** en un nodo `p` que tiene
hijo izquierdo `q` hace subir a `q` al lugar de `p`: `p` baja a ser el hijo
derecho de `q`, y el subárbol derecho de `q` pasa a ser el subárbol izquierdo
de `p`. Los otros dos subárboles siguen colgados del mismo nodo que antes.

<BinaryPicture tree={ROTATION_BEFORE} subtrees={['A', 'B', 'C']} tones={{ p: 'accent', q: 'accent', B: 'mark' }} label="Antes de rotar: p arriba, con q a su izquierda y el subárbol C a su derecha; q tiene a los subárboles A y B." caption="antes: p arriba, q su hijo izquierdo" />
<BinaryPicture tree={ROTATION_AFTER} subtrees={['A', 'B', 'C']} tones={{ p: 'accent', q: 'accent', B: 'mark' }} label="Después de rotar a la derecha en p: q arriba, con el subárbol A a su izquierda y p a su derecha; p tiene a B a la izquierda y a C a la derecha." caption="después: q arriba, y B cambió de padre" />
</div>

</Slide>

<Slide title="Por qué la rotación conserva el orden">
Antes de rotar, los valores de B estaban en el subárbol derecho de `q` y en el
izquierdo de `p`: eran mayores que `q` y menores que `p`. Después siguen
siendo las dos cosas, porque B quedó a la izquierda de `p`, y `p` quedó a la
derecha de `q`. A sigue a la izquierda de `q`, y C a la derecha de `p`.
Ningún valor cambia de lado respecto de ningún nodo: **la invariante de orden
se mantiene**.

<div style={{ display: 'grid', gridTemplateColumns: 'repeat(auto-fit, minmax(240px, 1fr))', gap: '1rem 2rem', alignItems: 'end' }}>
<BinaryPicture tree={ROTATION_BEFORE} subtrees={['A', 'B', 'C']} strip label="Antes de rotar, con el inorden debajo: A, q, B, p, C." caption="inorden antes: A, q, B, p, C" />
<BinaryPicture tree={ROTATION_AFTER} subtrees={['A', 'B', 'C']} strip label="Después de rotar, con el inorden debajo: A, q, B, p, C, el mismo de antes." caption="inorden después: el mismo" />
</div>

Cada nodo y cada subárbol está dibujado en la columna de su lugar en el
inorden: al rotar, nada cambia de columna. Los nodos solo suben o bajan.

</Slide>

<Slide title="El código de la rotación a la derecha">
Tres referencias cambian, una por línea. El método devuelve `q`, el nodo que
subió, y quien lo llamó lo guarda donde estaba `p`: en `root`, o en el hijo
del padre de `p`. Mientras tanto, por un momento, un subárbol tiene dos
padres, y `q` apunta hacia arriba sin que nadie le apunte.

<SequenceStepper eda="avl" operation="rotate-right" values={[12, 8, 14, 4, 10]} target={12} />

</Slide>

<Slide title="La rotación a la izquierda">
La **rotación a la izquierda** es la simétrica. En un nodo `p` que tiene hijo
derecho `q`, `q` sube al lugar de `p`, `p` baja a ser el hijo izquierdo de
`q`, y el subárbol izquierdo de `q` pasa a ser el subárbol derecho de `p`.

<SequenceStepper eda="avl" operation="rotate-left" values={[4, 2, 8, 6, 10]} target={4} />

</Slide>

<Slide title="Lo que una rotación hace con la altura">
Al rotar a la derecha, todo el subárbol A sube un nivel, todo C baja uno, y B
se queda en el suyo. Un árbol cargado hacia la izquierda queda más parejo: la
rotación pasa altura de un lado al otro, sin tocar el orden.

Altura 1." caption="después de rotar a la derecha en 6: altura 1" />
</div>

</Slide>

## El árbol AVL

{/* A tree that keeps the balance invariant, and one that breaks it at a single node, the 8. */}

export const NOT_AVL = { v: 8, l: { v: 4, l: { v: 2 }, r: { v: 6, r: { v: 7 } } }, r: { v: 12 } };

<Slide title="Un árbol de búsqueda que cuida su forma">
El primer árbol de búsqueda balanceado lo publicaron Georgy Adelson-Velsky y
Evgenii Landis en 1962, y lleva sus iniciales: el **árbol AVL**. Es un árbol
binario de búsqueda cuyas inserciones y eliminaciones, al terminar, revisan
el camino que recorrieron y **rotan** donde el árbol quedó cargado hacia un
lado.

<div style={{ display: 'grid', gridTemplateColumns: 'repeat(auto-fit, minmax(240px, 1fr))', gap: '1rem 2rem', alignItems: 'end' }}>
<BinaryPicture tree={EVENS_CHAIN} ruler="h = 6" compact label="Los valores 2 a 14 insertados de menor a mayor en un árbol de búsqueda: una cadena de altura 6." caption="de menor a mayor, en un árbol de búsqueda: altura 6" />
<BinaryPicture tree={EVENS} ruler="h = 2" compact minColumns={7} label="Los mismos valores insertados de menor a mayor en un árbol AVL: un árbol lleno de altura 2." caption="los mismos, en un AVL: altura 2" />
</div>

Los valores pueden llegar en el peor orden: la forma la cuida el árbol.

</Slide>

<Slide title="La invariante de balance">
Las tres invariantes del árbol de búsqueda siguen en pie, sin cambios. El AVL
agrega una cuarta:

4. **En cada nodo, las alturas de sus dos subárboles difieren a lo más en
   1.** Ningún lado puede ser dos niveles más alto que el otro, en ningún
   nodo.

<div style={{ display: 'grid', gridTemplateColumns: 'repeat(auto-fit, minmax(240px, 1fr))', gap: '1rem 2rem', alignItems: 'end' }}>
<BinaryPicture tree={EVENS_SHUFFLED} minColumns={7} label="Un árbol AVL: 10 en la raíz, con 4 y 14 debajo; el 4 con 2 y 8, el 8 con 6, y el 14 con 12. En cada nodo, las alturas de los dos subárboles difieren a lo más en 1." caption="cumple la invariante de balance en cada nodo" />
<BinaryPicture tree={NOT_AVL} minColumns={7} tones={{ 8: 'mark' }} notes={{ 8: 'izq. 2, der. 0' }} label="Un árbol de búsqueda que no es AVL: en el 8, el subárbol izquierdo tiene altura 2 y el derecho, el 12, altura 0." caption="en el 8, la izquierda es dos niveles más alta" />
</div>

Es la invariante que cuesta: obliga a cada inserción y a cada eliminación a
revisar su camino y, a veces, a rotar. Y es la que paga: mantiene la altura en
$$O(\log n)$$.

</Slide>

<Slide title="El factor de balance">
El **factor de balance** de un nodo es la altura de su subárbol derecho menos
la de su subárbol izquierdo, contando $$-1$$ como la altura del árbol vacío.
La invariante de balance dice que todo factor es $$-1$$, $$0$$ o $$+1$$. Un
factor negativo dice que el nodo está **cargado a la izquierda**; uno
positivo, **a la derecha**; y un $$-2$$ o un $$+2$$ dice que ahí la invariante
se rompió.

<div style={{ display: 'grid', gridTemplateColumns: 'repeat(auto-fit, minmax(240px, 1fr))', gap: '1rem 2rem', alignItems: 'end' }}>
<BinaryPicture tree={EVENS_SHUFFLED} minColumns={7} badges={{ 10: '−1', 4: '+1', 2: '0', 8: '−1', 6: '0', 14: '−1', 12: '0' }} label="El árbol AVL con el factor de balance de cada nodo: 10, menos 1; 4, más 1; 2, 0; 8, menos 1; 6, 0; 14, menos 1; 12, 0." caption="todos los factores entre −1 y +1" />
<BinaryPicture tree={NOT_AVL} minColumns={7} tones={{ 8: 'mark' }} badges={{ 8: '−2', 4: '+1', 2: '0', 6: '+1', 7: '0', 12: '0' }} label="El árbol que no es AVL con sus factores: 8, menos 2; 4, más 1; 2, 0; 6, más 1; 7, 0; 12, 0." caption="el −2 del 8 rompe la invariante" />
</div>

</Slide>

<Slide title="El nodo que guarda su altura">
Calcular la altura de un subárbol recorriéndolo cuesta $$\Theta(n)$$, y el
AVL la necesita en cada nodo de cada camino. Por eso cada nodo **guarda su
altura**: es el nodo del árbol de búsqueda con un campo más, `height`. Un
nodo nuevo es una hoja, y su altura empieza en 0.

```java
class Node<T> {
    T value;
    Node<T> left;
    Node<T> right;
    int height;

    Node(T value) {
        this.value = value;
    }
}
```

</Slide>

<Slide title="La clase AVL y la altura de un subárbol">
La clase guarda la raíz, como el árbol de búsqueda. `height` lee la altura de
un subárbol en tiempo constante, con $$-1$$ para el árbol vacío;
`updateHeight` la vuelve a calcular a partir de las de sus dos hijos, y hay
que llamarla cada vez que un nodo cambia de hijos; `factor` es el factor de
balance.

```java
class AVL<T extends Comparable<T>> {
    Node<T> root;

    int height(Node<T> node) {
        return node == null ? -1 : node.height;
    }

    void updateHeight(Node<T> node) {
        node.height = 1 + Math.max(height(node.left),
                                   height(node.right));
    }

    int factor(Node<T> node) {
        return height(node.right) - height(node.left);
    }
}
```

</Slide>

<Slide title="Las rotaciones actualizan las alturas">
Una rotación cambia los hijos de dos nodos, así que las dos rotaciones
agregan dos líneas antes de devolver `q`: primero se actualiza `p`, que quedó
abajo, y después `q`, cuya altura depende de la de `p`. Los subárboles que se
movieron enteros no cambian de altura.

```java
Node<T> rotateRight(Node<T> p) {
    Node<T> q = p.left;
    p.left = q.right;
    q.right = p;
    updateHeight(p);
    updateHeight(q);
    return q;
}
```

`rotateLeft` agrega las mismas dos líneas, en el mismo orden.

</Slide>

<Slide title="Los cuatro casos de desbalance">
Cuando un nodo queda con factor $$-2$$ o $$+2$$, lo que hay que hacer depende
de dos cosas: hacia qué lado está cargado el nodo, y hacia qué lado está
cargado su hijo de ese lado. Son cuatro casos, y cada uno tiene su rotación:
la **rotación simple a la derecha**, la **doble a la derecha**, la **simple a
la izquierda** y la **doble a la izquierda**. En inglés, los cuatro casos se
llaman *left-left*, *left-right*, *right-right* y *right-left*.

izquierda, una **rotación simple a la derecha**. El hijo sube, el nodo baja
hacia el lado liviano, y los dos quedan con factor 0.

el árbol queda cargado igual de fuerte, pero hacia el otro.

<Slide title="La rotación doble">
La **rotación doble** endereza primero al hijo: una rotación en el hijo, hacia
el lado donde está cargado el nodo, lo deja cargado hacia el mismo lado que
el nodo. Ahí basta la rotación simple en el nodo. La **doble a la derecha** es
una rotación a la izquierda en el hijo izquierdo y, después, una a la derecha
en el nodo.

<Slide title="La regla para elegir la rotación">
La rotación sale del factor del nodo y del factor de su hijo del lado
cargado:

| Factor del nodo | Factor del hijo del lado cargado | Rotación                 |
| --------------- | -------------------------------- | ------------------------ |
| $$-2$$          | $$-1$$ o $$0$$                   | simple a la derecha      |
| $$-2$$          | $$+1$$                           | doble a la derecha       |
| $$+2$$          | $$+1$$ o $$0$$                   | simple a la izquierda    |
| $$+2$$          | $$-1$$                           | doble a la izquierda     |

Dicho en una frase: si el hijo está cargado hacia el lado contrario, doble; si
no, simple. Un hijo con factor 0 nunca aparece al insertar; aparece al
eliminar, y ahí basta la rotación simple.

</Slide>

<Slide title="El código de balance">
`balance` actualiza la altura del nodo, calcula su factor y, si la invariante
se rompió, hace la rotación de la regla: si el hijo del lado cargado está
cargado hacia el lado contrario, primero lo rota a él. Devuelve la raíz del
subárbol que queda: el mismo nodo, o el que subió al rotar.

```java
Node<T> balance(Node<T> node) {
    updateHeight(node);
    int b = factor(node);
    if (b < -1) {
        if (factor(node.left) > 0) {
            node.left = rotateLeft(node.left); // doble
        }
        return rotateRight(node);
    }
    if (b > 1) {
        if (factor(node.right) < 0) {
            node.right = rotateRight(node.right); // doble
        }
        return rotateLeft(node);
    }
    return node;
}
```

</Slide>

<Slide title="Insertar en un árbol AVL">
`insert` es el del árbol de búsqueda con una sola diferencia: en vez de
devolver el nodo, devuelve `balance(node)`. La bajada es la misma; al volver,
cada nodo del camino pasa por `balance`, que actualiza su altura y, si su
factor llegó a $$\pm 2$$, rota.

un árbol de altura 9; en un árbol de búsqueda sin balance, la misma secuencia
deja una cadena de altura 999.

Cada rotación cuesta lo mismo, unas pocas referencias y dos alturas, y el
camino de vuelta tiene a lo más $$h + 1$$ nodos: una eliminación hace a lo
más $$O(\log n)$$ rotaciones, y sigue costando $$O(\log n)$$.

<Slide title="La altura de un árbol AVL">
El árbol AVL **más flaco** de cada altura, el que tiene menos nodos, es una
raíz sobre los más flacos de las dos alturas anteriores. Sus tamaños crecen
como los números de Fibonacci: 1, 2, 4, 7, 12, 20, 33… y eso es crecer de
forma exponencial. Al revés, la altura de un AVL de $$n$$ nodos crece como
$$\log n$$: Adelson-Velsky y Landis demostraron que es menor que
$$1{,}45 \cdot \log_2(n + 2)$$, un resultado que aquí se cita sin demostrar.

<Slide title="Costos del árbol AVL">
Las operaciones son las del árbol de búsqueda, y cuestan la altura; la
diferencia es que ahora la altura está acotada por $$O(\log n)$$, llegue lo que
llegue.

| Molde     | Operación           | Peor caso       | Invariante que restaura                                         |
| --------- | ------------------- | --------------- | --------------------------------------------------------------- |
| Consultar | `contains`          | $$O(\log n)$$   | Ninguna: no cambia el árbol                                     |
| Consultar | mínimo, máximo      | $$O(\log n)$$   | Ninguna: no cambia el árbol                                     |
| Consultar | sucesor, predecesor | $$O(\log n)$$   | Ninguna: no cambia el árbol                                     |
| Modificar | `insert`            | $$O(\log n)$$   | La de orden, y la de balance con a lo más una rotación          |
| Modificar | `remove`            | $$O(\log n)$$   | La de orden, y la de balance con a lo más una rotación por nivel |

</Slide>

<Slide title="El precio del balance">
El árbol AVL garantiza $$O(\log n)$$ en todas sus operaciones, y lo paga de
tres maneras. Cada nodo guarda un entero más, su altura. Cada inserción y cada
eliminación recorren de vuelta todo su camino, actualizando alturas y
revisando factores, aunque no haya nada que rotar. Y el código es más largo:
cuatro casos de rotación y una invariante más que mantener en cada
modificación.

Cuando hay muchas más búsquedas que modificaciones, lo que se paga al
modificar se recupera en cada búsqueda.

</Slide>

## Otros árboles de búsqueda

<Slide title="Árboles balanceados de otras formas">
El AVL no es la única manera de acotar la altura. Otros árboles de búsqueda
balanceados cuidan la forma con otras reglas, y cada uno cambia un poco de
trabajo por otra ventaja.

| Árbol         | Qué cuida                                                                              | Para qué se usa                                                                                 |
| ------------- | -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Rojo-negro    | Cada nodo es rojo o negro, ningún rojo tiene un hijo rojo, y todos los caminos hacia abajo tienen la misma cantidad de negros | Al eliminar rota a lo más tres veces, contra $$O(\log n)$$ del AVL; es el que usan `TreeMap` y `TreeSet` de Java |
| Árbol 2-3     | Nodos de uno o dos valores, y todas las hojas en el mismo nivel                         | El modelo con que se explica el rojo-negro                                                      |
| *Splay*       | Nada fijo: cada búsqueda sube el nodo encontrado hasta la raíz                          | Datos donde unos pocos valores se buscan una y otra vez                                         |

</Slide>

<Slide title="Los árboles B">
Un **árbol B** guarda en cada nodo muchos valores ordenados —cientos— y tiene
un hijo entre cada par de ellos. Cada nodo ocupa una página del disco, y leer
una página cuesta mucho más que comparar lo que trae. Con nodos tan anchos, el
árbol es muy bajo: con tres o cuatro niveles alcanza para millones de valores,
así que una búsqueda lee tres o cuatro páginas.

<Slide title="Árboles para otras preguntas">
Otros árboles no buscan un valor por comparación, sino que responden otras
preguntas rápido.

| Árbol                | Qué responde rápido                                           | Dónde se usa                                   |
| -------------------- | ------------------------------------------------------------- | ---------------------------------------------- |
| *Trie*               | Qué palabras empiezan con un prefijo: cada nivel es una letra | Autocompletar, diccionarios, rutas de red      |
| Árbol de segmentos   | La suma o el mínimo de un tramo de un arreglo que cambia      | Consultas por rango en datos que se actualizan |
| *Treap*              | Un árbol de búsqueda balanceado en promedio, con prioridades al azar | Una alternativa simple al AVL y al rojo-negro |
| *Quadtree*           | Qué puntos de un plano caen en una región                     | Mapas, geolocalización, colisiones en juegos   |
| Árbol de decisión    | Qué respuesta dar según una serie de preguntas                | Clasificadores en aprendizaje automático       |

</Slide>

<Slide title="Renunciar al orden completo">
Un árbol de búsqueda balanceado responde cualquier pregunta sobre el orden en
$$O(\log n)$$, y paga por eso dos referencias por nodo y una invariante que
ordena **todo**: cada valor queda del lado correcto de cada uno de sus
ancestros.

Hay problemas que no preguntan por todo el orden. En una sala de urgencias
solo importa quién es el paciente más grave; un planificador solo necesita la
tarea más urgente. ¿Y si el árbol renunciara al orden completo y pidiera solo
que **cada padre sea mayor que sus hijos**? El máximo quedaría siempre en la
raíz, y sacarlo o agregar un valor seguiría costando $$O(\log n)$$. Con un
orden tan débil, el árbol puede quedar siempre completo y guardarse en un
arreglo, sin referencias. Lo que se pierde es buscar un valor cualquiera: sin
orden entre los lados, vuelve a costar $$\Theta(n)$$. Ese intercambio es el del
**heap**.

</Slide>

<Slide title="El ancestro común más bajo">
Un **ancestro común** de dos nodos tiene a los dos en su subárbol, y un nodo
cuenta en su propio subárbol. El **ancestro común más bajo** es el más
profundo de todos: en un árbol genealógico, el antepasado más cercano que dos
personas comparten.

<Slide title="La raíz como respuesta">
La raíz tiene a todos los nodos en su subárbol, así que siempre es un ancestro
común. Pero no siempre es el más bajo: más abajo puede haber otro nodo que
también tiene a los dos. Una respuesta correcta tiene que saber **hasta dónde
bajar** sin dejar a ninguno de los dos afuera.

<Slide title="Bajar mientras los dos estén del mismo lado">
Por la invariante del árbol de búsqueda, en cada nodo se sabe de qué lado está
cada valor. Si los dos son menores que el nodo, los dos están en su subárbol
izquierdo, y el ancestro común más bajo también: se baja a la izquierda. Si
los dos son mayores, a la derecha. En cuanto los dos **dejan de estar del
mismo lado** —uno a cada lado, o uno es el nodo mismo—, ningún nodo de más
abajo tiene a los dos: ese nodo es la respuesta.

<Slide title="Un valor que es ancestro del otro, y el costo">
Cuando uno de los dos valores **es** el nodo, no es menor ni mayor que él, y
las dos condiciones de bajar fallan: el ciclo responde ese nodo. Es correcto,
porque un nodo cuenta en su propio subárbol. Con dos valores iguales pasa lo
mismo al llegar a ese valor. Como los dos valores están en el árbol, la bajada
siempre se detiene en un nodo y nunca llega a un subárbol vacío.

<BinaryPicture tree={EVENS} path={[8, 4]} tones={{ 4: 'keep', 6: 'mark', 8: 'done', 12: 'faint', 10: 'faint', 14: 'faint', 2: 'faint' }} label="4 y 6: se baja del 8 al 4, y ahí el 4 no es menor ni mayor que el nodo, porque es el nodo. <Slide title="Insertar en orden">
El árbol de búsqueda ya sabe insertar. Pero si los valores del arreglo se
insertan en el orden en que vienen, cada uno es mayor que todos los
anteriores y se cuelga siempre a la derecha: del 1 al 7 queda una cadena de
altura 6, la **más alta** posible. El arreglo ordenado es justo el peor
orden de llegada.

<Slide title="El medio como raíz">
Para que el árbol quede bajo, la raíz tiene que dejar la mitad de los
valores a cada lado: la raíz es el **elemento del medio**. Los menores, que
están a su izquierda en el arreglo, forman el subárbol izquierdo, y los
mayores, el derecho. Cada mitad es un arreglo ordenado más pequeño, y se arma
con la misma regla: es la recursión de **dividir y conquistar**, y el árbol
que resulta es el de las decisiones de una búsqueda binaria.

Con el 1 al 7: el medio es 4. A su izquierda quedan 1, 2 y 3, con medio 2; a
su derecha, 5, 6 y 7, con medio 6. Cada mitad que queda tiene un solo
elemento, y es una hoja.

</Slide>

<Slide title="Un arreglo de largo par y el arreglo vacío">
Con un largo par, como 1 2 3 4, no hay un único medio: la división entera
elige el de la izquierda, el 2. A su derecha quedan 3 y 4, que arman un
subárbol de altura 1, y el árbol queda de altura 2, que es
$$\lfloor \log_2 4 \rfloor$$: un lado queda un elemento más largo que el otro,
y eso nunca suma un nivel de más. Con el arreglo vacío, `lo` es 0 y `hi` es
$$-1$$: el primer caso devuelve `null` sin crear nada.

**Tiempo.** Cada llamada con un tramo no vacío crea exactamente un nodo, y
cada valor está en un solo tramo como medio: $$n$$ nodos, cada uno en tiempo
constante, $$\Theta(n)$$. **Memoria.** El árbol ocupa $$\Theta(n)$$; la
recursión, aparte, tiene la profundidad del árbol que arma,
$$\lfloor \log_2 n \rfloor + 1$$ llamadas: $$\Theta(\log n)$$.

```java starter
class Node<T> {
    T value;
    Node<T> left;
    Node<T> right;
    Node(T value) { this.value = value; }
}

class Solution {
    static Node<Integer> build(int[] sorted,
            int lo, int hi) {
        if (lo > hi) return null;
        int mid = (lo + hi) / 2;
        Node<Integer> node = new Node<>(sorted[mid]);
        node.left = build(sorted, lo, mid - 1);
        node.right = build(sorted, mid + 1, hi);
        return node;
    }

    static Node<Integer> build(int[] sorted) {
        return build(sorted, 0, sorted.length - 1);
    }
}
```

<Exercise title="Verificación de un árbol de búsqueda">

Un árbol binario dice ser un árbol de búsqueda. Escribamos `isBST`, que
recibe su raíz y responde si cumple la invariante: para cada nodo, **todos**
los valores de su subárbol izquierdo son menores que el suyo, y **todos** los
de su subárbol derecho son mayores. El árbol vacío la cumple.

El árbol 5, con hijos 3 y 8, y con 1 y 4 debajo del 3, la cumple. El mismo
árbol con un 7 en lugar del 4 no la cumple: el 7 es mayor que su padre, el 3,
pero está a la izquierda del 5.

```java solution
class Node<T> {
    T value;
    Node<T> left;
    Node<T> right;
    Node(T value) { this.value = value; }
}

class Solution {
    static boolean isBST(Node<Integer> root) {
        return isBST(root, Long.MIN_VALUE, Long.MAX_VALUE);
    }

    static boolean isBST(Node<Integer> node, long min, long max) {
        if (node == null) return true;
        if (node.value <= min || node.value >= max) return false;
        return isBST(node.left, min, node.value)
            && isBST(node.right, node.value, max);
    }
}
```

## Lo que sigue

Un árbol binario con un orden más débil que el de búsqueda —cada padre mayor
que sus hijos— guarda siempre el máximo en su raíz, queda completo y vive en
un arreglo, sin referencias.
