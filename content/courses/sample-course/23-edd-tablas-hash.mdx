# Estructuras de Datos Avanzadas · Tablas Hash

Lo que más repite un programa con lo que guarda es preguntar si un dato ya
está. Las estructuras de la unidad responden esa pregunta comparando, y la más
rápida de ellas compara más veces mientras más datos guarda. Para que la
respuesta cueste lo mismo con mil datos que con un millón, hace falta otra
manera de buscar.

{/* Casilleros — the cloakroom drawn as the unit draws an array: a contiguous strip of cells, the index over each, a name or nothing inside. `paint` colours a cell as the widget does (focus: under the eye; visited: already looked at; found: the one looked for; mark: just written), `notes` writes a short mark over a cell — a visit order, a shift, a hash — and `struck` strikes a key through: the mark of a removed key in the probing table. File-local (add-a-course-document.md §6e-quater). */}

export function Casilleros({ cells, index, paint = {}, notes = {}, struck = [], caption, label, cell = 64 }) {
  const pad = 12;
  const noteY = 15;
  const indexY = 31;
  const cellY = 38;
  const cellH = 40;
  const stripW = cells.length * cell;
  const width = Math.max(2 * pad + stripW, caption ? caption.length * 6.6 + 24 : 0);
  const left = (width - stripW) / 2;
  const height = cellY + cellH + (caption ? 34 : 12);
  const fill = { focus: 'var(--color-surface)', visited: 'var(--color-sunk)', found: 'var(--color-keep-soft)', mark: 'var(--color-mark-soft)' };
  const stroke = { focus: 'var(--color-focus)', visited: 'var(--color-rule-strong)', found: 'var(--color-keep)', mark: 'var(--color-mark)' };
  // Painted cells last, so a strong outline is never drawn under its neighbour.
  const order = cells.map((_, i) => i).sort((a, b) => (paint[a] ? 1 : 0) - (paint[b] ? 1 : 0));
  return (
    <svg viewBox={`0 0 ${width} ${height}`} style={{ width: '100%', maxWidth: `${Math.round(width * 1.3)}px`, height: 'auto', display: 'block', margin: '0.4rem auto' }} role="img" aria-label={label}>
      {order.map((i) => {
        const p = paint[i];
        const x = left + i * cell;
        return (
          <g key={i}>
            {notes[i] ? (
              <text x={x + cell / 2} y={noteY} textAnchor="middle" fontSize="12" fontWeight="700" style={{ fill: 'var(--color-ink-soft)' }}>{notes[i]}</text>
            ) : null}
            <text x={x + cell / 2} y={indexY} textAnchor="middle" fontSize="11" style={{ fill: 'var(--color-ink-faint)' }}>{index ? index[i] : i}</text>
            <rect x={x} y={cellY} width={cell} height={cellH} style={{ fill: p ? fill[p] : 'var(--color-surface)', stroke: p ? stroke[p] : 'var(--color-rule-strong)' }} strokeWidth={p && p !== 'visited' ? 2.4 : 1.2} />
            {cells[i] ? (
              <text x={x + cell / 2} y={cellY + cellH / 2 + 5} textAnchor="middle" fontSize="14" fontWeight="600" textDecoration={struck.includes(i) ? 'line-through' : undefined} style={{ fill: struck.includes(i) ? 'var(--color-ink-faint)' : 'var(--color-ink)' }}>{cells[i]}</text>
            ) : null}
          </g>
        );
      })}
      {caption ? (
        <text x={width / 2} y={height - 10} textAnchor="middle" fontSize="12" style={{ fill: 'var(--color-ink-soft)' }}>{caption}</text>
      ) : null}
    </svg>
  );
}

{/* Reparto — where a rule sends each key: the keys as chips in a row, the positions as a contiguous strip under them, one arrow per key down to its position. A position that receives two keys or more is painted `mark` and its count written under it: a collision. `contents` writes inside the cells (a coat already there) and `hit` paints one cell as found. File-local (§6e-quater). */}

export function Reparto({ keys, cells, index, contents = [], hit, caption, label, cell = 56, id }) {
  const pad = 12;
  const chipH = 28;
  const chipGap = 10;
  const chipW = keys.map((k) => Math.max(52, k.name.length * 8.4 + 18));
  const chipsW = chipW.reduce((a, b) => a + b, 0) + (keys.length - 1) * chipGap;
  const stripW = cells * cell;
  const width = Math.max(2 * pad + Math.max(chipsW, stripW), caption ? caption.length * 6.6 + 24 : 0);
  const stripLeft = (width - stripW) / 2;
  const chipsLeft = (width - chipsW) / 2;
  const chipY = pad;
  const cellY = chipY + chipH + 70;
  const cellH = 34;
  const height = cellY + cellH + 18 + (caption ? 30 : 8);
  const count = Array.from({ length: cells }, (_, c) => keys.filter((k) => k.to === c).length);
  const chipX = (k) => chipsLeft + chipW.slice(0, k).reduce((a, b) => a + b, 0) + k * chipGap;
  return (
    <svg viewBox={`0 0 ${width} ${height}`} style={{ width: '100%', maxWidth: `${Math.round(width * 1.3)}px`, height: 'auto', display: 'block', margin: '0.4rem auto' }} role="img" aria-label={label}>
      <defs>
        <marker id={`${id}-punta`} markerWidth="7" markerHeight="7" refX="6" refY="3.5" orient="auto">
          <path d="M0,0 L7,3.5 L0,7 z" style={{ fill: 'var(--color-ink-soft)' }} />
        </marker>
        <marker id={`${id}-punta-choque`} markerWidth="7" markerHeight="7" refX="6" refY="3.5" orient="auto">
          <path d="M0,0 L7,3.5 L0,7 z" style={{ fill: 'var(--color-mark)' }} />
        </marker>
      </defs>
      {keys.map((k, n) => {
        const clash = count[k.to] > 1;
        const x1 = chipX(n) + chipW[n] / 2;
        const x2 = stripLeft + k.to * cell + cell / 2;
        return (
          <line key={`a${n}`} x1={x1} y1={chipY + chipH} x2={x2} y2={cellY - 3} style={{ stroke: clash ? 'var(--color-mark)' : 'var(--color-ink-soft)' }} strokeWidth={clash ? 1.8 : 1.2} markerEnd={`url(#${id}-${clash ? 'punta-choque' : 'punta'})`} />
        );
      })}
      {keys.map((k, n) => (
        <g key={`k${n}`}>
          <rect x={chipX(n)} y={chipY} width={chipW[n]} height={chipH} rx="14" style={{ fill: 'var(--color-surface)', stroke: count[k.to] > 1 ? 'var(--color-mark)' : 'var(--color-rule-strong)' }} strokeWidth={count[k.to] > 1 ? 2 : 1.2} />
          <text x={chipX(n) + chipW[n] / 2} y={chipY + chipH / 2 + 5} textAnchor="middle" fontSize="13" fontWeight="600" style={{ fill: 'var(--color-ink)' }}>{k.name}</text>
        </g>
      ))}
      {Array.from({ length: cells }, (_, c) => {
        const clash = count[c] > 1;
        const found = hit === c;
        const x = stripLeft + c * cell;
        return (
          <g key={`c${c}`}>
            <rect x={x} y={cellY} width={cell} height={cellH} style={{ fill: found ? 'var(--color-keep-soft)' : clash ? 'var(--color-mark-soft)' : 'var(--color-surface)', stroke: found ? 'var(--color-keep)' : clash ? 'var(--color-mark)' : 'var(--color-rule-strong)' }} strokeWidth={found || clash ? 2.2 : 1.2} />
            {contents[c] ? (
              <text x={x + cell / 2} y={cellY + cellH / 2 + 5} textAnchor="middle" fontSize="13" fontWeight="600" style={{ fill: 'var(--color-ink)' }}>{contents[c]}</text>
            ) : null}
            <text x={x + cell / 2} y={cellY + cellH + 14} textAnchor="middle" fontSize="11" style={{ fill: 'var(--color-ink-faint)' }}>{index ? index[c] : c}</text>
            {clash ? (
              <text x={x + cell / 2} y={cellY + cellH / 2 + 5} textAnchor="middle" fontSize="13" fontWeight="700" style={{ fill: 'var(--color-mark)' }}>{`×${count[c]}`}</text>
            ) : null}
          </g>
        );
      })}
      {caption ? (
        <text x={width / 2} y={height - 8} textAnchor="middle" fontSize="12" style={{ fill: 'var(--color-ink-soft)' }}>{caption}</text>
      ) : null}
    </svg>
  );
}

<Slide title="Buscar un dato">
Muchos programas repiten millones de veces una misma pregunta: si un dato
está guardado.

- **Un registro de usuarios**, al crear una cuenta, revisa si el nombre
  elegido ya está tomado.
- **Un corrector ortográfico** busca cada palabra que se escribe en un
  diccionario de cientos de miles de palabras.
- **Un compilador** revisa, por cada nombre que aparece en el programa, si fue
  declarado.
- **Un navegador**, antes de descargar una imagen, revisa si ya la tiene
  guardada.

Al dato que se busca —un nombre de usuario, una palabra, el nombre de una
variable, una dirección— se le llama **clave**, porque identifica a cada
elemento: dos elementos nunca tienen la misma. Sobre el conjunto de claves se
hacen tres operaciones —**buscar** si una clave está, **agregar** una clave
nueva y **eliminar** una—, y la que más se repite es buscar.

</Slide>

<Slide title="El costo de buscar">
Las estructuras de la unidad ya hacen las tres operaciones, cada una a su
precio cuando guarda $$N$$ claves:

| Estructura          | Buscar             | Agregar                  | Eliminar           |
| ------------------- | ------------------ | ------------------------ | ------------------ |
| Arreglo sin orden   | $$\Theta(N)$$      | $$\Theta(1)$$ amortizado | $$\Theta(N)$$      |
| Arreglo ordenado    | $$\Theta(\log N)$$ | $$\Theta(N)$$            | $$\Theta(N)$$      |
| Árbol AVL           | $$O(\log N)$$      | $$O(\log N)$$            | $$O(\log N)$$      |
| **Lo que buscamos** | $$\Theta(1)$$      | $$\Theta(1)$$            | $$\Theta(1)$$      |

Con un millón de claves, buscar en el arreglo sin orden es revisar hasta un
millón; la búsqueda binaria y el árbol AVL comparan unas $$\log_2 10^6 \approx 20$$ veces. $$\log N$$ crece
muy despacio, pero crece con $$N$$. **El objetivo** es una estructura en la
que las tres operaciones cuesten lo mismo con mil claves que con un millón.

</Slide>

<Slide title="El límite de comparar">
La manera más rápida de buscar que conocemos es la búsqueda binaria, y un
árbol AVL busca de la misma manera. En un arreglo ordenado, cada comparación
tiene tres respuestas posibles —es la clave, va antes o va después—, y si no
es la clave descarta la mitad de lo que queda. Dibujadas, sus comparaciones
forman un árbol binario, el **árbol de decisiones**: la raíz es la primera
comparación, con el elemento del medio, y cada búsqueda es un camino desde la
raíz hacia abajo, con una comparación por nivel.

<BinaryPicture

  label="El árbol de decisiones de una búsqueda entre siete nombres en orden alfabético. La raíz es Leo; a la izquierda, Bea, con Ana y Eva debajo; a la derecha, Sol, con Luz y Teo debajo. />

Cualquier búsqueda que compare dibuja un árbol así; el de una lista sin orden
es un solo camino de $$N$$ niveles. Una búsqueda solo sabe que una clave está
cuando la compara con ella, así que cada una de las $$N$$ claves tiene que ser
un nodo del árbol. Como cada nodo tiene a lo más dos hijos, un árbol de $$k$$
niveles tiene a lo más

$$
1 + 2 + 4 + \cdots + 2^{k - 1} = 2^k - 1
$$

nodos. Para que quepan las $$N$$ claves hace falta que $$2^k - 1 \ge N$$, es
decir, que $$k \ge \log_2 (N + 1)$$, y buscar una clave del último nivel cuesta
$$k$$ comparaciones. Ninguna búsqueda que compare baja de $$\log_2 (N + 1)$$
comparaciones en el peor caso: la búsqueda binaria ya es la más rápida
posible.

**Para buscar más rápido hay que llegar a la clave sin compararla con las
demás: hay que calcular dónde está.**

</Slide>

<Slide title="Las fichas de un guardarropa">
El guardarropa de un teatro llega a cada abrigo sin comparar. Al recibir un
abrigo, quien atiende lo cuelga en un casillero y le entrega al dueño una
**ficha numerada** con el número de ese casillero. Al terminar la obra,
cientos de personas piden su abrigo a la vez, y nadie compara nombres: la
ficha dice en qué casillero está cada uno. Con la ficha, guardar, buscar y
retirar un abrigo toman un solo paso: ir al casillero de ese número.

<Reparto

  contents={['Sara', 'Leo', 'Ana', 'Juan', 'Eva', 'Bea', null, null]}
  hit={5}
  caption="la ficha 5 lleva directo al casillero 5, sin mirar ningún otro"
  label="Una ficha con el número 5 y una flecha directa al casillero 5 de una fila de ocho, donde está el abrigo de Bea."
/>

Es el **acceso directo** de un arreglo: el elemento de una posición se lee en
un solo paso, en tiempo $$\Theta(1)$$, sin compararlo con ningún otro.
Funciona por dos razones. La primera, la clave la elige el guardarropa: es el
número de la ficha que entregó. La segunda, esa clave es un entero pequeño, y
hay un casillero para cada ficha posible.

</Slide>

{/* Universo — the keys a cloakroom can be asked for, against the ones it keeps and the lockers it has: a large box for U, every possible key, dotted; a dashed cluster inside it for the keys stored; an arrow with a question mark to the strip of M lockers. File-local (§6e-quater). */}

export function Universo({ stored, cells, caption, label, id }) {
  const pad = 14;
  const boxW = 300;
  const boxH = 176;
  const top = 26;
  const gap = 110;
  const cell = 40;
  const core = 2 * pad + boxW + gap + cells * cell;
  const width = Math.max(core, caption ? caption.length * 6.6 + 24 : 0);
  const x0 = (width - core) / 2 + pad;
  const stripX = x0 + boxW + gap;
  const stripY = top + boxH / 2 - 20;
  const sub = { x: x0 + 150, y: top + 60, w: 130, h: 92 };
  const height = top + boxH + (caption ? 36 : 10);
  const dots = [];
  for (let r = 0; r < 8; r++) {
    for (let c = 0; c < 16; c++) {
      const cx = x0 + 12 + c * 18 + (r % 2) * 9;
      const cy = top + 14 + r * 21;
      const inside = cx > sub.x - 6 && cx < sub.x + sub.w + 6 && cy > sub.y - 6 && cy < sub.y + sub.h + 6;
      if (!inside && cx < x0 + boxW - 6) dots.push([cx, cy]);
    }
  }
  const half = Math.ceil(stored.length / 2);
  return (
    <svg viewBox={`0 0 ${width} ${height}`} style={{ width: '100%', maxWidth: `${Math.round(width * 1.3)}px`, height: 'auto', display: 'block', margin: '0.4rem auto' }} role="img" aria-label={label}>
      <defs>
        <marker id={`${id}-punta`} markerWidth="8" markerHeight="8" refX="7" refY="4" orient="auto">
          <path d="M0,0 L8,4 L0,8 z" style={{ fill: 'var(--color-ink-soft)' }} />
        </marker>
      </defs>
      <text x={x0 + boxW / 2} y={top - 9} textAnchor="middle" fontSize="12" fontWeight="700" style={{ fill: 'var(--color-ink-soft)' }}>U, todos los nombres posibles</text>
      <rect x={x0} y={top} width={boxW} height={boxH} rx="12" style={{ fill: 'var(--color-surface)', stroke: 'var(--color-rule-strong)' }} strokeWidth="1.4" />
      {dots.map(([cx, cy], n) => (
        <circle key={`d${n}`} cx={cx} cy={cy} r="2.2" style={{ fill: 'var(--color-ink-faint)' }} />
      ))}
      <rect x={sub.x} y={sub.y} width={sub.w} height={sub.h} rx="8" style={{ fill: 'var(--color-keep-soft)', stroke: 'var(--color-keep)' }} strokeWidth="1.8" strokeDasharray="5 4" />
      <text x={sub.x + sub.w / 2} y={sub.y - 6} textAnchor="middle" fontSize="11" fontWeight="700" style={{ fill: 'var(--color-ink-soft)' }}>los guardados</text>
      {stored.map((name, n) => (
        <text key={`s${n}`} x={sub.x + (n < half ? 36 : 96)} y={sub.y + 24 + (n % half) * 22} textAnchor="middle" fontSize="13" fontWeight="600" style={{ fill: 'var(--color-ink)' }}>{name}</text>
      ))}
      <line x1={x0 + boxW + 10} y1={stripY + 20} x2={stripX - 10} y2={stripY + 20} style={{ stroke: 'var(--color-ink-soft)' }} strokeWidth="1.6" markerEnd={`url(#${id}-punta)`} />
      <text x={x0 + boxW + gap / 2} y={stripY + 10} textAnchor="middle" fontSize="20" fontWeight="700" style={{ fill: 'var(--color-ink-soft)' }}>?</text>
      <text x={stripX + (cells * cell) / 2} y={stripY - 12} textAnchor="middle" fontSize="12" fontWeight="700" style={{ fill: 'var(--color-ink-soft)' }}>{`M = ${cells} casilleros`}</text>
      {Array.from({ length: cells }, (_, c) => (
        <g key={`c${c}`}>
          <rect x={stripX + c * cell} y={stripY} width={cell} height="40" style={{ fill: 'var(--color-surface)', stroke: 'var(--color-rule-strong)' }} strokeWidth="1.2" />
          <text x={stripX + c * cell + cell / 2} y={stripY + 56} textAnchor="middle" fontSize="11" style={{ fill: 'var(--color-ink-faint)' }}>{c}</text>
        </g>
      ))}
      {caption ? (
        <text x={width / 2} y={height - 10} textAnchor="middle" fontSize="12" style={{ fill: 'var(--color-ink-soft)' }}>{caption}</text>
      ) : null}
    </svg>
  );
}

<Slide title="Claves que no son posiciones">
Sin fichas, cada persona pide su abrigo por su nombre, y las dos razones dejan
de valer. La clave ya no la elige el guardarropa: la trae cada persona, y un
nombre no es un número de casillero. Tampoco se puede tener un casillero por
cada nombre posible: con las 26 letras del alfabeto inglés se escriben
$$26^5 = 11\,881\,376$$ nombres de cinco letras, y en una noche se guardan
unos cientos de abrigos. Al conjunto de todas las claves posibles se le llama
**universo**, $$U$$.

Hace falta un arreglo de $$M$$ casilleros, del tamaño de lo que se guarda y
no del universo, y una manera de calcular, a partir del nombre, el casillero
que le toca, tan rápido como se lee el número de una ficha.

</Slide>

<Slide title="La regla que asigna los casilleros">
Lo que falta es una regla: recibe un nombre y entrega un casillero, siempre el
mismo para el mismo nombre, para que lo guardado se encuentre donde se dejó.
Dibujada, la regla es una flecha desde cada nombre hasta su casillero.

<Reparto
  id="regla"
  keys={[{ name: 'Ana', to: 2 }, { name: 'Bea', to: 3 }, { name: 'Eva', to: 0 }, { name: 'Sara', to: 4 }]}

  caption="una flecha desde cada nombre hasta su casillero"

A una regla así las matemáticas la llaman **función**, y tienen palabras
precisas para lo que se le pide: que a cada nombre le toque un solo
casillero, que se usen todos los casilleros y que dos nombres no compartan
uno.

</Slide>

{/* Sagital — a function drawn as school draws it, a diagrama sagital: the domain and the codomain as two ovals, an arrow from each element to its image. `arrows` lists [from, to] index pairs, or [from, to, tone] to paint one, `mark` for the arrow to look at and `flag` for a wrong one; `clash` paints mark every image that receives two arrows or more, with the arrows that reach it; `hit` paints keep every image that receives one, the range; `more` writes ⋮ under the domain, which has more elements than are drawn; `tones` paints some domain elements, `{ index: 'mark' | 'flag' }`, and `toTones` some codomain elements the same way, over what `clash` and `hit` would paint. File-local (add-a-course-document.md §6e-quater). */}

export function Sagital({ from, to, arrows, fromTitle, toTitle, more = false, clash = false, hit = false, tones = {}, toTones = {}, caption, label, id }) {
  const rowH = 30;
  const nL = from.length + (more ? 1 : 0);
  const rows = Math.max(nL, to.length);
  const top = 30;
  const ry = (rows * rowH) / 2 + 14;
  const cy = top + ry;
  const core = 430;
  const width = Math.max(core, caption ? caption.length * 6.6 + 24 : 0);
  const off = (width - core) / 2;
  const lx = off + 105;
  const rx = off + 325;
  const height = top + 2 * ry + (caption ? 34 : 10);
  const yAt = (i, n) => cy - ((n - 1) * rowH) / 2 + i * rowH;
  const into = to.map((_, j) => arrows.filter((a) => a[1] === j).length);
  const toneOf = (a) => a[2] ?? (clash && into[a[1]] > 1 ? 'mark' : 'idle');
  const boxW = (t) => Math.max(30, String(t).length * 8.5 + 14);
  const line = { idle: 'var(--color-ink-soft)', mark: 'var(--color-mark)', flag: 'var(--color-flag)' };
  return (
    <svg viewBox={`0 0 ${width} ${height}`} style={{ width: '100%', maxWidth: `${Math.round(width * 1.3)}px`, height: 'auto', display: 'block', margin: '0.4rem auto' }} role="img" aria-label={label}>
      <defs>
        {Object.entries(line).map(([tone, color]) => (
          <marker key={tone} id={`${id}-punta-${tone}`} markerWidth="7" markerHeight="7" refX="6" refY="3.5" orient="auto">
            <path d="M0,0 L7,3.5 L0,7 z" style={{ fill: color }} />
          </marker>
        ))}
      </defs>
      <text x={lx} y={16} textAnchor="middle" fontSize="12" fontWeight="700" style={{ fill: 'var(--color-ink-soft)' }}>{fromTitle}</text>
      <text x={rx} y={16} textAnchor="middle" fontSize="12" fontWeight="700" style={{ fill: 'var(--color-ink-soft)' }}>{toTitle}</text>
      <ellipse cx={lx} cy={cy} rx="80" ry={ry} style={{ fill: 'var(--color-surface)', stroke: 'var(--color-rule-strong)' }} strokeWidth="1.4" />
      <ellipse cx={rx} cy={cy} rx="56" ry={ry} style={{ fill: 'var(--color-surface)', stroke: 'var(--color-rule-strong)' }} strokeWidth="1.4" />
      {arrows.map((a, n) => {
        const tone = toneOf(a);
        return (
          <line key={`a${n}`} x1={lx + 38} y1={yAt(a[0], nL)} x2={rx - boxW(to[a[1]]) / 2 - 4} y2={yAt(a[1], to.length)} style={{ stroke: line[tone] }} strokeWidth={tone === 'idle' ? 1.3 : 2} markerEnd={`url(#${id}-punta-${tone})`} />
        );
      })}
      {from.map((name, i) => {
        const y = yAt(i, nL);
        const tone = tones[i];
        return (
          <g key={`f${i}`}>
            {tone ? (
              <rect x={lx - boxW(name) / 2} y={y - 13} width={boxW(name)} height="26" rx="4" style={{ fill: `var(--color-${tone}-soft)`, stroke: `var(--color-${tone})` }} strokeWidth="1.8" />
            ) : null}
            <text x={lx} y={y + 5} textAnchor="middle" fontSize="14" fontWeight="600" style={{ fill: 'var(--color-ink)' }}>{name}</text>
          </g>
        );
      })}
      {more ? (
        <text x={lx} y={yAt(from.length, nL) + 6} textAnchor="middle" fontSize="16" fontWeight="700" style={{ fill: 'var(--color-ink-faint)' }}>⋮</text>
      ) : null}
      {to.map((name, j) => {
        const y = yAt(j, to.length);
        const tone = toTones[j] ?? (clash && into[j] > 1 ? 'mark' : hit && into[j] > 0 ? 'keep' : null);
        return (
          <g key={`t${j}`}>
            {tone ? (
              <rect x={rx - boxW(name) / 2} y={y - 13} width={boxW(name)} height="26" rx="4" style={{ fill: `var(--color-${tone}-soft)`, stroke: `var(--color-${tone})` }} strokeWidth="1.8" />
            ) : null}
            <text x={rx} y={y + 5} textAnchor="middle" fontSize="14" fontWeight="600" style={{ fill: 'var(--color-ink)' }}>{name}</text>
          </g>
        );
      })}
      {caption ? (
        <text x={width / 2} y={height - 10} textAnchor="middle" fontSize="12" style={{ fill: 'var(--color-ink-soft)' }}>{caption}</text>
      ) : null}
    </svg>
  );
}

<Slide title="La definición de función">
Una **función** es una regla que a cada elemento de un conjunto le asigna
exactamente un elemento de otro conjunto. Se escribe $$f : A \to B$$, y se lee
«$$f$$ va de $$A$$ a $$B$$».

- $$A$$ es el **dominio**: los elementos a los que la función les asigna algo.
- $$B$$ es el **codominio**: el conjunto de donde la función toma lo que
  asigna.
- Lo que le toca a un elemento $$a$$ se escribe $$f(a)$$, y se llama su
  **imagen**.

Una función se dibuja como la regla de los casilleros: una flecha desde cada
elemento del dominio hasta su imagen. Por ejemplo, la regla que a cada persona
le asigna su mes de cumpleaños es una función, porque cada persona cumple años
en un solo mes.

Sale una flecha de cada persona hacia su mes de cumpleaños: Ana a marzo, Bea a enero, Eva a marzo y Leo a julio."

f(\text{Ana}) = \text{marzo}, \quad f(\text{Bea}) = \text{enero}, \quad f(\text{Eva}) = \text{marzo}, \quad f(\text{Leo}) = \text{julio}
$$

<Slide title="El recorrido de una función">
El codominio dice dónde **puede** caer una imagen; el **recorrido** dice dónde
**cae**. Es el conjunto de las imágenes de todos los elementos del dominio,

$$
\operatorname{Rec}(f) = \{\, f(a) : a \in A \,\} \subseteq B,
$$

que se lee «el conjunto de los $$f(a)$$, con $$a$$ en $$A$$». En el diagrama,
son los elementos del codominio a los que llega al menos una flecha. El
recorrido siempre está dentro del codominio, y puede ser todo el codominio o
solo una parte.

<Sagital
  id="mes-recorrido"

/>

$$
\operatorname{Rec}(f) = \{\text{enero}, \text{marzo}, \text{julio}\} \;\ne\; \{\text{enero}, \text{marzo}, \text{julio}, \text{octubre}\} = B
$$

</Slide>

<Slide title="Funciones sobreyectivas">
Una función $$f : A \to B$$ es **sobreyectiva** si todo elemento del
codominio es imagen de al menos un elemento del dominio:

$$
f \text{ es sobreyectiva} \iff \forall b \in B, \; \exists a \in A \text{ tal que } f(a) = b,
$$

que se lee «$$f$$ es sobreyectiva si y solo si, para todo $$b$$ en $$B$$,
existe un $$a$$ en $$A$$ tal que $$f(a) = b$$». Como el recorrido reúne
justamente las imágenes, la definición equivale a pedir que el recorrido sea
todo el codominio:

$$
f \text{ es sobreyectiva} \iff \operatorname{Rec}(f) = B.
$$

En el diagrama, a cada elemento del codominio llega al menos una flecha.

$$
\operatorname{Rec}(f) = \{\text{enero}, \text{marzo}, \text{julio}, \text{octubre}\} = B
$$

</Slide>

<Slide title="Funciones inyectivas">
Una función $$f : A \to B$$ es **inyectiva** si elementos distintos del
dominio tienen siempre imágenes distintas:

$$
f \text{ es inyectiva} \iff \forall a_1, a_2 \in A, \; f(a_1) = f(a_2) \implies a_1 = a_2,
$$

que se lee «$$f$$ es inyectiva si y solo si, para todo $$a_1$$ y $$a_2$$ en
$$A$$, si $$f(a_1) = f(a_2)$$, entonces $$a_1$$ y $$a_2$$ son el mismo
elemento». En el diagrama, a ningún elemento del codominio llega más de una
flecha.

Una función $$f : A \to B$$ es **biyectiva** si es inyectiva y sobreyectiva a

$$
f \text{ es biyectiva} \iff \forall b \in B, \; \exists!\, a \in A \text{ tal que } f(a) = b,
$$

que se lee «$$f$$ es biyectiva si y solo si, para todo $$b$$ en $$B$$, existe
un único $$a$$ en $$A$$ tal que $$f(a) = b$$». En el diagrama, a cada elemento
del codominio llega exactamente una flecha.

## Funciones hash

<Slide title="La idea de una función hash">
Una **función hash** es la regla que asigna los casilleros: recibe una clave
cualquiera —un nombre, un número, un texto— y la convierte en una posición
del arreglo, calculada a partir de la clave sola, sin mirar las otras claves
guardadas.

<Pasos
  id="idea"
  boxes={[{ title: 'clave', text: '«Ana»' }, { title: 'posición', text: '2' }]}
  steps={['función hash']}
  caption="la función hash recibe la clave y entrega su posición"
  label="Dos cajas unidas por una flecha. La clave Ana; una flecha rotulada función hash lleva a la posición 2."
/>

Desde el principio se le exigen dos cosas. La primera, que entregue
**siempre la misma posición para la misma clave**: si no, una clave guardada
en un casillero se buscaría después en otro. La segunda, que sea **rápida de
calcular**: si calcular la posición costara tanto como comparar, no se ganaría
nada frente a la búsqueda binaria.

El nombre viene del inglés _to hash_, picar y mezclar: una buena función hash
desarma la clave y mezcla sus partes hasta obtener un número pequeño.

</Slide>

<Slide title="La definición de función hash">
Formalmente, una **función hash** para un universo de claves $$U$$ —**todas**
las claves posibles, no solo las que se guardan— y un arreglo de $$M$$
posiciones es una función

$$
h : U \to \{0, 1, \ldots, M - 1\},
$$

que se lee «$$h$$ va de $$U$$ al conjunto de los enteros entre $$0$$ y
$$M - 1$$, ambos incluidos». Su dominio es el universo y su codominio, las
posiciones del arreglo: a cada clave posible le asigna una posición. La
posición de una clave $$k$$ es su imagen, $$h(k)$$, y guardar, buscar y
retirar $$k$$ empiezan por calcular $$h(k)$$ e ir directo a ese casillero. El
arreglo, junto con su función hash, es una **tabla hash**.

<Sagital
  id="hash"
  from={['Ana', 'Bea', 'Eva', 'Sara']}
  to={['0', '1', '2', '3', '4', '5', '6']}
  arrows={[[0, 2], [1, 3], [2, 0], [3, 4]]}
  more
  fromTitle="dominio: U, las claves"
  toTitle="codominio: posiciones"
  label="Un diagrama de flechas de una función hash con M igual a 7. A la izquierda, el dominio U, las claves: Ana, Bea, Eva y Sara, y tres puntos debajo, porque hay muchas más. A la derecha, el codominio: las posiciones del 0 al 6. h de Ana es 2, h de Bea es 3, h de Eva es 0 y h de Sara es 4."
/>

$$
\begin{gathered}
M = 7, \qquad h : U \to \{0, 1, \ldots, 6\} \\
h(\text{«Ana»}) = 2, \quad h(\text{«Bea»}) = 3, \quad h(\text{«Eva»}) = 0, \quad h(\text{«Sara»}) = 4
\end{gathered}
$$

Que $$h$$ sea una función es justamente la primera exigencia: a cada clave le
toca exactamente una posición, siempre la misma.

</Slide>

<Slide title="Funciones hash inyectivas">
La ficha del guardarropa reparte los abrigos de la mejor manera posible: uno
por casillero. Una función hash que hiciera lo mismo sería **inyectiva**: cada
casillero guardaría a lo más una clave, y buscar una clave sería ir a su
casillero y mirar una sola.

<Sagital
  id="hash-inyectiva"
  from={['Ana', 'Bea', 'Eva', 'Sara']}
  to={['0', '1', '2', '3', '4', '5', '6']}
  arrows={[[0, 2], [1, 3], [2, 0], [3, 4]]}
  fromTitle="claves guardadas"
  toTitle="posiciones"
  caption="cada posición recibe a lo más una clave"
  label="El diagrama de flechas de la función hash con M igual a 7: Ana va al 2, Bea al 3, Eva al 0 y Sara al 4. A cada posición llega a lo más una flecha."
/>

La ficha lo logra porque hay un casillero para cada ficha posible. Una
función hash inyectiva necesitaría lo mismo: una posición propia para cada
clave de $$U$$.

</Slide>

<Slide title="Ninguna función hash es inyectiva">
Las posiciones no alcanzan: $$U$$ tiene muchísimas más claves que posiciones
el arreglo. Lo asegura el **principio del palomar**, también llamado
**principio de Dirichlet**: si se reparten más palomas que nidos, algún nido
recibe al menos dos.

<Sagital
  id="palomar"
  from={['Ana', 'Bea', 'Eva', 'Leo']}
  to={['0', '1', '2']}
  arrows={[[0, 2], [1, 0], [2, 1], [3, 2]]}
  clash
  fromTitle="abrigos"
  toTitle="casilleros"
  caption="cuatro abrigos en tres casilleros: como sea que se repartan, alguno recibe dos"
  label="Un diagrama de flechas de cuatro abrigos, de Ana, Bea, Eva y Leo, a tres casilleros, del 0 al 2. Ana y Leo van al 2, que está destacado con sus dos flechas; Bea va al 0 y Eva al 1."
/>

La cantidad de elementos de un conjunto $$A$$ se llama su **cardinalidad** y
se escribe $$|A|$$. Con esa notación, el principio se enuncia así:

$$
|A| > |B| \implies \text{ninguna función } f : A \to B \text{ es inyectiva},
$$

que se lee «si $$A$$ tiene más elementos que $$B$$, ninguna función de $$A$$ en
$$B$$ es inyectiva». En una tabla hash, $$A$$ es $$U$$ y $$B$$ son las $$M$$
posiciones: como $$|U| > M$$, ninguna función hash es inyectiva.

</Slide>

El principio parece no decir nada, y sin embargo asegura que algo ocurre sin
decir dónde ni a quién. En un grupo de 13 personas, dos están de cumpleaños el
mismo mes, porque hay 12 meses; y como nadie tiene más de un millón de pelos
en la cabeza y en Santiago viven más de un millón de personas, dos tienen
exactamente la misma cantidad. La primera mención escrita que se conoce es de
1622, del jesuita francés Jean Leurechon, y es justamente la de los pelos. El
matemático alemán Peter Gustav Lejeune Dirichlet lo usó en 1834 con el nombre
de _Schubfachprinzip_, el principio de los cajones, y de ahí su otro nombre.
En inglés es el _pigeonhole principle_: un _pigeonhole_ es cada casillero de
un mueble donde se dejan las cartas.

<Slide title="Las colisiones">
Como ninguna función hash es inyectiva, siempre existen dos claves distintas
con la misma posición,

$$
a \ne b \quad \text{y} \quad h(a) = h(b),
$$

y cuando las dos se guardan, **colisionan**: les toca el mismo casillero.

<Reparto
  id="choque"
  keys={[{ name: 'Eva', to: 0 }, { name: 'Ana', to: 2 }, { name: 'Bea', to: 3 }, { name: 'Sara', to: 4 }, { name: 'Leo', to: 2 }]}
  cells={7}
  caption="con siete casilleros, «Leo» cae en el casillero de «Ana»"
  label="Cinco nombres en siete casilleros: Eva va al 0, Ana al 2, Bea al 3 y Sara al 4. Leo va al casillero 2, el mismo de Ana: los dos colisionan."
/>

$$
h(\text{«Leo»}) = h(\text{«Ana»}) = 2, \qquad \text{«Leo»} \ne \text{«Ana»}
$$

El principio no dice qué claves colisionan, solo que algunas lo harán. Por
eso las colisiones no son un defecto de una función en particular: ninguna
función hash las evita.

</Slide>

<Slide title="Funciones hash perfectas">
Si las claves que se van a guardar se conocen de antemano, sí se puede elegir
una función que no las haga colisionar: una **función hash perfecta** para
esas claves. Si además hay exactamente tantas posiciones como claves, la
función es biyectiva sobre ellas —cada casillero recibe una clave y ninguno
sobra— y se llama **perfecta mínima**. Pero es perfecta solo para esas claves:
una clave nueva puede caer donde ya hay otra.

/>

  id="perfecta-nueva"
  from={['Ana', 'Bea', 'Eva', 'Leo']}
  to={['0', '1', '2']}
  arrows={[[0, 2], [1, 0], [2, 1], [3, 0]]}

Por eso se usan solo con claves fijas, como las palabras reservadas de un
lenguaje de programación. Una tabla que recibe claves que no conoce no puede
contar con una función perfecta.

</Slide>

<Slide title="La paradoja del cumpleaños">
Sin conocer las claves, que las $$N$$ guardadas caigan en posiciones
distintas es cuestión de suerte, y esa suerte se acaba mucho antes de lo que
parece. Lo muestra la **paradoja del cumpleaños**: si los cumpleaños caen al
azar entre los 365 días del año, en un grupo de 23 personas lo más probable
es que dos estén de cumpleaños el mismo día. Se llama paradoja porque 23
personas parecen muy pocas para tantos días.

| Personas | Probabilidad de que dos compartan cumpleaños |
| -------- | -------------------------------------------- |
| 10       | 12 %                                         |
| 23       | 51 %                                         |
| 40       | 89 %                                         |
| 57       | 99 %                                         |

Es la misma situación de una tabla hash: las personas son las claves, y los
días, las $$M = 365$$ posiciones.

</Slide>

{/* Elecciones — keys arriving one by one without colliding: one row per key, the M positions, the ones the earlier keys took greyed with their name, the free ones outlined, and at the right how many of the M are still free for this key. File-local (§6e-quater). */}

export function Elecciones({ rows, cells, caption, label }) {
  const pad = 12;
  const nameW = 70;
  const cell = 56;
  const rowH = 52;
  const countW = 120;
  const core = 2 * pad + nameW + cells * cell + countW;
  const width = Math.max(core, caption ? caption.length * 6.6 + 24 : 0);
  const x0 = (width - core) / 2 + pad;
  const sx = x0 + nameW;
  const top = 22;

<Slide title="La probabilidad de no colisionar">
Las claves llegan una por una, y cada una cae al azar en cualquiera de las
$$M$$ posiciones, sin depender de las demás. Para que no haya colisiones, cada
clave tiene que caer en una posición libre: la primera siempre encuentra una,
la segunda tiene $$M - 1$$ libres de $$M$$, la tercera $$M - 2$$, y así. La
probabilidad de que ninguna choque, es decir, de que el reparto sea
inyectivo, es el producto de esas fracciones:

$$
P(\text{sin colisiones}) = \frac{M}{M} \cdot \frac{M - 1}{M} \cdot \frac{M - 2}{M} \cdots \frac{M - N + 1}{M}.
$$

$$
\frac{4}{4} \cdot \frac{3}{4} \cdot \frac{2}{4} = \frac{24}{64} = 37{,}5\,\%
$$

Desde la segunda, cada fracción es menor que $$1$$, y al multiplicar muchas el
producto cae muy rápido: con $$M = 365$$, a las 23 personas ya es menor que un medio.
Con 31 claves en 41 posiciones, la probabilidad de que no haya colisiones es
de una en diez millones.

<Slide title="El supuesto de dispersión uniforme">
Para calcular cuánto cuestan las operaciones de una tabla hash, hay que
suponer algo sobre cómo reparte las claves su función. Se supone que las
reparte como si las lanzara al azar, igual que en la primera colisión: es el
**supuesto de dispersión uniforme**. Dice que cada clave cae en cualquiera de
las $$M$$ posiciones con la misma probabilidad,

$$
P\big(h(k) = i\big) = \frac{1}{M} \qquad \text{para } i = 0, 1, \ldots, M - 1,
$$

que se lee «la clave $$k$$ cae en la posición $$i$$ con probabilidad $$1/M$$,
para todas las posiciones». Además, dónde cae una clave no cambia dónde cae
otra. Como todas las posiciones tienen la misma probabilidad, todas reciben,
en promedio, la misma cantidad de claves: $$N / M$$, el reparto parejo.

<Abanico
  id="uniforme"
  name="Ana"
  cells={7}
  caption="«Ana» puede caer en cualquiera de las siete posiciones, todas con la misma probabilidad"
  label="La clave Ana sobre siete casilleros, del 0 al 6, con una flecha a cada uno. Dentro de cada casillero dice un séptimo: la probabilidad de que Ana caiga ahí."
/>

Es solo un supuesto: ninguna función lo cumple con todos los conjuntos de
claves. Como $$U$$ es mucho más grande que el arreglo, alguna posición recibe
muchísimas claves de $$U$$, y si las claves que llegan son justo esas, caen
todas en la misma posición, por buena que sea la función. De una buena
función se espera que, con las claves que de verdad llegan, el reparto se
parezca al del azar. Los costos esperados de una tabla hash se calculan bajo
este supuesto.

</Slide>

<Slide title="Los requisitos de una función hash">
Una buena función hash cumple tres requisitos.

1. **Determinista.** La misma clave da siempre la misma posición: la posición
   depende solo de la clave. Si no, una clave guardada en un casillero se
   buscaría después en otro, y no se encontraría.
2. **Eficiente.** Calcularla cuesta poco, y el costo no depende de cuántas
   claves hay guardadas. Si costara tanto como comparar, no se ganaría nada
   frente a la búsqueda binaria.
3. **Uniforme.** Reparte las claves parejo: cada posición recibe más o menos
   $$N / M$$ claves. Como las colisiones no se pueden evitar, es lo mejor que
   se le puede pedir.

Con estos tres requisitos, la función lleva cada clave a su posición sin
comparar, que era lo que se buscaba. Pero quedan dos cosas por decidir, de
naturaleza distinta.

- **Cómo calcular la función.** Es un problema de la función: cumplir los tres
  requisitos con claves reales, que se parecen entre sí —nombres que empiezan
  igual, números que terminan igual—. Una regla que mira solo una parte de la
  clave hereda esos parecidos, así que la posición tiene que depender de
  **toda** la clave.
- **Qué hacer cuando dos claves colisionan.** Es un problema de la tabla: como
  ninguna función evita las colisiones, y llegan pronto, la tabla tiene que
  poder guardar dos claves que caen en la misma posición.

</Slide>

<Slide title="La suma de los caracteres">
Para que cuente todo el nombre, se pueden sumar sus letras. El computador
guarda cada carácter como un número, su código en la tabla
[ASCII](https://es.wikipedia.org/wiki/ASCII): `'A'` es 65 y `'a'`, 97. Java
usa Unicode, que extiende esa tabla y les da a esas letras los mismos códigos.
La regla suma el código de cada carácter y usa la suma como posición.

Ahora todas las letras cuentan, pero la suma no mira el orden: dos nombres con
las mismas letras en otro orden suman lo mismo, y colisionan siempre.

| Clave    | Códigos de sus caracteres | Suma |
| -------- | ------------------------- | ---- |

una posición que exista en la tabla.

</Slide>

<Slide title="El recorrido de la suma">
La suma falla también por otro lado. Una tabla que guarda miles de nombres,
como los de los alumnos de una universidad, necesita miles de casilleros:
digamos 10 000. Pero la suma de un nombre es un número chico. El código de
cada letra está entre 65, la `'A'`, y 122, la `'z'`, así que un nombre de tres
a ocho letras suma entre 259 y 944. Todos los nombres caen en esa franja, y los
demás casilleros no reciben nunca una clave: la suma está lejos de ser
sobreyectiva.

$$
\begin{gathered}
259 = 65 + 2 \cdot 97 \;\le\; \operatorname{suma} \;\le\; 90 + 7 \cdot 122 = 944 \\
\frac{944 - 259 + 1}{10\,000} = \frac{686}{10\,000} \approx 6{,}9\,\%
\end{gathered}
$$

La suma no sirve como función hash: no mira el orden de las letras y, por
grande que sea la tabla, da apenas unos cientos de valores distintos.

<Slide title="De un texto a un número">
Los tres intentos fallan por lo mismo: miran solo una parte del nombre, lo
miran sin orden, o dan muy pocos valores distintos. El orden es lo más
delicado: «Irma» y «Mari» tienen las mismas letras. Para que el orden cuente,
cada letra tiene que pesar según su lugar.

Así funcionan los números que escribimos todos los días. 347 y 743 tienen las
mismas cifras, pero son números distintos, porque cada cifra se multiplica por
un peso según su lugar: la primera por 100, la segunda por 10 y la última
por 1.

$$
347 = 3 \cdot 100 + 4 \cdot 10 + 7 \cdot 1, \qquad 743 = 7 \cdot 100 + 4 \cdot 10 + 3 \cdot 1
$$

Un nombre se puede leer igual, con cada carácter como una cifra. Como los
códigos de las letras son menores que 256, los pesos no son 100, 10 y 1 sino
potencias de 256: es leer el nombre como un número en **base 256**.

| Carácter de «Ana»   | `'A'`         | `'n'`        | `'a'`        | Número de «Ana» |
| ------------------- | ------------- | ------------ | ------------ | --------------- |
| Código              | 65            | 110          | 97           |                 |
| Peso                | $$256^2$$     | $$256^1$$    | $$256^0$$    |                 |
| Aporte              | 4 259 840     | 28 160       | 97           | 4 288 097       |

Así, dos textos distintos dan siempre números distintos, y «Irma» y «Mari» ya
no se confunden. Además, cada letra cuenta, y con más letras el número crece
sin límite. Lo que falta es llevar ese número, enorme, a una de las $$M$$
posiciones de la tabla.

</Slide>

<Slide title="El método de la división">
Para usar un número como posición, tiene que quedar dentro de la tabla, entre
$$0$$ y $$M - 1$$, por grande que sea. La manera más usada de limitarlo es el
**método de la división**: la posición es el resto de dividir $$x$$ por $$M$$,

$$
h(x) = x \bmod M,
$$

que se lee «$$x$$ módulo $$M$$». El resto de dividir por $$M$$ siempre está
entre $$0$$ y $$M - 1$$. Con esto, la función hash queda en **dos pasos**: de
la clave a un número, y del número a una posición.

$$

$$

</Slide>

<Slide title="La elección de M">
Que la división reparta parejo depende de $$M$$. Si $$M$$ es una potencia de
2, $$M = 2^k$$, el resto se queda solo con los $$k$$ bits más bajos del
número: la regla vuelve a mirar una parte de la clave. Con un texto leído en
base 256, $$M = 256$$ deja solo el último carácter, y todos los nombres que
terminan igual caen en la misma posición. Con un $$M$$ **primo**, lejos de una
potencia de 2, el resto depende de todo el número, y cuentan todas las letras.

| Nombre   | Número, en base 256 | Con $$M = 256$$ | Con $$M = 251$$, primo |
| -------- | ------------------- | --------------- | ---------------------- |
| «Ana»    | 4 288 097           | 97              | 13                     |
| «Bea»    | 4 351 329           | 97              | 244                    |
| «Eva»    | 4 552 289           | 97              | 153                    |
| «Sara»   | 1 398 895 201       | 97              | 164                    |

Con $$M = 256$$, los cuatro nombres colisionan en la 97, el código de la «a»
final.

</Slide>

<Slide title="La regla de Horner">
El número de un texto crece muy rápido: cada carácter lo multiplica por la
base. Un `int` de Java llega hasta $$2^{31} - 1 = 2\,147\,483\,647$$, y
cualquier nombre de cinco letras lo supera, porque su primera cifra ya pesa
$$256^4 = 2^{32}$$. Hace falta calcular la posición sin armar nunca el número
completo, y el primer paso es la **regla de Horner**.

La idea se ve con 347. Sacando el 10 como factor común de los dos primeros
términos,

$$
347 = 3 \cdot 100 + 4 \cdot 10 + 7 = (3 \cdot 10 + 4) \cdot 10 + 7,
$$

y el número se arma leyendo sus cifras de izquierda a derecha: 3, después
$$3 \cdot 10 + 4 = 34$$, después $$34 \cdot 10 + 7 = 347$$. Cada paso
multiplica lo anterior por la base y suma la cifra siguiente. Con un texto
$$c_0 c_1 \ldots c_{n-1}$$ en base $$B$$ es lo mismo:

$$
\begin{gathered}
c_0 \cdot B^{n-1} + c_1 \cdot B^{n-2} + \cdots + c_{n-1} \\
= \Big(\big(c_0 \cdot B + c_1\big) \cdot B + c_2\Big) \cdot B + \cdots + c_{n-1},
\end{gathered}
$$

con una multiplicación y una suma por carácter, sin calcular potencias.

</Slide>

<Slide title="El resto en cada paso">
Horner todavía arma el número completo, que no cabe en un `int`. La tabla, en
cambio, solo necesita el resto de dividirlo por $$M$$, y el resto tiene una
propiedad que permite no armarlo nunca: **el resto de una suma o de un
producto solo depende de los restos de sus partes**. Por eso, antes de sumar o
de multiplicar, un número se puede reemplazar por su resto, y el resto final
no cambia:

$$
\begin{gathered}
(a + b) \bmod M = \big((a \bmod M) + b\big) \bmod M \\
(a \cdot b) \bmod M = \big((a \bmod M) \cdot b\big) \bmod M
\end{gathered}
$$

Es la base de la **aritmética modular**. Con ella, cada paso de Horner se
queda solo con el resto,

$$
h = (h \cdot B + c) \bmod M,
$$

y $$h$$ siempre es menor que $$M$$. Con «Ana», en base 256 y con $$M = 7$$:

| Carácter | Código | Horner, sin reducir                        | Horner, reduciendo en cada paso                      |
| -------- | ------ | ------------------------------------------ | ---------------------------------------------------- |
| `'A'`    | 65     | $$65$$                                     | $$65 \bmod 7 = 2$$                                   |
| `'n'`    | 110    | $$65 \cdot 256 + 110 = 16\,750$$           | $$(2 \cdot 256 + 110) \bmod 7 = 622 \bmod 7 = 6$$    |
| `'a'`    | 97     | $$16\,750 \cdot 256 + 97 = 4\,288\,097$$   | $$(6 \cdot 256 + 97) \bmod 7 = 1\,633 \bmod 7 = 2$$  |

Las dos columnas llegan a la misma posición, $$4\,288\,097 \bmod 7 = 2$$. Pero
en la segunda, $$h$$ nunca llega a 7, y
la cuenta más grande, 1 633, queda muy lejos del límite de un `int`.

</Slide>

<Slide title="Primo o potencia de 2">
La división reparte bien con un $$M$$ primo, pero un tamaño primo tiene dos
costos. El primero aparece al crecer: la tabla no puede simplemente duplicar
su tamaño, porque el doble de un primo es par, y tiene que buscar el siguiente
primo. El segundo está en cada cálculo: dividir por un número cualquiera es,
para el procesador, una cuenta larga, como una división hecha a mano, bastante
más lenta que una suma o una multiplicación.

Con $$M$$ potencia de 2, las dos cosas se simplifican. La tabla crece
duplicándose, y dividir por $$2^k$$ es correr los bits del número $$k$$
lugares, como en decimal dividir por 1 000 es correr la coma tres lugares: el
resto son los $$k$$ bits que quedan atrás, y se obtiene sin ninguna cuenta
larga.

Pero eso es justo lo que la división no tolera: con $$M = 2^k$$, el resto son
solo los $$k$$ bits más bajos del número, y la regla vuelve a mirar una parte
de la clave. Las dos preferencias chocan.

</Slide>

<Slide title="El método de la multiplicación">
Para tablas de tamaño potencia de 2 hay otra manera de llevar un número $$x$$
a una posición, el **método de la multiplicación**. Elige una constante $$A$$
entre 0 y 1, y da tres pasos:

1. multiplica $$x$$ por $$A$$; el producto puede ser mayor que 1;
2. se queda con la parte decimal del producto, un número entre 0 y 1;
3. multiplica esa parte decimal por $$M$$ y redondea hacia abajo.

Con símbolos,

$$
h(x) = \big\lfloor M \cdot (A \cdot x \bmod 1) \big\rfloor,
$$

donde $$\bmod 1$$ se queda con la parte decimal y $$\lfloor\,\cdot\,\rfloor$$
redondea hacia abajo. Knuth propone $$A = (\sqrt{5} - 1)/2 \approx 0{,}618$$.
Con ese $$A$$ y $$M = 8$$:

| $$x$$ | $$A \cdot x$$ | Parte decimal | Por $$M = 8$$ | Posición |
| ----- | ------------- | ------------- | ------------- | -------- |
| 1     | 0,618         | 0,618         | 4,94          | 4        |
| 2     | 1,236         | 0,236         | 1,89          | 1        |
| 3     | 1,854         | 0,854         | 6,83          | 6        |

Las tres claves quedan en posiciones distintas. A diferencia de la división,
el método reparte bien con cualquier $$M$$, también con una potencia de 2.

</Slide>

<Slide title="La razón áurea">
La constante que propone Knuth no es un número cualquiera: es el inverso de la
**razón áurea** $$\varphi$$,

$$
\varphi = \frac{1 + \sqrt{5}}{2} \approx 1{,}618, \qquad A = \frac{1}{\varphi} = \varphi - 1 \approx 0{,}618,
$$

el número al que se acerca el cociente entre dos números de Fibonacci
consecutivos, como $$34/55$$ o $$55/89$$.

Tiene una propiedad que la hace buena para repartir. Si llegan las claves 1,
2, 3, …, una a una, la parte decimal de $$A \cdot x$$ de cada clave nueva cae
en uno de los huecos más grandes que dejaron las anteriores, así que cada
clave queda lejos de las que ya están. Por eso claves seguidas, o que avanzan
de a un paso fijo, se reparten por toda la tabla: con $$M = 8$$, las claves 1
a 8 ocupan las ocho posiciones, una cada una.
Al método con esta constante se le llama **hashing de Fibonacci**.

$$

<Slide title="El código de la multiplicación">
En código, el método son tres líneas, una por paso. `A` es una constante de la
clase, y `table.length` es $$M$$.

```java
private static final double A = (Math.sqrt(5) - 1) / 2;

private int hash(int x) {
    double product = x * A;
    double fraction = product - Math.floor(product);
    return (int) (fraction * table.length);
}
```

`Math.floor` redondea hacia abajo, así que `product - Math.floor(product)`
es la parte decimal, y convertir a `int` redondea hacia abajo la posición. Con
$$x = 8$$ y $$M = 16$$:

$$
8 \cdot 0{,}618 = 4{,}944, \qquad 4{,}944 - 4 = 0{,}944, \qquad \lfloor 0{,}944 \cdot 16 \rfloor = \lfloor 15{,}1 \rfloor = 15
$$

La multiplicación necesita el número completo de la clave. Con claves que ya
son números, como folios o identificadores, se aplica directo. Con un texto,
en cambio, ese número no cabe en un `int` apenas el texto es un poco largo,
mientras que la división se puede aplicar en cada paso de Horner y sirve para
textos de cualquier largo.

<Vara determinista eficiente uniforme note="con un tamaño potencia de 2" />

</Slide>

<Slide title="La división frente a la multiplicación">
Las dos técnicas dan el segundo paso, del número a una posición, y las dos son
deterministas. Se diferencian en el tamaño de tabla que piden y en lo que
cuestan.

|                         | División                               | Multiplicación                                  |
| ----------------------- | -------------------------------------- | ----------------------------------------------- |
| Posición                | $$x \bmod M$$                          | $$\lfloor M \cdot (A \cdot x \bmod 1) \rfloor$$ |
| Tamaño de la tabla      | Un primo, lejos de una potencia de 2   | Una potencia de 2                               |
| Costo                   | Una división                           | Una multiplicación                              |
| Claves con un patrón    | Las reparte, si $$M$$ es primo         | Las reparte                                     |
| Al crecer la tabla      | Hay que buscar el siguiente primo      | Basta duplicarla                                |
| La usan                 | `unordered_map` de GCC                 | El núcleo de Linux, `ThreadLocal` de Java       |

La división es la más simple de entender y de programar, reparte bien con un
$$M$$ primo y sirve directo para textos de cualquier largo. La multiplicación
es la más rápida, y la que conviene con claves que ya son números y con tablas
que crecen duplicando su tamaño.

</Slide>

  const left = (width - core) / 2 + pad;
  const height = top + boxH + (caption ? 40 : 12);
  const bx = (i) => left + i * (boxW + gap);
  return (
    <svg viewBox={`0 0 ${width} ${height}`} style={{ width: '100%', maxWidth: `${Math.round(width * 1.3)}px`, height: 'auto', display: 'block', margin: '0.4rem auto' }} role="img" aria-label={label}>
      <defs>
        <marker id={`${id}-punta`} markerWidth="8" markerHeight="8" refX="7" refY="4" orient="auto">
          <path d="M0,0 L8,4 L0,8 z" style={{ fill: 'var(--color-ink-soft)' }} />
        </marker>
      </defs>
      {boxes.map((b, i) => (
        <g key={`b${i}`}>
          <text x={bx(i) + boxW / 2} y={top - 9} textAnchor="middle" fontSize="12" style={{ fill: 'var(--color-ink-faint)' }}>{b.title}</text>
          <rect x={bx(i)} y={top} width={boxW} height={boxH} rx="4" style={{ fill: 'var(--color-surface)', stroke: 'var(--color-rule-strong)' }} strokeWidth="1.4" />
          <text x={bx(i) + boxW / 2} y={top + boxH / 2 + 6} textAnchor="middle" fontSize="16" fontWeight="600" style={{ fill: 'var(--color-ink)' }}>{b.text}</text>
        </g>
      ))}
      {steps.map((s, i) => (
        <g key={`s${i}`}>
          <line x1={bx(i) + boxW + 6} y1={top + boxH / 2} x2={bx(i + 1) - 8} y2={top + boxH / 2} style={{ stroke: 'var(--color-ink-soft)' }} strokeWidth="1.6" markerEnd={`url(#${id}-punta)`} />
          <text x={bx(i) + boxW + gap / 2} y={top + boxH / 2 - 8} textAnchor="middle" fontSize="13" fontFamily="var(--font-mono, monospace)" style={{ fill: 'var(--color-ink-soft)' }}>{s}</text>
        </g>
      ))}
      {caption ? (
        <text x={width / 2} y={height - 8} textAnchor="middle" fontSize="12" style={{ fill: 'var(--color-ink-soft)' }}>{caption}</text>
      ) : null}
    </svg>
  );
}

<Slide title="De la clave a la posición en dos pasos">
La división y la multiplicación dan solo el segundo paso, del número a una
posición, y no les importa de qué tipo era la clave. El primer paso, de la
clave a un número, sí depende del tipo.

- **Un entero** ya es un número, y el primer paso no hace nada.
- **Un texto** se lee como un número con la regla de Horner, o con otra
  función que mezcle sus caracteres.
- **Un objeto** combina los números de sus campos, como Horner combina las
  letras, y cada lenguaje decide cómo.

En Java, el primer paso es el método `hashCode()`, que tiene todo objeto, y el
segundo lo da la tabla. Para un `Integer`, `hashCode()` devuelve el mismo
número.

  steps={['hashCode()', 'mod 7']}
  label="Tres cajas unidas por flechas. La clave, el entero 2024; una flecha rotulada hashCode lleva al número 2024, el mismo; otra flecha rotulada mod 7 lleva a la posición 1."
/>

$$
2024 \bmod 7 = 1
$$

</Slide>

<Slide title="Las funciones hash de cada lenguaje">
Cada biblioteca elige cómo dar los dos pasos.

| Biblioteca                    | De un texto a un número                        | Del número a una posición                                        |
| ----------------------------- | ---------------------------------------------- | ---------------------------------------------------------------- |
| Java, `HashMap`               | Horner con 31                                  | Mezcla los 16 bits altos con los bajos y se queda con los bajos |
| C++, `unordered_map` de GCC   | MurmurHash                                     | El resto de dividir por un primo                                 |
| Python, `dict`                | SipHash, con una clave al azar                 | Los bits bajos                                                   |
| Rust, `HashMap`               | SipHash, con una clave al azar                 | Una parte de sus bits                                            |
| Go, `map`                     | Basada en AES o en wyhash, con semilla al azar | Una parte de sus bits                                            |

Python, Rust y Go eligen al azar la clave de su función hash cada vez que
arranca un programa: quien no la conoce no puede elegir claves que colisionen.

En la práctica, el texto se resuelve en el primer paso: `hashCode()` u otra
función lo acota a un número de 32 o 64 bits, y desde ahí cualquier segundo
paso sirve. Por eso casi todas estas tablas tienen un tamaño potencia de 2 y
se quedan con los bits bajos: su primer paso ya mezcló todos los bits, como
Java al mezclar los 16 altos con los bajos.

</Slide>

<Slide title="Una función hash que cumple los tres requisitos">
La primera decisión era cómo calcular una función hash determinista, eficiente
y uniforme con claves reales, que se parecen entre sí. La respuesta tiene dos
pasos:

1. **De la clave a un número**, leyéndola completa: cada carácter pesa según
   su lugar, con la regla de Horner. Así la posición depende de **toda** la
   clave.
2. **Del número a una posición**: con la división, si $$M$$ es primo, o con la
   multiplicación, si $$M$$ es potencia de 2.

Es determinista, porque la posición depende solo de la clave; eficiente,
porque recorre la clave una sola vez, sin importar cuántas claves haya en la
tabla; y uniforme, porque mira la clave completa y la reparte con un $$M$$
primo o con la razón áurea.

<Vara determinista eficiente uniforme />

Queda la segunda decisión, que es de la tabla: qué hacer cuando dos claves
colisionan. Ninguna función lo evita, y pasa pronto, con la tabla casi vacía.

</Slide>

export function Listas({ chains, picked, only = false, paint = {}, cut, window: shown, caption, label }) {
  const pad = 12;
  const pitch = 78;
  const cellH = 30;
  const nodeW = 56;
  const keyH = 22;
  const nodeH = 34;
  const gap = 18;
  const indexY = 18;
  const cellY = 26;
  const [lo, hi] = shown ?? [0, chains.length - 1];
  const longest = Math.max(1, ...chains.slice(lo, hi + 1).map((c) => c.length));
  const stripW = (hi - lo + 1) * pitch;
  const width = Math.max(2 * pad + stripW + (shown ? 40 : 0), caption ? caption.length * 6.6 + 24 : 0);
  const left = (width - stripW) / 2;
  const nodeY = (k) => cellY + cellH + gap + k * (nodeH + gap);
  const height = nodeY(longest) - gap + 18 + (caption ? 30 : 6);
  const fill = { mark: 'var(--color-mark-soft)', found: 'var(--color-keep-soft)', visited: 'var(--color-sunk)', focus: 'var(--color-surface)' };
  const stroke = { mark: 'var(--color-mark)', found: 'var(--color-keep)', visited: 'var(--color-rule-strong)', focus: 'var(--color-focus)' };
  return (
    <svg viewBox={`0 0 ${width} ${height}`} style={{ width: '100%', maxWidth: `${Math.round(width * 1.3)}px`, height: 'auto', display: 'block', margin: '0.4rem auto' }} role="img" aria-label={label}>

        <text x={left - 12} y={cellY + cellH / 2 + 4} textAnchor="middle" fontSize="13" style={{ fill: 'var(--color-ink-faint)' }}>…</text>
      ) : null}
      {hi < chains.length - 1 ? (
        <text x={left + stripW + 12} y={cellY + cellH / 2 + 4} textAnchor="middle" fontSize="13" style={{ fill: 'var(--color-ink-faint)' }}>…</text>
      ) : null}

        if (i < lo || i > hi) return null;

        return (

              <text x={cx} y={cellY + cellH / 2 + 4} textAnchor="middle" fontSize="11" style={{ fill: 'var(--color-ink-faint)' }}>null</text>

'var(--color-rule)' : p ? stroke[p] : 'var(--color-rule)' }} strokeWidth={leaving || (p && p !== 'visited') ? 2.4 : 1.2} strokeDasharray={leaving ? '4 3' : undefined} />

            })}

  );

<Slide title="Las invariantes de la tabla con listas">
1. **Ninguna clave está dos veces.** La tabla guarda un conjunto: agregar una
   clave que ya está no la duplica.
2. **`size` es la cantidad de nodos de todas las listas.** Es el $$N$$ de la
   tabla, y se mantiene sin recorrerla.
3. **Cada clave está en la lista de la posición `hash(key)`.** Es la
   invariante que hace barata la búsqueda: para saber si una clave está, basta
   mirar una sola lista.

La tercera es también la que encarece una operación. La posición de una clave
depende del tamaño de la tabla, así que si la tabla cambia de tamaño, cada clave tiene que
moverse a la lista de su nueva posición.

</Slide>

<Slide title="El factor de carga">
Cuánto mide una lista depende de cuántas claves hay por posición: con $$N$$
claves en $$M$$ posiciones, un reparto parejo le da a cada una $$N / M$$. Ese
cociente es el **factor de carga** de la tabla,

$$
\alpha = \frac{N}{M},
$$

que se lee «alfa es la cantidad de claves dividida por la de posiciones». En el
guardarropa, es cuántos abrigos cuelgan en promedio de cada casillero. Bajo el
supuesto de dispersión uniforme, una lista mide en promedio $$\alpha$$ nodos.

  chains={TABLA}
  caption="seis claves en siete posiciones"
  label="La tabla de siete posiciones con seis claves: Eva, Juan, Leo, Ana, Bea y Sara. Su factor de carga es seis séptimos, casi 0,86."
/>

$$
\alpha = \frac{N}{M} = \frac{6}{7} \approx 0{,}86
$$

</Slide>

<Slide title="Las dos condiciones del costo constante">
Buscar, agregar y eliminar hacen el mismo trabajo: calculan la posición de la
clave y recorren la lista de esa posición, hasta dar con la clave o hasta el
final. Por eso las tres cuestan lo mismo en promedio,

$$
\Theta(1 + \alpha),
$$

el 1 por calcular la posición, que no depende de $$N$$, y el $$\alpha$$ por
recorrer la lista.

Ese costo es constante solo si se cumplen dos condiciones, y cada una tiene su
responsable:

- **La función hash reparte parejo.** Si no, las claves se juntan en pocas
  listas y, en el extremo, caen todas en la misma: una sola lista de $$N$$
  nodos, que cuesta $$\Theta(N)$$ recorrer. Es tarea de la función: que sea
  uniforme.
- **La tabla crece con las claves.** Aunque la función reparta perfecto, con
  $$M$$ fijo cada clave nueva sube $$\alpha = N / M$$, y el costo crece de
  forma lineal con las claves. Es tarea de la tabla.

$$
M = 7, \quad N = 700 \quad \Rightarrow \quad \alpha = 100
$$

</Slide>

<Slide title="Costos de la tabla con listas">
| Molde     | Operación             | Peor caso     | Esperado                 | Invariante que restaura                                   |
| --------- | --------------------- | ------------- | ------------------------ | --------------------------------------------------------- |
| crear     | `ChainedHashTable(M)` | $$\Theta(M)$$ | $$\Theta(M)$$            | Las tres: sin claves, y `size` en 0                       |
| consultar | `contains(key)`       | $$\Theta(N)$$ | $${\Theta(1 + \alpha)}$$ | Ninguna: no cambia la tabla                               |
| modificar | `add(key)`            | $$\Theta(N)$$ | $${\Theta(1 + \alpha)}$$ | La clave entra una vez, en su lista; `size` sube en 1     |
| modificar | `remove(key)`         | $$\Theta(N)$$ | $${\Theta(1 + \alpha)}$$ | La clave sale de su lista, las demás quedan; `size` baja en 1 |

**Queda la segunda condición: que la tabla crezca junto con las claves.**

</Slide>

<Slide title="Una tabla que crece">
Para que la tabla crezca junto con las claves, se le pone un límite al factor
de carga. Cuando ya tiene tantas claves como posiciones, antes de agregar otra
se crea un arreglo más grande y las claves pasan a él: la tabla se
**redimensiona**. Con esa regla el factor de carga nunca pasa de 1,

$$
\alpha = \frac{N}{M} \le 1,
$$

y el costo esperado de las tres operaciones, $$\Theta(1 + \alpha)$$, queda
acotado por una constante.

</Slide>

<Slide title="Por qué las claves cambian de posición">
Un arreglo no se alarga: el más grande es un arreglo nuevo, y las claves
tienen que pasar a él. Pero no a la misma posición que tenían. La posición es
el resto de dividir el número de la clave por $$M$$, y con otro $$M$$ el resto
es otro, así que casi todas las claves cambian de posición. Cada una vuelve a
entrar con su hash calculado de nuevo, en la lista de su posición en la tabla
nueva.

<Slide title="El tamaño nuevo">
El arreglo nuevo tiene que tener al menos el doble de posiciones: así la
próxima redimensión llega solo después de otras tantas inserciones, y su costo
se reparte entre ellas. Cómo se llega a ese tamaño depende del método que
calcula la posición:

- con el **método de la división**, el tamaño tiene que ser primo, y el doble
  de un primo es par: se busca el primer primo después del doble, $$2M$$;
- con el **método de la multiplicación**, el tamaño es una potencia de 2, y
  basta duplicarla.

$$
\text{división: } 3 \to 7 \to 17 \to 37 \qquad \text{multiplicación: } 4 \to 8 \to 16 \to 32
$$

</Slide>

<Slide title="La búsqueda del primo">
`add` le pasa a `nextPrime` el doble del tamaño, y `nextPrime` prueba los
números desde ahí, uno a uno, hasta dar con uno sin divisores.

```java
private static int nextPrime(int n) {
    while (!isPrime(n)) {
        n++;
    }
    return n;
}

private static boolean isPrime(int n) {
    if (n < 2) return false;
    for (int d = 2; d * d <= n; d++) {
        if (n % d == 0) return false;
    }
    return true;
}
```

En la práctica, las bibliotecas que usan tamaños primos no los buscan en cada
redimensión: los guardan en una lista calculada de antemano y toman de ella el
primero desde el doble, como el `unordered_map` de C++ que trae GCC o el
`Dictionary` de C#. Las que usan potencias de 2, como `HashMap` de Java o
`dict` de Python, no tienen nada que buscar.

</Slide>

<Slide title="La inserción con redimensión">
`add` gana una línea: antes de enganchar la clave nueva, si la tabla ya tiene
tantas claves como posiciones, la redimensiona.

```java
public boolean add(String key) {
    if (contains(key)) return false;
    if (size == table.length)
        resize(nextPrime(2 * table.length));
    int i = hash(key);
    Node fresh = new Node(key);
    fresh.next = table[i];
    table[i] = fresh;
    size++;
    return true;
}
```

</Slide>

<Slide title="El código de la redimensión">
`resize` es privado: solo lo llama `add`. Guarda el arreglo viejo en `old`,
crea el nuevo, pone `size` en 0 y vuelve a agregar con `add` cada clave de
`old`. Recorre las $$M$$ posiciones viejas y vuelve a agregar las $$N$$ claves;
como redimensiona cuando $$N = M$$, cuesta $$\Theta(N)$$ en total.

<Slide title="El costo amortizado de la inserción">
Agregar hace dos cosas que cuestan. La primera es revisar si la clave ya está,
recorriendo la lista de su posición: el mismo recorrido de las operaciones de
buscar y de eliminar. Con la redimensión, el factor de carga nunca pasa de 1:

$$
\alpha = \frac{N}{M} \le 1 \quad \Rightarrow \quad \Theta(1 + \alpha) = \Theta(1)
$$

La segunda es redimensionar, que cuesta $$\Theta(N)$$ pero pasa pocas veces.
Cada redimensión mueve más del doble de claves que la anterior, así que, al
agregar $$N$$ claves, entre todas mueven menos de $$2N$$ claves:

$$
N + \frac{N}{2} + \frac{N}{4} + \cdots < 2N
$$

Repartido entre las $$N$$ inserciones, cada `add` paga en promedio menos de dos
movimientos además del suyo: redimensionar le cuesta $$\Theta(1)$$
**amortizado** a cada inserción, igual que agregar en el arreglo dinámico.

$$

$$

**Como las dos partes son constantes, agregar cuesta $$\Theta(1)$$ amortizado.**

</Slide>

<Slide title="Costos con redimensión">
| Molde     | Operación       | Peor caso     | Esperado      | Invariante que restaura                        |
| --------- | --------------- | ------------- | ------------- | ---------------------------------------------- |
| consultar | `contains(key)` | $$\Theta(N)$$ | $$\Theta(1)$$ | Ninguna: no cambia la tabla                    |
| modificar | `add(key)`      | $$\Theta(N)$$ | $$\Theta(1)$$ amortizado | La clave entra una vez, en su lista, y la tabla crece antes si $$\alpha$$ llegó a 1 |
| modificar | `remove(key)`   | $$\Theta(N)$$ | $$\Theta(1)$$ | La clave sale de su lista, las demás quedan; `size` baja en 1 |

Los costos no lo muestran, pero las listas tienen un precio: cada clave
necesita un nodo propio, con su referencia al siguiente, y esos nodos quedan
repartidos por la memoria, así que recorrer una lista es saltar de un lugar a
otro. La otra manera de resolver las colisiones no usa nodos: guarda las
claves en las celdas del propio arreglo, una al lado de la otra.

</Slide>

## Sondeo lineal

export const SONDEO = ['Pablo', null, null, null, null, 'Mia', 'Alba', null, null, null, 'Julia'];

<Slide title="Una clave en cada posición">
Si cada celda del arreglo guarda una sola clave, una clave cuya celda ya está
ocupada tiene que quedar en otra. La regla más simple es probar la celda
siguiente, y la siguiente, hasta dar con una libre; después de la última viene
la primera.

A esta forma de resolver las colisiones se le llama **sondeo lineal** (en
inglés, *linear probing*): «sondeo» porque prueba celdas, y «lineal» porque las
prueba de a una, en orden.

  notes={{ 0: 'h 10', 5: 'h 5', 6: 'h 5', 10: 'h 10' }}
  caption="11 celdas: «Alba» encuentra ocupada la celda de su hash y queda en la siguiente; «Pablo» da la vuelta hasta el 0"
  label="Once celdas numeradas del 0 al 10. Pablo está en el 0, Mia en el 5, Alba en el 6 y Julia en el 10. Sobre cada uno, su hash: Pablo 10, Mia 5, Alba 5 y Julia 10."

$$
\begin{gathered}
M = 11 \\
h(\text{«Mia»}) = h(\text{«Alba»}) = 5, \qquad h(\text{«Julia»}) = h(\text{«Pablo»}) = 10
\end{gathered}
$$

</Slide>

<Slide title="Las invariantes del sondeo lineal">
1. **Ninguna clave está dos veces.** Como en la tabla con listas, la tabla
   guarda un conjunto.
2. **Siempre queda al menos una celda vacía.** Es lo que garantiza que una
   búsqueda termine aunque la clave no esté: sin celdas vacías, daría vueltas
   para siempre.
3. **Entre la celda `hash(key)` y la celda de `key` no hay ninguna celda
   vacía.** Una clave queda en la primera celda libre desde su hash, así que
   todas las anteriores estaban ocupadas cuando entró.

La tercera es la que hace correcta la búsqueda: al llegar a una celda vacía,
la clave buscada no puede estar más allá. Y es también la que complica
eliminar: una celda ocupada no se puede volver a vaciar sin romperla.

</Slide>

<Slide title="La clase de la tabla con sondeo lineal">
Las claves se guardan en un arreglo de `String`, `null` donde no hay ninguna.
Como una celda ocupada no se puede vaciar, eliminar una clave no la borra: la
marca en un arreglo paralelo del mismo largo, `deleted`. `size` cuenta las
claves que siguen en la tabla, y `used` las celdas que no son `null`, las de
las claves y también las marcadas. `hash(String key)` es la misma regla de
Horner, con `keys.length` como $$M$$, y una tabla necesita al menos dos celdas:
con una sola, no quedaría ninguna vacía.

```java
class ProbingHashTable {
    private String[] keys;
    private boolean[] deleted;
    private int size;
    private int used;

    ProbingHashTable(int capacity) {
        if (capacity < 2) throw new IllegalArgumentException();
        keys = new String[capacity];
        deleted = new boolean[capacity];
    }
}
```

</Slide>

<Slide title="Buscar con sondeo lineal">
**Buscar** responde si una clave está: recibe la clave, responde sí o no, y no
cambia nada. Empieza en la celda de su hash y avanza de a una, dando la vuelta
al final del arreglo, hasta encontrarla o llegar a una celda vacía. Como entre
el hash de una clave y su celda no hay celdas vacías, la clave no puede estar
más allá de esa celda vacía.

<Slide title="La redimensión de la tabla con sondeo lineal">
Para que siempre queden celdas vacías donde una búsqueda se detenga, y los
tramos ocupados sean cortos, `add` redimensiona antes de que la clave nueva
deje ocupadas más de la mitad de las celdas. En el sondeo, el factor de carga
cuenta todas las celdas ocupadas, `used`, también las marcadas, que ocupan su
celda igual que una clave; con esa regla, nunca pasa de un medio:

$$
\alpha = \frac{\texttt{used}}{M} \le \frac{1}{2}
$$

`resize` es el de la tabla con listas, con dos diferencias: recorre las celdas
del arreglo viejo en lugar de sus listas, y salta las claves marcadas. La
tabla nueva solo recibe las claves que siguen en el conjunto, así que las
marcas desaparecen.

```java
private void resize(int capacity) {
    String[] oldKeys = keys;
    boolean[] oldDeleted = deleted;
    keys = new String[capacity];
    deleted = new boolean[capacity];
    size = 0;
    used = 0;
    for (int i = 0; i < oldKeys.length; i++) {
        if (oldKeys[i] != null && !oldDeleted[i]) {
            add(oldKeys[i]);
        }
    }
}
```

Recorre las $$M$$ celdas viejas y vuelve a agregar cada clave: cuesta
$$\Theta(N + M)$$, y como el tamaño pasa a más del doble, sale $$\Theta(1)$$
amortizado por inserción, igual que con listas.

</Slide>

$$
h(\text{«Eva»}) = 5
$$

</Slide>

<Slide title="Los racimos">
Las celdas ocupadas forman tramos seguidos, los **racimos**. Una clave cuyo
hash cae en cualquier celda de un racimo recorre el resto del racimo y queda
al final, haciéndolo más largo: mientras más largo es un racimo, más claves
lo alcanzan y más rápido crece. Dos racimos que se tocan se funden en uno.

<Casilleros
  cells={['Pablo', null, null, null, null, 'Mia', 'Alba', 'Eva', null, null, 'Julia']}
  paint={{ 5: 'visited', 6: 'visited', 7: 'visited', 8: 'mark' }}
  caption="un racimo del 5 al 7; con dos claves más, se funde con el de «Julia» y «Pablo»"
  label="Once celdas con un racimo de tres claves seguidas, del 5 al 7: Mia, Alba y Eva. La celda 8 está destacada: ahí termina cualquier clave cuyo hash caiga entre el 5 y el 8. Julia, en el 10, y Pablo, en el 0, forman otro racimo, que da la vuelta al final del arreglo."
/>

$$
5 \le h(k) \le 8 \;\Longrightarrow\; k \text{ queda en el } 8
$$

Hay variantes que dispersan los saltos: el **sondeo cuadrático** prueba
$$h + 1, h + 4, h + 9, \ldots$$, y el **doble hashing** salta con un paso que
calcula una segunda función hash. Las dos rompen los racimos, a cambio de
una búsqueda menos simple. Las tres forman la familia del **direccionamiento
abierto** (en inglés, *open addressing*): todas guardan las claves en el
propio arreglo.

</Slide>

<Slide title="El costo del sondeo lineal">
Bajo el supuesto de dispersión uniforme, Knuth calculó cuántas celdas mira en
promedio una búsqueda:

$$
\text{si la clave está:}\quad \frac{1}{2}\left(1 + \frac{1}{1 - \alpha}\right)
\qquad\qquad
\text{si no está:}\quad \frac{1}{2}\left(1 + \frac{1}{(1 - \alpha)^2}\right)
$$

Con $$\alpha$$ cerca de 1, los racimos hacen crecer ese costo muy rápido.

| $$\alpha$$ | Celdas si la clave está | Celdas si no está |
| ---------- | ----------------------- | ----------------- |
| 0,5        | 1,5                     | 2,5               |
| 0,75       | 2,5                     | 8,5               |
| 0,9        | 5,5                     | 50,5              |

Con la redimensión, $$\alpha$$ no pasa de $$1/2$$, y una búsqueda mira en
promedio a lo más 2,5 celdas.

</Slide>

<Slide title="Costos de la tabla con sondeo lineal">
| Molde     | Operación       | Peor caso     | Esperado, con $$\alpha \le 1/2$$ | Invariante que restaura               |
| --------- | --------------- | ------------- | -------------------------------- | ------------------------------------- |
| consultar | `contains(key)` | $$\Theta(N)$$ | $$\Theta(1)$$                    | Ninguna: no cambia la tabla           |
| modificar | `add(key)`      | $$\Theta(N)$$ | $$\Theta(1)$$                    | La clave entra una vez, en la primera celda libre desde su hash; `size` sube |
| modificar | `remove(key)`   | $$\Theta(N)$$ | $$\Theta(1)$$                    | La clave queda marcada y su celda no se vacía; `size` baja |

</Slide>

<Slide title="Listas frente a sondeo lineal">
|                         | Listas                                   | Sondeo lineal                                 |
| ----------------------- | ---------------------------------------- | --------------------------------------------- |
| Memoria por clave       | Un nodo aparte, con una referencia       | Una celda del arreglo, y un `boolean`         |
| Dónde están las claves  | Repartidas por la memoria                | Seguidas en un arreglo, rápidas de recorrer   |
| Factor de carga         | A lo más 1, por la redimensión           | A lo más 1/2, por la redimensión, con las marcas |
| Eliminar                | Desenganchar el nodo                     | Marcar la celda                               |
| Peor caso               | $$\Theta(N)$$                            | $$\Theta(N)$$                                 |

Las dos dan $$\Theta(1)$$ esperado. El sondeo lineal ahorra objetos y
aprovecha que las celdas de un arreglo están seguidas en la memoria; las
listas toleran mejor una tabla llena y eliminan sin dejar rastro. Java y C++
usan listas; Python, Rust y Go usan variantes del sondeo.

</Slide>

## El peor caso de una tabla hash

<Slide title="Claves elegidas para colisionar">
El costo esperado de las dos tablas descansa en el supuesto de dispersión
uniforme, y ninguna función fija lo cumple con todos los conjuntos de claves:
como el universo de claves es mucho más grande que la tabla, a cada posición
le corresponden muchísimas claves. Si las que llegan son justo esas, todas
caen en la misma posición, y cada operación cuesta $$\Theta(N)$$.

<Listas
  chains={[[], [], ['Lucas', 'Carla', 'Leo', 'Ana'], [], [], [], []]}
  picked={2}
  caption="cuatro claves en la posición 2, y las otras seis posiciones vacías"
  label="Una tabla de siete posiciones con encadenamiento. De la posición 2, destacada, cuelga una lista de cuatro nodos: Lucas, Carla, Leo y Ana. Las otras seis posiciones guardan null."
/>

$$
h(\text{«Ana»}) = h(\text{«Leo»}) = h(\text{«Carla»}) = h(\text{«Lucas»}) = 2
$$

Con datos comunes eso casi nunca pasa, pero quien conoce la función puede
elegir esas claves a propósito. En 2011 se mostró que servidores web de varios
lenguajes dejaban de responder con una sola petición que traía miles de
parámetros con nombres elegidos para colisionar: guardarlos costaba
$$\Theta(N^2)$$ en total.

</Slide>

<Slide title="Listas que se vuelven árboles">
Una manera de defenderse es limitar el daño. Una lista larga se puede
reemplazar por un **árbol de búsqueda balanceado**, como un AVL: cuando la
lista de una posición pasa de cierto largo, sus claves se guardan en un árbol,
y buscar en esa posición cuesta $$O(\log N)$$ en lugar de $$\Theta(N)$$. Las
posiciones con pocas claves siguen siendo listas, que para dos o tres claves
son más baratas que un árbol.

Así lo hace la tabla hash de Java: en una tabla de al menos 64 posiciones, una
lista que llega a más de 8 nodos se vuelve un árbol rojo-negro, otro árbol de
búsqueda balanceado, y si vuelve a bajar a 6, el árbol vuelve a ser una lista.
El $$O(\log N)$$ se cumple con claves que se pueden comparar, como los
`String`.

</Slide>

<Slide title="Hashing universal">
La otra manera de defenderse es que nadie sepa qué función usa la tabla. El
**hashing universal** elige la función al azar, de una familia de funciones,
cada vez que se crea una tabla. Con listas, para cualquier conjunto de claves
—también uno elegido para dañar— la lista que recorre una operación tiene en
promedio a lo más $$1 + \alpha$$ claves, así que su costo esperado es
$$\Theta(1)$$: el azar está en la función, no en los datos. Es un resultado de
Carter y Wegman, que se cita sin demostrarlo. El sondeo lineal necesita
familias más exigentes, pero la idea es la misma.

Los lenguajes combinan las defensas. Python elige al azar, cada vez que
arranca un programa, una parte del cálculo del hash de los `String`. Java no
lo hace, y limita el daño con los árboles: aunque todas las claves caigan en
la misma posición, buscar cuesta $$O(\log N)$$ si se pueden comparar.

</Slide>

## Más allá de las tablas hash

<Slide title="Funciones hash fuera de las tablas">
Una función que resume un dato en un número sirve para más que ubicar claves,
y en cada uso pide otras cosas.

- **El dígito verificador del RUT** resume el número en un dígito, con una
  suma ponderada módulo 11: detecta un dígito mal copiado.
- **La verificación de un archivo descargado** compara su resumen —SHA-256, por
  ejemplo— con el que publica quien lo distribuye: si un solo bit cambió, el
  resumen es otro.
- **Las contraseñas** se guardan como el resumen de la contraseña, con un
  agregado al azar para cada usuario, y nunca la contraseña misma.

Las dos últimas usan funciones **criptográficas**, que piden lo contrario de
una tabla: que sea imposible en la práctica encontrar dos datos con el mismo
resumen, o el dato a partir de su resumen, aunque calcularla cueste más. Una
tabla solo pide que reparta parejo y sea barata.

</Slide>

<Slide title="El orden que la dispersión no guarda">
Una tabla hash responde si una clave está en tiempo constante esperado porque
la función reparte las claves por la tabla sin ninguna relación con su orden:
dos claves vecinas en el orden caen en posiciones que no tienen nada que ver.
Esa misma invariante
—cada clave en la posición de su hash— deja sin atajo cualquier pregunta sobre
el orden.

| Pregunta                          | Tabla hash             | Árbol de búsqueda balanceado |
| --------------------------------- | ---------------------- | ---------------------------- |
| ¿Está la clave?                   | $$\Theta(1)$$ esperado | $$O(\log N)$$                |
| La clave menor, o la mayor        | $$\Theta(N + M)$$      | $$O(\log N)$$                |
| La siguiente a una clave dada     | $$\Theta(N + M)$$      | $$O(\log N)$$                |
| Todas las claves, en orden        | $$\Theta(N \log N)$$   | $$\Theta(N)$$                |

Renunciar al orden abarata la pregunta «¿está?»; conservarlo, como hace un
árbol de búsqueda balanceado, responde todas las demás en $$O(\log N)$$ y cobra
ese mismo $$O(\log N)$$ por cada búsqueda.

</Slide>

## Lo que sigue

Una tabla hash y un árbol de búsqueda balanceado guardan el mismo conjunto de
claves y responden las mismas tres operaciones, a precios distintos. Los TDAs
**Set** y **Map** —este último con un valor junto a cada clave— formalizan el
contrato que las dos cumplen, y permiten compararlas como dos implementaciones
del mismo contrato para decidir cuándo usar cada una.
Ahí aparecen también las tablas hash de Java, `HashSet` y `HashMap`, y cómo
calcula Java el hash de una clave de cualquier tipo.
