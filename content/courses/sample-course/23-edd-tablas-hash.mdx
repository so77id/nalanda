# Estructuras de Datos Avanzadas · Tablas Hash

En el guardarropa de un teatro, cada abrigo se guarda con el nombre de su
dueño, y al terminar la función todos vuelven a la vez a pedir el suyo. Con
miles de abrigos, quien atiende no puede revisarlos uno por uno: necesita ir
directo al abrigo de cada nombre. Una **tabla hash** hace exactamente eso con
un conjunto de claves: buscar, agregar y sacar una clave cuesta, en promedio,
un tiempo que no crece con la cantidad de claves guardadas.

{/* Casilleros — the cloakroom drawn as the unit draws an array: a contiguous strip of cells, the index over each, a name or nothing inside. `paint` colours a cell as the widget does (focus: under the eye; visited: already looked at; found: the one looked for; mark: just written), `notes` writes a short mark over a cell — a visit order, a shift, a hash — and `struck` strikes a key through: the mark of a removed key in the probing table. File-local (add-a-course-document.md §6e-quater). */}

export function Casilleros({ cells, index, paint = {}, notes = {}, struck = [], caption, label, cell = 64 }) {
  const pad = 12;
  const noteY = 15;
  const indexY = 31;
  const cellY = 38;
  const cellH = 40;
  const stripW = cells.length * cell;
  const width = Math.max(2 * pad + stripW, caption ? caption.length * 6.6 + 24 : 0);
  const left = (width - stripW) / 2;
  const height = cellY + cellH + (caption ? 34 : 12);
  const fill = { focus: 'var(--color-surface)', visited: 'var(--color-sunk)', found: 'var(--color-keep-soft)', mark: 'var(--color-mark-soft)' };
  const stroke = { focus: 'var(--color-focus)', visited: 'var(--color-rule-strong)', found: 'var(--color-keep)', mark: 'var(--color-mark)' };
  // Painted cells last, so a strong outline is never drawn under its neighbour.
  const order = cells.map((_, i) => i).sort((a, b) => (paint[a] ? 1 : 0) - (paint[b] ? 1 : 0));
  return (
    <svg viewBox={`0 0 ${width} ${height}`} style={{ width: '100%', maxWidth: `${Math.round(width * 1.3)}px`, height: 'auto', display: 'block', margin: '0.4rem auto' }} role="img" aria-label={label}>
      {order.map((i) => {
        const p = paint[i];
        const x = left + i * cell;
        return (
          <g key={i}>
            {notes[i] ? (
              <text x={x + cell / 2} y={noteY} textAnchor="middle" fontSize="12" fontWeight="700" style={{ fill: 'var(--color-focus)' }}>{notes[i]}</text>
            ) : null}
            <text x={x + cell / 2} y={indexY} textAnchor="middle" fontSize="11" style={{ fill: 'var(--color-ink-faint)' }}>{index ? index[i] : i}</text>
            <rect x={x} y={cellY} width={cell} height={cellH} style={{ fill: p ? fill[p] : 'var(--color-surface)', stroke: p ? stroke[p] : 'var(--color-rule-strong)' }} strokeWidth={p && p !== 'visited' ? 2.4 : 1.2} />
            {cells[i] ? (
              <text x={x + cell / 2} y={cellY + cellH / 2 + 5} textAnchor="middle" fontSize="14" fontWeight="600" textDecoration={struck.includes(i) ? 'line-through' : undefined} style={{ fill: struck.includes(i) ? 'var(--color-ink-faint)' : 'var(--color-ink)' }}>{cells[i]}</text>
            ) : null}
          </g>
        );
      })}
      {caption ? (
        <text x={width / 2} y={height - 10} textAnchor="middle" fontSize="12" style={{ fill: 'var(--color-ink-soft)' }}>{caption}</text>
      ) : null}
    </svg>
  );
}

{/* Reparto — where a rule sends each key: the keys as chips in a row, the positions as a contiguous strip under them, one arrow per key down to its position. A position that receives two keys or more is painted `mark` and its count written under it: a collision. `contents` writes inside the cells (a coat already there) and `hit` paints one cell as found. File-local (§6e-quater). */}

export function Reparto({ keys, cells, index, contents = [], hit, caption, label, cell = 56, id }) {
  const pad = 12;
  const chipH = 28;
  const chipGap = 10;
  const chipW = keys.map((k) => Math.max(52, k.name.length * 8.4 + 18));
  const chipsW = chipW.reduce((a, b) => a + b, 0) + (keys.length - 1) * chipGap;
  const stripW = cells * cell;
  const width = Math.max(2 * pad + Math.max(chipsW, stripW), caption ? caption.length * 6.6 + 24 : 0);
  const stripLeft = (width - stripW) / 2;
  const chipsLeft = (width - chipsW) / 2;
  const chipY = pad;
  const cellY = chipY + chipH + 70;
  const cellH = 34;
  const height = cellY + cellH + 18 + (caption ? 30 : 8);
  const count = Array.from({ length: cells }, (_, c) => keys.filter((k) => k.to === c).length);
  const chipX = (k) => chipsLeft + chipW.slice(0, k).reduce((a, b) => a + b, 0) + k * chipGap;
  return (
    <svg viewBox={`0 0 ${width} ${height}`} style={{ width: '100%', maxWidth: `${Math.round(width * 1.3)}px`, height: 'auto', display: 'block', margin: '0.4rem auto' }} role="img" aria-label={label}>
      <defs>
        <marker id={`${id}-punta`} markerWidth="7" markerHeight="7" refX="6" refY="3.5" orient="auto">
          <path d="M0,0 L7,3.5 L0,7 z" style={{ fill: 'var(--color-ink-soft)' }} />
        </marker>
        <marker id={`${id}-punta-choque`} markerWidth="7" markerHeight="7" refX="6" refY="3.5" orient="auto">
          <path d="M0,0 L7,3.5 L0,7 z" style={{ fill: 'var(--color-mark)' }} />
        </marker>
      </defs>
      {keys.map((k, n) => {
        const clash = count[k.to] > 1;
        const x1 = chipX(n) + chipW[n] / 2;
        const x2 = stripLeft + k.to * cell + cell / 2;
        return (
          <line key={`a${n}`} x1={x1} y1={chipY + chipH} x2={x2} y2={cellY - 3} style={{ stroke: clash ? 'var(--color-mark)' : 'var(--color-ink-soft)' }} strokeWidth={clash ? 1.8 : 1.2} markerEnd={`url(#${id}-${clash ? 'punta-choque' : 'punta'})`} />
        );
      })}
      {keys.map((k, n) => (
        <g key={`k${n}`}>
          <rect x={chipX(n)} y={chipY} width={chipW[n]} height={chipH} rx="14" style={{ fill: 'var(--color-surface)', stroke: count[k.to] > 1 ? 'var(--color-mark)' : 'var(--color-rule-strong)' }} strokeWidth={count[k.to] > 1 ? 2 : 1.2} />
          <text x={chipX(n) + chipW[n] / 2} y={chipY + chipH / 2 + 5} textAnchor="middle" fontSize="13" fontWeight="600" style={{ fill: 'var(--color-ink)' }}>{k.name}</text>
        </g>
      ))}
      {Array.from({ length: cells }, (_, c) => {
        const clash = count[c] > 1;
        const found = hit === c;
        const x = stripLeft + c * cell;
        return (
          <g key={`c${c}`}>
            <rect x={x} y={cellY} width={cell} height={cellH} style={{ fill: found ? 'var(--color-keep-soft)' : clash ? 'var(--color-mark-soft)' : 'var(--color-surface)', stroke: found ? 'var(--color-keep)' : clash ? 'var(--color-mark)' : 'var(--color-rule-strong)' }} strokeWidth={found || clash ? 2.2 : 1.2} />
            {contents[c] ? (
              <text x={x + cell / 2} y={cellY + cellH / 2 + 5} textAnchor="middle" fontSize="13" fontWeight="600" style={{ fill: 'var(--color-ink)' }}>{contents[c]}</text>
            ) : null}
            <text x={x + cell / 2} y={cellY + cellH + 14} textAnchor="middle" fontSize="11" style={{ fill: 'var(--color-ink-faint)' }}>{index ? index[c] : c}</text>
            {clash ? (
              <text x={x + cell / 2} y={cellY + cellH / 2 + 5} textAnchor="middle" fontSize="13" fontWeight="700" style={{ fill: 'var(--color-mark)' }}>{`×${count[c]}`}</text>
            ) : null}
          </g>
        );
      })}
      {caption ? (
        <text x={width / 2} y={height - 8} textAnchor="middle" fontSize="12" style={{ fill: 'var(--color-ink-soft)' }}>{caption}</text>
      ) : null}
    </svg>
  );
}

<Slide title="Un guardarropa">
Un guardarropa guarda abrigos, y de cada abrigo importa una sola cosa: el
nombre de su dueño. Sobre ese conjunto de nombres se hacen tres operaciones:

- **guardar** el abrigo de un nombre nuevo;
- **buscar** si el abrigo de un nombre está;
- **retirar** el abrigo de un nombre.

El nombre es la **clave**: identifica a cada abrigo y es lo que se dice para
pedirlo. Dos abrigos nunca tienen la misma clave. Lo que interesa es cuánto
cuesta cada operación cuando hay $$N$$ abrigos guardados.

  cells={['Sara', 'Leo', 'Ana', 'Juan', 'Eva', 'Bea', null, null]}
  caption="un guardarropa de 8 casilleros con 6 abrigos"
  label="Ocho casilleros en fila, numerados del 0 al 7. Los seis primeros guardan los abrigos de Sara, Leo, Ana, Juan, Eva y Bea; los dos últimos están libres."
/>

</Slide>

<Slide title="Guardar sin orden">
La manera más simple de guardar un abrigo es usar cualquier casillero libre.
Guardar no mira a los demás abrigos y cuesta $$\Theta(1)$$.

Buscar un nombre, en cambio, obliga a revisar los casilleros uno por uno,
porque nada indica dónde quedó el abrigo. En el peor caso se revisan los
$$N$$: buscar cuesta $$\Theta(N)$$, y retirar también, porque empieza por
buscar.

<Casilleros
  cells={['Sara', 'Leo', 'Ana', 'Juan', 'Eva', 'Bea', null, null]}
  paint={{ 0: 'visited', 1: 'visited', 2: 'visited', 3: 'found' }}
  notes={{ 0: '1', 1: '2', 2: '3', 3: '4' }}
  caption="buscar «Juan»: se revisan los casilleros en orden, hasta el cuarto"
  label="Los mismos ocho casilleros. La búsqueda de Juan revisa el casillero 0, el 1 y el 2, sin encontrarlo, y lo encuentra en el 3, el cuarto revisado."
/>

</Slide>

<Slide title="Guardar en orden alfabético">
Si los abrigos se guardan en orden alfabético, buscar puede usar la
**búsqueda binaria**: se compara con el nombre del casillero del medio y se
descarta la mitad que no puede tener el buscado. Buscar cuesta
$$\Theta(\log N)$$.

<Casilleros
  cells={['Ana', 'Bea', 'Ema', 'Eva', 'Juan', 'Leo', 'Sara', 'Teo', null]}
  paint={{ 0: 'visited', 1: 'visited', 2: 'visited', 3: 'visited', 5: 'found' }}
  notes={{ 3: '1', 5: '2' }}
  caption="buscar «Leo»: «Eva» va antes, se descarta la mitad izquierda; el medio de la otra mitad es «Leo»"
  label="Nueve casilleros con Ana, Bea, Ema, Eva, Juan, Leo, Sara y Teo en orden alfabético, y el último libre. La búsqueda de Leo compara primero con Eva, en el casillero 3, descarta los casilleros 0 a 3, y después compara con Leo, en el 5, donde lo encuentra."
/>

Pero un abrigo nuevo tiene que entrar en su lugar, y todos los que van
después se corren un casillero. Guardar y retirar cuestan $$\Theta(N)$$.

<Casilleros
  cells={['Ana', 'Bea', 'Ema', 'Eva', 'Iván', 'Juan', 'Leo', 'Sara', 'Teo']}
  paint={{ 4: 'mark', 5: 'focus', 6: 'focus', 7: 'focus', 8: 'focus' }}
  notes={{ 5: '→', 6: '→', 7: '→', 8: '→' }}
  caption="guardar «Iván»: «Juan», «Leo», «Sara» y «Teo» se corren un casillero para hacerle lugar"
  label="Los mismos casilleros después de guardar a Iván en el casillero 4. Juan, Leo, Sara y Teo se corrieron un casillero a la derecha, del 4 al 5, del 5 al 6, del 6 al 7 y del 7 al 8."
/>

</Slide>

<Slide title="Fichas numeradas">
Muchos guardarropas lo resuelven de otra manera: al recibir un abrigo entregan
una **ficha numerada**, y el número de la ficha es el número del casillero.
Con la ficha en la mano, guardar, buscar y retirar son un solo paso: ir al
casillero de ese número.

<Reparto
  id="ficha"
  keys={[{ name: 'ficha 5', to: 5 }]}
  cells={8}
  contents={['Sara', 'Leo', 'Ana', 'Juan', 'Eva', 'Bea', null, null]}
  hit={5}
  caption="la ficha 5 lleva directo al casillero 5, sin mirar ningún otro"
  label="Una ficha con el número 5 y una flecha directa al casillero 5 de una fila de ocho, donde está el abrigo de Bea."
/>

Es el **acceso directo** de un arreglo: el elemento de una posición se lee en
un paso, $$\Theta(1)$$. Funciona por dos razones. La clave la elige el
guardarropa, y es un entero chico: hay un casillero para cada ficha posible.

</Slide>

<Slide title="Tres maneras de guardar">
| Guardarropa                 | Guardar          | Buscar             | Retirar          |
| --------------------------- | ---------------- | ------------------ | ---------------- |
| Sin orden                   | $$\Theta(1)$$    | $$\Theta(N)$$      | $$\Theta(N)$$    |
| En orden alfabético         | $$\Theta(N)$$    | $$\Theta(\log N)$$ | $$\Theta(N)$$    |
| Con fichas numeradas        | $$\Theta(1)$$    | $$\Theta(1)$$      | $$\Theta(1)$$    |

Un árbol de búsqueda balanceado también guardaría los nombres en orden, con
las tres operaciones en $$O(\log N)$$. Las fichas son más rápidas que
cualquier orden: no comparan claves, calculan dónde está cada abrigo.

</Slide>

<Slide title="Claves que no son posiciones">
La ficha no siempre es posible. Si cada persona pide su abrigo por su nombre,
la clave la trae el dueño y no la elige el guardarropa. Y un casillero por
cada nombre posible no cabe en ningún edificio: con solo cinco letras se
escriben $$26^5 = 11\,881\,376$$ nombres distintos, mientras que los abrigos
de una función son unos pocos miles.

Hace falta un arreglo de tamaño razonable, de $$M$$ casilleros, y una manera
de llegar desde el nombre a uno de ellos tan rápido como desde una ficha.

</Slide>

<Slide title="La función hash">
Una **función hash** es una regla que convierte cada clave $$k$$ en una
posición del arreglo, un entero $$h(k)$$ entre $$0$$ y $$M - 1$$. Para
guardar, buscar o retirar una clave, se calcula su posición y se va directo a
ese casillero, sin mirar los demás. El arreglo, junto con su función hash, es
una **tabla hash**.

<Reparto
  id="regla"
  keys={[{ name: 'Bea', to: 0 }, { name: 'Eva', to: 1 }, { name: 'Ana', to: 4 }, { name: 'Leo', to: 6 }]}
  cells={7}
  caption="una regla que lleva cada nombre a uno de 7 casilleros: h(«Ana») = 4"
  label="Cuatro nombres y siete casilleros numerados del 0 al 6. Una flecha lleva a Bea al casillero 0, a Eva al 1, a Ana al 4 y a Leo al 6."
/>

Calcular la posición tiene un costo, pero depende del largo de la clave, no de
cuántas claves hay en la tabla.

</Slide>

<Slide title="Casilleros por inicial">
La regla más simple usa la inicial del nombre: 26 casilleros, de la A a la Z.
Es fácil de calcular, pero falla de dos maneras. Dos nombres con la misma
inicial van al mismo casillero. Y las iniciales no se reparten parejo: unas
letras juntan muchos nombres mientras otras dejan sus casilleros vacíos.

<Slide title="Las colisiones">
Cuando dos claves distintas tienen la misma posición, **colisionan**. Ninguna
función hash evita las colisiones: hay muchas más claves posibles que
posiciones, y por el **principio del palomar** —si hay más palomas que nidos,
algún nido recibe al menos dos— algunas comparten casillero.

<Reparto
  id="choque"
  keys={[{ name: 'Bea', to: 0 }, { name: 'Eva', to: 1 }, { name: 'Ana', to: 4 }, { name: 'Leo', to: 6 }, { name: 'Sara', to: 4 }]}
  cells={7}
  caption="con 7 casilleros, h(«Sara») = 4, el casillero de «Ana»"
  label="Los cuatro nombres de antes y Sara, en siete casilleros. Sara va al casillero 4, el mismo de Ana: los dos colisionan."
/>

Lo que una buena función hash sí puede lograr es repartir las claves parejo,
de modo que cada casillero reciba más o menos la misma cantidad.

</Slide>

<Slide title="La paradoja del cumpleaños">
Las colisiones aparecen mucho antes de llenar la tabla. Si una función reparte
las claves al azar y parejo entre $$M$$ casilleros, la probabilidad de que
$$N$$ claves caigan todas en casilleros distintos es

$$
\left(1 - \frac{1}{M}\right)\left(1 - \frac{2}{M}\right)\cdots\left(1 - \frac{N - 1}{M}\right),
$$

y cae muy rápido. Es la cuenta que dice que, en un grupo de 23 personas, lo
más probable es que dos estén de cumpleaños el mismo día.

| Claves, con $$M = 365$$ | Probabilidad de al menos una colisión |
| ----------------------- | ------------------------------------- |
| 10                      | 12 %                                  |
| 23                      | 51 %                                  |
| 40                      | 89 %                                  |
| 57                      | 99 %                                  |

La primera colisión llega alrededor de $$\sqrt{M}$$ claves, muy lejos de
$$M$$. Una tabla hash tiene que contar con ellas: necesita una regla que
reparta las claves parejo, y una manera de guardar dos claves que caen en la
misma posición.

</Slide>

## Funciones hash

{/* Bits — integer keys written in binary, one cell per bit, the `low` lowest boxed: what `x mod 2^k` keeps. `notes` writes, beside each row, what the row's key gives under each M. File-local (§6e-quater). */}

export function Bits({ rows, low, label, caption }) {
  const bits = Math.max(...rows.map((r) => r.value.toString(2).length));
  const cw = 22;
  const ch = 28;
  const pad = 12;
  const labelW = 60;
  const noteW = 250;
  const top = 34;
  const width = pad + labelW + bits * cw + 18 + noteW + pad;
  const height = top + rows.length * (ch + 12) + (caption ? 28 : 6);
  const lowX = pad + labelW + (bits - low) * cw;
  return (
    <svg viewBox={`0 0 ${width} ${height}`} style={{ width: '100%', maxWidth: `${Math.round(width * 1.3)}px`, height: 'auto', display: 'block', margin: '0.4rem auto' }} role="img" aria-label={label}>
      <path d={`M ${lowX} ${top - 8} V ${top - 14} H ${lowX + low * cw} V ${top - 8}`} fill="none" style={{ stroke: 'var(--color-focus)' }} strokeWidth="1.6" />
      <text x={lowX + (low * cw) / 2} y={top - 19} textAnchor="middle" fontSize="12" fontWeight="700" style={{ fill: 'var(--color-focus)' }}>{`los ${low} bits bajos`}</text>
      {rows.map((r, n) => {
        const y = top + n * (ch + 12);
        const digits = r.value.toString(2).padStart(bits, '0').split('');
        return (
          <g key={r.value}>
            <text x={pad + labelW - 10} y={y + ch / 2 + 5} textAnchor="end" fontSize="14" fontWeight="600" style={{ fill: 'var(--color-ink)' }}>{r.value}</text>
            {digits.map((d, i) => {
              const isLow = i >= bits - low;
              return (
                <g key={i}>
                  <rect x={pad + labelW + i * cw} y={y} width={cw} height={ch} style={{ fill: isLow ? 'var(--color-sunk)' : 'var(--color-surface)', stroke: 'var(--color-rule-strong)' }} strokeWidth="1" />
                  <text x={pad + labelW + i * cw + cw / 2} y={y + ch / 2 + 5} textAnchor="middle" fontSize="13" fontFamily="var(--font-mono, monospace)" style={{ fill: 'var(--color-ink)' }}>{d}</text>
                </g>
              );
            })}
            <text x={pad + labelW + bits * cw + 18} y={y + ch / 2 + 5} fontSize="13" style={{ fill: 'var(--color-ink-soft)' }}>{r.note}</text>
          </g>
        );
      })}
      {caption ? (
        <text x={width / 2} y={height - 8} textAnchor="middle" fontSize="12" style={{ fill: 'var(--color-ink-soft)' }}>{caption}</text>
      ) : null}
    </svg>
  );
}

<Slide title="Tres requisitos de una función hash">
Una función hash sirve para una tabla si cumple tres requisitos.

1. **Es determinista.** La misma clave da siempre la misma posición. Si no,
   un abrigo guardado en un casillero se buscaría después en otro.
2. **Reparte parejo.** Las claves se distribuyen de manera uniforme entre las
   $$M$$ posiciones: cada posición recibe más o menos $$N / M$$ claves. Una
   regla que llena unas posiciones y deja otras vacías convierte la tabla en
   unas pocas filas largas.
3. **Es barata.** Calcularla cuesta poco, y no depende de cuántas claves hay
   en la tabla. Una regla que tarda más que revisar los casilleros no ahorra
   nada.

</Slide>

<Slide title="El método de la división">
Si la clave es un entero $$x$$, la regla más usada es el **método de la
división**: la posición es el resto de dividir por el tamaño de la tabla,

$$
h(x) = x \bmod M,
$$

que siempre es un entero entre $$0$$ y $$M - 1$$. Es determinista y se
calcula con una sola operación.

<Reparto
  id="division"
  keys={[{ name: '2024', to: 1 }, { name: '1985', to: 4 }, { name: '3141', to: 5 }, { name: '2718', to: 2 }]}
  cells={7}
  caption="con M = 7: 2024 mod 7 = 1, 1985 mod 7 = 4, 3141 mod 7 = 5, 2718 mod 7 = 2"
  label="Cuatro números y siete casilleros. 2024 va al casillero 1, 1985 al 4, 3141 al 5 y 2718 al 2: cada uno al resto de dividirlo por 7."
/>

</Slide>

<Slide title="Por qué M es primo">
Que el método reparta parejo depende de $$M$$. Si $$M$$ es una potencia de
2, $$M = 2^k$$, el resto de dividir por $$M$$ son exactamente los $$k$$ bits
más bajos de la clave: dos claves que terminan en los mismos $$k$$ bits
colisionan, aunque todo el resto sea distinto. Las claves reales suelen
repetir esos patrones —números pares, múltiplos de 4, folios que solo cambian
en sus cifras altas— y la tabla los hereda.

<Bits
  rows={[
    { value: 1482, note: 'mod 1024 = 458 · mod 1009 = 473' },
    { value: 7626, note: 'mod 1024 = 458 · mod 1009 = 563' },
  ]}
  low={10}
  caption="1024 = 2¹⁰ solo mira los 10 bits bajos, y ahí las dos claves son iguales; con 1009, primo, no colisionan"

Con un $$M$$ **primo**, y lejos de una potencia de 2, el resto depende de
todos los bits de la clave, y esos patrones se reparten.

</Slide>

<Slide title="De un texto a un número">
La clave de un guardarropa es un nombre, un texto, y el método de la división
necesita un entero. Cada carácter ya es un número —su código: `'A'` es 65,
`'n'` es 110, `'a'` es 97—, así que un texto se puede leer como un número
escrito en una base, con un carácter por cifra.

| Carácter de «Ana»   | `'A'`         | `'n'`        | `'a'`        | Número de «Ana» |
| ------------------- | ------------- | ------------ | ------------ | --------------- |
| Código              | 65            | 110          | 97           |                 |
| Peso, en base 256   | $$256^2$$     | $$256^1$$    | $$256^0$$    |                 |
| Aporte              | 4 259 840     | 28 160       | 97           | 4 288 097       |

El número crece muy rápido con el largo del texto: cada carácter lo multiplica
por la base. Un `int` de Java llega hasta $$2^{31} - 1 = 2\,147\,483\,647$$, y
cualquier nombre de cinco letras lo supera, porque su primera cifra ya pesa
$$256^4 = 2^{32}$$.

</Slide>

<Slide title="La regla de Horner">
El número de un texto $$c_0 c_1 \ldots c_{n-1}$$ en una base $$B$$ es

$$
c_0 \cdot B^{n-1} + c_1 \cdot B^{n-2} + \cdots + c_{n-1},
$$

y la **regla de Horner** lo calcula sin potencias, con una multiplicación y
una suma por carácter:

$$
\Big(\big(c_0 \cdot B + c_1\big) \cdot B + c_2\Big) \cdot B + \cdots + c_{n-1}.
$$

Como lo que la tabla necesita es ese número $$\bmod M$$, se puede reducir
$$\bmod M$$ en cada paso: el resultado es el mismo, y ningún paso pasa de
$$B \cdot M$$ más el código de un carácter. Con base 31 —un primo chico, la base que usa Java para los
`String`— cada paso es

$$
h = (31 \cdot h + c) \bmod M.
$$

| Paso | Carácter | Código | $$31 \cdot h + c$$     | $$h$$, con $$M = 7$$ |
| ---- | -------- | ------ | ---------------------- | -------------------- |
| 1    | `'A'`    | 65     | $$31 \cdot 0 + 65 = 65$$   | $$65 \bmod 7 = 2$$   |
| 2    | `'n'`    | 110    | $$31 \cdot 2 + 110 = 172$$ | $$172 \bmod 7 = 4$$  |
| 3    | `'a'`    | 97     | $$31 \cdot 4 + 97 = 221$$  | $$221 \bmod 7 = 4$$  |

</Slide>

<Slide title="El código de hash">
La regla de Horner, en un método de la tabla. `table.length` es $$M$$, y una
clave `null` no tiene posición: es un error, no una clave.

```java
private int hash(String key) {
    if (key == null) throw new IllegalArgumentException();
    int h = 0;
    for (int i = 0; i < key.length(); i++) {
        h = (31 * h + key.charAt(i)) % table.length;
    }
    return h;
}
```

Hace una multiplicación, una suma y un resto por carácter: cuesta
$$\Theta(L)$$, con $$L$$ el largo de la clave, y no depende de cuántas claves
hay en la tabla. Como $$h$$ siempre es menor que $$M$$, `31 * h + key.charAt(i)`
no se sale de un `int` para ningún tamaño de tabla razonable.

</Slide>

<Slide title="El método de la multiplicación">
Hay otra regla clásica para claves enteras, el **método de la
multiplicación**:

$$
h(x) = \big\lfloor M \cdot (A \cdot x \bmod 1) \big\rfloor,
$$

donde $$A$$ es una constante entre 0 y 1 y $$A \cdot x \bmod 1$$ es la parte
fraccionaria de $$A \cdot x$$. Knuth propone
$$A = (\sqrt{5} - 1)/2 \approx 0{,}618$$, el inverso de la razón áurea: con
ella, las partes fraccionarias de $$A$$, $$2A$$, $$3A, \ldots$$ se reparten
parejo en el intervalo entre 0 y 1. A diferencia de la división, funciona bien
con cualquier $$M$$, también con una potencia de 2.

</Slide>

<Slide title="Las invariantes de la tabla con listas">
1. **Ninguna clave está dos veces.** La tabla guarda un conjunto: agregar una
   clave que ya está no la duplica.
2. **`size` es la cantidad de nodos de todas las listas.** Es el $$N$$ de la
   tabla, y se mantiene sin recorrerla.
3. **Cada clave está en la lista de la posición `hash(key)`.** Es la
   invariante que hace barata la búsqueda: para saber si una clave está, basta
   mirar una sola lista.

La tercera es también la que cobra. La posición de una clave depende del
tamaño de la tabla, así que si la tabla cambia de tamaño, cada clave tiene que
moverse a la lista de su nueva posición.

</Slide>

<Slide title="Buscar en una tabla con listas">
Para buscar una clave se calcula su posición y se recorre solo la lista de esa
posición, comparando cada clave con la buscada. La búsqueda termina al
encontrarla o al llegar a `null`: por la invariante, la clave no puede estar
en ninguna otra lista.

Las claves son `String`, y se comparan con `equals`, que compara los
caracteres; `==` compararía las referencias.

}

<Slide title="El factor de carga">
El **factor de carga** de una tabla es

$$
\alpha = \frac{N}{M},
$$

la cantidad de claves por posición: en el guardarropa, cuántos abrigos cuelgan
en promedio de cada casillero. Si la función hash reparte parejo, cada clave
cae en cada posición con probabilidad $$1 / M$$, y una lista mide en promedio
$$N / M = \alpha$$ nodos.

  chains={TABLA}
  caption="N = 6 claves en M = 7 posiciones: α = 6/7 ≈ 0,86"
  label="La tabla de siete posiciones con seis claves: Bea, Juan, Eva, Sara, Ana y Leo. Su factor de carga es seis séptimos, casi 0,86."
/>

</Slide>

<Slide title="El costo esperado y el peor caso">
Buscar una clave que no está recorre una lista entera, y una que está recorre
en promedio la mitad. Si la función reparte parejo, las dos cuestan en
promedio $$\Theta(1 + \alpha)$$: calcular el hash más recorrer una lista de
largo esperado $$\alpha$$ (resultado que se cita, sin demostrarlo). Con
$$\alpha$$ acotado por una constante, eso es $$\Theta(1)$$.

Nada impide, sin embargo, el peor caso: si todas las claves caen en la misma
posición, la tabla es una sola lista, y buscar cuesta $$\Theta(N)$$.

<Slide title="Costos de la tabla con listas">
| Molde     | Operación                 | Peor caso     | Esperado               | Invariante que restaura                   |
| --------- | ------------------------- | ------------- | ---------------------- | ----------------------------------------- |
| crear     | `ChainedHashTable(M)`     | $$\Theta(M)$$ | $$\Theta(M)$$          | Listas vacías                             |
| consultar | `contains(key)`           | $$\Theta(N)$$ | $$\Theta(1 + \alpha)$$ | Ninguna: no cambia la tabla               |
| modificar | `add(key)`                | $$\Theta(N)$$ | $$\Theta(1 + \alpha)$$ | La clave, una vez, en la lista de su hash |
| modificar | `remove(key)`             | $$\Theta(N)$$ | $$\Theta(1 + \alpha)$$ | Las demás, en la lista de su hash         |

El peor caso de `add` es el de `contains`, que corre antes de enganchar. Con
$$M$$ fijo, $$\alpha$$ crece con cada clave que se agrega, y con él el costo
esperado: para que se mantenga constante, la tabla tiene que crecer con
$$N$$.

</Slide>

export function Agregados({ moves, total, caption, label }) {
  const pad = 14;
  const bw = 24;
  const unit = 7;
  const top = 26;

      <line x1={pad} y1={base} x2={width - pad} y2={base} style={{ stroke: 'var(--color-rule-strong)' }} strokeWidth="1" />

        const moved = moves[i] ?? 0;
        const h = (1 + moved) * unit;

              </g>

            ) : null}
          </g>

      })}

<Slide title="Una tabla que crece">
Con $$M$$ fijo, cada clave que se agrega sube el factor de carga
$$\alpha = N / M$$, y con él el largo esperado de las listas. Para que buscar
siga costando $$\Theta(1)$$ en promedio, la tabla tiene que crecer junto con
$$N$$: en el guardarropa, abrir más casilleros cuando los que hay se llenan.

La regla es redimensionar cuando hay tantas claves como posiciones, cuando
`size == table.length`, es decir, cuando $$\alpha$$ llega a 1: un abrigo por
casillero, en promedio. Así, $$\alpha$$ nunca pasa de 1.

</Slide>

<Slide title="Por qué cada clave cambia de posición">
La posición de una clave es el resto de dividir por $$M$$, así que al cambiar
$$M$$ cambia la posición de casi todas. Una tabla nueva no se llena copiando
las listas a las mismas posiciones: la invariante pide que cada clave esté en
la lista de **su** posición, y con el $$M$$ nuevo esa posición es otra. Cada
clave tiene que volver a entrar, con su hash recalculado.

| Clave  | $$h$$, con $$M = 3$$ | $$h$$, con $$M = 7$$ |
| ------ | -------------------- | -------------------- |
| «Ana»  | 2                    | 4                    |
| «Bea»  | 0                    | 0                    |
| «Eva»  | 2                    | 1                    |

</Slide>

<Slide title="El tamaño nuevo">
La tabla nueva tiene el primer primo desde $$2M$$: así el tamaño se mantiene
primo, como pide el método de la división, y casi se duplica. Duplicar sin más
daría un número par.

La búsqueda del primo es una función auxiliar que no lleva ninguna idea de la
tabla: prueba los números desde $$2M$$ hasta dar con uno sin divisores.

```java
private static int nextPrime(int n) {
    while (!isPrime(n)) {
        n++;
    }
    return n;
}

private static boolean isPrime(int n) {
    if (n < 2) return false;
    for (int d = 2; d * d <= n; d++) {
        if (n % d == 0) return false;
    }
    return true;
}
```

</Slide>

<Slide title="add con redimensión">
`add` gana una línea: antes de enganchar la clave nueva, si la tabla está
llena, la redimensiona.

```java
boolean add(String key) {
    if (contains(key)) return false;
    if (size == table.length) resize(nextPrime(2 * table.length));
    int i = hash(key);
    Node fresh = new Node(key);
    fresh.next = table[i];
    table[i] = fresh;
    size++;
    return true;
}
```

`resize` guarda la tabla vieja en `old`, crea el arreglo nuevo, pone `size` en
0 y recorre todas las listas de `old`, volviendo a agregar cada clave con
`add`. Mientras corre, las claves que todavía no vuelven a entrar están en la
lista de su posición vieja: la invariante se restaura clave por clave.

</Slide>

<Slide title="El costo de una redimensión">
Una redimensión recorre las $$M$$ posiciones de la tabla vieja y vuelve a
agregar sus $$N$$ claves, cada una en $$\Theta(1)$$ esperado, porque en la
tabla nueva $$\alpha$$ es cerca de $$1/2$$. Cuesta $$\Theta(N + M)$$, y como
redimensiona cuando $$N = M$$, $$\Theta(N)$$.

Es caro, pero raro. Después de redimensionar, el tamaño casi se duplicó, y
la próxima redimensión solo llega cuando se agregaron otras tantas claves.

</Slide>

<Slide title="El costo amortizado de add">
Repartido entre todas las inserciones, el costo de las redimensiones es
constante. Cada redimensión mueve las claves que hay en ese momento, y cada
una mueve al menos el doble que la anterior: si la última movió $$k$$ claves,
la anterior movió menos de $$k/2$$, la de antes menos de $$k/4$$, y así. En
total, al agregar $$N$$ claves se mueven menos de
$$N + N/2 + N/4 + \cdots < 2N$$, y cada `add` paga en promedio menos de dos
movimientos además del suyo: $$\Theta(1)$$ **amortizado**.

</Slide>

<Slide title="Costos con redimensión">
Con la redimensión, $$\alpha$$ no pasa de 1, y el costo esperado de las tres
operaciones es constante.

| Molde     | Operación       | Peor caso     | Esperado      | Amortizado                  |
| --------- | --------------- | ------------- | ------------- | --------------------------- |
| consultar | `contains(key)` | $$\Theta(N)$$ | $$\Theta(1)$$ | $$\Theta(1)$$               |
| modificar | `add(key)`      | $$\Theta(N)$$ | $$\Theta(1)$$ | <span style={{ color: 'var(--color-keep)', fontWeight: 700 }}>$$\Theta(1)$$, con redimensión</span> |
| modificar | `remove(key)`   | $$\Theta(N)$$ | $$\Theta(1)$$ | $$\Theta(1)$$               |

Las tres son $$\Theta(1)$$ en promedio, pero las listas tienen un precio que
el costo no muestra: una referencia y un objeto aparte por cada clave, que el
programa tiene que ir a buscar a otro lugar de la memoria. La otra manera de
resolver las colisiones guarda las claves en el propio arreglo.

</Slide>

## Sondeo lineal

export const SONDEO = ['Tomas', null, null, null, 'Leo', 'Ana', 'Bea', null, null, null, 'Olga'];

<Slide title="Un abrigo por casillero">
La otra manera de resolver las colisiones no usa listas: cada casillero guarda
a lo más una clave, y todas viven en el propio arreglo. Si el casillero que
indica el hash está ocupado, la clave prueba el siguiente, y el siguiente,
hasta dar con uno libre; después del último viene el primero. En el
guardarropa, si el casillero de un abrigo está ocupado, se cuelga en el
próximo libre.

A esta forma de resolver las colisiones se le llama **sondeo lineal**, y
necesita que haya siempre más casilleros que claves: $$N < M$$, es decir,
$$\alpha < 1$$.

</Slide>

<Slide title="Las invariantes del sondeo lineal">
1. **Ninguna clave está dos veces.** Como en la tabla con listas, la tabla
   guarda un conjunto.
2. **Siempre queda al menos una celda vacía.** Es lo que garantiza que una
   búsqueda termine aunque la clave no esté.
3. **Entre la posición `hash(key)` y la celda de `key` no hay ninguna celda
   vacía.** Una clave queda en la primera celda libre desde su hash, así que
   todas las anteriores estaban ocupadas cuando entró.

La tercera es la que hace correcta la búsqueda: al llegar a una celda vacía,
la clave buscada no puede estar más allá. Y es también la que cobra: una
celda ocupada no se puede volver a vaciar sin romperla.

</Slide>

<Slide title="La clase de la tabla con sondeo lineal">
Las claves se guardan en un arreglo de `String`, `null` donde no hay ninguna.
Junto a él, un arreglo `deleted` del mismo largo marca las claves eliminadas.
`hash(String key)` es la misma regla de Horner, con `keys.length` como
$$M$$. Con una sola posición no quedaría ninguna vacía.

```java
class ProbingHashTable {
    private String[] keys;
    private boolean[] deleted;
    private int size;

    ProbingHashTable(int capacity) {
        if (capacity < 2) throw new IllegalArgumentException();
        keys = new String[capacity];
        deleted = new boolean[capacity];
    }
}
```

</Slide>

<Slide title="Buscar con sondeo lineal">
Para buscar una clave se empieza en la celda de su hash y se avanza de a una,
dando la vuelta al final del arreglo, hasta encontrarla o llegar a una celda
vacía. Por la invariante, la clave no puede estar después de esa celda vacía.

<Slide title="Los racimos">
Las celdas ocupadas forman tramos seguidos, los **racimos**. Una clave cuyo
hash cae en cualquier celda de un racimo recorre el resto del racimo y queda
al final, haciéndolo más largo: mientras más largo es un racimo, más claves
lo alcanzan y más rápido crece. Dos racimos que se tocan se funden en uno.

Hay variantes que dispersan los saltos: el **sondeo cuadrático** prueba
$$h + 1, h + 4, h + 9, \ldots$$, y el **doble hashing** salta con un paso que
calcula una segunda función hash. Las dos rompen los racimos, a cambio de
una búsqueda menos simple.

</Slide>

<Slide title="El costo del sondeo lineal">
Si la función reparte parejo, Knuth calculó cuántas celdas mira en promedio
una búsqueda (resultado que se cita, sin demostrarlo):

$$
\text{si la clave está:}\quad \frac{1}{2}\left(1 + \frac{1}{1 - \alpha}\right)
\qquad\qquad
\text{si no está:}\quad \frac{1}{2}\left(1 + \frac{1}{(1 - \alpha)^2}\right)
$$

Con $$\alpha$$ cerca de 1, los racimos hacen crecer ese costo muy rápido.

| $$\alpha$$ | Celdas si la clave está | Celdas si no está |
| ---------- | ----------------------- | ----------------- |
| 0,5        | 1,5                     | 2,5               |
| 0,75       | 2,5                     | 8,5               |
| 0,9        | 5,5                     | 50,5              |

</Slide>

<Slide title="Costos de la tabla con sondeo lineal">
La tabla se redimensiona antes de que $$\alpha$$ pase de $$1/2$$, contando
también las celdas marcadas, que ocupan lugar igual que una clave. Al volver a
agregar las claves en la tabla nueva, las marcas desaparecen.

| Molde     | Operación       | Peor caso     | Esperado, con $$\alpha \le 1/2$$ | Invariante que restaura               |
| --------- | --------------- | ------------- | -------------------------------- | ------------------------------------- |
| consultar | `contains(key)` | $$\Theta(N)$$ | $$\Theta(1)$$                    | Ninguna: no cambia la tabla           |
| modificar | `add(key)`      | $$\Theta(N)$$ | $$\Theta(1)$$                    | Ninguna celda vacía antes de la nueva |
| modificar | `remove(key)`   | $$\Theta(N)$$ | $$\Theta(1)$$                    | La celda queda ocupada, con su marca  |

</Slide>

<Slide title="Listas frente a sondeo lineal">
|                         | Listas                                   | Sondeo lineal                                 |
| ----------------------- | ---------------------------------------- | --------------------------------------------- |
| Memoria por clave       | Un nodo aparte, con una referencia       | Una celda del arreglo, y un `boolean`         |
| Dónde están las claves  | Repartidas por la memoria                | Seguidas en un arreglo, rápidas de recorrer   |
| Factor de carga         | Puede pasar de 1                         | Menor que 1; en la práctica, a lo más 1/2     |
| Eliminar                | Desenganchar el nodo                     | Marcar la celda                               |
| Peor caso               | $$\Theta(N)$$                            | $$\Theta(N)$$                                 |

Las dos dan $$\Theta(1)$$ esperado. El sondeo lineal ahorra objetos y
aprovecha que las celdas de un arreglo están seguidas en la memoria; las
listas toleran mejor una tabla llena y eliminan sin dejar rastro. Las dos,
tal como están escritas, solo guardan claves `String`.

</Slide>

## Una tabla para cualquier clave

<Slide title="Claves que son objetos">
Las dos tablas guardan claves `String`. Para guardar claves de cualquier tipo
—personas, puntos, fechas— la tabla necesita dos cosas de cada clave: un
número para calcular su posición, y una manera de decidir si dos claves son la
misma. Java se las da a todo objeto: los métodos `hashCode()` y
`equals(Object)`, que toda clase hereda de `Object`.

La tabla usa `hashCode()` en lugar de su propio ciclo, y `equals` para
comparar, como ya hacía con los `String`. El `hashCode()` de un `String` es la
misma regla de Horner con 31, sin reducir: en un texto largo el `int` se
desborda y puede quedar negativo. Y en Java el resto de un número negativo es
negativo, así que la posición se calcula con `Math.floorMod`, que siempre da
un resultado entre 0 y $$M - 1$$.

| Clave              | `hashCode()`   | `hashCode() % 7` | `Math.floorMod(hashCode(), 7)` |
| ------------------ | -------------- | ---------------- | ------------------------------ |
| «Ana»              | 65 972         | 4                | 4                              |
| «Constantinopla»   | −324 698 497   | −4               | 3                              |

</Slide>

<Slide title="La tabla genérica">
Con un tipo `T` para las claves, el nodo pasa a ser `Node<T>`, con un campo
`T key`, y `hash` deja el ciclo de Horner en manos de `hashCode()`. Un arreglo
de un tipo genérico no se puede crear directamente: se crea un arreglo de
`Node` y se convierte.

```java
class ChainedHashTable<T> {
    private Node<T>[] table;
    private int size;

    ChainedHashTable(int capacity) {
        if (capacity < 1) throw new IllegalArgumentException();
        table = (Node<T>[]) new Node[capacity];
    }

    private int hash(T key) {
        if (key == null) throw new IllegalArgumentException();
        return Math.floorMod(key.hashCode(), table.length);
    }
}
```

`contains`, `add` y `remove` no cambian: solo reciben un `T` en lugar de un
`String`, y siguen comparando con `equals`.

</Slide>

<Slide title="El contrato entre hashCode y equals">
La tabla busca una clave en la lista de **su** posición, y dentro de ella
compara con `equals`. Para que eso funcione, `hashCode` y `equals` tienen que
cumplir un contrato:

> si `a.equals(b)`, entonces `a.hashCode() == b.hashCode()`.

Dos claves iguales tienen que ir a la misma posición, o la búsqueda de una
mira la lista equivocada y no encuentra la otra. Lo inverso no es necesario:
dos claves distintas pueden tener el mismo `hashCode`, y eso es solo una
colisión, que la tabla ya sabe resolver.

</Slide>

<Slide title="Un contrato roto">
Una `Persona` cuya igualdad es el RUT sobrescribe `equals`, pero si no
sobrescribe `hashCode`, hereda el de `Object`, que depende de cada objeto en
memoria. Dos personas iguales tienen entonces `hashCode` distintos: caen en
listas distintas, y `contains` busca en la que no es.

<Reparto
  id="contrato"
  keys={[{ name: 'Ana · 12345, agregada', to: 2 }, { name: 'Ana · 12345, buscada', to: 5 }]}
  cells={7}

El error no se ve al compilar ni al ejecutar: la tabla simplemente responde
que la clave no está. Una clase que sobrescribe `equals` sobrescribe
también `hashCode`.

</Slide>

<Slide title="Escribir hashCode">
`hashCode` combina los mismos campos que compara `equals`, con la misma regla
de Horner: cada campo multiplica lo anterior por 31 y suma su propio valor.
Para un `Punto` con campos `x` e `y`:

```java
@Override
public boolean equals(Object o) {
    if (!(o instanceof Punto)) return false;
    Punto p = (Punto) o;
    return x == p.x && y == p.y;
}

@Override
public int hashCode() {
    return 31 * x + y;
}
```

Dos puntos iguales tienen los mismos `x` e `y`, y por lo tanto el mismo
`hashCode`. `Objects.hash(x, y)`, de `java.util.Objects`, hace la misma
cuenta con cualquier cantidad de campos, y un `record` trae `equals` y
`hashCode` ya escritos con todos sus campos.

</Slide>

<Slide title="Claves que cambian">
Si una clave cambia después de agregarse, cambia también su `hashCode`. La
clave sigue en la lista de la posición que tenía al entrar, pero una búsqueda
la busca en la posición nueva: la tabla la pierde, y ni ella misma ni una
igual a la original se encuentran.

<Reparto

Por eso las claves de una tabla hash son **inmutables**: `String`, `Integer`,
un `record`, o una clase cuyos campos son `final`. Las tablas de la biblioteca
de Java funcionan exactamente así: piden las claves con `hashCode` y
`equals`, y confían en ese contrato.

</Slide>

## Las tablas hash de Java

<Slide title="La clase HashSet">
`java.util.HashSet<E>` es una tabla hash de claves de cualquier tipo, con las
mismas tres operaciones: `add`, `contains` y `remove`, que devuelven
`boolean` como las de la tabla con listas, más `size`.

```java
Set<String> guardarropa = new HashSet<>();
guardarropa.add("Ana");
guardarropa.add("Sara");
guardarropa.add("Ana");                         // false: ya estaba
System.out.println(guardarropa.contains("Sara")); // true
guardarropa.remove("Sara");
System.out.println(guardarropa.size());           // 1
```

Por dentro, un `HashSet` es un `HashMap` —una tabla que guarda junto a cada
clave un valor— en el que todas las claves comparten un mismo valor que nadie
lee.

</Slide>

<Slide title="Por dentro de HashMap">
`HashMap` resuelve las colisiones con **listas**, como la tabla con listas, y
elige otro tamaño: una potencia de 2, que empieza en 16 y se duplica cuando el
factor de carga pasa de **0,75**. Con $$M = 2^k$$, la posición es
`hash & (M - 1)`: los $$k$$ bits bajos del hash, que se calculan más rápido
que un resto.

Usar solo los bits bajos es justo lo que hace mala una potencia de 2: dos
claves que difieren solo en sus bits altos colisionan. Por eso `HashMap` no
usa `hashCode()` directamente, sino que antes lo mezcla, combinando sus 16
bits altos con los 16 bajos:

```java
h ^ (h >>> 16)
```

Así, los bits altos de la clave también deciden su posición.

</Slide>

<Slide title="Listas que se vuelven árboles">
Si muchas claves caen en la misma posición, su lista se vuelve larga y
buscar en ella cuesta $$\Theta(N)$$. `HashMap` se defiende: cuando una lista
llega a más de 8 nodos y la tabla tiene al menos 64 posiciones, convierte esa
lista en un **árbol rojo-negro**, un árbol de búsqueda balanceado. Si la
tabla es más chica, en cambio, la duplica, para repartir la lista.

Con claves comparables, como `String`, buscar en esa posición pasa a costar
$$O(\log N)$$ en lugar de $$\Theta(N)$$. Si la lista vuelve a bajar a 6 nodos,
el árbol vuelve a ser una lista.

</Slide>

<Slide title="Cuándo se rompe el costo esperado">
El $$\Theta(1)$$ esperado descansa en un supuesto: que la función hash reparte
las claves parejo, como si las repartiera al azar. Es un supuesto sobre los
datos, no una garantía, y hay cinco maneras de romperlo:

1. **Una función hash pobre**, como la inicial del nombre, que junta las claves
   en pocas posiciones.
2. **Claves elegidas por un adversario.** Quien conoce la función puede elegir
   claves que caigan todas en la misma posición. En 2011 se mostró que
   servidores web de varios lenguajes se caían con una sola petición que
   traía miles de parámetros con nombres elegidos para colisionar.
3. **Un factor de carga que crece** sin redimensionar.
4. **Claves que cambian** después de agregarse.
5. **Un contrato roto** entre `hashCode` y `equals`.

</Slide>

<Slide title="Universal hashing">
Contra el adversario, la defensa es que no sepa qué función se usa. El
**universal hashing** elige la función al azar, de una familia de funciones,
al crear la tabla. Para cualquier conjunto de claves —también uno elegido para
dañar— el costo esperado de cada operación es $$\Theta(1)$$, porque el azar
está en la función y no en los datos (resultado de Carter y Wegman, que se
cita sin demostrarlo).

Los lenguajes combinan las defensas. Python elige al azar, cada vez que
arranca un programa, una parte del cálculo del hash de los `String`. Java no
lo hace, y limita el daño con los árboles: aunque todas las claves caigan en
la misma posición, buscar cuesta $$O(\log N)$$ si son comparables.

</Slide>

<Slide title="Costos de HashSet">
| Operación       | Esperado      | Peor caso, claves comparables | Peor caso, claves no comparables |
| --------------- | ------------- | ----------------------------- | -------------------------------- |
| `add(x)`        | $$\Theta(1)$$ amortizado | $$O(\log N)$$      | $$\Theta(N)$$                    |
| `contains(x)`   | $$\Theta(1)$$ | $$O(\log N)$$                 | $$\Theta(N)$$                    |
| `remove(x)`     | $$\Theta(1)$$ | $$O(\log N)$$                 | $$\Theta(N)$$                    |
| `size()`        | $$\Theta(1)$$ | $$\Theta(1)$$                 | $$\Theta(1)$$                    |

El esperado es el de una tabla con un factor de carga acotado, y el peor caso
el de una posición donde caen todas las claves, ya convertida en árbol.

</Slide>

<Slide title="Otras tablas, otras decisiones">
Cada biblioteca elige su manera de resolver las colisiones según lo que más le
cuesta.

| Lenguaje | Tabla                       | Colisiones                                           |
| -------- | --------------------------- | ---------------------------------------------------- |
| Java     | `HashMap`, `HashSet`        | Listas, que se vuelven árboles si crecen             |
| C++      | `std::unordered_map`        | Listas                                               |
| Python   | `dict`, `set`               | Sondeo, con saltos que no son de a una celda         |
| Rust     | `HashMap`                   | Sondeo, en una tabla que revisa varias celdas a la vez |
| Go       | `map`                       | Sondeo, desde la versión 1.24; antes, listas         |

Las listas convienen cuando cada clave ya es un objeto aparte en la memoria;
el sondeo, cuando las claves caben en el arreglo y recorrer celdas seguidas es
lo más rápido que puede hacer el procesador. No hay una respuesta única.

</Slide>

<Slide title="Funciones hash fuera de las tablas">
Una función que resume un dato en un número sirve para más que ubicar claves,
y en cada uso pide otras cosas.

- **El dígito verificador del RUT** resume el número en un dígito, con una
  suma ponderada módulo 11: detecta un dígito mal copiado.
- **La verificación de un archivo descargado** compara su resumen —SHA-256, por
  ejemplo— con el que publica quien lo distribuye: si un solo bit cambió, el
  resumen es otro.
- **Las contraseñas** se guardan como el resumen de la contraseña, con un
  agregado al azar para cada usuario, y nunca la contraseña misma.

Las dos últimas usan funciones **criptográficas**, que piden lo contrario de
una tabla: que sea imposible en la práctica encontrar dos datos con el mismo
resumen, o el dato a partir de su resumen, aunque calcularla cueste más. Una
tabla solo pide que reparta parejo y sea barata.

</Slide>

<Slide title="El orden que la dispersión no guarda">
Una tabla hash responde si una clave está en tiempo constante esperado porque
la función reparte las claves por la tabla sin ninguna relación con su orden:
dos claves vecinas en el orden caen en posiciones que no tienen nada que ver.
Esa misma invariante
—cada clave en la posición de su hash— deja sin atajo cualquier pregunta sobre
el orden.

| Pregunta                          | Tabla hash             | Árbol de búsqueda balanceado |
| --------------------------------- | ---------------------- | ---------------------------- |
| ¿Está la clave?                   | $$\Theta(1)$$ esperado | $$O(\log N)$$                |
| La clave menor, o la mayor        | $$\Theta(N + M)$$      | $$O(\log N)$$                |
| La siguiente a una clave dada     | $$\Theta(N + M)$$      | $$O(\log N)$$                |
| Todas las claves, en orden        | $$\Theta(N \log N)$$   | $$\Theta(N)$$                |

Renunciar al orden abarata la pregunta «¿está?»; conservarlo, como hace un
árbol de búsqueda balanceado, responde todas las demás en $$O(\log N)$$ y cobra
ese mismo $$O(\log N)$$ por cada búsqueda.

</Slide>

## Lo que sigue

Una tabla hash y un árbol de búsqueda balanceado guardan el mismo conjunto de
claves y responden las mismas tres operaciones, a precios distintos. La
próxima clase formaliza el contrato que las dos cumplen —los TDAs **Set** y
**Map**, este último con un valor junto a cada clave— y las compara como dos
implementaciones del mismo contrato, para decidir cuándo usar cada una.
