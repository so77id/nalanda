# Estructuras de Datos · Introducción

Hasta aquí estudiamos **algoritmos**: cómo resolver un problema y
cuánto cuesta resolverlo. Desde aquí estudiamos **dónde viven los
datos** sobre los que esos algoritmos trabajan.

Esta clase abre la unidad con tres palabras — **TDA**, **estructura de
datos** e **invariante** —, formaliza el arreglo que ya conocemos,
lo hace crecer hasta el arreglo dinámico y cierra con el contrato que
ambos cumplen.

<SectionBreak />

## Vocabulario · TDA, EDA e invariante

<Slide title="Del algoritmo al dato">
Un algoritmo describe **qué hacemos** con los datos. Una estructura de
datos describe **cómo están guardados** para que ese "qué" sea posible
— y barato.

Los dos lados se necesitan. La búsqueda binaria de
[[diseno-algoritmos-divide-y-venceras|Divide y Conquista]] cuesta
$$\Theta(\log N)$$ solamente si llegar a la posición `i` cuesta
$$\Theta(1)$$. Sobre los mismos datos guardados de otra manera, el
mismo algoritmo es lento, o directamente imposible.

Hasta aquí estudiamos el primer lado. Esta unidad estudia el segundo:
qué organizaciones de datos existen, qué operaciones ofrece cada una,
y cuánto cuesta cada operación.

Empezamos por el vocabulario, porque las tres palabras que siguen se
usan en todas las clases de la unidad.

</Slide>

<Slide title="Tipo de dato abstracto · el contrato">
Un **tipo de dato abstracto** (TDA) es un **contrato**: la lista de
operaciones que una colección ofrece, con el significado de cada una,
y sin decir nada sobre cómo están guardados los elementos.

> La interfaz es una **especificación** — el problema. La estructura de
> datos es una **representación** — la solución.
>
> — Erik Demaine, *MIT 6.006 · Introduction to Algorithms*, 2020
> ("interface is a specification — the problem; data structure is a
> representation — the solution")

Un TDA se lee entero sin abrir ningún archivo de implementación. Dice
**qué se puede pedir**, nunca **cómo se responde**.

El contrato más pequeño que ya conocemos es
[[diseno-algoritmos-ordenamiento|`Comparable`]]: una sola operación,
un significado preciso, y ninguna palabra sobre representación.

```java
public interface Comparable<T> {
    // Negativo si this va antes que o, cero si van en la misma
    // posición del orden, positivo si this va después.
    int compareTo(T o);
}
```

Ningún algoritmo de ordenamiento pregunta cómo está implementado
`compareTo`. Le basta el contrato.

</Slide>

<Slide title="Estructura de datos · la representación">
Una **estructura de datos** (EDA) es una **representación**: la manera
concreta de guardar los elementos en memoria, más los algoritmos que
implementan cada operación del contrato.

Donde el TDA dice _"se puede pedir el elemento de la posición `i`"_, la
EDA dice _"los elementos están en posiciones consecutivas de memoria, y
el elemento `i` está en `base + i × tamaño`"_.

De ahí sale la afirmación que ordena toda la unidad:

**Un TDA admite muchas EDA, y cada una tiene costos distintos.**

Elegir entre ellas es el trabajo de ingeniería: el contrato ya está
decidido por el problema, y lo que queda por decidir es cuál
representación tiene baratas justamente las operaciones que el programa
va a pedir más veces. La misma elección aparece en cada clase de esta
unidad.

</Slide>

<Slide title="Invariante · la propiedad que se preserva">
Un **invariante** es una propiedad que se cumple **antes y después de
cada operación**. Adentro de una operación puede romperse; cuando la
operación termina, vuelve a valer.

El invariante es lo que hace que una operación sea correcta sin
revisar todo el dato: si la propiedad valía al empezar y la operación
la restaura al terminar, cada operación siguiente puede confiar en
ella.

Dos invariantes que ya usamos, aunque no los llamamos así:

**Búsqueda binaria** — _si `t` está en el arreglo, está en
`a[lo..hi]`_. Cada iteración achica el rango a la mitad y vuelve a
dejar el invariante en pie; por eso descartar media entrada no pierde
la respuesta.

```java
static int bs(int[] a, int lo, int hi, int t) {
    if (lo > hi) return -1;              // rango vacío: t no está
    int mid = (lo + hi) / 2;
    if (a[mid] == t) return mid;
    if (t < a[mid]) return bs(a, lo, mid - 1, t);
    return bs(a, mid + 1, hi, t);
}
```

**Partición de quicksort** — _en `a[lo..store-1]` todo es menor que el
pivote, y en `a[store..j-1]` todo es mayor o igual_. La operación lo
mantiene en cada vuelta del bucle, y por eso al terminar el pivote
queda en su posición definitiva.

```java
static int partition(int[] a, int lo, int hi) {
    int pivote = a[lo];
    swap(a, lo, hi);
    int store = lo;
    for (int j = lo; j < hi; j++) {
        // a[lo..store-1] < pivote  y  a[store..j-1] >= pivote
        if (a[j] < pivote) { swap(a, store, j); store++; }
    }
    swap(a, store, hi);
    return store;
}
```

</Slide>

<Slide title="Contrato, representación e invariante">
Las tres palabras describen tres capas distintas del mismo objeto, y se
encadenan en una sola dirección:

1. El **TDA** fija las operaciones y su significado.
2. Una **EDA** elige una representación e implementa esas operaciones.
3. Los **invariantes** de esa representación son lo que hace que las
   implementaciones sean correctas y tengan el costo que declaran.

La dependencia va hacia abajo y no hacia arriba. El TDA no sabe nada de
los invariantes; los invariantes son asunto privado de cada
representación. Dos estructuras que cumplen el mismo contrato pueden
mantener invariantes completamente distintos, y esa es exactamente la
libertad que las hace tener costos distintos.

Por eso, en el resto de la unidad, cada estructura se presenta en el
mismo orden: primero la idea, después los invariantes, después las
operaciones con su costo, después las limitaciones.

</Slide>

<Slide title="El vocabulario, en una tabla">
| Palabra | Qué es | Responde a | Ejemplo conocido |
|---|---|---|---|
| **TDA** | Un contrato | ¿Qué operaciones ofrece? | `Comparable`, con `compareTo` |
| **Estructura de datos** | Una representación | ¿Cómo están guardados los elementos? | El arreglo, en memoria consecutiva |
| **Invariante** | Una propiedad preservada | ¿Qué sigue valiendo entre operaciones? | Si `t` está, está en `a[lo..hi]` |

Las tres palabras vuelven a aparecer, nombradas, en cada estructura de
la unidad. El costo de una operación siempre se lee junto al invariante
que esa operación tiene que restaurar: cuando una operación es cara, la
razón es casi siempre el trabajo de dejar el invariante en pie.

</Slide>

## La EDA Arreglo

<Slide title="El arreglo, ahora como estructura de datos">
El arreglo de [[arrays-y-funciones|Arreglos y funciones]] es la
representación más directa que existe: los elementos están en
**posiciones consecutivas de memoria**, todas del mismo tamaño.

Esa decisión de representación da la propiedad que hace famoso al
arreglo. Para llegar al elemento `i` no hay que recorrer nada:

$$
\text{dirección}(i) = \text{base} + i \times \text{tamaño del elemento}
$$

Una multiplicación y una suma, sin importar si `i` es 3 o 3 millones.
El acceso cuesta $$\Theta(1)$$ y esa es la razón por la que la búsqueda
binaria puede ser $$\Theta(\log N)$$.

Un arreglo de Java, sin embargo, no es todavía un contenedor: `datos.length`
dice cuántas casillas se reservaron, no cuántas están usadas. La
estructura que estudiamos aquí es el arreglo **más un entero**:

```java
class Arreglo {
    private int[] datos;  // la representación: N casillas consecutivas
    private int size;     // cuántas de esas casillas son válidas

    Arreglo(int capacidad) {
        datos = new int[capacidad];
        size = 0;
    }
}
```

`datos.length` es la **capacidad** — casillas reservadas. `size` es el
**largo** — casillas ocupadas. Los dos números son distintos, y la
distancia entre ellos es de lo que trata el resto de la clase.

</Slide>

<Slide title="Los invariantes del arreglo">
Tres propiedades se cumplen antes y después de cada operación. Ninguna
está escrita en el lenguaje: son responsabilidad de la estructura.

1. **`0 ≤ size ≤ datos.length`.** El largo nunca es negativo y nunca
   supera la capacidad reservada. Si esta propiedad se rompe, cualquier
   recorrido sale del arreglo.
2. **Los elementos del contenedor son exactamente `datos[0..size-1]`.**
   Están juntos y empiezan en la posición 0: no hay huecos en el medio.
   Esta propiedad es la que permite recorrer con un `for` de `0` a
   `size - 1` y no revisar nada más.
3. **`datos[size..datos.length-1]` es basura.** Esas casillas existen y
   tienen algún valor — el cero por omisión, o un elemento borrado que
   quedó ahí —, pero no pertenecen al contenedor y no se leen nunca.

La segunda propiedad es la cara y la barata al mismo tiempo. Es barata
porque hace que el acceso sea aritmética pura. Es cara porque cualquier
operación que agregue o quite un elemento del medio tiene que volver a
dejar todo junto antes de terminar, y "volver a dejar todo junto"
significa mover elementos.

</Slide>

<Slide title="Operaciones y sus costos">
Cada fila lee igual: qué invariante deja en pie la operación, y qué
cuesta dejarlo en pie. La notación asintótica es la de
[[complejidad-de-hilbert-al-big-o|Complejidad]], sobre $$N$$ = `size`, el número de elementos guardados.

| Operación | Peor caso | Invariante que restaura |
|---|---|---|
| `get_at(i)`, `set_at(i, x)` | $$\Theta(1)$$ | Ninguno: no cambian `size` ni el orden |
| `insert_last(x)` | $$\Theta(1)$$ con capacidad libre; **imposible** si `size == datos.length` | Los válidos siguen siendo `datos[0..size-1]` |
| `delete_last()` | $$\Theta(1)$$ | Los válidos siguen siendo `datos[0..size-1]` |
| `insert_at(i, x)` | $$\Theta(N)$$ | Deja los válidos juntos desde 0, con `x` en la posición `i` |
| `insert_first(x)` | $$\Theta(N)$$ | Igual que `insert_at(0, x)`: el caso más caro |
| `delete_at(i)` | $$\Theta(N)$$ | Cierra el hueco: los válidos vuelven a quedar juntos |
| `delete_first()` | $$\Theta(N)$$ | Igual que `delete_at(0)`: el caso más caro |
| Construir con capacidad `c` | $$\Theta(c)$$ | Establece los tres invariantes por primera vez |

Los dos extremos del arreglo no son simétricos, y la tabla lo muestra:
trabajar al final es $$\Theta(1)$$ y trabajar al principio es
$$\Theta(N)$$. La diferencia no viene del hardware sino del segundo
invariante — al final no hay nada a la derecha que mover, al principio
hay todo.

</Slide>

<Slide title="Insertar en el medio · el corrimiento">
Insertar en la posición `i` no puede simplemente escribir en `datos[i]`:
eso pisaría el elemento que ya estaba ahí y rompería el invariante que
dice que los válidos son `datos[0..size-1]`. Hay que abrir el hueco
primero, moviendo hacia la derecha todo lo que está en `[i..size-1]`.

```java
void insertAt(int i, int x) {
    if (size == datos.length) {
        throw new IllegalStateException("arreglo lleno");
    }
    for (int j = size; j > i; j--) {  // de derecha a izquierda
        datos[j] = datos[j - 1];
    }
    datos[i] = x;
    size++;
}
```

El bucle recorre de derecha a izquierda a propósito: de izquierda a
derecha, cada copia pisaría el elemento que todavía falta mover.

El costo son $$N - i$$ copias, con $$N$$ = `size`. Para `i = N` no hay ninguna —
insertar al final es gratis. Para `i = 0` son $$N$$ — insertar al
principio mueve el arreglo entero. El invariante que la operación tiene
que restaurar es exactamente lo que se está pagando.

Borrar es la misma historia al revés: `delete_at(i)` corre hacia la
izquierda los elementos de `[i+1..size-1]` para cerrar el hueco, y
después baja `size` en uno.

</Slide>

<Slide title="La limitación · capacidad fija">
Todo lo anterior asume que hay capacidad libre. Cuando no la hay, el
arreglo no se pone lento: se acaba.

```java
Arreglo a = new Arreglo(100);
// ... 100 insertLast ...
a.insertLast(x);  // IllegalStateException: arreglo lleno
```

La capacidad se decide **al construir la estructura**, y a esa altura
casi nunca sabemos cuántos elementos van a entrar. Las dos salidas
obvias son malas las dos:

- **Reservar de más.** Un arreglo de un millón de casillas para guardar
  veinte elementos desperdicia memoria proporcional a lo que no se usó,
  y sigue sin dar ninguna garantía: el elemento un millón uno tampoco
  entra.
- **Reservar lo justo y volver a empezar cuando se llena.** Crear un
  arreglo más grande y copiar cuesta $$\Theta(N)$$. Si esto pasa en cada
  inserción, agregar $$N$$ elementos cuesta
  $$1 + 2 + \dots + N = N(N+1)/2 \in \Theta(N^2)$$, que para un millón
  de elementos son unas $$5 \times 10^{11}$$ copias.

La pregunta que queda abierta es concreta: **¿existe una manera de
crecer que no pague $$\Theta(N)$$ por elemento?** La respuesta es que
sí, y cambia una sola cosa de la segunda salida.

</Slide>
