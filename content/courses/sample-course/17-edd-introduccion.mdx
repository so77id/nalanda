# Estructuras de Datos · Introducción

Hasta aquí estudiamos algoritmos. Esta unidad estudia dónde viven los
datos sobre los que esos algoritmos trabajan: qué formas hay de guardar
una colección, qué operaciones ofrece cada una y cuánto cuesta cada
operación.

Esta clase abre la unidad con tres palabras — TDA, estructura de datos e
invariante —, formaliza el arreglo que ya usamos, lo hace crecer hasta
el arreglo dinámico y cierra con el contrato que ambos cumplen.

<SectionBreak />

## Vocabulario · TDA, EDA e invariante

<Slide title="Lo mismo, dos veces">
Estas dos líneas declaran lo mismo y construyen cosas distintas:

```java
List<Integer> a = new ArrayList<>();
List<Integer> b = new LinkedList<>();

a.add(0, 7);   b.add(0, 7);      // insertar al principio
a.get(3);      b.get(3);         // pedir el de la posición 3
```

Las dos responden `add`, `get`, `remove`, `size`. Un método que reciba un
`List` funciona con cualquiera de las dos sin enterarse de cuál le
tocó.

Algo se está separando ahí: **qué se le puede pedir** a una colección,
por un lado, y **cómo lo resuelve**, por el otro. Esta clase le pone
nombre a los dos lados, y a lo que los conecta.

</Slide>

<Slide title="Tipo de dato abstracto · el contrato">
Un **tipo de dato abstracto** (TDA) es un conjunto de operaciones **con
su significado**, sin decir nada sobre cómo están guardados los
elementos.

`List` es un TDA. Dice que los elementos ocupan posiciones `0..n-1`, que
`get(i)` devuelve el que está en la posición `i`, que `add(i, e)` mete a
`e` ahí y corre el resto. No dice dónde vive ninguno de ellos.

```java
public interface List<E> {
    int size();
    E get(int index);            // el elemento de la posición index
    E set(int index, E e);       // reemplaza el de esa posición
    void add(int index, E e);    // inserta e y corre el resto
    E remove(int index);         // saca el de index y lo devuelve
}
```

**Cuidado con una confusión fácil: no toda interfaz es un TDA.**
`Comparable` es un contrato — declara que un tipo tiene orden — pero no
describe ninguna colección, y no hay dos maneras de implementarlo que
cuesten distinto. Lo mismo vale para `Runnable` o `Serializable`.

Un TDA se reconoce porque **admite varias representaciones y elegir
entre ellas importa**.

</Slide>

<Slide title="Estructura de datos · la representación">
Una **estructura de datos** es la decisión que el contrato dejó
abierta: dónde están los elementos y cómo se implementa cada operación.

`ArrayList` los guarda en **memoria consecutiva**. `LinkedList` los
guarda en **nodos enlazados**, cada uno sabiendo dónde está el
siguiente. Mismo contrato, distinta máquina.

> La interfaz es una **especificación** — el problema. La estructura de
> datos es una **representación** — la solución.
>
> — Erik Demaine, MIT 6.006, 2020

Demaine dice _interfaz_ donde nosotros venimos diciendo _contrato_: la
palabra está sobrecargada. En Java, `interface` es un mecanismo del
lenguaje; en la literatura de algoritmos, la interfaz de una estructura
es su TDA. Son cosas distintas y conviene no mezclarlas.

Lo que importa es la consecuencia: **los costos no salen del contrato,
salen de la representación.** Sobre un millón de elementos, `get(500000)`
es inmediato en un `ArrayList` y camina medio millón de nodos en un
`LinkedList`. Ninguna de las dos es mejor; son distintas, y esta unidad
estudia esa diferencia.

</Slide>

<Slide title="Invariante · lo que se mantiene">
Falta la pieza que conecta las dos anteriores, y aparece con una
pregunta sobre código conocido.

```java
static int bs(int[] a, int lo, int hi, int t) {
    if (lo > hi) return -1;
    int mid = (lo + hi) / 2;
    if (a[mid] == t) return mid;
    if (t < a[mid]) return bs(a, lo, mid - 1, t);
    return bs(a, mid + 1, hi, t);
}
```

**¿Por qué está permitido tirar media entrada sin mirarla?**

Porque hay una propiedad que valía antes del paso y sigue valiendo
después: **si `t` está en el arreglo, está en `a[lo..hi]`**. Cada
llamada la deja en pie sobre un rango la mitad de grande, así que lo
que se descarta no podía contener la respuesta.

Una propiedad así se llama **invariante**: vale antes y después de cada
operación, aunque durante la operación se rompa.

Y con eso se cierra la cadena: **una operación es barata cuando puede
confiar en el invariante, y cara cuando tiene que restaurarlo.**

</Slide>

<Slide title="Un invariante que ya usamos">
El invariante casi nunca está escrito. En `partition` sí, y quizá pasó
desapercibido:

```java
static int partition(int[] a, int lo, int hi) {
    int pivot = a[lo];
    swap(a, lo, hi);
    int store = lo;
    for (int j = lo; j < hi; j++) {
        // a[lo..store-1] < pivot  y  a[store..j-1] >= pivot
        if (a[j] < pivot) { swap(a, store, j); store++; }
    }
    swap(a, store, hi);
    return store;
}
```

Ese comentario es el invariante del bucle. Se cumple en cada vuelta, y
es lo único que garantiza que al terminar el pivote quede en su posición
definitiva — sin él, quicksort no sería correcto.

</Slide>

<Figure

/>

La dependencia baja y nunca sube: el contrato no sabe nada de los
invariantes, y los invariantes son asunto privado de cada
representación. Esa libertad es la que permite que dos estructuras con
el mismo contrato tengan costos distintos — y el resto de la unidad es
recorrer esta cadena, una estructura por vez.

</Slide>

## La EDA Arreglo

<Slide title="El arreglo en memoria">
El arreglo de [[arrays-y-funciones|Arreglos y funciones]] guarda los
elementos en **posiciones consecutivas**, todas del mismo tamaño. Esa
sola decisión da la propiedad que lo hace famoso:

$$
\text{dirección}(i) = \text{base} + i \times \text{tamaño}
$$

<Figure
  src="./arreglo-memoria.svg"
  alt="Ocho casillas consecutivas numeradas de 0 a 7 con valores adentro. Una flecha marca la dirección base sobre la casilla 0 y otra la casilla 3, rotulada base más 3 por el tamaño del elemento. Ninguna casilla intermedia se recorre."
/>

Una multiplicación y una suma. Llegar a la posición 3 y a la 3 000 000
cuesta lo mismo: $$\Theta(1)$$.

</Slide>

<Slide title="Capacidad y largo">
Un arreglo de Java todavía no es un contenedor: `data.length` dice
cuántas casillas se reservaron, no cuántas se están usando. La
estructura que estudiamos es el arreglo **más un entero**.

```java
class StaticArray {
    private int[] data;   // la representación
    private int size;     // cuántas casillas son válidas

    StaticArray(int capacity) {
        data = new int[capacity];
        size = 0;
    }
}
```

`data.length` es la **capacidad**: casillas reservadas. `size` es el
**largo**: casillas ocupadas. Son dos números distintos, y la distancia
entre ellos es de lo que trata el resto de la clase.

</Slide>

<Slide title="Los invariantes del arreglo">
<Figure
  src="./arreglo-invariantes.svg"
  alt="Un arreglo de capacidad diez con largo seis. Las casillas 0 a 5 tienen borde sólido y valores; las casillas 6 a 9 tienen borde punteado y un signo de interrogación. Una llave superior abarca las diez y dice capacidad; dos llaves inferiores separan los seis válidos de las cuatro casillas de basura."
/>

1. **`0 ≤ size ≤ data.length`.** El largo nunca supera la capacidad.
2. **Los elementos son exactamente `data[0..size-1]`.** Juntos y desde
   la posición 0, sin huecos en el medio.
3. **`data[size..]` es basura.** Existe, tiene algún valor, y no se lee.

El segundo es el caro y el barato a la vez: hace que el acceso sea
aritmética pura, y obliga a mover elementos cada vez que algo entra o
sale del medio.

</Slide>

<Slide title="Operaciones y sus costos">
Sobre $$N$$ = `size`, con la notación de
[[complejidad-de-hilbert-al-big-o|Complejidad]]:

| Operación | Peor caso | Invariante que restaura |
|---|---|---|
| `getAt(i)`, `setAt(i, x)` | $$\Theta(1)$$ | Ninguno: no cambian el largo |
| `insertLast(x)`, `deleteLast()` | $$\Theta(1)$$ | Los válidos siguen juntos desde 0 |
| `insertAt(i, x)`, `deleteAt(i)` | $$\Theta(N)$$ | Los válidos vuelven a quedar juntos |
| `insertFirst(x)`, `deleteFirst()` | $$\Theta(N)$$ | El caso más caro de los anteriores |

Los dos extremos no son simétricos: al final no hay nada a la derecha
que mover, al principio hay todo. La diferencia no viene del hardware,
viene del segundo invariante.

</Slide>

El bucle va de derecha a izquierda a propósito: al revés, cada copia
pisaría el elemento que todavía falta mover. El costo son $$N - i$$
copias — ninguna al final, todas al principio.

</Slide>

<Slide title="La limitación · capacidad fija">
Todo lo anterior asume que hay capacidad libre. Cuando no la hay, el
arreglo no se pone lento: se acaba.

```java
StaticArray a = new StaticArray(100);
// ... 100 insertLast ...
a.insertLast(x);   // IllegalStateException
```

La capacidad se decide al construir la estructura, y a esa altura casi
nunca sabemos cuántos elementos van a entrar. Reservar de más
desperdicia memoria y sigue sin dar garantías. Reservar lo justo y
copiar a un arreglo nuevo en cada inserción cuesta
$$1 + 2 + \dots + N \in \Theta(N^2)$$.

**¿Hay una manera de crecer que no pague $$\Theta(N)$$ por elemento?**

</Slide>

## El arreglo dinámico

<Slide title="Duplicar en vez de crecer de a uno">
La estrategia que funciona cambia una sola cosa: **cuánto** más grande
es el arreglo nuevo. En vez de una casilla más, el doble.

<StepShow
  language="java"
  title="insertLast(e) sobre un arreglo lleno"
  code={`void insertLast(int x) {
    if (size == data.length) {
        int[] bigger = new int[2 * data.length];
        for (int j = 0; j < size; j++) {
            bigger[j] = data[j];
        }
        data = bigger;
    }
    data[size] = x;
    size++;
}`}

Copiar sigue costando $$\Theta(N)$$, pero ocurre cada vez menos seguido:
entre una duplicación y la siguiente hay el doble de inserciones baratas
que entre las dos anteriores. Es lo que hay adentro de `ArrayList` en
Java, de `vector` en C++ y de `list` en Python.

<Slide title="El arreglo dinámico en Java">
El programa completo. Al ejecutarlo, cada duplicación se anuncia sola.

<Slide title="El análisis ingenuo">
Operación por operación, la conclusión es incómoda: **`insertLast` es
$$\Theta(N)$$ en el peor caso**, porque cuando toca duplicar copia todo
lo que había.

Si el análisis terminara ahí, la estructura sería mala. Pero el peor
caso de una operación aislada no es la pregunta correcta cuando el
programa hace una **secuencia** de operaciones.

| Inserción | ¿Duplica? | Capacidad | Copias | Costo |
|---|---|---|---|---|
| 1 | — | 1 | 0 | 1 |
| 2 | sí | 2 | 1 | 2 |
| 3 | sí | 4 | 2 | 3 |
| 4 | no | 4 | 0 | 1 |
| 5 | sí | 8 | 4 | 5 |
| 6, 7, 8 | no | 8 | 0 | 1 cada una |
| 9 | sí | 16 | 8 | 9 |
| 10 … 16 | no | 16 | 0 | 1 cada una |

Cuatro filas caras, doce baratas.

</Slide>

<Slide title="La cuenta de dieciséis inserciones">
Cada duplicación copia el largo que había en ese momento, y esos largos
son potencias de dos:

$$
\text{copias} = 1 + 2 + 4 + 8 = 15
$$

Las escrituras son una por inserción, $$16$$. El total de la secuencia
completa es

$$
16 + 15 = 31 < 2 \times 16
$$

Menos de dos operaciones elementales por inserción — contando las caras.

</Slide>

<Slide title="Costo amortizado">
Una operación cuesta $$\Theta(1)$$ **amortizado** cuando cualquier
secuencia de $$N$$ operaciones cuesta a lo más $$c \cdot N$$ en total.
No es un promedio sobre entradas al azar: es una garantía de peor caso
sobre la secuencia entera.

Para un $$N$$ cualquiera, las copias son la suma de las potencias de dos
que no superan a $$N$$, y esa suma es menor que el doble de la última:

$$
1 + 2 + 4 + \dots + 2^{k} < 2^{k+1} \le 2N
$$

$$
\underbrace{N}_{\text{escrituras}} + \underbrace{\text{copias}}_{<\,2N} < 3N \in \Theta(N)
$$

Las operaciones caras siguen costando $$\Theta(N)$$. Son tan raras que,
repartidas en la secuencia, salen constantes.

</Slide>

<Slide title="La medición">
Las dos estrategias difieren en un número — `+ 1` contra `* 2` — y esa
diferencia se puede cronometrar.

<Slide title="Achicar sin thrashing · la regla del cuarto">
Al borrar elementos conviene devolver capacidad. La regla obvia —
achicar a la mitad cuando el arreglo queda medio vacío — es un error, y
su falla tiene nombre: *thrashing*.

<Figure
  src="./regla-del-cuarto.svg"
  alt="Dos barras de capacidad, cada una con sus dos fronteras de redimensionamiento y con el punto donde queda el largo justo después de una. En la de arriba, marcada con una cruz, achicar se dispara en la mitad y tras duplicar el largo cae exactamente sobre esa frontera, así que la operación siguiente vuelve a redimensionar. En la de abajo, marcada con un visto, achicar se dispara en el cuarto y crecer al llenarse; el largo cae en la mitad, a media capacidad de la frontera de crecer y a un cuarto de la de achicar."
/>

Con la regla mala, tras duplicar el largo queda **justo sobre** la
frontera de achicar: insertar y borrar alternadamente copia $$N$$
elementos en cada operación. Separando las fronteras —
**duplicar al llenarse, achicar a la mitad cuando el largo baja al
cuarto** — entre dos redimensionamientos siempre quedan $$\Omega(N)$$
operaciones baratas que pagan el siguiente. Es la regla de Sedgewick y
Wayne en *Algorithms*.

</Slide>

<Slide title="Costos del arreglo dinámico">
| Operación | Peor caso | Amortizado | Invariante que restaura |
|---|---|---|---|
| `getAt(i)`, `setAt(i, x)` | $$\Theta(1)$$ | $$\Theta(1)$$ | Ninguno |
| `insertLast(x)` | $$\Theta(N)$$ | $$\Theta(1)$$ | Capacidad $$\ge$$ largo |
| `deleteLast()` | $$\Theta(N)$$ | $$\Theta(1)$$ | Largo $$\ge$$ capacidad$$/4$$ |
| `insertAt(i, x)`, `deleteAt(i)` | $$\Theta(N)$$ | $$\Theta(N)$$ | Los válidos juntos desde 0 |
| `insertFirst(x)`, `deleteFirst()` | $$\Theta(N)$$ | $$\Theta(N)$$ | El caso más caro |

Solo las operaciones **en el extremo final** ganan algo con el análisis
amortizado, porque solo ellas tienen un costo caro que es raro.
Insertar al principio es $$\Theta(N)$$ siempre: el corrimiento no
depende de la capacidad.

El arreglo dinámico no cambió ninguna complejidad. Quitó la obligación
de decidir la capacidad de antemano, y cobró por eso un factor
constante.

</Slide>

## Un contrato para los dos arreglos

<Slide title="Dos representaciones, las mismas operaciones">
El arreglo de capacidad fija y el arreglo dinámico guardan cosas
distintas y mantienen invariantes distintos. Y sin embargo responden
exactamente las mismas preguntas: dame el de la posición `i`,
reemplazarlo, insertar en la posición `i`, borrar la posición `i`, y los
cuatro atajos para los extremos.

<Figure
  src="./un-tda-dos-edas.svg"
  alt="Un recuadro superior con el TDA Sequence y sus operaciones. Dos flechas bajan a dos recuadros: el arreglo de capacidad fija y el arreglo dinámico. Cada uno declara su propio invariante y su propia lista de costos, y los dos responden las mismas operaciones."
/>

Un programa escrito contra esas operaciones no cambia una línea al
cambiar de una a la otra. Cambia cuánto tarda.

</Slide>

<Slide title="El TDA Sequence · el contrato">
Una **secuencia** es una colección en un orden que el programa decide —
el de las posiciones 0, 1, 2, … — y no el que resulte de comparar los
elementos entre sí.

```java
public interface Sequence<T> {
    int len();                  // cuántos elementos hay
    T getAt(int i);             // el de la posición i
    void setAt(int i, T x);     // reemplaza el de la posición i

    void insertAt(int i, T x);  // mete x en i, corriendo el resto
    T deleteAt(int i);          // saca el de i y lo devuelve

    void insertFirst(T x);
    T deleteFirst();
    void insertLast(T x);
    T deleteLast();
}
```

Los cuatro atajos son abreviaturas de `insertAt(0, x)`, `deleteAt(0)`,
`insertAt(len(), x)` y `deleteAt(len()-1)`. Existen porque los extremos
son los casos frecuentes y muchas representaciones los resuelven mucho
más rápido.

Lo que el contrato **no** dice importa tanto como lo que dice: ni
memoria consecutiva, ni capacidad, ni duplicación, ni corrimientos.

</Slide>

<Slide title="Dos implementaciones, dos tablas de costos">
| Operación | Capacidad fija | Dinámico |
|---|---|---|
| `getAt`, `setAt` | $$\Theta(1)$$ | $$\Theta(1)$$ |
| `insertLast`, `deleteLast` | $$\Theta(1)$$, falla si está lleno | $$\Theta(1)$$ amortizado |
| `insertFirst`, `deleteFirst` | $$\Theta(N)$$ | $$\Theta(N)$$ |
| `insertAt`, `deleteAt` | $$\Theta(N)$$ | $$\Theta(N)$$ |
| Capacidad | fija al construir | crece y se achica sola |

Las dos brillan y sufren en lo mismo, porque comparten la decisión de
fondo: memoria consecutiva. De ahí sale que llegar a una posición sea
gratis y que abrir un hueco en el medio cueste $$\Theta(N)$$.

La diferencia real no está en la tabla: está en **qué hay que saber de
antemano**.

</Slide>

<Slide title="El cabo suelto">
Las dos implementaciones comparten una debilidad: insertar o borrar al
principio cuesta $$\Theta(N)$$. La culpa es del invariante de memoria
consecutiva — para que la posición `i` esté en `base + i × tamaño` no
puede haber huecos, y no tener huecos obliga a correr elementos.

**¿Y si renunciamos a la memoria consecutiva?**

Si cada elemento supiera dónde está el siguiente, insertar al principio
sería cambiar un puntero: $$\Theta(1)$$. El precio sería el otro lado de
la tabla: sin aritmética de direcciones, llegar a la posición `i`
obligaría a caminar `i` pasos, y `getAt` dejaría de ser $$\Theta(1)$$.

Esa estructura es la **lista enlazada**, cumple el mismo TDA Sequence, y
su tabla de costos es casi la imagen espejo. Es la clase que viene.

</Slide>
