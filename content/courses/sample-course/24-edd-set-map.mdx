# Estructuras de Datos Avanzadas · TDAs Set y Map

Una tabla hash y un árbol de búsqueda balanceado responden las mismas
preguntas sobre un conjunto de claves: si una clave está, cómo agregar una y
cómo sacarla. Las responden a precios distintos, y el árbol responde además
preguntas que la tabla no sabe responder. Separar lo que se pregunta de cómo
se guarda permite escribir un programa una sola vez y elegir después la
estructura que lo hace más barato.

VOTED lists them in the order they arrive; VOTED_TABLE is the chaining table with M = 7 those arrivals build under the hash class's own `hash` (Horner, base 256, over the text with its dots, each key at the FRONT of its list), and VOTED_TREE is the AVL tree the same arrivals build. {/* KeySet — a set drawn as what the contract sees: a rounded region holding its elements as chips, with no positions and no order. `probe` draws a question over it — a chip «¿x?» with an arrow — that lands on the chip that answers it, painted `keep`, or on the edge of the region when nothing answers. `tones` paints chips `mark`: what the slide points at. File-local (add-a-course-document.md §6e-quater): no catalog entry, one consumer. */}

export function KeySet({ title, keys, probe, tones = {}, caption, label, id }) {
  const chipW = 112;
  const chipH = 30;
  const gap = 12;
  const inner = 16;
  const perRow = 3;
  const rows = Math.ceil(keys.length / perRow);
  const blobW = perRow * chipW + (perRow - 1) * gap + 2 * inner;
  const blobH = rows * chipH + (rows - 1) * gap + 2 * inner;
  const probeW = chipW + 26;
  const blobY = probe ? 12 + chipH + 46 : 26;
  const width = Math.max(blobW + 24, caption ? caption.length * 6.6 + 24 : 0);
  const blobX = (width - blobW) / 2;
  const height = blobY + blobH + (caption ? 34 : 12);
  const chipX = (n) => blobX + inner + (n % perRow) * (chipW + gap);
  const chipY = (n) => blobY + inner + Math.floor(n / perRow) * (chipH + gap);
  const at = probe === undefined ? -1 : keys.indexOf(probe);
  // The question sits over the chip that answers it, so its arrow goes
  // straight down: it must land in the first row to cross no other chip.
  const probeX = at >= 0 ? chipX(at) + chipW / 2 : width / 2;
  const toX = probeX;
  const toY = at >= 0 ? chipY(at) - 4 : blobY - 4;
  const arrow = at >= 0 ? 'var(--color-keep)' : 'var(--color-ink-soft)';
  return (
    <svg viewBox={`0 0 ${width} ${height}`} style={{ width: '100%', maxWidth: `${Math.round(width * 1.3)}px`, height: 'auto', display: 'block', margin: '0.4rem auto' }} role="img" aria-label={label}>
      <defs>
        <marker id={`${id}-punta`} markerWidth="8" markerHeight="8" refX="7" refY="4" orient="auto">
          <path d="M0,0 L8,4 L0,8 z" style={{ fill: arrow }} />
        </marker>
      </defs>
      <rect x={blobX} y={blobY} width={blobW} height={blobH} rx="18" style={{ fill: 'var(--color-sunk)', stroke: 'var(--color-rule-strong)' }} strokeWidth="1.4" />
      <text x={blobX + 14} y={blobY - 8} fontSize="12" fontWeight="700" style={{ fill: 'var(--color-ink-soft)' }}>{title}</text>
      {keys.map((k, n) => {
        const fill = n === at ? 'var(--color-keep-soft)' : tones[k] === 'mark' ? 'var(--color-mark-soft)' : 'var(--color-surface)';
        const stroke = n === at ? 'var(--color-keep)' : tones[k] === 'mark' ? 'var(--color-mark)' : 'var(--color-rule-strong)';
        return (
          <g key={k}>
            <rect x={chipX(n)} y={chipY(n)} width={chipW} height={chipH} rx="15" style={{ fill, stroke }} strokeWidth={n === at || tones[k] ? 2.2 : 1.2} />
            <text x={chipX(n) + chipW / 2} y={chipY(n) + chipH / 2 + 5} textAnchor="middle" fontSize="13" fontWeight="600" style={{ fill: 'var(--color-ink)' }}>{k}</text>
          </g>
        );
      })}
      {probe !== undefined ? (
        <g>
          <rect x={probeX - probeW / 2} y={12} width={probeW} height={chipH} rx="15" style={{ fill: 'var(--color-surface)', stroke: arrow }} strokeWidth="1.6" strokeDasharray={at >= 0 ? undefined : '5 4'} />
          <text x={probeX} y={12 + chipH / 2 + 5} textAnchor="middle" fontSize="13" fontWeight="600" style={{ fill: 'var(--color-ink)' }}>{`¿${probe}?`}</text>
          <line x1={probeX} y1={12 + chipH + 2} x2={toX} y2={toY} style={{ stroke: arrow }} strokeWidth="1.6" markerEnd={`url(#${id}-punta)`} />
        </g>
      ) : null}
      {caption ? (
        <text x={width / 2} y={height - 10} textAnchor="middle" fontSize="12" style={{ fill: 'var(--color-ink-soft)' }}>{caption}</text>
      ) : null}
    </svg>
  );
}

{/* ChainTable — a hash table with chaining drawn still, with nodes wide enough for a RUT. COPIES the look of the hash-chaining recipe of <SequenceStepper> (sequenceStepperHashLayout.ts: a contiguous strip with its index, nodes with the key over a `next` field, lists hanging down, `null` where one ends), as the file-local `Chains` of 23-edd-tablas-hash.mdx does at a narrower node; neither copy is tested, so a change in the recipe is carried to both by hand and checked in a browser. Not `Chains` itself: that one draws names in 56 px, and a RUT needs twice that. `order` numbers every node in the order a walk over the table meets it — position by position, each list from its front —, `tones` paints a key's node (`keep`, `mark`, `visited`, `faint`), `picked` outlines the position a search goes to, and `window={[from, to]}` draws only those positions, with «…» where the table goes on, as `Chains` does, so two drawings side by side keep a size a projector can read. File-local (§6e-quater). */}

export function ChainTable({ chains, tones = {}, order = false, picked, window: shown, caption, label }) {
  const pad = 12;
  const pitch = 108;
  const cellH = 30;
  const nodeW = 98;
  const keyH = 24;
  const nodeH = 36;
  const gap = 18;
  const indexY = 18;
  const cellY = 26;
  const [lo, hi] = shown ?? [0, chains.length - 1];
  const longest = Math.max(1, ...chains.slice(lo, hi + 1).map((c) => c.length));
  const stripW = (hi - lo + 1) * pitch;
  const width = Math.max(2 * pad + stripW + (shown ? 40 : 0), caption ? caption.length * 6.6 + 24 : 0);
  const left = (width - stripW) / 2;
  const nodeY = (k) => cellY + cellH + gap + k * (nodeH + gap);
  const height = nodeY(longest) - gap + 18 + (caption ? 30 : 6);
  const fill = { keep: 'var(--color-keep-soft)', mark: 'var(--color-mark-soft)', visited: 'var(--color-sunk)', faint: 'var(--color-surface)' };
  const stroke = { keep: 'var(--color-keep)', mark: 'var(--color-mark)', visited: 'var(--color-rule-strong)', faint: 'var(--color-rule)' };
  const rank = {};
  chains.flat().forEach((key, n) => {
    rank[key] = n + 1;
  });
  return (
    <svg viewBox={`0 0 ${width} ${height}`} style={{ width: '100%', maxWidth: `${Math.round(width * 1.3)}px`, height: 'auto', display: 'block', margin: '0.4rem auto' }} role="img" aria-label={label}>
      {lo > 0 ? (
        <text x={left - 12} y={cellY + cellH / 2 + 4} textAnchor="middle" fontSize="13" style={{ fill: 'var(--color-ink-faint)' }}>…</text>
      ) : null}
      {hi < chains.length - 1 ? (
        <text x={left + stripW + 12} y={cellY + cellH / 2 + 4} textAnchor="middle" fontSize="13" style={{ fill: 'var(--color-ink-faint)' }}>…</text>
      ) : null}
      {chains.map((chain, i) => {
        if (i < lo || i > hi) return null;
        const x0 = left + (i - lo) * pitch;
        const cx = x0 + pitch / 2;
        return (
          <g key={i}>
            <text x={cx} y={indexY} textAnchor="middle" fontSize="11" fontWeight={picked === i ? 700 : 400} style={{ fill: picked === i ? 'var(--color-ink)' : 'var(--color-ink-faint)' }}>{i}</text>
            <rect x={x0} y={cellY} width={pitch} height={cellH} style={{ fill: 'var(--color-surface)', stroke: 'var(--color-rule-strong)' }} strokeWidth="1.2" />
            {chain.length === 0 ? (
              <text x={cx} y={cellY + cellH / 2 + 4} textAnchor="middle" fontSize="11" style={{ fill: 'var(--color-ink-faint)' }}>null</text>
            ) : (
              <g>
                <circle cx={cx} cy={cellY + cellH / 2} r="3" style={{ fill: 'var(--color-ink-soft)' }} />
                <line x1={cx} y1={cellY + cellH / 2} x2={cx} y2={nodeY(0) - 2} style={{ stroke: 'var(--color-ink-soft)' }} strokeWidth="1.4" />
                <path d={`M ${cx - 4} ${nodeY(0) - 7} L ${cx} ${nodeY(0) - 1} L ${cx + 4} ${nodeY(0) - 7} z`} style={{ fill: 'var(--color-ink-soft)' }} />
              </g>
            )}
            {chain.map((key, k) => {
              const y = nodeY(k);
              const t = tones[key];
              return (
                <g key={key} opacity={t === 'faint' ? 0.45 : undefined}>
                  <rect x={cx - nodeW / 2} y={y} width={nodeW} height={nodeH} rx="3" style={{ fill: t ? fill[t] : 'var(--color-surface)', stroke: t ? stroke[t] : 'var(--color-rule)' }} strokeWidth={t === 'keep' || t === 'mark' ? 2.2 : 1.2} />
                  <line x1={cx - nodeW / 2} y1={y + keyH} x2={cx + nodeW / 2} y2={y + keyH} style={{ stroke: t ? stroke[t] : 'var(--color-rule)' }} strokeWidth="1" />
                  <text x={cx} y={y + keyH / 2 + 5} textAnchor="middle" fontSize="12.5" fontWeight="600" style={{ fill: 'var(--color-ink)' }}>{key}</text>
                  {k < chain.length - 1 ? (
                    <g>
                      <circle cx={cx} cy={y + keyH + (nodeH - keyH) / 2} r="2.5" style={{ fill: 'var(--color-ink-soft)' }} />
                      <line x1={cx} y1={y + keyH + (nodeH - keyH) / 2} x2={cx} y2={nodeY(k + 1) - 2} style={{ stroke: 'var(--color-ink-soft)' }} strokeWidth="1.4" />
                      <path d={`M ${cx - 4} ${nodeY(k + 1) - 7} L ${cx} ${nodeY(k + 1) - 1} L ${cx + 4} ${nodeY(k + 1) - 7} z`} style={{ fill: 'var(--color-ink-soft)' }} />
                    </g>
                  ) : (
                    <text x={cx} y={y + nodeH + 13} textAnchor="middle" fontSize="10" style={{ fill: 'var(--color-ink-faint)' }}>null</text>
                  )}
                  {order ? (
                    <g>
                      <circle cx={cx - nodeW / 2} cy={y} r="8.5" strokeWidth="2" style={{ fill: 'var(--color-surface)', stroke: 'var(--color-ink-soft)' }} />
                      <text x={cx - nodeW / 2} y={y + 3.8} textAnchor="middle" fontSize="10.5" fontWeight="700" style={{ fill: 'var(--color-ink)' }}>{rank[key]}</text>
                    </g>
                  ) : null}
                </g>
              );
            })}
            {picked === i ? (
              <rect x={x0} y={cellY} width={pitch} height={cellH} fill="none" style={{ stroke: 'var(--color-focus)' }} strokeWidth="2.4" />
            ) : null}
          </g>
        );
      })}
      {caption ? (
        <text x={width / 2} y={height - 8} textAnchor="middle" fontSize="12" style={{ fill: 'var(--color-ink-soft)' }}>{caption}</text>
      ) : null}
    </svg>
  );
}

{/* KeyTree — a binary search tree whose keys are too wide for <BinaryPicture>'s circles: the same placement (every node in the column of its inorder position, on the row of its depth) and the same tones and inorder colour (design-system.md §The tree figures' palette), with each node a pill as wide as a RUT. `order` numbers the nodes in inorder, as BinaryPicture's `visits="in"` does, and `strip` writes the inorder under the tree, each key in its node's column, which is why the row comes out sorted. `minColumns` widens the canvas as BinaryPicture's does, so a tree drawn beside a wider figure comes out at the same size. `tones` paints a node and its slot in the strip. File-local (§6e-quater); BinaryPicture is the component, this only exists because a RUT does not fit in it. */}

export function KeyTree({ tree, tones = {}, order = false, strip = false, minColumns = 0, caption, label }) {
  const pad = 12;
  const nodeW = 98;
  const nodeH = 30;
  const colW = 108;
  const levelH = 62;
  const slotH = 30;
  const nodes = [];
  const place = (t, depth) => {
    if (!t) return;
    place(t.l, depth + 1);
    nodes.push({ v: t.v, l: t.l, r: t.r, depth, column: nodes.length });
    place(t.r, depth + 1);
  };
  place(tree, 0);
  const column = Object.fromEntries(nodes.map((n) => [n.v, n.column]));
  const deepest = Math.max(...nodes.map((n) => n.depth));
  const treeW = nodes.length * colW;
  const width = Math.max(2 * pad + Math.max(nodes.length, minColumns) * colW, caption ? caption.length * 6.6 + 24 : 0);
  const left = (width - treeW) / 2;
  const cx = (v) => left + column[v] * colW + colW / 2;
  const cy = (depth) => pad + 8 + nodeH / 2 + depth * levelH;
  const stripY = cy(deepest) + nodeH / 2 + 28;
  const bottom = strip ? stripY + slotH : cy(deepest) + nodeH / 2;
  const height = bottom + (caption ? 34 : 12);
  const tone = {
    keep: ['var(--color-keep-soft)', 'var(--color-keep)', 2.2],
    focus: ['var(--color-surface)', 'var(--color-focus)', 2.4],
    mark: ['var(--color-mark-soft)', 'var(--color-mark)', 2.2],
  };
  const paint = (v) => tone[tones[v]] ?? ['var(--color-surface)', 'var(--color-rule-strong)', 1.3];
  return (
    <svg viewBox={`0 0 ${width} ${height}`} style={{ width: '100%', maxWidth: `${Math.round(width * 1.3)}px`, height: 'auto', display: 'block', margin: '0.4rem auto' }} role="img" aria-label={label}>
      {nodes.flatMap((n) =>
        [n.l, n.r].filter(Boolean).map((child) => (
          <line key={`e${child.v}`} x1={cx(n.v)} y1={cy(n.depth) + nodeH / 2} x2={cx(child.v)} y2={cy(n.depth + 1) - nodeH / 2} style={{ stroke: 'var(--color-rule-strong)' }} strokeWidth="1.4" />
        )),
      )}
      {nodes.map((n) => {
        const [fill, stroke, weight] = paint(n.v);
        return (
          <g key={n.v} opacity={tones[n.v] === 'faint' ? 0.45 : undefined}>
            <rect x={cx(n.v) - nodeW / 2} y={cy(n.depth) - nodeH / 2} width={nodeW} height={nodeH} rx={nodeH / 2} style={{ fill, stroke }} strokeWidth={weight} />
            <text x={cx(n.v)} y={cy(n.depth) + 5} textAnchor="middle" fontSize="12.5" fontWeight="600" style={{ fill: 'var(--color-ink)' }}>{n.v}</text>
            {order ? (
              <g>
                <circle cx={cx(n.v) - nodeW / 2 + 6} cy={cy(n.depth) - nodeH / 2} r="8.5" strokeWidth="2" style={{ fill: 'var(--color-surface)', stroke: 'var(--color-accent)' }} />
                <text x={cx(n.v) - nodeW / 2 + 6} y={cy(n.depth) - nodeH / 2 + 3.8} textAnchor="middle" fontSize="10.5" fontWeight="700" style={{ fill: 'var(--color-ink)' }}>{n.column + 1}</text>
              </g>
            ) : null}
            {strip ? (
              <g>
                <line x1={cx(n.v)} y1={cy(n.depth) + nodeH / 2 + 3} x2={cx(n.v)} y2={stripY - 3} style={{ stroke: 'var(--color-rule)' }} strokeWidth="1" strokeDasharray="2 4" />
                <rect x={left + n.column * colW} y={stripY} width={colW} height={slotH} style={{ fill: tones[n.v] === 'keep' ? 'var(--color-keep-soft)' : 'var(--color-surface)', stroke: 'var(--color-accent)' }} strokeWidth="1.6" />
                <text x={cx(n.v)} y={stripY + slotH / 2 + 5} textAnchor="middle" fontSize="12.5" fontWeight="600" style={{ fill: 'var(--color-ink)' }}>{n.v}</text>
              </g>
            ) : null}
          </g>
        );
      })}
      {caption ? (
        <text x={width / 2} y={height - 10} textAnchor="middle" fontSize="12" style={{ fill: 'var(--color-ink-soft)' }}>{caption}</text>
      ) : null}
    </svg>
  );
}

<Slide title="Dos clases para las mismas tres operaciones">
Las dos estructuras resuelven el registro, pero no se usan de la misma
manera. Sus métodos públicos hacen lo mismo con otros nombres, y no
responden lo mismo:

| Operación | Tabla hash con listas          | Árbol AVL                   |
| --------- | ------------------------------ | --------------------------- |
| Preguntar | `boolean contains(String key)` | `boolean contains(T target)` |
| Agregar   | `boolean add(String key)`      | `void insert(T value)`      |
| Sacar     | `boolean remove(String key)`   | `void remove(T value)`      |

Un programa escrito para la tabla llama a `add` en cada voto; cambiarla por
el árbol obliga a reescribir cada una de esas llamadas, y `insert` ya no
responde si el RUT era nuevo. Elegir la estructura no debería cambiar el
programa que la usa.

Lo que hace falta es fijar las operaciones —sus nombres, lo que reciben y lo
que responden— sin decir cómo se guardan los elementos. Eso es un **tipo de
dato abstracto** (TDA), y el de una colección sin repetidos se llama **Set**.

</Slide>

## Set · Conjunto

<Slide title="El TDA Set">
Un **Set** —en español, **conjunto**— es una colección de elementos **sin
repetidos**: cada elemento está una vez o no está. No hay posiciones, ni un
primero ni un último.

<Slide title="Las reglas del contrato Set">
El Set es el conjunto de las matemáticas, que no distingue cuántas veces ni en
qué orden se escribe un elemento:

$$
\{a, b, a\} = \{a, b\} = \{b, a\}
$$

Se lee «el conjunto de $$a$$, $$b$$ y $$a$$ es el mismo que el de $$a$$ y
$$b$$». La cantidad de elementos de un conjunto $$A$$ se escribe $$|A|$$, y es
lo que retorna `size()`. De ahí salen las reglas del contrato:

- **`add(x)` de un elemento que ya está no lo agrega otra vez.** El conjunto
  queda igual y `add` retorna falso: quien llama sabe si el elemento era
  nuevo sin preguntar antes.
- **`remove(x)` de un elemento que no está no cambia nada**, y retorna falso.
- **El recorrido entrega cada elemento exactamente una vez**, en un orden que
  el contrato no promete.

Qué significa que dos elementos sean **iguales** no lo decide el conjunto: lo
decide el tipo de los elementos. El conjunto solo pregunta.

</Slide>

<Slide title="Set en Java">
Java declara el contrato en la interfaz `java.util.Set`, con los mismos
nombres:

| El TDA        | Java `Set<E>`                     |
| ------------- | --------------------------------- |
| `contains(x)` | `contains(x)`                     |
| `size()`      | `size()`                          |
| `iterator()`  | `iterator()`, o un `for` sobre el conjunto |
| `add(x)`      | `add(x)`                          |
| `remove(x)`   | `remove(x)`                       |

```java
public interface Set<E> {
    boolean contains(Object o);
    int size();
    Iterator<E> iterator();
    boolean add(E e);
    boolean remove(Object o);
}
```

La interfaz trae además otros métodos —`isEmpty`, `addAll`, `clear`— que no
son parte del TDA: son comodidades escritas sobre estos cinco. Una interfaz
no se puede instanciar; quien guarda los elementos es una clase que la
implementa.

</Slide>

<Slide title="Un Set sobre una tabla hash">
La tabla hash con listas ya cumple el contrato. Su primera invariante,
**ninguna clave está dos veces**, es la regla del Set, y sus tres métodos
públicos son las tres operaciones: `contains` recorre una sola lista, `add`
pregunta antes con `contains` y `remove` desengancha el nodo. `size()`
retorna el contador `size` que la tabla ya lleva.

- **Lo que paga.** Las tres operaciones cuestan $$\Theta(1)$$ esperado,
  siempre que la función hash reparta parejo y la tabla crezca con las claves;
  si todas caen en la misma lista, $$\Theta(N)$$.
- **Lo que no sabe hacer.** Nada que dependa del orden. La función reparte las
  claves sin relación con su orden, así que el recorrido, que va posición por
  posición, las entrega en un orden que no significa nada.

<Slide title="Un Set sobre un árbol AVL">
El árbol AVL también cumple el contrato. Su invariante de orden impide que un
valor esté dos veces —uno igual no estaría ni a la izquierda ni a la
derecha—, y sus tres operaciones bajan por un solo camino. Para responder lo
que pide `add`, basta con preguntar antes con `contains`, como hace la tabla.

- **Lo que paga.** Las tres operaciones cuestan $$O(\log N)$$ en el peor
  caso, llegue lo que llegue: la invariante de balance acota la altura. Cada
  modificación lo paga con las rotaciones y las alturas que actualiza al
  volver.
- **Lo que sabe hacer además.** El recorrido en inorden entrega los
  elementos ordenados, y el menor, el mayor o el siguiente a uno dado se
  encuentran bajando un camino.

<Slide title="Costos de las dos implementaciones">
| Operación     | Tabla hash, esperado        | Tabla hash, peor caso | Árbol AVL, peor caso |
| ------------- | --------------------------- | --------------------- | -------------------- |
| `contains(x)` | $$\Theta(1)$$               | $$\Theta(N)$$         | $$O(\log N)$$        |
| `add(x)`      | $$\Theta(1)$$ amortizado    | $$\Theta(N)$$         | $$O(\log N)$$        |
| `remove(x)`   | $$\Theta(1)$$               | $$\Theta(N)$$         | $$O(\log N)$$        |
| `size()`      | $$\Theta(1)$$               | $$\Theta(1)$$         | $$\Theta(1)$$        |
| `iterator()`  | $$\Theta(N + M)$$           | $$\Theta(N + M)$$     | $$\Theta(N)$$        |

$$M$$ es el tamaño de la tabla. `size()` cuesta $$\Theta(1)$$ en las dos
porque cada una lleva un contador que sube con `add` y baja con `remove`, y
un recorrido de la tabla pasa por todas sus posiciones, también por las
vacías.

**Memoria.** Las dos ocupan $$\Theta(N)$$, pagada de otra forma. La tabla
paga el arreglo de $$M$$ posiciones, que la redimensión mantiene en al menos
$$N$$, y un nodo por clave con una referencia al siguiente. El árbol no tiene
arreglo, y paga un nodo por clave con dos referencias, una por hijo, y su
altura.

</Slide>

<Slide title="Las preguntas que dependen del orden">
Algunos problemas piden más que las tres operaciones: preguntas que dependen
del **orden** de los elementos.

- recorrerlos en orden;
- el menor o el mayor;
- el siguiente o el anterior a uno dado;
- todos los que caen entre dos valores.

En el árbol, los elementos de un tramo del orden son un tramo seguido de su
inorden: se llega al primero bajando un camino, y desde ahí el inorden
entrega los demás, uno detrás del otro.

<Slide title="Tabla hash o árbol según el orden">
| Pregunta                             | Tabla hash                 | Árbol AVL           |
| ------------------------------------ | -------------------------- | ------------------- |
| ¿Está $$x$$?                         | $$\Theta(1)$$ esperado     | $$O(\log N)$$       |
| El menor, o el mayor                 | $$\Theta(N + M)$$          | $$O(\log N)$$       |
| El siguiente a $$x$$                 | $$\Theta(N + M)$$          | $$O(\log N)$$       |
| Los $$k$$ que están entre $$a$$ y $$b$$ | $$\Theta(N + M)$$       | $$O(\log N + k)$$   |
| Todos, en orden                      | $$\Theta(M + N \log N)$$   | $$\Theta(N)$$       |

En la tabla, cada pregunta sobre el orden mira todas las claves, y la última
además las ordena. En el árbol, el tramo entre $$a$$ y $$b$$ se encuentra
bajando un camino, y después se entregan sus $$k$$ elementos en inorden.

**Si el problema solo pregunta, agrega y saca, la tabla hash; si pregunta
por el orden, el árbol.** Una pregunta por el orden que se hace una sola vez,
al final —la lista de votantes ordenada por RUT, al cerrar—, no cambia la
elección: se ordena una vez, en $$\Theta(N \log N)$$, y la tabla sigue siendo
la más barata durante el día.

</Slide>

Java implementa el contrato Set sobre una tabla hash con listas en la clase
`java.util.HashSet`. El registro de votantes se escribe con las operaciones
del contrato, y la variable se declara del tipo del contrato, `Set`: solo la
línea que crea el conjunto nombra la estructura.

Set<String> voted = new HashSet<>();
voted.add("18.155.218-2");
voted.add("13.180.992-1");
voted.add("13.959.276-K");
voted.add("17.814.358-1");

voted.size();                   // 6

`add`, `remove` y `contains` cuestan $$\Theta(1)$$ esperado, como en la tabla
con listas: la tabla de `HashSet` empieza con 16 posiciones y duplica su
tamaño cuando el factor de carga pasa de $$0{,}75$$.

<Slide title="El recorrido de un HashSet">
Un `for` recorre el conjunto con su `iterator()`, que entrega cada elemento
una vez, en el orden de las posiciones de la tabla:

```java
for (String rut : voted) {
    System.out.println(rut);
}
```

son dos elementos distintos, aunque nombren a la misma persona: `add` del
segundo retorna verdadero, y el registro la cuenta dos veces.

Lo que identifica a una persona es el número de su RUT, no la manera de
escribirlo. Hace falta un tipo para el RUT, con su propia regla para decidir
cuándo dos son iguales.

</Slide>

<Slide title="Una clase para el RUT">
Un `Rut` guarda el número y el dígito verificador por separado. Cada mesa lee
el texto, le quita los puntos y separa el número del dígito, así que las dos
escrituras dan el mismo `Rut`.

```java
class Rut {
    private final int number;
    private final char dv;

    Rut(int number, char dv) {
        if (number <= 0) throw new IllegalArgumentException();
        this.number = number;
        this.dv = dv;
    }
}
```

Con esta clase, el registro todavía cuenta dos veces:

```java
Set<Rut> voted = new HashSet<>();
voted.add(new Rut(13180992, '1'));
voted.add(new Rut(13180992, '1')); // true: lo agrega otra vez
voted.size();                      // 2
```

Para decidir si un elemento ya está, `HashSet` pregunta con `equals`, y el
`equals` que `Rut` hereda de `Object` responde verdadero solo para el mismo
objeto. Dos objetos con los mismos campos son, para él, dos elementos.

</Slide>

<Slide title="La igualdad de dos RUT">
`equals` es el método que decide si dos objetos son iguales. `Rut` lo
reescribe para comparar los campos: dos RUT son iguales si tienen el mismo
número y el mismo dígito.

```java
@Override
public boolean equals(Object other) {
    if (!(other instanceof Rut)) return false;
    Rut r = (Rut) other;
    return number == r.number && dv == r.dv;
}
```

`equals` recibe un `Object`, porque cualquier objeto se puede comparar con
cualquier otro: si el otro no es un `Rut`, no es igual. `@Override` le pide
al compilador que verifique que el método reemplaza al de `Object`; con un
parámetro de otro tipo, el compilador lo rechaza.

</Slide>

<Slide title="Un equals sin hashCode">
Con `equals`, los dos `Rut` son iguales, y el registro sigue contándolos dos
veces: `contains` de una copia retorna falso. La tabla no compara un elemento
con todos los que guarda. Le pide su número al método **`hashCode`**, lo
reduce a una posición y compara con `equals` solo los elementos de esa lista.
El `hashCode` que `Rut` hereda de `Object` da, en la práctica, un número
distinto para cada objeto, así que dos RUT iguales caen en posiciones
distintas, y `equals` nunca llega a compararlos.

<Slide title="El contrato entre equals y hashCode">
Para que una tabla hash encuentre un objeto, su `equals` y su `hashCode` tienen
que cumplir un contrato:

$$
a.\text{equals}(b) \;\Rightarrow\; a.\text{hashCode}() = b.\text{hashCode}()
$$

que se lee «si $$a$$ es igual a $$b$$, sus `hashCode` son iguales». Al revés
no hace falta: dos objetos distintos pueden tener el mismo `hashCode`, y esa
colisión la resuelve la lista. Por eso los dos métodos se escriben juntos y
con los mismos campos:

```java
@Override
public int hashCode() {
    return 31 * number + dv;
}
```

Dos RUT iguales tienen el mismo número y el mismo dígito, y con eso el mismo
`hashCode`. Es la regla de Horner con base 31 sobre los campos, la misma que
usa `String.hashCode` sobre sus caracteres.

</Slide>

<Slide title="Un RUT encontrado por su hashCode">
Con los dos métodos, cada `Rut` cae en la posición de su `hashCode`, y una
copia cae en la misma. `contains` recorre esa sola lista y compara con
`equals` cada elemento hasta dar con el igual. El registro vuelve a contar
una vez a cada persona.

<Slide title="Objects.hash como atajo">
Escribir la combinación a mano es fácil con dos campos y propenso a errores
con muchos. `java.util.Objects.hash` la hace para cualquier cantidad de
campos:

```java
@Override
public int hashCode() {
    return Objects.hash(number, dv);
}
```

Combina los campos con la misma regla —multiplica por 31 y suma el
siguiente—, así que cumple el contrato si recibe los mismos campos que compara
`equals`. El número que da no es el mismo que el de la versión escrita a mano,
y no importa: el contrato pide que dos RUT iguales tengan el mismo
`hashCode`, no un número en particular.

</Slide>

<Slide title="Una clave que cambia después de entrar">
La otra falla aparece con objetos que pueden cambiar. Si `Rut` tuviera un
método para corregir un RUT mal digitado, cambiando sus campos, corregir uno

```java
Rut typed = new Rut(13180992, '1');
voted.add(typed);
typed.fix(13180993, 'K');  // corrige los campos
voted.contains(typed);     // false
```

El objeto sigue en la lista de la posición que le tocó al entrar. Buscado con
su valor nuevo, la tabla mira la posición del `hashCode` nuevo; buscado con el
valor viejo, llega a su lista, pero `equals` dice que ya no es ese RUT.
