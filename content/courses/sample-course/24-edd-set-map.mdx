# Estructuras de Datos Avanzadas · TDAs Set y Map

Una tabla hash y un árbol de búsqueda balanceado responden las mismas
preguntas sobre un conjunto de claves: si una clave está, cómo agregar una y
cómo sacarla. Las responden a precios distintos, y el árbol responde además
preguntas que la tabla no sabe responder. Separar lo que se pregunta de cómo
se guarda permite escribir un programa una sola vez y elegir después la
estructura que lo hace más barato.

export const codeText = (text) => text.split(/(`[^`]+`)/).map((part, i) => (part.startsWith('`') ? <tspan key={i} fontFamily="var(--font-mono, monospace)" fontWeight="700">{part.slice(1, -1)}</tspan> : part));

{/* KeySet — a set drawn as what the contract sees: a rounded region holding its elements as chips, with no positions and no order. `probe` draws a question over it — a chip «¿x?» with an arrow — that lands on the chip that answers it, painted `keep`, or on the edge of the region when nothing answers. `adds` draws the same chip as an element arriving, «+ x», instead of a question. `tones` paints chips `mark`: what the slide points at. `values` writes each key's value after it, «key → value», for a map; the question still names the key alone. File-local (add-a-course-document.md §6e-quater): no catalog entry, one consumer. */}

export function KeySet({ title, keys, probe, adds = false, tones = {}, values, caption, label, id }) {
  const text = (k) => (values ? `${k} → ${values[k]}` : k);
  const chipW = Math.max(112, ...keys.map((k) => text(k).length * 7.6 + 20));
  const chipH = 30;
  const gap = 12;
  const inner = 16;
  const perRow = 3;
  const rows = Math.ceil(keys.length / perRow);
  const blobW = perRow * chipW + (perRow - 1) * gap + 2 * inner;
  const blobH = rows * chipH + (rows - 1) * gap + 2 * inner;
  const probeW = 138;
  const blobY = probe ? 12 + chipH + 46 : 26;
  const width = Math.max(blobW + 24, caption ? caption.length * 6.6 + 24 : 0);
  const blobX = (width - blobW) / 2;
  const height = blobY + blobH + (caption ? 34 : 12);
  const chipX = (n) => blobX + inner + (n % perRow) * (chipW + gap);
  const chipY = (n) => blobY + inner + Math.floor(n / perRow) * (chipH + gap);
  const at = probe === undefined ? -1 : keys.indexOf(probe);
  // The question sits over the chip that answers it, so its arrow goes
  // straight down: it must land in the first row to cross no other chip.
  const probeX = at >= 0 ? chipX(at) + chipW / 2 : width / 2;
  const toX = probeX;
  const toY = at >= 0 ? chipY(at) - 4 : blobY - 4;
  const arrow = at >= 0 ? 'var(--color-keep)' : 'var(--color-ink-soft)';
  return (
    <svg viewBox={`0 0 ${width} ${height}`} style={{ width: '100%', maxWidth: `${Math.round(width * 1.3)}px`, height: 'auto', display: 'block', margin: '0.4rem auto' }} role="img" aria-label={label}>
      <defs>
        <marker id={`${id}-punta`} markerWidth="8" markerHeight="8" refX="7" refY="4" orient="auto">
          <path d="M0,0 L8,4 L0,8 z" style={{ fill: arrow }} />
        </marker>
      </defs>
      <rect x={blobX} y={blobY} width={blobW} height={blobH} rx="18" style={{ fill: 'var(--color-sunk)', stroke: 'var(--color-rule-strong)' }} strokeWidth="1.4" />
      <text x={blobX + 14} y={blobY - 8} fontSize="12" fontWeight="700" style={{ fill: 'var(--color-ink-soft)' }}>{title}</text>
      {keys.map((k, n) => {
        const fill = n === at ? 'var(--color-keep-soft)' : tones[k] === 'mark' ? 'var(--color-mark-soft)' : 'var(--color-surface)';
        const stroke = n === at ? 'var(--color-keep)' : tones[k] === 'mark' ? 'var(--color-mark)' : 'var(--color-rule-strong)';
        return (
          <g key={k}>
            <rect x={chipX(n)} y={chipY(n)} width={chipW} height={chipH} rx="15" style={{ fill, stroke }} strokeWidth={n === at || tones[k] ? 2.2 : 1.2} />
            <text x={chipX(n) + chipW / 2} y={chipY(n) + chipH / 2 + 5} textAnchor="middle" fontSize="13" fontWeight="600" style={{ fill: 'var(--color-ink)' }}>{text(k)}</text>
          </g>
        );
      })}
      {probe !== undefined ? (
        <g>
          <rect x={probeX - probeW / 2} y={12} width={probeW} height={chipH} rx="15" style={{ fill: 'var(--color-surface)', stroke: arrow }} strokeWidth="1.6" strokeDasharray={at >= 0 ? undefined : '5 4'} />
          <text x={probeX} y={12 + chipH / 2 + 5} textAnchor="middle" fontSize="13" fontWeight="600" style={{ fill: 'var(--color-ink)' }}>{adds ? `+ ${probe}` : `¿${probe}?`}</text>
          <line x1={probeX} y1={12 + chipH + 2} x2={toX} y2={toY} style={{ stroke: arrow }} strokeWidth="1.6" markerEnd={`url(#${id}-punta)`} />
        </g>
      ) : null}
      {caption ? (
        <text x={width / 2} y={height - 10} textAnchor="middle" fontSize="12" style={{ fill: 'var(--color-ink-soft)' }}>{caption}</text>
      ) : null}
    </svg>
  );
}

{/* ChainTable — a hash table with chaining drawn still, with nodes wide enough for a RUT. COPIES the look of the hash-chaining recipe of <SequenceStepper> (sequenceStepperHashLayout.ts: a contiguous strip with its index, nodes with the key over a `next` field, lists hanging down, `null` where one ends), as the file-local `Chains` of 23-edd-tablas-hash.mdx does at a narrower node; neither copy is tested, so a change in the recipe is carried to both by hand and checked in a browser. Not `Chains` itself: that one draws names in 56 px, and a RUT needs twice that. `order` numbers every node in the order a walk over the table meets it — position by position, each list from its front —, `tones` paints a key's node (`keep`, `mark`, `visited`, `faint`), `values` adds a band under each key with its value, the node of a map: key, value, `next`; `picked` outlines the position a search goes to, and `window={[from, to]}` draws only those positions, with «…» where the table goes on, as `Chains` does, so two drawings side by side keep a size a projector can read. File-local (§6e-quater). */}

export function ChainTable({ chains, tones = {}, values, order = false, picked, window: shown, caption, label }) {
  const pad = 12;
  const pitch = 108;
  const cellH = 30;
  const nodeW = 98;
  const keyH = 24;
  const valueH = values ? 20 : 0;
  const nodeH = keyH + valueH + 12;
  const gap = 18;
  const indexY = 18;
  const cellY = 26;
  const [lo, hi] = shown ?? [0, chains.length - 1];
  const longest = Math.max(1, ...chains.slice(lo, hi + 1).map((c) => c.length));
  const stripW = (hi - lo + 1) * pitch;
  const width = Math.max(2 * pad + stripW + (shown ? 40 : 0), caption ? caption.replace(/`/g, '').length * 6.6 + 24 : 0);
  const left = (width - stripW) / 2;
  const nodeY = (k) => cellY + cellH + gap + k * (nodeH + gap);
  const height = nodeY(longest) - gap + 18 + (caption ? 30 : 6);
  const fill = { keep: 'var(--color-keep-soft)', mark: 'var(--color-mark-soft)', flag: 'var(--color-flag-soft)', visited: 'var(--color-sunk)', faint: 'var(--color-surface)' };
  const stroke = { keep: 'var(--color-keep)', mark: 'var(--color-mark)', flag: 'var(--color-flag)', visited: 'var(--color-rule-strong)', faint: 'var(--color-rule)' };
  const rank = {};
  chains.flat().forEach((key, n) => {
    rank[key] = n + 1;
  });
  return (
    <svg viewBox={`0 0 ${width} ${height}`} style={{ width: '100%', maxWidth: `${Math.round(width * 1.3)}px`, height: 'auto', display: 'block', margin: '0.4rem auto' }} role="img" aria-label={label}>
      {lo > 0 ? (
        <text x={left - 12} y={cellY + cellH / 2 + 4} textAnchor="middle" fontSize="13" style={{ fill: 'var(--color-ink-faint)' }}>…</text>
      ) : null}
      {hi < chains.length - 1 ? (
        <text x={left + stripW + 12} y={cellY + cellH / 2 + 4} textAnchor="middle" fontSize="13" style={{ fill: 'var(--color-ink-faint)' }}>…</text>
      ) : null}
      {chains.map((chain, i) => {
        if (i < lo || i > hi) return null;
        const x0 = left + (i - lo) * pitch;
        const cx = x0 + pitch / 2;
        return (
          <g key={i}>
            <text x={cx} y={indexY} textAnchor="middle" fontSize="11" fontWeight={picked === i ? 700 : 400} style={{ fill: picked === i ? 'var(--color-ink)' : 'var(--color-ink-faint)' }}>{i}</text>
            <rect x={x0} y={cellY} width={pitch} height={cellH} style={{ fill: 'var(--color-surface)', stroke: 'var(--color-rule-strong)' }} strokeWidth="1.2" />
            {chain.length === 0 ? (
              <text x={cx} y={cellY + cellH / 2 + 4} textAnchor="middle" fontSize="11" style={{ fill: 'var(--color-ink-faint)' }}>null</text>
            ) : (
              <g>
                <circle cx={cx} cy={cellY + cellH / 2} r="3" style={{ fill: 'var(--color-ink-soft)' }} />
                <line x1={cx} y1={cellY + cellH / 2} x2={cx} y2={nodeY(0) - 2} style={{ stroke: 'var(--color-ink-soft)' }} strokeWidth="1.4" />
                <path d={`M ${cx - 4} ${nodeY(0) - 7} L ${cx} ${nodeY(0) - 1} L ${cx + 4} ${nodeY(0) - 7} z`} style={{ fill: 'var(--color-ink-soft)' }} />
              </g>
            )}
            {chain.map((key, k) => {
              const y = nodeY(k);
              const t = tones[key];
              return (
                <g key={key} opacity={t === 'faint' ? 0.45 : undefined}>
                  <rect x={cx - nodeW / 2} y={y} width={nodeW} height={nodeH} rx="3" style={{ fill: t ? fill[t] : 'var(--color-surface)', stroke: t ? stroke[t] : 'var(--color-rule)' }} strokeWidth={t === 'keep' || t === 'mark' ? 2.2 : 1.2} />
                  <line x1={cx - nodeW / 2} y1={y + keyH} x2={cx + nodeW / 2} y2={y + keyH} style={{ stroke: t ? stroke[t] : 'var(--color-rule)' }} strokeWidth="1" />
                  <text x={cx} y={y + keyH / 2 + 5} textAnchor="middle" fontSize="12.5" fontWeight="600" style={{ fill: 'var(--color-ink)' }}>{key}</text>
                  {values ? (
                    <g>
                      <line x1={cx - nodeW / 2} y1={y + keyH + valueH} x2={cx + nodeW / 2} y2={y + keyH + valueH} style={{ stroke: t ? stroke[t] : 'var(--color-rule)' }} strokeWidth="1" />
                      <text x={cx} y={y + keyH + valueH / 2 + 4} textAnchor="middle" fontSize="11.5" style={{ fill: 'var(--color-ink-soft)' }}>{values[key]}</text>
                    </g>
                  ) : null}
                  {k < chain.length - 1 ? (
                    <g>
                      <circle cx={cx} cy={y + keyH + valueH + (nodeH - keyH - valueH) / 2} r="2.5" style={{ fill: 'var(--color-ink-soft)' }} />
                      <line x1={cx} y1={y + keyH + valueH + (nodeH - keyH - valueH) / 2} x2={cx} y2={nodeY(k + 1) - 2} style={{ stroke: 'var(--color-ink-soft)' }} strokeWidth="1.4" />
                      <path d={`M ${cx - 4} ${nodeY(k + 1) - 7} L ${cx} ${nodeY(k + 1) - 1} L ${cx + 4} ${nodeY(k + 1) - 7} z`} style={{ fill: 'var(--color-ink-soft)' }} />
                    </g>
                  ) : (
                    <text x={cx} y={y + nodeH + 13} textAnchor="middle" fontSize="10" style={{ fill: 'var(--color-ink-faint)' }}>null</text>
                  )}
                  {order ? (
                    <g>
                      <circle cx={cx - nodeW / 2} cy={y} r="8.5" strokeWidth="2" style={{ fill: 'var(--color-surface)', stroke: 'var(--color-ink-soft)' }} />
                      <text x={cx - nodeW / 2} y={y + 3.8} textAnchor="middle" fontSize="10.5" fontWeight="700" style={{ fill: 'var(--color-ink)' }}>{rank[key]}</text>
                    </g>
                  ) : null}
                </g>
              );
            })}
            {picked === i ? (
              <rect x={x0} y={cellY} width={pitch} height={cellH} fill="none" style={{ stroke: 'var(--color-focus)' }} strokeWidth="2.4" />
            ) : null}
          </g>
        );
      })}
      {caption ? (
        <text x={width / 2} y={height - 8} textAnchor="middle" fontSize="12" style={{ fill: 'var(--color-ink-soft)' }}>{codeText(caption)}</text>
      ) : null}
    </svg>
  );
}

{/* KeyTree — a binary search tree whose keys are too wide for <BinaryPicture>'s circles: the same placement (every node in the column of its inorder position, on the row of its depth) and the same tones and inorder colour (design-system.md §The tree figures' palette), with each node a pill as wide as a RUT. `order` numbers the nodes in inorder, as BinaryPicture's `visits="in"` does, and `strip` writes the inorder under the tree, each key in its node's column, which is why the row comes out sorted. `values` writes each key's value under it inside a taller node, the node of a map. `minColumns` widens the canvas as BinaryPicture's does, so a tree drawn beside a wider figure comes out at the same size. `tones` paints a node and its slot in the strip. File-local (§6e-quater); BinaryPicture is the component, this only exists because a RUT does not fit in it. */}

export function KeyTree({ tree, tones = {}, values, order = false, strip = false, minColumns = 0, caption, label }) {
  const pad = 12;
  const nodeW = 98;
  const nodeH = values ? 42 : 30;
  const colW = 108;
  const levelH = values ? 70 : 62;
  const slotH = 30;
  const nodes = [];
  const place = (t, depth) => {
    if (!t) return;
    place(t.l, depth + 1);
    nodes.push({ v: t.v, l: t.l, r: t.r, depth, column: nodes.length });
    place(t.r, depth + 1);
  };
  place(tree, 0);
  const column = Object.fromEntries(nodes.map((n) => [n.v, n.column]));
  const deepest = Math.max(...nodes.map((n) => n.depth));
  const treeW = nodes.length * colW;
  const width = Math.max(2 * pad + Math.max(nodes.length, minColumns) * colW, caption ? caption.length * 6.6 + 24 : 0);
  const left = (width - treeW) / 2;
  const cx = (v) => left + column[v] * colW + colW / 2;
  const cy = (depth) => pad + 8 + nodeH / 2 + depth * levelH;
  const stripY = cy(deepest) + nodeH / 2 + 28;
  const bottom = strip ? stripY + slotH : cy(deepest) + nodeH / 2;
  const height = bottom + (caption ? 34 : 12);
  const tone = {
    keep: ['var(--color-keep-soft)', 'var(--color-keep)', 2.2],
    focus: ['var(--color-surface)', 'var(--color-focus)', 2.4],
    mark: ['var(--color-mark-soft)', 'var(--color-mark)', 2.2],
  };
  const paint = (v) => tone[tones[v]] ?? ['var(--color-surface)', 'var(--color-rule-strong)', 1.3];
  return (
    <svg viewBox={`0 0 ${width} ${height}`} style={{ width: '100%', maxWidth: `${Math.round(width * 1.3)}px`, height: 'auto', display: 'block', margin: '0.4rem auto' }} role="img" aria-label={label}>
      {nodes.flatMap((n) =>
        [n.l, n.r].filter(Boolean).map((child) => (
          <line key={`e${child.v}`} x1={cx(n.v)} y1={cy(n.depth) + nodeH / 2} x2={cx(child.v)} y2={cy(n.depth + 1) - nodeH / 2} style={{ stroke: 'var(--color-rule-strong)' }} strokeWidth="1.4" />
        )),
      )}
      {nodes.map((n) => {
        const [fill, stroke, weight] = paint(n.v);
        return (
          <g key={n.v} opacity={tones[n.v] === 'faint' ? 0.45 : undefined}>
            <rect x={cx(n.v) - nodeW / 2} y={cy(n.depth) - nodeH / 2} width={nodeW} height={nodeH} rx={values ? 12 : nodeH / 2} style={{ fill, stroke }} strokeWidth={weight} />
            <text x={cx(n.v)} y={cy(n.depth) + (values ? -2 : 5)} textAnchor="middle" fontSize="12.5" fontWeight="600" style={{ fill: 'var(--color-ink)' }}>{n.v}</text>
            {values ? (
              <text x={cx(n.v)} y={cy(n.depth) + 14} textAnchor="middle" fontSize="11.5" style={{ fill: 'var(--color-ink-soft)' }}>{values[n.v]}</text>
            ) : null}
            {order ? (
              <g>
                <circle cx={cx(n.v) - nodeW / 2 + 6} cy={cy(n.depth) - nodeH / 2} r="8.5" strokeWidth="2" style={{ fill: 'var(--color-surface)', stroke: 'var(--color-accent)' }} />
                <text x={cx(n.v) - nodeW / 2 + 6} y={cy(n.depth) - nodeH / 2 + 3.8} textAnchor="middle" fontSize="10.5" fontWeight="700" style={{ fill: 'var(--color-ink)' }}>{n.column + 1}</text>
              </g>
            ) : null}
            {strip ? (
              <g>
                <line x1={cx(n.v)} y1={cy(n.depth) + nodeH / 2 + 3} x2={cx(n.v)} y2={stripY - 3} style={{ stroke: 'var(--color-rule)' }} strokeWidth="1" strokeDasharray="2 4" />
                <rect x={left + n.column * colW} y={stripY} width={colW} height={slotH} style={{ fill: tones[n.v] === 'keep' ? 'var(--color-keep-soft)' : 'var(--color-surface)', stroke: 'var(--color-accent)' }} strokeWidth="1.6" />
                <text x={cx(n.v)} y={stripY + slotH / 2 + 5} textAnchor="middle" fontSize="12.5" fontWeight="600" style={{ fill: 'var(--color-ink)' }}>{n.v}</text>
              </g>
            ) : null}
          </g>
        );
      })}
      {caption ? (
        <text x={width / 2} y={height - 10} textAnchor="middle" fontSize="12" style={{ fill: 'var(--color-ink-soft)' }}>{caption}</text>
      ) : null}
    </svg>
  );
}

## Set · Conjunto

<Slide title="Un conjunto">
Un **conjunto** es una colección en la que cada elemento está una vez o no
está: no hay repetidos ni posiciones, y el conjunto no recuerda en qué orden
llegaron sus elementos. Es el
conjunto de las matemáticas, que no distingue cuántas veces ni en qué orden
se escribe un elemento:

$$
\{a, b, a\} = \{a, b\} = \{b, a\}
$$

Se lee «el conjunto de $$a$$, $$b$$ y $$a$$ es el mismo que el de $$a$$ y
$$b$$, y que el de $$b$$ y $$a$$». La cantidad de elementos de un conjunto
$$A$$ se escribe $$|A|$$.

En el registro, una persona votó o no votó. Agregar un RUT que ya está deja
el conjunto como estaba, y contar sus RUTs da cuántas personas votaron.

<Slide title="Conjuntos en la vida real">
Un conjunto aparece en cualquier lugar donde importa si algo está, no cuántas
veces ni en qué orden llegó.

- **El corrector ortográfico.** Guarda las palabras válidas del idioma y, por
  cada palabra escrita, pregunta si está; la que no está se subraya.
- **Los números bloqueados del teléfono.** Cada llamada que entra pregunta si
  su número está entre los bloqueados. Bloquear agrega un número, y
  desbloquear lo saca.
- **Los ramos aprobados de un estudiante.** Inscribir un ramo pregunta si su
  prerrequisito está entre los aprobados, y cada semestre agrega los que
  aprobó.
- **Las páginas que visita un buscador.** El programa que recorre la web
  sigue los enlaces de cada página y, antes de visitar una, pregunta si ya
  pasó por ella: sin esa pregunta, recorrería las mismas páginas para
  siempre.

Los cuatro hacen lo mismo que el registro: preguntar si un elemento está,
agregarlo y sacarlo, y cada elemento está una vez o no está. Ese
comportamiento está definido en un **tipo de dato abstracto** (TDA) llamado
**Set**.

</Slide>

<Slide title="El TDA Set">
Un **Set** —en español, **conjunto**— es una colección **sin repetidos** y

<Slide title="Las reglas del contrato Set">
Un conjunto no tiene repetidos ni posiciones, y de ahí salen las reglas del
contrato:

- **`add(x)` de un elemento que ya está no lo agrega otra vez.** El conjunto
  queda igual y `add` retorna falso: quien llama sabe si el elemento era
  nuevo sin preguntar antes.
- **`remove(x)` de un elemento que no está no cambia nada**, y retorna falso.
- **El recorrido entrega cada elemento exactamente una vez**, en un orden que
  el contrato no promete.

Para un conjunto $$A$$, `size()` retorna $$|A|$$: cuenta cada elemento una
vez.

Qué significa que dos elementos sean **iguales** no lo decide el conjunto: lo
decide el tipo de los elementos. El conjunto solo pregunta.

</Slide>

<Slide title="Un Set sobre una tabla hash">
Dos estructuras de la unidad ya cumplen el contrato, y la primera es la
**tabla hash con listas**. Su primera invariante, **ninguna clave está dos
veces**, es la regla del Set, y sus tres métodos
públicos son las tres operaciones: `contains` recorre una sola lista, `add`
pregunta antes con `contains` y `remove` desengancha el nodo. `size()`
retorna el contador `size` que la tabla ya lleva.

- **Lo que paga.** Las tres operaciones cuestan $$\Theta(1)$$ esperado,
  siempre que la función hash reparta parejo y la tabla crezca con las claves;
  si todas caen en la misma lista, $$\Theta(N)$$.
- **Lo que no sabe hacer.** Nada que dependa del orden. La función reparte las
  claves sin relación con su orden, así que el recorrido, que va posición por
  posición, las entrega en un orden que no significa nada.

<Slide title="Un Set sobre un árbol AVL">
El árbol AVL también cumple el contrato. Su invariante de orden impide que un
valor esté dos veces —uno igual no estaría ni a la izquierda ni a la
derecha—, y sus tres operaciones bajan por un solo camino. Su `insert` y su
`remove` no responden si cambiaron algo; para responder lo que piden `add` y
`remove`, basta con preguntar antes con `contains`, como hace la tabla en su
`add`.

- **Lo que paga.** Las tres operaciones cuestan $$O(\log N)$$ en el peor
  caso, llegue lo que llegue: la invariante de balance acota la altura. Cada
  modificación lo paga con las rotaciones y las alturas que actualiza al
  volver.
- **Lo que sabe hacer además.** El recorrido en inorden entrega los
  elementos ordenados, y el menor, el mayor o el siguiente a uno dado se
  encuentran bajando un camino.

<Slide title="Costos de las dos implementaciones">
| Operación     | Tabla hash, esperado     | Tabla hash, peor caso | Árbol AVL, esperado | Árbol AVL, peor caso |
| ------------- | ------------------------ | --------------------- | ------------------- | -------------------- |
| `contains(x)` | $$\Theta(1)$$            | $$\Theta(N)$$         | $$O(\log N)$$       | $$O(\log N)$$        |
| `add(x)`      | $$\Theta(1)$$ amortizado | $$\Theta(N)$$         | $$O(\log N)$$       | $$O(\log N)$$        |
| `remove(x)`   | $$\Theta(1)$$            | $$\Theta(N)$$         | $$O(\log N)$$       | $$O(\log N)$$        |
| `size()`      | $$\Theta(1)$$            | $$\Theta(1)$$         | $$\Theta(1)$$       | $$\Theta(1)$$        |
| `iterator()`  | $$\Theta(N + M)$$        | $$\Theta(N + M)$$     | $$\Theta(N)$$       | $$\Theta(N)$$        |

El caso esperado de la tabla supone que la función hash reparte las claves
parejo; si todas caen en la misma lista, cada operación la recorre entera. El
árbol no supone nada: la invariante de balance acota su altura llegue lo que
llegue, y sus dos columnas son iguales.

$$M$$ es la cantidad de posiciones del arreglo de la tabla. `size()` cuesta
$$\Theta(1)$$ en las dos porque cada una lleva un contador que sube con `add`
y baja con `remove`. Recorrer la tabla cuesta $$\Theta(N + M)$$ porque pasa por
todas sus posiciones, también por las vacías.

</Slide>

<Slide title="La memoria de las dos implementaciones">
La tabla guarda el arreglo de $$M$$ posiciones y un nodo por clave, con la
clave y una referencia al siguiente de su lista. Ocupa $$\Theta(N + M)$$, que
crece con la mayor de las dos cantidades:

- **Mientras solo entran claves**, cada redimensión duplica $$M$$ cuando $$N$$
  lo alcanza. $$M$$ crece al ritmo de $$N$$, y la tabla ocupa $$\Theta(N)$$.
- **Al sacar claves**, la tabla no se achica. Si salen casi todas, sigue
  pagando el arreglo que tenía, y $$M$$ puede ser mucho mayor que $$N$$.

El árbol no tiene arreglo. Guarda un nodo por clave, con la clave, una
referencia a cada hijo y su altura, y ocupa $$\Theta(N)$$ siempre.

</Slide>

<Slide title="Las preguntas que dependen del orden">
Las operaciones del contrato miran un elemento a la vez: si está, agregarlo o
sacarlo. Otras preguntas dependen del **orden** de los elementos, de cuál va
antes que cuál. La lista que el registro publica al cerrar, ordenada por RUT,
es una de ellas. Las más comunes son:

- recorrer los elementos de menor a mayor;
- el menor o el mayor;
- el siguiente o el anterior a uno dado;
- todos los que caen entre dos valores.

Ninguna es parte del contrato Set. Las dos implementaciones pueden
responderlas, pero a precios muy distintos: una guarda los elementos sin
relación con su orden, y la otra, ordenados.

</Slide>

<Slide title="El orden en la tabla hash">
La función hash reparte las claves por el arreglo sin ninguna relación con su
orden: dos claves vecinas en el orden caen en posiciones que no tienen nada
que ver. Eso hace barato preguntar si una clave está, y deja a la tabla sin
atajo para el orden. Nada indica dónde está la menor ni cuál sigue a una
clave dada, así que cada pregunta mira todas las posiciones:

- **la menor, la mayor o la siguiente a una dada:** recorre la tabla entera
  quedándose con la que busca, en $$\Theta(N + M)$$;
- **las que caen entre dos valores:** recorre la tabla entera y separa las
  del tramo, también en $$\Theta(N + M)$$;
- **todas en orden:** las copia a una lista y la ordena, en
  $$\Theta(M + N \log N)$$.

<Slide title="El orden en el árbol AVL">
En el árbol, el orden está en su forma: la invariante de orden pone a la
izquierda de cada nodo todo lo menor que él, y a su derecha todo lo mayor.
Por eso el inorden entrega los valores de menor a mayor, y las preguntas por
un valor se responden bajando un solo camino, de largo $$O(\log N)$$:

- **todos en orden:** el inorden, en $$\Theta(N)$$;
- **el menor:** bajar por la izquierda hasta el último nodo; **el mayor**,
  por la derecha;
- **el siguiente a $$x$$:** bajar desde la raíz, a la izquierda en cada valor
  mayor que $$x$$ y a la derecha en los demás, anotando cada mayor; el último
  anotado es el siguiente. **El anterior**, al revés.

En la fila del inorden, los valores que caen entre $$a$$ y $$b$$ son casillas
seguidas. Para entregarlos se baja hasta el primero que no es menor que $$a$$,
por un camino de largo $$O(\log N)$$, y desde ahí se sigue el inorden, uno
detrás del otro, hasta pasar $$b$$. Si el tramo tiene $$k$$ valores, cuesta
$$O(\log N + k)$$: un camino para llegar y un paso por cada valor que
entrega.

<Slide title="Los costos de las preguntas por el orden">
| Pregunta                             | Tabla hash                 | Árbol AVL           |
| ------------------------------------ | -------------------------- | ------------------- |
| ¿Está $$x$$?                         | $$\Theta(1)$$ esperado     | $$O(\log N)$$       |
| El menor, o el mayor                 | $$\Theta(N + M)$$          | $$O(\log N)$$       |
| El siguiente a $$x$$                 | $$\Theta(N + M)$$          | $$O(\log N)$$       |
| Los $$k$$ que están entre $$a$$ y $$b$$ | $$\Theta(N + M)$$       | $$O(\log N + k)$$   |
| Todos, en orden                      | $$\Theta(M + N \log N)$$   | $$\Theta(N)$$       |

La tabla responde cada pregunta por el orden mirando todas sus posiciones, y
para entregarlos todos en orden, además los ordena. El árbol las responde
bajando un camino, o con el inorden. En la única pregunta que no depende del
orden, si un elemento está, gana la tabla: $$\Theta(1)$$ esperado contra
$$O(\log N)$$.

</Slide>

<Slide title="Tabla hash o árbol según el orden">
La elección depende de qué preguntas se le harán al conjunto, y de cuántas
veces:

- **Si entre ellas están las del orden, y se hacen una y otra vez**, conviene
  un árbol: las responde bajando un camino, y la tabla miraría todas sus
  posiciones en cada una.
- **Si no hay ninguna**, conviene una tabla hash: responde las tres
  operaciones del contrato en $$\Theta(1)$$ esperado, contra el
  $$O(\log N)$$ del árbol.
- **Si hay una sola, al final**, también conviene la tabla: se ordena una
  vez, cuando hace falta.

El registro es este último caso. Durante el día, cada voto pregunta si el RUT
está y lo agrega, mientras la persona espera en la mesa: cada voto cuesta
$$\Theta(1)$$ esperado con la tabla y $$O(\log N)$$ con el árbol. La lista
ordenada se pide una sola vez, al cerrar, cuando ya nadie espera: la tabla
copia sus RUTs a una lista y la ordena, en $$\Theta(M + N \log N)$$.

En el total del día, los dos gastan $$\Theta(N \log N)$$, la tabla en el caso
esperado. Lo que cambia es cuándo se paga el orden: la tabla lo paga una vez,
al final, y el árbol lo cobra en cada voto.

</Slide>

## HashSet

<Slide title="Set en Java">
Java declara el contrato en la interfaz `java.util.Set`, con los mismos
nombres:

| El TDA        | Java `Set<E>`                     |
| ------------- | --------------------------------- |
| `contains(x)` | `contains(x)`                     |
| `size()`      | `size()`                          |
| `iterator()`  | `iterator()`, o un `for` sobre el conjunto |
| `add(x)`      | `add(x)`                          |
| `remove(x)`   | `remove(x)`                       |

```java
public interface Set<E> {
    boolean contains(Object o);
    int size();
    Iterator<E> iterator();
    boolean add(E e);
    boolean remove(Object o);
}
```

La interfaz trae además otros métodos —`isEmpty`, `addAll`, `clear`— que no
son parte del TDA: son comodidades escritas sobre estos cinco. Una interfaz
no se puede instanciar; quien guarda los elementos es una clase que la
implementa.

Java implementa el contrato Set sobre una tabla hash con listas en la clase
`java.util.HashSet`. El registro de votantes se escribe con las operaciones
del contrato, y la variable se declara del tipo del contrato, `Set`: solo la
línea que crea el conjunto nombra la estructura.

```java
Set<String> voted = new HashSet<>();
voted.add("18.155.218-2");
voted.add("13.180.992-1");
voted.add("13.959.276-K");
voted.add("17.814.358-1");
voted.add("22.715.853-0");
voted.add("12.547.354-7");

voted.add("13.180.992-1");      // false: ya votó
voted.contains("13.959.276-K"); // true
voted.contains("20.118.702-8"); // false
voted.size();                   // 6
```

`add`, `remove` y `contains` cuestan $$\Theta(1)$$ esperado, como en la tabla
con listas: la tabla de `HashSet` empieza con 16 posiciones y duplica su
tamaño cuando el factor de carga pasa de $$0{,}75$$.

</Slide>

<Slide title="El recorrido de un HashSet">
Un `for` recorre el conjunto con su `iterator()`, que entrega cada elemento
una vez, en el orden de las posiciones de la tabla:

```java
for (String rut : voted) {
    System.out.println(rut);
}
```


No es el orden en que votaron ni el de los RUTs: es el que dejó la función
hash de `String` con el tamaño de esa tabla, y cambia si la tabla crece. La
lista que el registro publica ordenada por RUT no puede contar con este orden.

</Slide>

<Slide title="Lo que la tabla le pide a un elemento">
Un `HashSet` guarda elementos de cualquier tipo, y para ubicar uno busca en
dos pasos, como la tabla con listas:

1. calcula un número del elemento con una **función hash**, y lo reduce a una
   posición;
2. compara el elemento buscado con los de la lista de esa posición, con una
   **igualdad**.

En Java, las dos cosas son métodos que escribe el tipo del elemento:
**`hashCode`** da el número, y **`equals`** decide la igualdad.

```java
words.contains(copy);               // true
"hola".hashCode();                  // 3208380
copy.hashCode();                    // 3208380
```

## Diseñar una clave

<Slide title="El mismo RUT escrito de dos maneras">

otra. Para un `HashSet<String>`, dos textos distintos
son dos elementos distintos, aunque nombren a la misma persona: `add` del
segundo retorna verdadero, y el registro la cuenta dos veces.

Lo que identifica a una persona es el número de su RUT, no la manera de
escribirlo. Hace falta un tipo propio para el RUT, con su propia igualdad.

</Slide>

<Slide title="Una clase para el RUT">
Un `Rut` guarda el número y el dígito verificador por separado. Cada mesa lee
el texto, le quita los puntos y separa el número del dígito, así que las dos
escrituras dan un `Rut` con los mismos campos.

```java
class Rut {
    private final int number;
    private final char dv;

    Rut(int number, char dv) {
        if (number <= 0) throw new IllegalArgumentException();
        this.number = number;
        this.dv = dv;
    }
}
```

Pero son dos objetos, y para Java todavía no son el mismo RUT:

```java
Rut a = new Rut(13180992, '1');
Rut b = new Rut(13180992, '1');
a.equals(b);   // false
```

El `equals` que `Rut` hereda de `Object` hace lo mismo que `==`: responde
verdadero solo para el mismo objeto.

</Slide>

<Slide title="El RUT en un HashSet">
Con la clase recién escrita, el `HashSet` todavía no funciona. `Rut` hereda de
`Object` un `equals` y un `hashCode` que miran el objeto y no sus campos:

```java
Set<Rut> voted = new HashSet<>();
voted.add(a);
voted.add(b);       // true: lo agrega otra vez
voted.size();       // 2
```

El `HashSet` cuenta dos veces a la misma persona. Hay que escribir los dos
métodos, empezando por la igualdad.

</Slide>

<Slide title="La igualdad de dos RUT">
`Rut` reescribe `equals` para comparar los campos: dos RUT son iguales si
tienen el mismo número y el mismo dígito.

```java
@Override
public boolean equals(Object other) {
    if (!(other instanceof Rut)) return false;
    Rut r = (Rut) other;
    return number == r.number && dv == r.dv;
}
```

`equals` recibe un `Object`, porque cualquier objeto se puede comparar con
cualquier otro: si el otro no es un `Rut`, no es igual. `@Override` le pide
al compilador que verifique que el método reemplaza al de `Object`; con un
parámetro de otro tipo, el compilador lo rechaza.

Con este `equals`, las dos lecturas son el mismo RUT:

```java
a.equals(b);   // true
```

</Slide>

<Slide title="Un equals sin hashCode">
Con `equals`, `a` y `b` son iguales, pero el registro todavía los cuenta dos
veces:

```java
Set<Rut> voted = new HashSet<>();
voted.add(a);
voted.add(b);   // true: lo agrega otra vez
voted.size();   // 2
```

Escribir `equals` arregla solo el segundo paso de la búsqueda. El primero
sigue usando el `hashCode` que `Rut` hereda de `Object`, que no mira los
campos: da un número propio de cada objeto. `a` y `b`, iguales para `equals`,
reciben números distintos, caen en posiciones distintas, y `equals` nunca
llega a compararlos.

</Slide>

<Slide title="Lo que se le pide a la función hash">
La función hash de una clave cumple los tres requisitos de toda función hash,
mirados desde su igualdad:

- **Determinista:** dos claves iguales dan el mismo número. Para eso usa solo
  los campos que compara la igualdad, y campos que no cambian mientras la
  clave está en una tabla.
- **Uniforme:** reparte las claves distintas. Para eso usa todos esos campos,
  no una parte.
- **Eficiente:** hace una cuenta por campo.

En Java, el primer requisito es el contrato entre `equals` y `hashCode`:

$$
a.\text{equals}(b) \;\Rightarrow\; a.\text{hashCode}() = b.\text{hashCode}()
$$

que se lee «si $$a$$ es igual a $$b$$, sus `hashCode` son iguales». Al revés
no hace falta: dos claves distintas pueden dar el mismo número, y esa
colisión la resuelve la lista.

</Slide>

<Slide title="Un hashCode constante">
El intento más simple es un `hashCode` que retorna siempre el mismo número.
Es determinista y cumple el contrato: dos RUT iguales dan el mismo número,
porque todos lo dan.

```java
@Override
public int hashCode() {
    return 0;
}
```

No es uniforme. Todos los elementos caen en la misma lista, y cada búsqueda
la recorre entera: la tabla pasa a costar $$\Theta(N)$$ por operación, lo que
cuesta una lista enlazada.

<Slide title="Qué base elegir">
Lo natural sería agregarle al número del RUT el dígito verificador como una
cifra más, con base 10:

$$
10 \cdot n + d
$$

con $$n$$ el número y $$d$$ el dígito. Pero en Java el dígito es un `char`, y en
una cuenta vale su código: de 48 a 57 para `'0'` a `'9'`, y 75 para `'K'`. Esos
códigos tienen dos cifras, y se meten en las del número:

$$
\begin{aligned}
10 \cdot 13\,903\,998 + 75 &= 139\,039\,980 + 75 = 139\,040\,055 \\
10 \cdot 13\,904\,000 + 55 &= 139\,040\,000 + 55 = 139\,040\,055
\end{aligned}
$$

El código de la K, 75, es 20 más que el del 7, 55, y con base 10 sumar 20 al
final es lo mismo que sumarle 2 al número. Por eso un RUT terminado en K choca
con el que está dos números más arriba, si ese termina en 7.

Un RUT en particular rara vez choca así, pero en un registro de millones pasa
miles de veces: entre los números 1 y 27 000 000 hay 4 864 parejas. Ninguna
rompe la tabla, porque la lista resuelve cada choque, pero cada una alarga una
lista, y una base mejor las evita todas. Con 31, los mismos dos RUT dan números
distintos:

$$
\begin{aligned}
31 \cdot 13\,903\,998 + 75 &= 431\,024\,013 \\
31 \cdot 13\,904\,000 + 55 &= 431\,024\,055
\end{aligned}
$$

</Slide>

<Slide title="Por qué Java usa 31">
Java usa 31 en `String.hashCode` y en `Objects.hash`, por tres razones.

**Es mayor que lo que difieren las letras.** Los códigos de `'a'` a `'z'`
difieren a lo más en 25, así que dos palabras cortas del mismo largo no se
compensan. Con base 10 chocan enseguida:

| Palabra | $$10 \cdot$$ primera $$+$$ segunda | $$31 \cdot$$ primera $$+$$ segunda |
| ------- | --------------------------------- | --------------------------------- |
| «al»    | 1 078                             | 3 115                             |
| «bb»    | 1 078                             | 3 136                             |

**Es impar.** Una base par, cuando el `int` se desborda, va perdiendo los bits
de los primeros caracteres.

**Es barata.** Multiplicar por 31 es multiplicar por 32 y restar una vez, y
como 32 es una potencia de 2, multiplicar por 32 es correr los bits cinco
lugares a la izquierda:

$$
31 \cdot x = 2^5 \cdot x - x
$$

```java
int h = (x << 5) - x;   // lo mismo que 31 * x
```

</Slide>

<Slide title="El hashCode de Rut">
Con base 31, la construcción está completa: el número del RUT por 31, más el
código de su dígito verificador.

```java
@Override
public int hashCode() {
    return 31 * number + dv;
}
```

Cumple los tres requisitos:

- **Determinista:** usa solo los dos campos que compara `equals`, que son
  `final`.
- **Uniforme:** usa los dos, y la base 31 separa dos RUT distintos.
- **Eficiente:** hace una multiplicación y una suma.

</Slide>

**Un objeto que está en un conjunto no cambia los campos que usan `equals` y

<Slide title="Qué identifica a un elemento">
Para cualquier clase, el diseño parte del problema: qué hace que dos
elementos sean el mismo. Esos son los **campos de la identidad**, y `equals` y
`hashCode` usan esos y ningún otro.

- **Un dato que cambia no es identidad.** Lo que le pasa a un elemento con el
  tiempo no lo convierte en otro.
- **Un campo que se calcula de otros puede quedar fuera.** No dice nada que
  los demás no digan.
- **Los campos de la identidad son `final`.** Así nada los cambia mientras el
  elemento está en una colección.

| Campo de una mesa de votación | ¿Identidad?               |
| ----------------------------- | ------------------------- |
| la comuna                     | sí                        |
| el local                      | sí                        |
| el número                     | sí                        |
| si ya cerró                   | no: cambia durante el día |
| los votos emitidos            | no: cambian con cada voto |

En el RUT, el dígito verificador se calcula del número. Si el constructor de
`Rut` lo verificara, el número solo bastaría; no lo verifica, así que un
dígito mal digitado es otro RUT, y los dos campos son su identidad.

</Slide>

<Slide title="La receta de una clave">
Con los campos de la identidad elegidos, los dos métodos salen de una
receta:

1. **`equals`:** `instanceof` y el cast, y después cada campo: con `==` si es
   primitivo, y con su `equals` si es un objeto.
2. **`hashCode`:** el número del primer campo y, por cada campo siguiente,
   multiplicar por 31 y sumar su número.
Al terminar, un chequeo: dos elementos iguales para `equals` dan el mismo
`hashCode`.

</Slide>

<Slide title="Una función hash para cualquier clave">
La construcción del RUT sirve para cualquier clave: cada campo se convierte
en un número con la función hash de su tipo, y los números se combinan con
Horner y una base impar. Con tres campos:

$$
h = (h_1 \cdot 31 + h_2) \cdot 31 + h_3
$$

se lee «el número del primer campo por 31, más el del segundo; todo eso por
31, más el del tercero». En Java, el número de cada campo es:

| Campo                       | Su número                                                       |
| --------------------------- | --------------------------------------------------------------- |
| `int`                       | el mismo                                                        |
| `char`                      | su código                                                       |
| `long`, `double`, `boolean` | `Long.hashCode(x)`, `Double.hashCode(x)`, `Boolean.hashCode(x)` |
| `String` u otro objeto      | su `hashCode()`, o 0 si es `null`                               |
| Un arreglo                  | `Arrays.hashCode(a)`                                            |

Con campos como los textos, los choques no se pueden evitar del todo: la base
los reparte, pero no los elimina.

</Slide>

<Slide title="Una mesa de votación">
Una mesa se identifica por su comuna, su local y su número, que son `final`;
si ya cerró es un dato, y queda fuera. `equals` compara los tres campos de la
identidad: el número con `==`, y los textos con su propio `equals`.

```java
class VotingTable {
    private final String commune;
    private final String place;
    private final int number;
    private boolean closed;   // un dato: cambia durante el día

    // el constructor rechaza textos null

    @Override
    public boolean equals(Object other) {
        if (!(other instanceof VotingTable)) return false;
        VotingTable t = (VotingTable) other;
        return number == t.number
            && commune.equals(t.commune)
            && place.equals(t.place);
    }
}
```

</Slide>

<Slide title="El hashCode de una mesa">
`hashCode` usa los mismos tres campos: parte del número del primer campo, y
por cada campo siguiente multiplica por 31 y le suma su número.

```java
@Override
public int hashCode() {
    int result = commune.hashCode();
    result = 31 * result + place.hashCode();
    result = 31 * result + number;
    return result;
}
```

Cada texto aporta su `String.hashCode`, que ya es Horner sobre sus
caracteres, y el número de la mesa se suma como está. Dos mesas iguales
tienen los mismos tres campos, y con eso el mismo número.

</Slide>

<Slide title="Las mesas en un HashSet">
Con los dos métodos, el `HashSet` encuentra una copia de una mesa, y no la
confunde con otra de otro local:

```java
Set<VotingTable> reported = new HashSet<>();
reported.add(new VotingTable("Ñuñoa", "Liceo 7", 3));
reported.contains(new VotingTable("Ñuñoa", "Liceo 7", 3)); // true
reported.contains(new VotingTable("Ñuñoa", "Liceo 8", 3)); // false
```

</Slide>

<Slide title="Objects.hash como atajo">
`java.util.Objects.hash` hace la receta del `hashCode` en una línea, con los
campos que recibe:

```java
@Override
public int hashCode() {
    return Objects.hash(commune, place, number);
}
```

Cumple el contrato si recibe los mismos campos que compara `equals`. Su número
no es el de la versión escrita a mano —su receta parte de 1, no del primer
campo—, y no importa: el contrato no pide un número en particular. Es algo
más lento, porque arma un arreglo con los campos.

</Slide>

<Slide title="Una clave hecha de otras claves">
Un vocal de mesa se identifica por la persona y por la mesa donde trabaja: sus
campos son un `Rut` y una `VotingTable`, dos clases que ya tienen su `equals` y
su `hashCode`. La receta no cambia, y cada método le pide a cada campo el
suyo:

```java
class PollWorker {
    private final Rut person;
    private final VotingTable table;

    @Override
    public boolean equals(Object other) {
        if (!(other instanceof PollWorker)) return false;
        PollWorker w = (PollWorker) other;
        return person.equals(w.person) && table.equals(w.table);
    }

    @Override
    public int hashCode() {
        return 31 * person.hashCode() + table.hashCode();
    }
}
```

`equals` usa el `equals` del `Rut` y el de la mesa, y `hashCode` combina sus
dos `hashCode` con la receta.

</Slide>

<Slide title="Errores en equals y hashCode">
| Error                                                     | Lo que pasa                                                                                                                  |
| --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `equals(VotingTable t)` en vez de `equals(Object other)`  | Es otro método, no el de `Object`: la colección sigue llamando al heredado, y una copia no se encuentra. `@Override` lo detecta. |
| `hashCode` usa un campo que `equals` no compara           | Dos elementos iguales pueden dar números distintos: rompe el contrato.                                                        |
| `hashCode` deja fuera un campo que `equals` compara       | Cumple el contrato, pero reparte peor: chocan los elementos que solo difieren en ese campo.                                   |
| `hashCode` suma los campos, como `number + dv`            | Los campos se compensan: 13.180.999-9 y 13.181.000-8 dan los dos 13 181 056.                                                  |
| Un campo de la identidad que no es `final`                | Si cambia mientras el elemento está en el `HashSet`, queda perdido en él.                                                     |

</Slide>

## TreeSet y el orden de una clave

<Slide title="La clase TreeSet">
Java implementa el contrato Set sobre un árbol de búsqueda balanceado en la
clase `java.util.TreeSet`. Su árbol es un **rojo-negro**, otro árbol de
búsqueda balanceado como el AVL, y `add`, `remove` y `contains` cuestan
$$O(\log N)$$ en el peor caso. En el registro cambia solo la línea que crea el
conjunto:

```java
Set<String> voted = new TreeSet<>();
// un add por cada voto
for (String rut : voted) {
    System.out.println(rut);
}
```

```text
12.547.354-7
13.180.992-1
13.959.276-K
17.814.358-1
18.155.218-2
22.715.853-0
```

El recorrido de un `TreeSet` es el inorden de su árbol: entrega los elementos
de menor a mayor. Para eso tiene que poder compararlos, y un `String` sabe
compararse: su `compareTo` ordena los textos.

</Slide>

<Slide title="Las preguntas del orden en TreeSet">
`TreeSet` responde también las preguntas que dependen del orden, con métodos
que no son parte del contrato Set: Java los declara en otro contrato, la
interfaz `NavigableSet`, que `TreeSet` implementa. Para usarlos, la variable
se declara de ese tipo:

| Pregunta                          | Método                 | Costo              |
| --------------------------------- | ---------------------- | ------------------ |
| El menor, el mayor                | `first()`, `last()`    | $$O(\log N)$$      |
| El siguiente a $$x$$, el anterior | `higher(x)`, `lower(x)` | $$O(\log N)$$     |
| El primero desde $$x$$, el último hasta $$x$$ | `ceiling(x)`, `floor(x)` | $$O(\log N)$$ |
| Los $$k$$ entre $$a$$ y $$b$$     | `subSet(a, b)`, `subSet(a, true, b, true)` | $$O(\log N + k)$$ |

```java
NavigableSet<String> voted = new TreeSet<>();
// un add por cada voto
voted.first();                 // "12.547.354-7"
voted.higher("13.180.992-1");  // "13.959.276-K"
voted.floor("20.118.702-8");   // "18.155.218-2"
voted.subSet("13.000.000", "18.000.000");
// [13.180.992-1, 13.959.276-K, 17.814.358-1]
```

`ceiling` y `floor` aceptan un valor que no está: responden el elemento más
cercano por arriba o por abajo. `subSet(a, b)` incluye a `a` y deja fuera a
`b`; con cuatro argumentos, cada booleano dice si su extremo entra, y
`subSet(a, true, b, true)` incluye a los dos.

</Slide>

<Slide title="Lo que el árbol le pide a un elemento">
Un `TreeSet` ubica un elemento como el árbol AVL: lo compara con el de cada
nodo y baja a la izquierda o a la derecha. No calcula ningún número ni usa
`equals`: necesita un **orden**, y con él decide también si un elemento ya
está. En Java, el orden es el método **`compareTo`** de la interfaz
`Comparable`, que escribe el tipo del elemento. Los tipos de Java ya lo
traen:

| Tipo        | `compareTo`              |
| ----------- | ------------------------ |
| `String`    | el orden del diccionario |
| `Integer`   | el orden de los números  |
| `Character` | el orden de los códigos  |

Un `TreeSet<String>` tiene un problema con los RUT. `String.compareTo` compara
dos textos carácter por carácter, de izquierda a derecha, y decide el primer carácter distinto. Entre RUTs del mismo largo, ese
orden es el de los números. Un RUT con un dígito menos ya no: su primer
dígito se compara con el primero de los demás, que vale diez veces más, y el
orden de los textos deja de ser el de los números.

esto, si trae su propio orden.

</Slide>

<Slide title="El RUT en un TreeSet">
Sin `compareTo`, el `TreeSet` ni siquiera parte: para ubicar el primer
elemento tiene que compararlo, y `Rut` no sabe compararse.

```java
Set<Rut> sorted = new TreeSet<>();
sorted.add(a);      // ClassCastException
```

`Rut` no implementa `Comparable`, y el `TreeSet` no tiene con qué ordenarlo.

</Slide>

<Slide title="El orden de los RUT">
`Rut` implementa `Comparable<Rut>`, y su `compareTo` compara en cascada:
primero el número y, si empatan, el dígito.

```java
class Rut implements Comparable<Rut> {
    // los campos, el constructor, equals y hashCode

    @Override
    public int compareTo(Rut other) {
        if (number != other.number) {
            return Integer.compare(number, other.number);
        }
        return Character.compare(dv, other.dv);
    }
}
```

Es la cascada de siempre: responde en el número si los números difieren, y
solo si empatan mira el dígito.

</Slide>

<Slide title="Los RUT en un TreeSet">
Con `compareTo`, el `TreeSet` ya acepta los `Rut`, y los ordena por número: el
RUT de siete dígitos queda primero.

El `TreeSet` no usa `equals` ni `hashCode`: decide si un elemento ya está con
`compareTo`. Para que guarde lo mismo que un `HashSet`, `compareTo` compara los
mismos campos que `equals` y responde 0 exactamente cuando `equals` responde
verdadero.

</Slide>

<Slide title="El orden de una clave">
Para cualquier clase, `compareTo` sale de los mismos campos de la identidad
que `equals`:

1. compara en cascada, desde el campo más importante, y responde en el
   primero que no empata;
2. compara los números con `Integer.compare`, nunca con una resta, y los
   objetos con su propio `compareTo`.

Si la clase no se puede cambiar, o hace falta otro orden, el orden se le pasa
al `TreeSet` como un `Comparator`, con las mismas reglas.

Al terminar, un chequeo: `compareTo` responde 0 exactamente cuando `equals`
responde verdadero.

</Slide>

<Slide title="El orden de una mesa">
`VotingTable` implementa `Comparable<VotingTable>`, y su `compareTo` ordena las
mesas por comuna, después por local y después por número, en cascada:

```java
@Override
public int compareTo(VotingTable other) {
    int byCommune = commune.compareTo(other.commune);
    if (byCommune != 0) return byCommune;
    int byPlace = place.compareTo(other.place);
    if (byPlace != 0) return byPlace;
    return Integer.compare(number, other.number);
}
```

Usa los mismos tres campos que `equals`, así que responde 0 exactamente cuando
las dos mesas son iguales. `closed` no aparece en ninguno de los tres métodos.

</Slide>

<Slide title="Las mesas en un TreeSet">
Con `compareTo`, el `TreeSet` recorre las mesas por comuna, local y número:

```java
Set<VotingTable> tables = new TreeSet<>();
tables.add(new VotingTable("Ñuñoa", "Liceo 8", 1));
tables.add(new VotingTable("Maipú", "Escuela 2", 4));
tables.add(new VotingTable("Ñuñoa", "Liceo 7", 3));
// Maipú Escuela 2 4, Ñuñoa Liceo 7 3, Ñuñoa Liceo 8 1
```

</Slide>

<Slide title="El orden de un vocal de mesa">
`PollWorker` implementa `Comparable<PollWorker>`, y su `compareTo` le pide el
orden a cada campo, en cascada: primero la mesa, con el `compareTo` de
`VotingTable`, y si es la misma, la persona, con el de `Rut`.

```java
@Override
public int compareTo(PollWorker other) {
    int byTable = table.compareTo(other.table);
    if (byTable != 0) return byTable;
    return person.compareTo(other.person);
}
```

Así, en un `TreeSet`, los vocales de una mesa quedan juntos, y dentro de cada
mesa, por RUT.

</Slide>

<Slide title="Errores en el orden">
| Error                                                   | Lo que pasa                                                                                                               |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `compareTo` con menos campos que `equals`               | El `TreeSet` guarda menos que el `HashSet`: si compara solo el número, dos mesas 3 de locales distintos son una sola. |
| `compareTo` con una resta, como `number - other.number` | Con números grandes la resta se desborda, y el orden sale al revés.                                                       |
| Un campo del orden que cambia                           | El elemento queda en el lugar de su orden viejo, y el `TreeSet` ya no lo encuentra.                                      |

</Slide>

<Slide title="Diccionarios en la vida real">
Un diccionario aparece en cualquier lugar donde algo se busca por un nombre o
un código para obtener otra cosa.

- **Los contactos del teléfono.** Cada nombre lleva a un número; guardar un
  contacto con un nombre que ya está cambia su número.
- **Un diccionario de la lengua.** Cada palabra lleva a su definición, y
  buscar es dar la palabra.
- **La caja de un supermercado.** Cada código de barras lleva a un producto
  y su precio; un precio nuevo reemplaza al anterior.
- **Un carrito de compras.** Cada producto lleva a la cantidad que se lleva:
  agregar uno más cambia la cantidad, no agrega otro producto.

Los cuatro hacen lo mismo que el registro: buscar un valor por su clave,
guardar y corregir el valor de una clave, y sacarla, con cada clave una sola
vez.

</Slide>

<Slide title="Las reglas del contrato Map">
Un diccionario es una **función** de sus claves en sus valores: a cada clave
guardada le corresponde un solo valor, y dos claves pueden tener el mismo.

$$
m : K \to V
$$

se lee «$$m$$ va del conjunto $$K$$ de las claves guardadas al conjunto $$V$$
de los valores». De ahí salen las reglas:

- **`put(k, v)` con una clave que ya está no agrega un par**: reemplaza su
  valor y retorna el que tenía. Así, cada clave está una sola vez.
- **`get(k)` de una clave que no está no retorna ningún valor.** Quien llama
  lo distingue del valor de una clave que sí está.
- **Qué claves son iguales lo decide el tipo de las claves**, como en el Set.
  El valor no interviene en ninguna búsqueda.

La palabra **colección** tiene aquí su sentido general, un grupo de elementos
guardados juntos. En Java es además el nombre de la interfaz
`java.util.Collection`, que extienden `List`, `Set` y `Queue` y que `Map` no
extiende: sus elementos son pares, no valores sueltos.

</Slide>

<Slide title="Map en Java">
Java declara el contrato en la interfaz `java.util.Map<K, V>`, con `K` el tipo
de las claves y `V` el de los valores:

| El TDA          | Java `Map<K, V>`                  |
| --------------- | --------------------------------- |
| `get(k)`        | `get(k)`, que retorna `null` si `k` no está |
| `containsKey(k)` | `containsKey(k)`                 |
| `size()`        | `size()`                          |
| `keys()`        | `keySet()`, un `Set` con las claves |
| `values()`      | `values()`                        |
| `put(k, v)`     | `put(k, v)`, que retorna `null` si `k` era nueva |
| `remove(k)`     | `remove(k)`, que retorna `null` si `k` no estaba |

Como `get` responde `null` cuando la clave no está, un valor `null` guardado
no se distingue de una clave ausente: para saber si una clave está se
pregunta con `containsKey`. `getOrDefault(k, d)` retorna el valor de `k`, o
`d` si no está, y evita la pregunta cuando hay un valor que sirve por omisión.

</Slide>

<Slide title="Un Map sobre una tabla hash">
Las dos implementaciones del Set guardan también un diccionario: cada nodo
lleva su valor además de la clave. Las operaciones son las mismas, buscando
siempre por la clave.

En la tabla hash, la clave decide la posición, y el valor viaja en el nodo
sin intervenir: `get` recorre la lista de la posición de la clave y retorna
el valor del nodo que la tiene; `put` hace lo mismo y, si la encuentra,
reemplaza el valor en ese nodo.

<Slide title="Costos de las dos implementaciones del Map">
| Operación                | Tabla hash, esperado     | Árbol AVL, peor caso |
| ------------------------ | ------------------------ | -------------------- |
| `get(k)`, `containsKey(k)` | $$\Theta(1)$$          | $$O(\log N)$$        |
| `put(k, v)`              | $$\Theta(1)$$ amortizado | $$O(\log N)$$        |
| `remove(k)`              | $$\Theta(1)$$            | $$O(\log N)$$        |
| `keys()`, `values()`     | $$\Theta(N + M)$$        | $$\Theta(N)$$        |
| La clave menor, la siguiente a `k` | $$\Theta(N + M)$$ | $$O(\log N)$$  |

Son los costos del Set: el valor viaja con su clave y no cambia ningún
recorrido. En el peor caso, la tabla cuesta $$\Theta(N)$$ por operación,
como antes. La elección es también la misma: **si las preguntas no dependen
del orden de las claves, la tabla hash; si dependen, el árbol.**

</Slide>

## HashMap y TreeMap

<Slide title="La clase HashMap">
Java implementa el contrato Map sobre una tabla hash con listas en la clase
`java.util.HashMap`. El registro guarda la mesa de cada `Rut`:

```java
Map<Rut, Integer> tableOf = new HashMap<>();
tableOf.put(new Rut(18155218, '2'), 3);
tableOf.put(new Rut(13180992, '1'), 1);
// un put por cada voto

tableOf.get(new Rut(13959276, 'K'));             // 3
tableOf.get(new Rut(20118702, '8'));             // null: no votó
tableOf.getOrDefault(new Rut(20118702, '8'), 0); // 0
tableOf.put(new Rut(13180992, '1'), 4);          // corrige: 1
tableOf.remove(new Rut(13180992, '1'));          // por error: 4
```

`get` encuentra el par con un `Rut` nuevo, distinto del objeto que se guardó,
porque `Rut` escribe `equals` y `hashCode`: la clave de un `HashMap` cumple el
mismo contrato que el elemento de un `HashSet`. `get`, `put` y `remove`
cuestan $$\Theta(1)$$ esperado.

</Slide>

<Slide title="La clase TreeMap">
Java implementa el contrato Map sobre un árbol rojo-negro en la clase
`java.util.TreeMap`. Recorre los pares en el orden de sus claves, y responde
las preguntas que dependen de ese orden con los métodos de otro contrato, la
interfaz `NavigableMap`, que `TreeMap` implementa:

| Pregunta                          | Método                       |
| --------------------------------- | ---------------------------- |
| La clave menor, la mayor          | `firstKey()`, `lastKey()`    |
| La siguiente a `k`, la anterior   | `higherKey(k)`, `lowerKey(k)` |
| La primera desde `k`, la última hasta `k` | `ceilingKey(k)`, `floorKey(k)` |
| Los pares con clave entre `a` y `b` | `subMap(a, b)`             |

```java
NavigableMap<Rut, Integer> tree = new TreeMap<>();
// un put por cada voto
tree.firstKey();                       // el Rut 12.547.354-7
tree.floorKey(new Rut(20118702, '8'));  // el Rut 18.155.218-2
tree.subMap(new Rut(13000000, '0'), new Rut(18000000, '0'));
// los pares de 13.180.992-1, 13.959.276-K y 17.814.358-1
```

Cada una cuesta $$O(\log N)$$, y `subMap` además lo que mide el tramo.

</Slide>

<Slide title="Las claves de un HashMap y de un TreeMap">
Lo que una tabla hash y un árbol de búsqueda piden de sus elementos lo piden
de sus claves, y de sus valores nada:

|                      | `HashMap`                                         | `TreeMap`                                            |
| -------------------- | ------------------------------------------------- | ---------------------------------------------------- |
| Cómo ubica una clave | Su `hashCode`, y `equals` en la lista             | `compareTo`, o el `Comparator` del constructor       |
| Lo que exige         | `equals` y `hashCode` con los mismos campos       | Un orden que responda 0 cuando `equals` es verdadero |
| Si falta             | Una clave igual no se encuentra                   | El primer `put` lanza `ClassCastException`           |

En los dos, **una clave no cambia mientras está en el diccionario**: la tabla
la dejaría en la lista de su `hashCode` viejo, y el árbol, en el lugar de su
orden viejo. Un valor, en cambio, puede cambiar cuando haga falta: ninguna
búsqueda lo mira.

</Slide>

<Slide title="El primer voto repetido">
Un sistema de votación electrónica recibe los RUTs en el orden en que se
presentan a votar, y tiene que detectar el primer intento de votar dos veces.

El **primer voto repetido** es la primera posición cuyo RUT ya apareció antes.
No es el RUT que llegó primero de los que se repiten: es el que se repite
primero.

<RutRow

El programa recibe los RUTs en el orden en que llegan, todos escritos de la

```java

```

**Entrada.** `ruts`, a lo más $$10^5$$ RUTs. $$N$$ es su largo.

**Salida.** El RUT del primer voto repetido, o `null`. Sin RUTs, `null`.

</Slide>

<Slide title="Comparar con todos los anteriores">
Lo primero que se piensa es comparar cada RUT con todos los que llegaron
antes. Es correcto, y es lento: el RUT de la posición $$i$$ hace $$i$$
comparaciones, y cuando nadie repite, todos las hacen.

<Slide title="Sin repeticiones y el costo de la primera repetición">
Si nadie vota dos veces, todos los `add` retornan verdadero, el ciclo termina
y la función retorna `null`: es el caso que recorre los $$N$$ RUTs. Sin RUTs,
el ciclo no corre; con uno solo, no tiene con quién repetirse.

<RutRow
  ruts={['18.155.218-2', '13.180.992-1', '13.959.276-K']}
  caption="tres RUTs distintos: firstRepeated retorna null"

**Tiempo.** Cada RUT hace un solo `add`, que cuesta $$\Theta(1)$$ esperado en
una tabla hash, así que la función cuesta $$O(N)$$ esperado: termina antes
si encuentra la repetición. Si la función hash juntara todos los RUTs en una
misma lista, cada `add` la recorrería entera, y el total sería $$\Theta(N^2)$$.

**Memoria.** `seen` guarda a lo más los $$N$$ RUTs: $$O(N)$$.

</Slide>

  const chipW = Math.max(96, ...records.map((r) => text(r).length * 7.4 + 20));

  const pad = 12;

  const rowY = indexY + 8;
  const boxY = rowY + chipH + (arrows ? 78 : 44);

  const height = boxY + boxH + 22 + (caption ? 30 : 6);

El programa recibe los RUTs y las notas en dos arreglos del mismo largo,
`ruts[i]` y `grades[i]` el RUT y la nota del registro `i`, y responde un
diccionario que lleva cada RUT a la lista de sus notas:

```java
static Map<String, List<Double>> byStudent(
        String[] ruts, double[] grades)
```

**Entrada.** A lo más $$10^5$$ registros, con los RUTs escritos todos de la
misma manera. $$N$$ es su cantidad, y $$E$$, la de estudiantes distintos.
Arreglos de largos distintos son un error: `IllegalArgumentException`.

**Salida.** Cada RUT con sus notas en el orden en que llegaron. Sin
registros, un diccionario vacío.

</Slide>

<Slide title="Recorrer los registros una vez por estudiante">
Lo primero que se piensa es armar los grupos de a uno: tomar un estudiante,
recorrer todos los registros guardando sus notas, y repetir con el siguiente.
Responde bien, y recorre los $$N$$ registros una vez por cada uno de los
$$E$$ estudiantes. Un estudiante tiene pocas notas en un semestre: si tiene a
lo más $$c$$, hay al menos $$N / c$$ estudiantes, y

$$
\frac{N^2}{c} \;\le\; E \cdot N \;\le\; N^2
$$

se lee «el trabajo queda entre $$N^2$$ dividido por $$c$$ y $$N^2$$»: es
$$\Theta(N^2)$$. Con $$10^5$$ registros y unas cinco notas por estudiante, son
$$2 \cdot 10^4$$ estudiantes y unos $$2 \cdot 10^9$$ pasos.

Cada registro, en cambio, sabe a qué grupo va: el de su RUT. Lo que hace falta
es llegar a ese grupo sin buscarlo.

</Slide>

<Slide title="Un solo estudiante, ningún registro y el costo de agrupar">
Si todos los registros son del mismo RUT, el diccionario tiene un solo grupo
con todas las notas, y una nota repetida aparece dos veces, porque la lista
guarda cada registro. Sin registros, el ciclo no corre y el diccionario sale
vacío. Si los arreglos no tienen el mismo largo, la función lanza la
excepción antes de leer un registro.

**Tiempo.** Cada registro hace un `get`, que cuesta $$\Theta(1)$$ esperado, y
a lo más un `put` y un `add` al final de una lista, que cuestan
$$\Theta(1)$$ amortizado: el `put` porque la tabla a veces crece, y el `add`
porque el arreglo de la lista también. En total, $$\Theta(N)$$ esperado, sin
importar cuántos estudiantes haya.

**Memoria.** Las listas guardan las $$N$$ notas, y el diccionario, los $$E$$
RUTs: $$\Theta(N + E)$$, que es $$\Theta(N)$$ porque no hay más estudiantes
que registros.

{/* AgendaColumn — one frame of the walk of the agenda, sized for the column beside its listing: the times taken as chips in their order, top to bottom — the inorder of the TreeSet —, with `slots` rows reserved so every frame keeps one size. `asked` is the time being booked, in its place in the order, painted `mark` when it is booked and `flag`, dashed, when `refused`; `near` paints its neighbours `keep` with how far each is written beside it, in `flag` when it is closer than 20 minutes; `gone` is a cancelled time, faint and struck; `from`/`to` bracket the times between them, or say that none is. export function AgendaColumn({ times, slots, asked, refused = false, near = [], gone, from, to, label }) {

  const chipH = 30;
  const gapY = 10;
  const pad = 14;
  const left = 64;
  const width = left + chipW + 120;
  const top = pad + 22;
  const height = top + slots * (chipH + gapY) - gapY + pad;
  const minutes = (t) => Math.floor(t / 100) * 60 + (t % 100);
  const text = (t) => `${Math.floor(t / 100)}:${String(t % 100).padStart(2, '0')}`;
  const rows = [...times, ...(gone !== undefined ? [gone] : []), ...(asked !== undefined ? [asked] : [])].sort((a, b) => a - b);
  const y = (i) => top + i * (chipH + gapY);
  const inRange = (t) => from !== undefined && t >= from && t <= to && t !== gone;
  const ranged = rows.map((t, i) => (inRange(t) ? i : -1)).filter((i) => i >= 0);
  return (
    <svg viewBox={`0 0 ${width} ${height}`} style={{ width: '100%', maxWidth: `${Math.round(width * 1.6)}px`, height: 'auto', display: 'block', margin: '0.4rem auto' }} role="img" aria-label={label}>
      <text x={left} y={pad + 8} fontSize="12" fontWeight="700" style={{ fill: 'var(--color-ink-soft)' }}>times, en orden</text>
      {rows.length === 0 ? (
        <text x={left + chipW / 2} y={y(0) + chipH / 2 + 5} textAnchor="middle" fontSize="13" style={{ fill: 'var(--color-ink-faint)' }}>ninguna</text>

<Slide title="Un arreglo ordenado o uno sin orden">
Guardar las horas en un arreglo obliga a elegir. **Sin orden**, `book` tiene
que mirar todas las horas para saber si alguna queda a menos de 20 minutos, y
`between`, para saber cuáles caen en el intervalo. **Ordenado**, una búsqueda
binaria encuentra en $$O(\log N)$$ las horas vecinas de la nueva y la primera
del intervalo, pero agendar y cancelar corren una posición todas las horas
posteriores.

| Arreglo     | `book`, `cancel` | `between`          |
| ----------- | ---------------- | ------------------ |
| Sin orden   | $$\Theta(N)$$    | $$\Theta(N)$$      |
| Ordenado    | $$\Theta(N)$$    | $$O(\log N + k)$$  |

Un casillero por cada minuto posible, con el acceso directo de un arreglo,
tampoco sirve: la agenda no tiene último día, y el universo de los minutos no
tiene fin. Con $$10^5$$ llamadas sobre una agenda que crece, un costo de
$$\Theta(N)$$ por hora agendada suma miles de millones de pasos.

</Slide>

siguientes del inorden: $$O(\log N + k)$$, sin importar cuántas horas haya
fuera del tramo.

**Memoria.** El árbol guarda las $$N$$ horas tomadas, y cada `between`, una
lista de $$k$$: $$\Theta(N + k)$$.

<Slide title="El mínimo y el máximo de una ventana de precios">
Una aplicación de inversiones muestra, junto al precio de una acción, el
mínimo y el máximo de los últimos $$k$$ precios, y los actualiza con cada
precio nuevo. Los $$k$$ precios más recientes forman la **ventana**: con cada
precio que llega, entra uno a la ventana y sale el más antiguo.

```java

```

**Entrada.** `prices`, a lo más $$10^5$$ enteros; $$N$$ es su largo. `k` es el
largo de la ventana, con $$1 \le k \le N$$; fuera de ese rango, la función
lanza `IllegalArgumentException`.

**Salida.** Una fila por ventana, de la primera a la última, cada una con el
mínimo y el máximo de esa ventana: $$N - k + 1$$ filas.

</Slide>

<Slide title="Recalcular cada ventana">
Lo primero que se piensa es recorrer cada ventana para encontrar su mínimo y
su máximo. Responde bien, y cada una de las $$N - k + 1$$ ventanas recorre sus
$$k$$ precios:

$$
(N - k + 1) \cdot k \in \Theta(N \cdot k)
$$

Con $$10^5$$ precios y una ventana de $$10^4$$, son unos $$9 \cdot 10^8$$
pasos. Y entre una ventana y la siguiente cambian solo dos precios: el que
entra y el que sale.

</Slide>

<Slide title="El mínimo que sale de la ventana">

compararlo con el que entra. Funciona hasta que el precio que **sale** es el
mínimo: la variable sigue recordando un precio que ya no está en la ventana,
y lo que queda no dice cuál es el nuevo mínimo sin recorrerla.

<Slide title="Una ventana de un precio y el costo de la ventana">
Con $$k = 1$$, cada ventana tiene un solo precio, y su mínimo y su máximo son
ese precio; con $$k = N$$, hay una sola ventana. Un `k` menor que 1 o mayor que
$$N$$ no define ninguna ventana, y la función lo rechaza antes de empezar, lo
que incluye a un arreglo vacío.

**Tiempo.** Cada precio entra una vez y sale a lo más una vez, y cada fila
lee la primera y la última clave. El diccionario guarda a lo más $$k + 1$$
precios —el que entra, por un instante, antes de que salga el más antiguo—,
así que cada una de esas operaciones cuesta $$O(\log k)$$:

$$
\underbrace{N \cdot O(\log k)}_{\text{entra}} + \underbrace{N \cdot O(\log k)}_{\text{sale}} + \underbrace{(N - k + 1) \cdot O(\log k)}_{\text{las filas}} = O(N \log k)
$$

**Memoria.** El diccionario guarda a lo más $$k + 1$$ precios, y la respuesta,
$$N - k + 1$$ filas: $$\Theta(N)$$.

</Slide>

```java starter
import java.util.TreeMap;

class Solution {
    static int[][] minMax(int[] prices, int k) {
        if (k < 1 || k > prices.length) {
            throw new IllegalArgumentException();
        }
        TreeMap<Integer, Integer> window = new TreeMap<>();
        int[][] answer = new int[prices.length - k + 1][];
        for (int i = 0; i < prices.length; i++) {
            int in = prices[i];
            window.put(in, window.getOrDefault(in, 0) + 1);
            if (i >= k) {
                int out = prices[i - k];
                int remaining = window.get(out) - 1;
                if (remaining == 0) {
                    window.remove(out);
                } else {
                    window.put(out, remaining);
                }
            }
            if (i >= k - 1) {
                answer[i - k + 1] = new int[] {
                    window.firstKey(), window.lastKey()};
            }
        }
        return answer;
    }
}
```

<Exercise title="El conteo de votos">

Al cerrar una mesa se cuentan los votos: cada voto es el nombre de un

los votos y responde un diccionario que lleva cada candidato a sus votos, y
`winner`, que responde el candidato con más votos: en un empate, el primero en
orden alfabético, y sin votos, `null`. A lo más $$10^5$$ votos; $$N$$ es su

Con los votos Rojas, Soto, Rojas, Araya y Soto, `tally` responde Rojas → 2,

Contar los votos de cada candidato recorriendo todos los votos una vez por

`compareTo`.

```java solution
import java.util.HashMap;
import java.util.Map;

class Solution {
    static Map<String, Integer> tally(String[] votes) {
        Map<String, Integer> counts = new HashMap<>();
        for (String vote : votes) {
            counts.put(vote, counts.getOrDefault(vote, 0) + 1);
        }
        return counts;
    }

    static String winner(String[] votes) {
        Map<String, Integer> counts = tally(votes);
        String best = null;
        for (String name : counts.keySet()) {
            if (best == null) {
                best = name;
                continue;
            }
            int mine = counts.get(name);
            int theirs = counts.get(best);
            if (mine > theirs || mine == theirs && name.compareTo(best) < 0) {
                best = name;
            }
        }
        return best;
    }
}
```

<Exercise title="Votantes distintos con y sin puntos">

Con 13.180.992-1, 13180992-1 y 18.155.218-2, `countDistinct` responde 2. Con

<Exercise title="La próxima salida">

Un terminal de buses publica salidas de cualquier día, sin un último día, que
se agregan y se cancelan a lo largo del tiempo, y los pasajeros preguntan, en
un instante dado, cuál es la próxima salida: la primera estrictamente
posterior. Un instante es un entero, los minutos desde la medianoche del día
0, y `at(día, hora, minuto)` hace esa cuenta. Escribamos la clase `Terminal`:
`add` agrega una salida y responde falso si ya estaba, `cancel` la saca y
responde falso si no estaba, y `next` responde la próxima salida, o `-1` si no
queda ninguna. A lo más $$10^5$$ llamadas; $$N$$ es la cantidad de salidas
publicadas.

Con salidas el día 2 a las 7:15, 9:00 y 12:30, la próxima a las 8:30 es la de
las 9:00; a las 9:00, la de las 12:30, porque tiene que ser posterior; y a las
13:00 no queda ninguna: -1. Cancelada la de las 12:30, a las 9:00 tampoco
queda ninguna.

Un arreglo ordenado responde `next` con una búsqueda binaria, pero cada salida
que se agrega o se cancela corre las posteriores: $$\Theta(N)$$. Un conjunto
ordenado agrega, cancela y responde «la primera estrictamente mayor que
$$x$$» con un solo método, `higher`, en $$O(\log N)$$.

```java solution
import java.util.TreeSet;

class Terminal {
    private TreeSet<Integer> departures = new TreeSet<>();

    static int at(int day, int hour, int minute) {
        return (day * 24 + hour) * 60 + minute;
    }

    public boolean add(int time) {
        return departures.add(time);
    }

    public boolean cancel(int time) {
        return departures.remove(time);
    }

    public int next(int time) {
        Integer after = departures.higher(time);
        return after == null ? -1 : after;
    }
}
```

<Exercise title="El evento más cercano">

Un calendario guarda eventos con su nombre, a lo más uno por día, en días
contados desde el día 0 y sin un último día. Escribamos la clase `Events`:
`add` guarda un evento, y si el día ya tenía uno, el nuevo lo reemplaza;
`nearest` responde el nombre del evento más cercano a un día, antes o después:
si dos están a la misma distancia, el anterior, y sin eventos, `null`. A lo más
$$10^5$$ llamadas; $$N$$ es la cantidad de días con evento.

Con un certamen el día 40, un feriado el 75 y una entrega el 120, el día 60
está a 20 días del certamen y a 15 del feriado: responde «feriado». El día 100
responde «entrega»; el 10, «certamen», y el 200, «entrega», la última. Si el
día 75 recibe un «paseo», el día 60 responde «paseo».

Recorrer todos los eventos en cada consulta cuesta $$\Theta(N)$$. En un
diccionario ordenado por día, que se arma una vez y dura entre las consultas,
el evento más cercano es el último que no es posterior al día o el primero que
no es anterior, y `floorKey` y `ceilingKey` los encuentran en
$$O(\log N)$$.

```java solution
import java.util.TreeMap;

class Events {
    private TreeMap<Integer, String> calendar = new TreeMap<>();

    public void add(int day, String name) {
        calendar.put(day, name);
    }

    public String nearest(int day) {
        Integer before = calendar.floorKey(day);
        Integer after = calendar.ceilingKey(day);
        if (before == null && after == null) {
            return null;
        }
        if (after == null || before != null && day - before <= after - day) {
            return calendar.get(before);
        }
        return calendar.get(after);
    }
}
```

## Más allá de Set y Map

<Slide title="Conjuntos y diccionarios para casos especiales">
`HashSet` y `TreeSet` están escritos sobre `HashMap` y `TreeMap`: sus
elementos son las claves de un diccionario cuyo valor no se usa, el mismo
objeto de relleno para todas. Alrededor de esos cuatro hay otros, exactos
como ellos, que cambian algo de la estructura para un caso que se repite:

| Estructura          | Qué cambia                                                           | Un uso                                                     |
| ------------------- | -------------------------------------------------------------------- | ---------------------------------------------------------- |
| `LinkedHashMap`     | Una tabla hash que además enlaza sus pares en el orden en que entraron, o en el de su último uso | Un caché que descarta el dato usado hace más tiempo        |
| *Trie*              | Un árbol para claves de texto, con una letra por nivel               | Autocompletar: todas las palabras que empiezan con un prefijo |
| `BitSet`            | Un conjunto de enteros pequeños guardado como un bit por entero posible | Marcar cuáles de un millón de números aparecen, en 125 KB  |
| `EnumMap`           | Un diccionario cuyas claves son los valores de un `enum`, guardado en un arreglo | Un horario por día de la semana                         |
| `ConcurrentHashMap` | Una tabla hash que varios hilos usan a la vez sin corromperla        | El caché compartido de un servidor                         |
| Árbol B+            | Un diccionario ordenado en disco, con cientos de claves por nodo     | Los índices de una base de datos                           |

Para seguir: la documentación de `java.util`, y Sedgewick y Wayne,
*Algorithms*, §3.5 y §5.2.
