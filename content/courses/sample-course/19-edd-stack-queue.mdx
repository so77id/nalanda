# Estructuras de Datos · Stack y Queue

La clase anterior terminó con una colección que deja pedir cualquier
posición, y con el precio de esa libertad: una implementación que cumpla el
contrato entero termina con alguna operación cara. Esta clase hace lo
contrario. Estudia dos contratos que **renuncian** a esa libertad a
propósito —la **pila** y la **cola**—, los construye sobre el arreglo y
sobre la lista enlazada, y compara las dos construcciones.

Restringir no es perder. Es lo que permite prometer un costo: mientras el
único lugar donde se opera sea un extremo conocido, no hay nada que
recorrer para llegar.

## Stack · Pila

<Slide title="Una pila">

uno sobre otro, y el único que está a la vista es el de más arriba, al que
llamamos **cima** o **top**. Poner y sacar ocurren los dos en ese mismo
lugar.

Las dos operaciones son la misma, pero en sentidos opuestos. `push`
(apilar) apoya un elemento nuevo sobre la cima; `pop` (desapilar) levanta el
de la cima y lo devuelve. No hay otra forma de acceder a los elementos: si
quieres sacar el que está en la cuarta posición desde arriba, tienes que
sacar antes los tres que tiene encima.

Los elementos salen, entonces, en el orden inverso al que entraron. Esa
regla se llama **LIFO**, del inglés _last in, first out_: **el último en
entrar es el primero en salir**.

</Slide>

<Slide title="Pilas en la vida real">
Una pila no es una idea de la programación. Es la forma de cualquier montón
donde sólo se puede tocar lo de encima.

- **Una torre de platos.** El que se apoyó último es el único que se puede
  levantar sin mover el resto.
- **El deshacer de un editor.** Cada cambio se apila cuando ocurre, y
  deshacer revierte el último, después el anterior a ése.
- **El botón «atrás» del navegador.** Cada página visitada queda sobre la
  anterior, y volver es sacar la de más arriba.
- **La pila de llamadas de un programa.** Cuando un método termina, el que
  retoma la ejecución es el que lo llamó: el último que quedó esperando. De
  ahí el nombre, y de ahí que una recursión sin caso base la desborde.

Los cuatro hacen lo mismo con palabras distintas: apoyar encima y levantar de
encima. Ese comportamiento está definido con precisión en un **tipo de dato
abstracto** (TDA) llamado **Stack**.

</Slide>


<Slide title="El TDA Stack">
El **Stack** es una colección donde sólo se trabaja en un extremo, la
**cima/top**: se pone encima y se saca de encima.

Esas cuatro operaciones son todo el contrato, y **LIFO es parte del
contrato**: `pop()` no devuelve un elemento cualquiera, devuelve el último
que entró. Ninguna operación recibe una posición, así que tampoco hay forma
de pedir otro.

Para eso está `empty()`. El protocolo es: **`top()` y `pop()` sólo se pueden
llamar cuando `empty()` es falso.** Sobre una pila vacía no hay nada que
devolver, así que llamarlas ahí queda fuera del contrato.

</Slide>

<Slide title="Cómo se implementa este TDA">
El contrato no dice dónde viven los elementos, así que hay que elegir. Las
dos opciones ya las tenemos: el **arreglo**, que los guarda juntos en un
bloque de casillas, y la **lista enlazada**, que los guarda sueltos y
encadenados desde `head`.

La pila se puede construir utilizando una de las dos estructuras de datos:

| Stack | Sobre arreglo dinámico | Sobre lista simple |
|---|---|---|
| `push(x)` | escribir en `data[size]`, subir `size` (crecer si está lleno) | `insertFirst(x)` |
| `pop()` | leer `data[size - 1]`, bajar `size` | `deleteFirst()` |
| `top()` | leer `data[size - 1]` | leer el valor de `head` |
| `empty()` | `size == 0` | `head == null` |

Mira en qué punta trabaja cada una: el arreglo por el final, la lista por la
cabeza. Es la punta donde cada estructura ya era rápida, y por eso ninguna
operación tiene que buscar dónde operar.

</Slide>

<Slide title="Sobre el arreglo dinámico">
La primera implementación guarda los elementos juntos, en un bloque de
casillas consecutivas que **puede cambiar de tamaño**: cuando se llena, la
estructura reserva uno más grande y copia. El **top/cima** es el último
elemento escrito, y está siempre en `data[size - 1]`.

Las cuatro invariantes del arreglo dinámico siguen valiendo tal cual:

1. **`0 ≤ size ≤ data.length`.** El largo nunca supera la capacidad.
2. **Los elementos son exactamente `data[0]` hasta `data[size - 1]`.** Juntos
   y desde la posición 0, sin huecos en el medio.
3. **`data[size..]` es basura.** Existe, tiene algún valor, y nadie lo lee.
4. **`data.length ≤ 4 × size`.** La capacidad no sobra: nunca hay más de
   cuatro casillas por elemento.

Y la pila agrega la suya:

5. **La cima es `data[size - 1]`.** Cuando `size` es cero no hay cima, y eso
   es exactamente una pila vacía.

La quinta es la que hace barata a esta implementación: la cima no hay que
buscarla, es una resta.

</Slide>

<Slide title="push sobre arreglo dinámico">
`push` **es `insertLast` sobre un arreglo dinámico**: agregar el elemento
que sigue en la cima y avanzar la cima. La pila no inventa una operación
nueva, le pone otro nombre a la que el arreglo ya tenía.

<SequenceStepper
  eda="dynamic-array"
  capacity={4}
  operation="insert-last"
  values={[42, 7]}
  value={[15, 4, 9, 23]}
  pointer="top"
  showCode={false}
/>

En el **peor caso** `push` cuesta $$\Theta(N)$$: cuando el bloque está
lleno hay que reservar uno del doble y copiar los $$N$$ elementos antes de
poder escribir. Cualquier otra llamada escribe en una casilla libre y sube
`size`, que es $$\Theta(1)$$.

El costo **amortizado** es $$\Theta(1)$$: como la capacidad se duplica,
entre dos llamadas caras hay $$N$$ baratas, así que el precio de la copia
repartido entre todas ellas es constante por llamada.

</Slide>

<Slide title="pop sobre arreglo dinámico">
`pop` **es `deleteLast` sobre un arreglo dinámico**: devolver el elemento de
la cima y retroceder la cima. No borra nada —el valor sigue escrito donde
estaba, y es la invariante que dice que los elementos válidos llegan hasta
`data[size - 1]` la que lo convierte en basura que nadie va a leer.

<SequenceStepper
  eda="dynamic-array"
  capacity={8}
  operation="remove-last"
  values={[42, 7, 15, 4, 9, 23]}
  times={3}
  pointer="top"
  showCode={false}
/>

En el **peor caso** `pop` cuesta $$\Theta(N)$$: al bajar `size` la capacidad
puede pasar a sobrar —`data.length > 4 × size`— y entonces el bloque se
achica, que es reservar uno más chico y copiar los elementos que quedan.
Cualquier otra llamada lee `data[size - 1]`, baja `size` y termina:
$$\Theta(1)$$.

El costo **amortizado** es $$\Theta(1)$$, por la misma razón que en `push`:
el achique ocurre sólo cuando el largo baja al cuarto de la capacidad, y al
achicar vuelve a quedar en la mitad. Hasta el próximo hay $$N$$ `pop` que no
copian nada.

</Slide>

<Slide title="Costos de Stack sobre arreglo dinámico">
| Operación | Peor caso | Amortizado | Invariante que restaura |
|---|---|---|---|
| `build()` | $$\Theta(1)$$ | $$\Theta(1)$$ | Deja `size` en cero: una pila sin cima |
| `top()` | $$\Theta(1)$$ | $$\Theta(1)$$ | Ninguna: lee y no cambia nada |
| `empty()` | $$\Theta(1)$$ | $$\Theta(1)$$ | Ninguna: `size` ya guarda el dato |
| `push(x)` | <span style={{ color: 'var(--color-mark)', fontWeight: 700 }}>$$\Theta(N)$$</span> | $$\Theta(1)$$ | La cima es `data[size - 1]`, y `size ≤ data.length` obliga a crecer |
| `pop()` | <span style={{ color: 'var(--color-mark)', fontWeight: 700 }}>$$\Theta(N)$$</span> | $$\Theta(1)$$ | La cima es `data[size - 1]`, y `data.length ≤ 4 × size` obliga a achicar |

**Lo que gana.** Las cuatro operaciones son aritmética sobre `size`: no hay
nada que recorrer ni ningún enlace que seguir. Y los valores quedan uno al
lado del otro en memoria, que es como el procesador los lee más rápido.

**Lo que paga.** `push` y `pop` casi siempre cuestan un paso, pero cada
tanto copian el arreglo entero. En promedio sale constante; una llamada
suelta puede tardar $$N$$, y no se sabe cuál va a ser.

Si lo que importa es el tiempo total de un programa, manda el promedio y
esto es una buena elección. Si lo que importa es cuánto puede tardar **una**
operación —un videojuego que dibuja 60 cuadros por segundo, un sistema de
tiempo real—, manda el peor caso, y esas copias son un problema.

La lista enlazada no las tiene: nunca copia nada.

</Slide>

Con esa decisión, las dos operaciones que la pila pide caen sobre el
principio de la cadena, que es el único lugar al que `head` llega sin
caminar. Una pila vacía es `head == null`.

La estructura entera son dos atributos y sus cuatro métodos, para respetar
la implementación del TDA:

```java
class Stack {
    private Node head;  // el primer nodo de la cadena: la cima
    private int size;   // cuántos elementos hay

    void push(int x)    // pone x en la cima
    int pop()           // saca el de la cima y lo devuelve
    int top()           // el de la cima, sin sacarlo
    boolean empty()     // si la pila no tiene ningún elemento
    int size()          // cuántos elementos tiene
}
```

</Slide>

<Slide title="Las invariantes de la pila sobre lista">
Tres propiedades sostienen esta implementación, y cada operación las deja
como las encontró.

1. **`head` apunta al primer nodo, o a `null` si la pila está vacía.** Es el
   único punto de entrada a la cadena. Si `head` queda apuntando a un nodo
   del medio, todo lo anterior se vuelve inalcanzable: sigue en memoria y no
   hay manera de llegar.

2. **Desde `head`, siguiendo `next`, se llega a todos los nodos y se termina
   en `null`.** La cadena no tiene cortes ni ciclos.

3. **La cima es el nodo al que `head` apunta.** Es la traducción del
   contrato a esta estructura, y es la que decide todos los costos: la
   cima es el único nodo al que se llega sin caminar.

La tercera es la que hace barata a esta implementación, igual que en el
arreglo lo era «la cima es `data[size - 1]`». Cambia la estructura, no el
papel que juega la invariante.

Lo que sí cambia es el trabajo que hay que hacer para llegar a la cima. En
el arreglo era una resta, `size - 1`, y después ir a esa casilla. Acá no hay
nada que calcular: `head` **es** la cima, y basta con mirarla.

</Slide>

<Slide title="Las consultas">
Las tres operaciones que no cambian la pila salen de los dos atributos, sin
tocar la cadena.

```java
boolean empty() {
    return size == 0;
}

int size() {
    return size;
}

int top() {
    if (head == null) {
        throw new NoSuchElementException();
    }
    return head.value;
}
```

- **`empty()`** dice si la pila no tiene elementos. Lee un campo: $$\Theta(1)$$.
- **`size()`** devuelve cuántos hay. También un campo, y por eso es
  $$\Theta(1)$$: el largo se mantiene en cada `push` y cada `pop`, así que
  nunca hay que recorrer la cadena para contarlo.
- **`top()`** devuelve el valor de la cima sin sacarla. `head` ya apunta ahí,
  así que tampoco hay nada que recorrer: $$\Theta(1)$$.

Ésa es toda la diferencia entre `top` y `pop`: **`pop` devuelve la cima y la
saca; `top` la devuelve y deja la pila como estaba.**

</Slide>

```java
int pop() {
    if (head == null) {
        throw new NoSuchElementException();
    }
    int x = head.value;
    head = head.next;
    size--;
    return x;
}
```

Una pila vacía no tiene cima, así que `pop()` no puede devolver un valor: lo
primero que hace es preguntar y fallar.

`pop` toca dos cosas y nada más: `head` y `size`. No recorre la cadena ni
mueve a nadie, y por eso no importa si la pila tiene tres elementos o un
millón —el trabajo es el mismo—: $$\Theta(1)$$. Costaría $$\Theta(N)$$ si
hubiera que buscar el nodo que sale, y no hay que buscarlo: `head` ya lo
tiene.

El nodo que sale queda sin nadie apuntándolo, y el colector de basura lo
recupera más tarde.

<Slide title="Costos de Stack sobre lista">
| Operación | Peor caso | Invariante que restaura |
|---|---|---|
| `build()` | $$\Theta(1)$$ | Deja `head` en `null` y `size` en cero |
| `top()` | $$\Theta(1)$$ | Ninguna: lee `head.value` y no cambia la cadena |
| `empty()` | $$\Theta(1)$$ | Ninguna: `size` ya guarda el dato |
| `size()` | $$\Theta(1)$$ | Ninguna: devuelve el campo que las otras mantienen |
| `push(x)` | $$\Theta(1)$$ | `head` apunta a la cima: el nodo nuevo enlaza al que lo era |
| `pop()` | $$\Theta(1)$$ | `head` apunta a la cima: pasa a ser el segundo |

Todo constante, y por una sola razón: cada operación trabaja sobre el primer
nodo, que es el único al que se llega sin caminar la cadena.

Y hay algo que esta tabla **no** tiene. No hay columna de amortizado, porque
no hace falta: la lista nunca copia nada, así que el peor caso de cada
operación es también su caso típico. No hay bloque que se pueda llenar —cada
nodo se pide cuando hace falta y se suelta cuando sobra—, y por eso ninguna
fila dice $$\Theta(N)$$.

Es exactamente lo que el arreglo no podía prometer.

</Slide>

<Slide title="Arreglo vs lista">
| | Sobre arreglo dinámico | Sobre lista simple |
|---|---|---|
| `push(x)` | $$\Theta(1)$$ amortizado — $$\Theta(N)$$ la corrida que copia | $$\Theta(1)$$ siempre |
| `pop()` | $$\Theta(1)$$ amortizado — $$\Theta(N)$$ la que achica | $$\Theta(1)$$ siempre |
| `top()`, `empty()` | $$\Theta(1)$$ | $$\Theta(1)$$ |
| memoria por elemento | el valor | el valor **y** un enlace |
| capacidad | crece y se achica, copiando | sin límite previo |
| los elementos en memoria | juntos | sueltos |

Las dos implementaciones cumplen el contrato con los mismos costos
constantes, así que la elección no se decide ahí. Se decide en las tres
filas de abajo.

El arreglo gana en memoria y en localidad: no paga un enlace por elemento y
guarda los valores juntos, que es lo que el procesador prefiere leer. Lo
paga en copias, baratas en promedio pero no en el instante en que ocurren.

La lista gana cuando ninguna corrida puede permitirse la pausa de una copia. Paga un enlace por elemento y
esparce los valores, y a cambio ninguna operación tiene un peor caso
distinto de su caso típico.

</Slide>

Las dos operaciones trabajan en extremos opuestos. `enqueue` (encolar) pone
un elemento nuevo en el final; `dequeue` (desencolar) saca el del frente y
lo devuelve. No hay otra forma de acceder a los elementos: si quieres sacar
el que está en el tercer lugar, tienes que sacar antes los dos que tiene
adelante.

Los elementos salen, entonces, en el mismo orden en que entraron. Esa regla
se llama **FIFO**, del inglés _first in, first out_: **el primero en entrar
es el primero en salir**.

</Slide>

<Slide title="Colas en la vida real">
Una cola no es una idea de la programación. Es la forma de cualquier espera
donde se atiende por orden de llegada.

- **La fila de una boletería.** El que llega se pone atrás, el que atienden
  es el de adelante, y nadie necesita saber cuántos hay ni en qué lugar
  está.
- **La cola de impresión.** Una impresora compartida recibe trabajos de
  varias personas a la vez e imprime de a uno, en el orden en que llegaron.
- **El búfer entre quien produce y quien consume.** El teclado genera
  pulsaciones más rápido de lo que el programa las procesa, y la tarjeta de
  red entrega paquetes cuando llegan y no cuando conviene. Entre los dos hay
  una cola, y su trabajo es que ninguno espere al otro.
- **Los pedidos de un servidor.** Llegan más rápido de lo que se atienden,
  y responderlos en desorden sería tratar distinto a dos clientes iguales.

Los cuatro hacen lo mismo con palabras distintas: poner atrás y atender
adelante. Ese comportamiento está definido con precisión en un **tipo de
dato abstracto** (TDA) llamado **Queue**.

</Slide>

Cuatro operaciones y ninguna recibe una posición. Lo que el contrato fija es
**por dónde** se entra y por dónde se sale: **FIFO**, del inglés _first in,
first out_.

Pedirle el frente a una cola vacía es un error, no un valor. `front()` y
`dequeue()` tienen sentido únicamente cuando `empty()` es falso.

</Slide>

<Slide title="Cómo se implementa este TDA">
El contrato no dice dónde viven los elementos, pero sí pide algo exigente:
**los dos extremos**, y los dos baratos.

La cola se puede construir utilizando una de las dos estructuras de datos:

| Queue | Sobre arreglo dinámico | Sobre lista simple con `tail` |
|---|---|---|
| `enqueue(x)` | escribir en `data[size]`, subir `size` (crecer si está lleno) | `insertLast(x)` |
| `dequeue()` | leer `data[0]`, correr todo lo demás, bajar `size` | `deleteFirst()` |
| `front()` | leer `data[0]` | leer el valor de `head` |
| `empty()` | `size == 0` | `head == null` |

Una de esas cinco casillas no se parece a las otras. El arreglo sabe operar
barato en **un** extremo —el final—, y la cola necesita los dos: desencolar
le queda en el lado incómodo. La lista, en cambio, llega a los dos sin
caminar, y lo único que le hace falta es una referencia de más.

</Slide>

<Slide title="Queue sobre un arreglo dinámico">
La primera idea es la directa: el mismo arreglo dinámico de la pila,
con los elementos en un bloque consecutivo desde la casilla cero, el frente
en `data[0]` y el final en `data[size - 1]`.

Con esa disposición, encolar es escribir en la primera casilla libre y subir
`size`, que es la operación barata del arreglo. Pero desencolar saca el de
`data[0]`, y para que el frente vuelva a estar en la casilla cero hay que
**correr todos los demás una casilla a la izquierda**.

Ese corrimiento cuesta $$\Theta(N)$$, y no es un detalle de implementación
que se pueda pulir: es la consecuencia directa de haber decidido que el
frente vive en una casilla fija. Una cola que se usa de verdad desencola
tantas veces como encola, así que la mitad de sus operaciones serían caras.

Y el contrato no pide nada de esto: pide sacar **el del frente**, no sacar
el de la casilla cero. Es guardar la cola en un bloque de casillas
consecutivas lo que ata el frente a la casilla cero, y es esa atadura la que
cuesta $$\Theta(N)$$ cada vez.

</Slide>

<Slide title="enqueue sobre arreglo dinámico">
`enqueue` **es `insertLast` sobre un arreglo dinámico**: escribir el
elemento nuevo en la primera casilla libre y avanzar el final. En este
extremo la cola no inventa nada, le pone otro nombre a la operación que el
arreglo ya hacía barata.

En el **peor caso** `enqueue` cuesta $$\Theta(N)$$: cuando el bloque está
lleno hay que reservar uno del doble y copiar los $$N$$ elementos antes de
poder escribir. Cualquier otra llamada escribe en una casilla libre y sube
`size`, que es $$\Theta(1)$$.

El costo **amortizado** es $$\Theta(1)$$: como la capacidad se duplica,
entre dos llamadas caras hay $$N$$ baratas, así que el precio de la copia
repartido entre todas ellas es constante por llamada.

</Slide>

<Slide title="dequeue sobre arreglo dinámico">
`dequeue` **es `deleteFirst` sobre un arreglo dinámico**: devolver el de la
casilla cero y correr a todos los demás una casilla a la izquierda, para que
el frente vuelva a estar donde estaba.

  eda="dynamic-array"
  capacity={8}
  operation="remove-first"
  values={[3, 8, 5, 9, 4]}
  times={3}
  pointer="front"
  showCode={false}

Mira cómo cambia el trabajo entre una llamada y la siguiente: el primer
`dequeue` copió cuatro elementos, el segundo tres, el tercero dos. Con
$$N$$ elementos son $$N - 1$$ copias, y por eso desencolar cuesta
$$\Theta(N)$$.

Y acá no hay amortizado que valga. En `push` la corrida cara era **una cada
$$N$$**, y las baratas la pagaban; el corrimiento ocurre en **cada** llamada,
así que no hay nada entre quién repartirlo: $$\Theta(N)$$ en el peor caso y
$$\Theta(N)$$ amortizado.

</Slide>

<Slide title="Costos de Queue sobre arreglo dinámico">
| Operación | Peor caso | Amortizado | Invariante que restaura |
|---|---|---|---|
| `front()` | $$\Theta(1)$$ | $$\Theta(1)$$ | Ninguna: lee `data[0]` y no cambia nada |
| `empty()` | $$\Theta(1)$$ | $$\Theta(1)$$ | Ninguna: `size` ya guarda el dato |
| `size()` | $$\Theta(1)$$ | $$\Theta(1)$$ | Ninguna: devuelve el campo que las otras mantienen |
| `enqueue(x)` | $$\Theta(N)$$ | $$\Theta(1)$$ | Los elementos ocupan `size` casillas seguidas: se escribe en la primera libre, y el bloque crece si no hay |
| `dequeue()` | <span style={{ color: 'var(--color-flag)', fontWeight: 700 }}>$$\Theta(N)$$</span> | <span style={{ color: 'var(--color-flag)', fontWeight: 700 }}>$$\Theta(N)$$</span> | **El frente vive en `data[0]`**: para restaurarla hay que correr a todos los demás |

`dequeue` cuesta $$\Theta(N)$$, y ese costo **no se amortiza**. La llamada
cara de `enqueue` ocurre una cada $$N$$ y las $$N-1$$ baratas la pagan; el
corrimiento ocurre en **cada** llamada, así que no hay entre quién
repartirlo.

Una cola que se usa de verdad desencola tantas veces como encola, así que la
mitad de sus operaciones serían caras. **El arreglo es la estructura
equivocada para este contrato.**

</Slide>

`head` entrega el frente sin caminar, que es lo que la lista ya daba. `tail`
entrega el final sin caminar, que es lo que la cola necesitaba: sin él,
encolar tendría que recorrer la cadena entera para encontrar al último y
costaría $$\Theta(N)$$.

Lo que se paga son dos referencias que mantener al día en vez de una,
incluida la cola de un solo nodo, donde las dos señalan al mismo.

```java
class Queue {
    private Node head;  // el primer nodo: el frente
    private Node tail;  // el último nodo: el final
    private int size;   // cuántos elementos hay

    void enqueue(int x)  // pone x en el final
    int dequeue()        // saca el del frente y lo devuelve
    int front()          // el del frente, sin sacarlo
    boolean empty()      // si la cola no tiene ningún elemento
    int size()           // cuántos elementos tiene
}
```

<Slide title="Las invariantes de la cola sobre lista">
Cuatro propiedades, y la cuarta es la que `tail` trae consigo.

1. **`head` apunta al primer nodo —el frente—, o a `null` si la cola está
   vacía.**

2. **Desde `head`, siguiendo `next`, se llega a todos los nodos y se
   termina en `null`.**

3. **`size` es la cantidad de nodos de esa cadena.**

4. **`tail` apunta al último nodo de la cadena, o a `null` si está
   vacía.** Si queda apuntando a un nodo que ya salió de la cola, el
   siguiente `enqueue` enlaza contra un nodo inalcanzable y el elemento
   nuevo nace perdido.

Las tres primeras son las de cualquier lista enlazada. La cuarta es el
precio de haber ganado el segundo extremo, y es una invariante de las que
cuestan cuidado y no tiempo: mantenerla no alarga ninguna operación, pero
olvidarla en un solo caso de borde rompe la estructura en silencio.

</Slide>

<Slide title="Las consultas">
Las tres operaciones que no cambian la cola salen de los atributos, sin
tocar la cadena.

```java
boolean empty() {
    return size == 0;
}

int size() {
    return size;
}

int front() {
    if (head == null) {
        throw new NoSuchElementException();
    }
    return head.value;
}
```

- **`empty()`** dice si la cola no tiene elementos. Lee un campo: $$\Theta(1)$$.
- **`size()`** devuelve cuántos hay. Lee el campo que `enqueue` y `dequeue`
  mantienen al día, así que nunca hay que recorrer la cadena para contarlo:
  $$\Theta(1)$$.
- **`front()`** devuelve el valor del frente sin sacarlo. `head` ya apunta
  ahí: $$\Theta(1)$$.

`front()` cae sobre `head` porque es la única referencia que se tiene sin
caminar. **Lo que hace de esto una cola y no una pila no son las consultas
sino dónde entra lo nuevo**: en el final, con `tail`, y no en la cabeza.

</Slide>

```java
void enqueue(int x) {
    Node fresh = new Node(x);
    if (head == null) {
        head = fresh;
    } else {
        tail.next = fresh;
    }
    tail = fresh;
    size++;
}
```

El método crea el nodo, lo engancha al final de la cadena, mueve `tail`
hasta él y sube `size`. Engancharlo es una sola asignación —`tail.next =
fresh`— porque `tail` ya tenía al último en la mano; sin esa referencia
habría que recorrer la cadena entera para encontrarlo. Nada de esto depende
del largo: $$\Theta(1)$$.

El `if` es un **caso borde**: la cola vacía. Ahí no hay un último al que
engancharse, así que lo que se asigna es `head`. En las dos ramas el nodo
nuevo termina siendo el último, y por eso `tail = fresh` va afuera del `if`
y se escribe una sola vez.

```java
    int x = head.value;
    head = head.next;
    if (head == null) {
        tail = null;
    }
    size--;
    return x;
}
```

El método guarda el valor del frente, mueve `head` al segundo nodo y baja
`size`. El que sale queda sin nadie apuntándolo, y el colector de basura lo
recupera más tarde. Nada de esto depende del largo: $$\Theta(1)$$.

Los dos `if` son **casos borde**. El primero es la cola vacía: no hay frente
que devolver, así que lanza. El segundo es la cola de un solo nodo: al salir
él, `head` queda en `null` y `tail` tiene que acompañarlo, porque si se
queda apuntando al nodo que ya salió, el próximo `enqueue` engancharía el
elemento nuevo a un nodo que no pertenece a la cola.

</Slide>

<Slide title="Costos de Queue sobre lista">
| Operación | Peor caso | Invariante que restaura |
|---|---|---|
| `build()` | $$\Theta(1)$$ | Deja `head` y `tail` en `null` y `size` en cero |
| `front()` | $$\Theta(1)$$ | Ninguna: lee `head.value` y no cambia la cadena |
| `empty()` | $$\Theta(1)$$ | Ninguna: `size` ya guarda el dato |
| `size()` | $$\Theta(1)$$ | Ninguna: devuelve el campo que las otras mantienen |
| `enqueue(x)` | $$\Theta(1)$$ | `tail` apunta al último: el que lo era enlaza al nuevo, y `tail` lo sigue |
| `dequeue()` | $$\Theta(1)$$ | `head` apunta al frente: pasa a ser el segundo, y si no queda ninguno `tail` lo acompaña |

Todas las operaciones son constantes, y por una sola razón: `head` y `tail`
dejan los dos extremos en la mano, así que ninguna tiene que caminar la
cadena para llegar a donde opera.

Llevar dos referencias en vez de una no cuesta tiempo, cuesta **cuidado**.
`dequeue` necesita un `if` que no hace nada mientras la cola tenga varios
elementos, y que lo es todo cuando sale el último: sin él, `tail` queda
apuntando a un nodo que ya salió de la cola.

</Slide>

<Slide title="Arreglo vs lista">
| | Sobre arreglo dinámico | Lista con `head` y `tail` |
|---|---|---|
| `enqueue(x)` | $$\Theta(1)$$ amortizado | $$\Theta(1)$$ siempre |
| `dequeue()` | <span style={{ color: 'var(--color-flag)', fontWeight: 700 }}>$$\Theta(N)$$</span> | $$\Theta(1)$$ |
| `front()`, `empty()` | $$\Theta(1)$$ | $$\Theta(1)$$ |
| memoria por elemento | el valor | el valor **y** un enlace |
| capacidad | crece copiando | sin límite previo |
| lo que hay que sostener | un índice | dos referencias y el caso de un nodo |

Acá no hay elección. La pila podía construirse igual de bien sobre las dos
estructuras y la decisión se jugaba en memoria y localidad; la cola no: el
arreglo pierde una fila entera, y es la fila de la operación que una cola
hace la mitad del tiempo.

Y la razón es geométrica, no de implementación. **Una pila toca un solo
extremo y un arreglo tiene uno barato.** Una cola toca los dos, y el arreglo
sólo tiene barato el final. La lista paga un enlace por elemento y a cambio
tiene los dos extremos en la mano.

Por eso, cuando alguien escribe una cola, la escribe sobre una lista.

</Slide>

<Slide title="Queue en Java">
Java no trae una clase `Queue`: trae una **interfaz** con ese nombre, que
fija las operaciones sin decir dónde se guardan los elementos. Quien escribe
el programa elige la clase que la implementa, y aquí usaremos `LinkedList`:
la lista enlazada con `tail`. Los nombres del contrato cambian:

| El TDA | Java |
|---|---|
| `enqueue(x)` | `add(x)` |
| `dequeue()` | `remove()` |
| `front()` | `element()` |
| `empty()` | `isEmpty()` |
| `size()` | `size()` |

```java
Queue<Integer> queue = new LinkedList<>();
queue.add(3);
queue.add(8);

int frente = queue.element();  // 3, y la cola queda igual
int x = queue.remove();        // 3, y ahora la cola sólo tiene el 8
```

A la izquierda del `=` va la interfaz y a la derecha la clase: la variable se
declara `Queue` y no `LinkedList`. Así el resto del programa sólo puede pedir
las operaciones del contrato, y cambiar la implementación es cambiar una
línea.

Sobre una cola vacía, `remove()` y `element()` lanzan
`NoSuchElementException`: no devuelven cero ni ninguna otra cosa. El trío
`offer`/`poll`/`peek` hace lo mismo devolviendo `false` o `null` en vez de
lanzar.

</Slide>

```java
static boolean isOpener(char c) {
    return c == '(' || c == '[' || c == '{';
}

static boolean isCloser(char c) {
    return c == ')' || c == ']' || c == '}';
}

static char openerFor(char c) {
    if (c == ')') return '(';
    if (c == ']') return '[';

}
```

si es uno de los tres cierres.

para `)`, `[` para `]`, `{` para `}`.

El algoritmo entero, con sus tres auxiliares. Los casos de prueba son
`({[]})`, `({[]()})`, `([)]`, `(()`, `())` y la cadena vacía. Presiona
**Comprobar** para correrlo, y después cambia lo que quieras.

```java starter
import java.util.Stack;

class Solution {

    static boolean isBalanced(String s) {
        Stack<Character> pending = new Stack<>();
        for (char c : s.toCharArray()) {
            if (isOpener(c)) {
                pending.push(c);
            } else if (isCloser(c)) {
                if (pending.empty()) return false;
                if (pending.pop() != openerFor(c)) return false;
            }
        }
        return pending.empty();
    }

    static boolean isOpener(char c) {
        return c == '(' || c == '[' || c == '{';
    }

    static boolean isCloser(char c) {
        return c == ')' || c == ']' || c == '}';
    }

    static char openerFor(char c) {
        if (c == ')') return '(';
        if (c == ']') return '[';
        return '{';
    }
}
```

<Slide title="Cada baja corre a todos los que quedan">

Mientras han llegado menos de $$K$$ números la ventana no está completa, y el

Con `k` en cero esa división sería cero entre cero y devolvería `NaN` en cada
llamada, que es la peor forma de fallar: sin ruido. La función lo rechaza de
entrada con `IllegalArgumentException`.

Cada número entra y sale de la cola exactamente una vez, y la suma se ajusta
con dos operaciones: $$\Theta(1)$$ por número y $$\Theta(N)$$ por la
secuencia entera. La cola nunca guarda más de $$K$$ números, así que el
espacio es $$\Theta(K)$$.
