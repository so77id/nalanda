# Grafos · Modelo y representación

Una ciudad tiene esquinas unidas por calles; una red social, personas que se
siguen; una malla curricular, ramos que piden otros antes. Los tres problemas
hablan de cosas y de cuáles están unidas, y de nada más. Un **grafo** guarda
exactamente eso, y con él preguntas que parecen distintas resultan ser la
misma. Para responderlas con un programa necesitamos guardar el grafo en
memoria, y hay más de una forma de hacerlo, cada una con su precio.

## Los puentes de Königsberg

{/* KonigsbergMap — Königsberg in one frame, at the three stages of the abstraction (#356): `city` the town as it is, houses in their blocks and the seven bridges in `mark`; `map` only land, water (`sunk`) and bridges, the zones lettered A to D; `graph` only a point on each zone and a line for each bridge, every line passing where its bridge stands, so the stages line up when shown side by side. Schematic, not to scale. File-local: only this class draws the city. */}

export function KonigsbergMap({ stage = 'map', caption, label }) {
  const width = 520;
  const height = 290 + (caption ? 24 : 0);
  const water = [[0, 105], [300, 105], [520, 45], [520, 95], [360, 150], [520, 205], [520, 255], [300, 195], [0, 195]];
  const bridges = [[125, 101, 10, 28], [212, 101, 10, 28], [125, 171, 10, 28], [212, 171, 10, 28], [258, 145, 104, 10], [435, 62, 10, 64], [435, 174, 10, 64]];
  const inWater = (px, py) => {
    let c = false;
    for (let i = 0, j = water.length - 1; i < water.length; j = i++) {
      const [xi, yi] = water[i];
      const [xj, yj] = water[j];
      if ((yi > py) !== (yj > py) && px < ((xj - xi) * (py - yi)) / (yj - yi) + xi) c = !c;
    }
    return c;
  };
  const onIsland = (px, py) => ((px - 175) / 74) ** 2 + ((py - 150) / 18) ** 2 <= 1;
  const nearBridge = (x, y, w, h) => bridges.some(([bx, by, bw, bh]) => x < bx + bw + 7 && x + w > bx - 7 && y < by + bh + 7 && y + h > by - 7);
  const blocks = [];
  if (stage === 'city') {
    for (let row = 0, y = 8; y < 280; row++, y += 22) {
      for (let x = 6 + (row % 2) * 14; x < 500; x += 34) {
        const w = 27;
        const h = 15;
        const corners = [[x - 3, y - 3], [x + w + 3, y - 3], [x - 3, y + h + 3], [x + w + 3, y + h + 3]];
        const land = corners.every(([cx, cy]) => !inWater(cx, cy)) || corners.every(([cx, cy]) => onIsland(cx, cy));
        if (land && !nearBridge(x, y, w, h)) blocks.push([x, y, w, h]);
      }
    }
  }
  const point = { A: [175, 150], B: [175, 52], C: [175, 248], D: [470, 150] };
  const lines = [
    'M 175 150 Q 85 129 175 52',
    'M 175 150 Q 259 129 175 52',
    'M 175 150 Q 85 171 175 248',
    'M 175 150 Q 259 171 175 248',
    'M 175 150 L 470 150',
    'M 175 52 Q 360 52 440 94 Q 470 112 470 150',
    'M 175 248 Q 360 248 440 206 Q 470 188 470 150',
  ];
  const name = (x, y, t, size) => (
    <text x={x} y={y} textAnchor="middle" fontSize={size} fontWeight="700" style={{ fill: 'var(--color-ink)' }}>{t}</text>
  );
  return (
    <svg viewBox={stage === 'graph' ? '70 18 450 264' : `0 0 ${width} ${height}`} style={{ width: '100%', maxWidth: stage === 'graph' ? '320px' : '560px', height: 'auto', display: 'block', margin: '0.6rem auto' }} role="img" aria-label={label}>
      {stage === 'graph' ? null : (
        <>
          <polygon points={water.map((p) => p.join(',')).join(' ')} style={{ fill: 'var(--color-sunk)', stroke: 'var(--color-rule-strong)' }} strokeWidth="1.2" />
          <ellipse cx="175" cy="150" rx="85" ry="25" style={{ fill: 'var(--color-ground)', stroke: 'var(--color-rule-strong)' }} strokeWidth="1.2" />
          {blocks.map(([x, y, w, h], k) => (
            <rect key={`h${k}`} x={x} y={y} width={w} height={h} rx="1.5" style={{ fill: 'var(--color-surface)', stroke: 'var(--color-rule-strong)' }} strokeWidth="0.8" />
          ))}
          {bridges.map(([x, y, w, h], k) => (
            <rect key={`b${k}`} x={x} y={y} width={w} height={h} rx="2" style={{ fill: stage === 'city' ? 'var(--color-mark)' : 'var(--color-ink-soft)' }} />
          ))}
        </>
      )}
      {stage === 'map' ? (
        <>
          {name(175, 64, 'B', 28)}
          {name(175, 266, 'C', 28)}
          {name(175, 160, 'A', 28)}
          {name(482, 160, 'D', 28)}
        </>
      ) : null}
      {stage === 'graph' ? (
        <>
          {lines.map((d, k) => (
            <path key={`l${k}`} d={d} fill="none" style={{ stroke: 'var(--color-rule-strong)' }} strokeWidth="2.1" />
          ))}
          {Object.entries(point).map(([v, [x, y]]) => (
            <g key={v}>
              <circle cx={x} cy={y} r="28" style={{ fill: 'var(--color-surface)', stroke: 'var(--color-rule-strong)' }} strokeWidth="2.1" />
              {name(x, y + 8, v, 23)}
            </g>
          ))}
        </>
      ) : null}
      {caption ? (
        <text x={width / 2} y={height - 8} textAnchor="middle" fontSize="13" style={{ fill: 'var(--color-ink-soft)' }}>{caption}</text>
      ) : null}
    </svg>
  );
}

## Las partes de un grafo

<Slide title="Los vértices">
Cada zona de tierra es un **vértice**, un punto del dibujo. Los vértices forman
un conjunto, que se llama $$V$$. Las llaves encierran los elementos de un
conjunto, y en un conjunto el orden no importa:

$$
V = \{A, B, C, D\} \qquad |V| = 4
$$

Se lee «$$V$$ es el conjunto de A, B, C y D, y tiene cuatro elementos».

<Slide title="Las aristas">
Cada puente es una **arista**: une dos vértices, sus **extremos**. El puente se
cruza en los dos sentidos, así que la arista no tiene dirección, y se escribe
como el conjunto de sus dos extremos.

<Slide title="Qué es un grafo">
Un **grafo** es el par formado por sus vértices y sus aristas:

$$
G = (V, E)
$$

Se lee «$$G$$ es el par formado por $$V$$ y $$E$$»: un par ordenado, primero
los vértices y después las aristas. $$E$$ reúne las aristas y puede repetir
una, como los dos puentes entre A y B, así que no se escribe entre llaves. Por
costumbre, en las cuentas se escribe $$V$$ y $$E$$ en vez de $$|V|$$ y $$|E|$$.

<Slide title="La forma y la posición no importan">
Un grafo no dice dónde va cada vértice ni cómo se dibuja cada arista: en
$$G = (V, E)$$ no hay posiciones. Dos dibujos con los mismos vértices y las mismas aristas son el **mismo grafo**,
aunque se vean distintos. El primero sigue el mapa de la ciudad y los otros
dos no, y los tres responden igual la pregunta del paseo.

<Slide title="Grafos isomorfos">
Si además se cambian los nombres de los vértices, puede seguir siendo el mismo
grafo con otros nombres. Cuando cada vértice de uno se puede emparejar con uno
del otro de modo que las aristas coincidan, los dos grafos son **isomorfos**:
$$G_1 \cong G_2$$, que se lee «$$G_1$$ es isomorfo a $$G_2$$». El emparejamiento
es una función biyectiva $$f\colon V_1 \to V_2$$ que conserva las aristas:
entre $$u$$ y $$v$$ hay tantas como entre $$f(u)$$ y $$f(v)$$.

<Slide title="Los vecinos de un vértice">
Dos vértices unidos por una arista son **vecinos**, o **adyacentes**: $$u$$ y
$$v$$ son vecinos si $$uv \in E$$, que se lee «la arista $$uv$$ está en $$E$$».
Un vértice puede tener muchos vecinos, o ninguno.

## Caminos y ciclos

<Slide title="Caminos">
El paseo va de zona en zona por los puentes; en el grafo, de vértice en
vértice por las aristas. Un **camino** es una secuencia de vértices en la que
cada uno es vecino del siguiente y ninguna arista se repite:

$$
v_0, v_1, \dots, v_k \qquad \text{con } v_i v_{i+1} \in E
$$

Se lee «de $$v_0$$ a $$v_k$$, cada vértice unido al siguiente por una arista».
Puede pasar varias veces por el mismo vértice. Su **largo** es la cantidad de
aristas que recorre, $$k$$.

## La respuesta de Euler

<Slide title="Cada paso por un vértice usa dos aristas">
Un paseo que cruza cada puente una vez es un camino que usa todas las
aristas del grafo.

Cuando el camino pasa por un vértice, llega por una arista y sale por otra.
Cada paso usa **dos** aristas del vértice, y como ninguna arista se repite, un
vértice por el que el camino solo pasa tiene que tener grado par.

Solo dos vértices escapan de esa cuenta: el del **comienzo**, donde el camino
sale sin haber llegado, y el del **final**, donde llega sin volver a salir. En
un ciclo los dos son el mismo vértice, y también usa sus aristas de a dos.

</Slide>

<Slide title="Los vértices de grado impar son una cantidad par">
La cuenta deja como impares, a lo más, el comienzo y el final. Que quede uno
solo no pasa nunca, y lo dice una suma. En una reunión, si cada persona cuenta
cuántas manos estrechó y sumamos esos números, cada apretón queda contado dos
veces. En un grafo, cada arista suma uno al grado de cada uno de sus dos
extremos:

$$
\sum_{v} \operatorname{grado}(v) = 2E
$$

Se lee «la suma de los grados de todos los vértices es dos veces la cantidad
de aristas»: es el **lema del apretón de manos**. La suma es par; los vértices
de grado par suman un número par, así que los de grado impar también, y una
suma de números impares es par solo si son una cantidad par. **En todo grafo,
la cantidad de vértices de grado impar es par.**

<Slide title="La regla de Euler">
En un grafo conexo, la cantidad de vértices de grado impar decide si hay un
**camino euleriano**, uno que usa cada arista exactamente una vez:

- **Ninguno impar**: hay uno que parte de cualquier vértice y termina donde
  empezó, un **ciclo euleriano**.
- **Dos impares**: hay uno que parte de uno de los dos y termina en el otro.
- **Más de dos impares**: no hay ninguno.

Un solo vértice impar no ocurre nunca: los vértices de grado impar son
siempre una cantidad par. Que las dos primeras condiciones alcancen también
es de Euler, y se demuestra construyendo el camino.

<Slide title="Por qué estudiar grafos">
- **Pocas ideas resuelven muchos problemas.** Unos pocos algoritmos de grafos
  responden preguntas de áreas que no se parecen en nada: aprenderlos una vez
  sirve para todas.
- **Aparecen en todas partes.** En algoritmos, redes, inteligencia artificial
  y compiladores, y son uno de los temas más frecuentes en las entrevistas
  técnicas de programación.
- **Todavía hay preguntas abiertas.** Para algunos problemas de grafos que se
  ven tan simples como el de Königsberg no se conoce un algoritmo eficiente.
  Saber si existe es la pregunta **P frente a NP**: ¿todo problema cuya
  solución se puede comprobar eficientemente también se puede encontrar
  eficientemente? Es uno de los siete Problemas del Milenio, con un premio de
  un millón de dólares.

## Clases de grafos

<Slide title="Grafos dirigidos">
Las mismas personas dan dos grafos según la relación que se mire. Ser amigos
va en los dos sentidos; seguir a alguien en una red social, no: no obliga a
que esa persona nos siga. En un **grafo dirigido**, cada arista va de un
vértice a otro y se dibuja como una flecha. En vez del conjunto $$\{u, v\}$$,
la arista es el par ordenado $$(u, v)$$: va de $$u$$ a $$v$$, y
$$(u, v) \neq (v, u)$$.

<Slide title="Grado de entrada y de salida">
En un grafo dirigido, cada vértice tiene dos grados. El **grado de salida**
cuenta las flechas que salen de él: las personas que sigue. El **grado de
entrada** cuenta las flechas que llegan a él: las personas que lo siguen. Se
escriben $$\operatorname{grado}^+(v)$$, el de salida, y $$\operatorname{grado}^-(v)$$, el
de entrada. En un grafo sin dirección los dos son el mismo número, el grado.

Un grafo simple con todas sus aristas posibles es **completo**: cada vértice
está unido con todos los demás. El completo de $$n$$ vértices se escribe
$$K_n$$. Cada uno de sus $$n$$ vértices se une con los otros $$n - 1$$, y así
cada arista se cuenta dos veces:

$$
\frac{n(n - 1)}{2}
$$

Se lee «$$n$$ por $$n - 1$$, dividido en dos».

Un **árbol** es un grafo conexo y sin ciclos. Entre dos de sus vértices hay
exactamente un camino simple, y tiene una arista menos que vértices:

$$

$$

Se lee «la cantidad de aristas es la de vértices menos uno». Con una arista
menos deja de ser conexo, y con una más cierra un ciclo. Un árbol con raíz es
un árbol en el que se elige un vértice como raíz.

{/* StreetPlan — a street map in one frame at two stages of the modelling pattern (#356): `city` the four streets with their blocks of buildings, one-way arrows and the minutes each stretch takes; `streets` only the corners, lettered, and the stretches with their minutes and senses. The third stage is the graph, a <NodeGraph> beside it. File-local. */}

export function StreetPlan({ stage = 'city', label }) {
  const at = { A: [80, 60], B: [240, 60], C: [80, 180], D: [240, 180] };
  const stretches = [['A', 'B', 4, true], ['A', 'C', 3, false], ['C', 'D', 5, false], ['D', 'B', 2, false]];
  const tip = (x1, y1, x2, y2) => {
    const d = Math.hypot(x2 - x1, y2 - y1);
    const ux = (x2 - x1) / d;
    const uy = (y2 - y1) / d;
    const bx = x2 - ux * 9;
    const by = y2 - uy * 9;
    return `${x2},${y2} ${bx - uy * 5},${by + ux * 5} ${bx + uy * 5},${by - ux * 5}`;
  };
  const blocks = [];
  if (stage === 'city') {
    for (const [x0, x1] of [[22, 70], [90, 230], [250, 298]]) {
      for (const [y0, y1] of [[22, 50], [70, 170], [190, 218]]) {
        const n = Math.max(1, Math.round((x1 - x0) / 50));
        const m = Math.max(1, Math.round((y1 - y0) / 50));
        const w = (x1 - x0 - (n - 1) * 5) / n;
        const h = (y1 - y0 - (m - 1) * 5) / m;
        for (let i = 0; i < n; i++) for (let j = 0; j < m; j++) blocks.push([x0 + i * (w + 5), y0 + j * (h + 5), w, h]);
      }
    }
  }
  return (
    <svg viewBox="0 0 320 240" style={{ width: '100%', maxWidth: '340px', height: 'auto', display: 'block', margin: '0.4rem auto' }} role="img" aria-label={label}>
      {stage === 'city'
        ? [[12, 60, 308, 60], [12, 180, 308, 180], [80, 12, 80, 228], [240, 12, 240, 228]].map(([x1, y1, x2, y2], k) => (
            <line key={`s${k}`} x1={x1} y1={y1} x2={x2} y2={y2} style={{ stroke: 'var(--color-sunk)' }} strokeWidth="18" />
          ))
        : null}
      {blocks.map(([x, y, w, h], k) => (
        <rect key={`b${k}`} x={x} y={y} width={w} height={h} rx="2" style={{ fill: 'var(--color-surface)', stroke: 'var(--color-rule-strong)' }} strokeWidth="0.8" />
      ))}
      {stretches.map(([v, w, minutes, both], k) => {
        const [x1, y1] = at[v];
        const [x2, y2] = at[w];
        const mx = (x1 + x2) / 2;
        const my = (y1 + y2) / 2;
        const ux = (x2 - x1) / Math.hypot(x2 - x1, y2 - y1);
        const uy = (y2 - y1) / Math.hypot(x2 - x1, y2 - y1);
        const chipX = mx + (uy !== 0 ? 30 : 0);
        const chipY = my + (uy !== 0 ? 0 : -19);
        return (
          <g key={`t${k}`}>
            {stage === 'streets' ? <line x1={x1} y1={y1} x2={x2} y2={y2} style={{ stroke: 'var(--color-rule-strong)' }} strokeWidth="2" /> : null}
            <polygon points={tip(mx - ux * 14, my - uy * 14, mx + ux * 14, my + uy * 14)} style={{ fill: 'var(--color-ink-soft)' }} />
            {both ? <polygon points={tip(mx + ux * 14, my + uy * 14, mx - ux * 14, my - uy * 14)} style={{ fill: 'var(--color-ink-soft)' }} /> : null}
            <rect x={chipX - 25} y={chipY - 10} width="50" height="20" rx="5" style={{ fill: 'var(--color-surface)', stroke: 'var(--color-rule)' }} strokeWidth="1" />
            <text x={chipX} y={chipY + 5} textAnchor="middle" fontSize="13" style={{ fill: 'var(--color-ink)' }}>{minutes} min</text>
          </g>
        );
      })}
      {stage === 'streets'
        ? Object.entries(at).map(([v, [x, y]]) => (
            <g key={v}>
              <circle cx={x} cy={y} r="13" style={{ fill: 'var(--color-surface)', stroke: 'var(--color-rule-strong)' }} strokeWidth="1.4" />
              <text x={x} y={y + 5} textAnchor="middle" fontSize="14" fontWeight="700" style={{ fill: 'var(--color-ink)' }}>{v}</text>
            </g>
          ))
        : null}
    </svg>
  );
}

## Graph · Grafo

<Slide title="Un grafo como lista de aristas">
Un grafo llega a un programa casi siempre como una **lista de aristas**: en
la primera línea, la cantidad de vértices y la de aristas; después, una línea
por arista con sus dos extremos. En un grafo sin dirección cada arista
aparece una sola vez.

```text
4 4
0 1
0 2
1 2
2 3
```

Guardar esas líneas tal cual, como una lista de pares, alcanza para contar
las aristas, pero no para la pregunta que más se le hace a un grafo: quiénes
son los vecinos de un vértice. Para saber los vecinos de `2` hay que leer las
$$E$$ aristas buscando las que lo tocan, y hacerlo para cada vértice cuesta
$$\Theta(V \cdot E)$$. El grafo tiene que guardarse de modo que esa pregunta
se responda sin leerlo entero.

</Slide>

<Slide title="Las reglas del contrato Graph">
Un grafo sin dirección cumple dos invariantes:

1. **Cada arista se ve desde sus dos extremos**: `w` está entre los vecinos
   de `v` si y solo si `v` está entre los vecinos de `w`. Por eso `addEdge(v,
   w)` deja la arista en los dos lados.
2. **`E()` cuenta cada arista una vez**, aunque se vea desde dos vértices.

Los vértices no cambian: el contrato no agrega ni saca vértices, y cada
vértice es un número de $$0$$ a $$V - 1$$.

</Slide>

<Slide title="El contrato Graph en Java">
Java no trae un grafo, así que escribimos el contrato como una interfaz:

```java
public interface Graph {
    int V();
    int E();
    Iterable<Integer> adj(int v);
    boolean hasEdge(int v, int w);
    void addEdge(int v, int w);
}
```

`adj` retorna un `Iterable<Integer>`: lo que se puede recorrer con un `for`.
El constructor no va en la interfaz; cada clase que la implementa recibe
`V` en el suyo.

</Slide>

<Slide title="El grado como cliente del contrato">
El grado de un vértice se calcula solo con el contrato: recorrer sus vecinos y
contarlos. El método no sabe cómo está guardado el grafo, y sirve para
cualquier implementación.

```java
static int degree(Graph g, int v) {
    int count = 0;
    for (int w : g.adj(v)) {
        count++;
    }
    return count;
}
```

Su costo es el de recorrer `adj(v)`, y ese costo lo decide la implementación.

</Slide>

<Slide title="Una matriz de adyacencia">
Una **matriz de adyacencia** es una tabla de $$V \times V$$ booleanos, con una
casilla por cada par de vértices:

$$
M[u][v] = \text{verdadero} \iff uv \in E
$$

Se lee «la casilla de la fila $$u$$ y la columna $$v$$ es verdadera si y solo si
la arista $$uv$$ está en $$E$$». En un grafo sin dirección cada arista llena dos
casillas, una a cada lado de la diagonal, y la matriz queda simétrica:
$$M[u][v] = M[v][u]$$.

<Slide title="El código de la matriz">
```java
public class AdjMatrixGraph implements Graph {
    private final boolean[][] matrix;
    private int E;

    public AdjMatrixGraph(int V) {
        matrix = new boolean[V][V];
    }

    public int V() { return matrix.length; }

    public int E() { return E; }

    public boolean hasEdge(int v, int w) { return matrix[v][w]; }

    public Iterable<Integer> adj(int v) {
        List<Integer> neighbors = new ArrayList<>();
        for (int w = 0; w < matrix.length; w++) {
            if (matrix[v][w]) {
                neighbors.add(w);
            }
        }
        return neighbors;
    }

    public void addEdge(int v, int w) {
        if (!matrix[v][w]) {
            E++;
        }
        matrix[v][w] = true;
        matrix[w][v] = true;
    }
}
```

`hasEdge` mira una casilla. `adj(v)` recorre la fila completa de `v` para
encontrar sus vecinos, aunque sean pocos. `addEdge` llena las dos casillas y
cuenta la arista solo si no estaba: una casilla no guarda dos aristas, así que
la matriz no admite aristas paralelas, y los dos puentes entre la isla y una
orilla de Königsberg quedarían como uno.

</Slide>

<Slide title="Unas listas de adyacencia">
Unas **listas de adyacencia** guardan, por cada vértice, una lista con sus
vecinos: la lista de $$v$$ tiene un $$w$$ por cada arista $$vw$$ de $$E$$.

$$
|\mathrm{adj}(v)| = \operatorname{grado}(v)
$$

Se lee «el largo de la lista de $$v$$ es el grado de $$v$$». En un grafo sin
dirección cada arista aparece dos veces: en la lista de cada uno de sus
extremos.

```java
public class AdjListGraph implements Graph {
    private final List<List<Integer>> lists;
    private int E;

    public AdjListGraph(int V) {
        lists = new ArrayList<>();
        for (int v = 0; v < V; v++) {
            lists.add(new ArrayList<>());
        }
    }

    public int V() { return lists.size(); }

    public int E() { return E; }

    public boolean hasEdge(int v, int w) { return lists.get(v).contains(w); }

    public Iterable<Integer> adj(int v) { return lists.get(v); }

    public void addEdge(int v, int w) {
        lists.get(v).add(w);
        lists.get(w).add(v);
        E++;
    }
}
```

`adj(v)` entrega la lista de `v` tal como está. `hasEdge` la recorre buscando
a `w`. `addEdge` agrega al final de las dos listas, sin revisar si la arista
ya estaba: agregarla dos veces deja dos aristas, como los dos puentes de
Königsberg.

<Slide title="Leer un grafo">
La lista de aristas se lee línea a línea. Cada arista entra con `addEdge`, que
en un grafo sin dirección la deja en las dos listas:

```java
static Graph read(Scanner in) {
    int V = in.nextInt();
    int E = in.nextInt();
    Graph g = new AdjListGraph(V);
    for (int i = 0; i < E; i++) {
        int v = in.nextInt();
        int w = in.nextInt();
        g.addEdge(v, w);
    }
    return g;
}
```

En un grafo dirigido, `addEdge(v, w)` agrega solo la flecha de `v` a `w`. Cada
implementación cambia una línea: la matriz llena una sola casilla y deja de
ser simétrica, y la flecha aparece solo en la lista de `v`. `adj(v)` entrega

símbolos, $$M[u][v]$$ es verdadera si y solo si $$(u, v) \in E$$, y
$$|\mathrm{adj}(v)| = \operatorname{grado}^+(v)$$.

<Slide title="El grado de entrada en un grafo dirigido">
`adj(v)` entrega las flechas que salen de `v`, así que el grado de salida
sale de recorrer `adj(v)`. Las flechas que **llegan** a `v` no están en su
lista: están repartidas en las listas de los otros vértices. Para contarlas
hay que recorrer todas las listas, o la columna de `v` en la matriz.

```java
static int inDegree(Graph g, int v) {
    int count = 0;
    for (int u = 0; u < g.V(); u++) {
        for (int w : g.adj(u)) {
            if (w == v) {
                count++;
            }
        }
    }
    return count;
}
```

Con listas cuesta $$\Theta(V + E)$$, porque pasa por cada lista y por cada
flecha.

<Slide title="Un grafo con pesos en Java">
Con pesos, el contrato cambia: `addEdge` recibe el peso de la arista, y
`adj(v)` entrega cada vecino junto con el peso de la arista que lleva a él.
Una clase chica, `Edge`, junta los dos, y el contrato es otra interfaz:

```java
public class Edge {
    public final int to;
    public final int weight;

    public Edge(int to, int weight) {
        this.to = to;
        this.weight = weight;
    }
}

public interface WeightedGraph {
    int V();
    int E();
    Iterable<Edge> adj(int v);
    void addEdge(int v, int w, int weight);
}
```

Las dos implementaciones con pesos cumplen este contrato.

<Slide title="Un grafo con pesos en la matriz">
Con pesos, la casilla guarda el peso de la arista en vez de un booleano:

$$
M[u][v] = \begin{cases} w(u, v) & \text{si } uv \in E \\ \infty & \text{si no} \end{cases}
$$

Se lee «la casilla de $$u$$ y $$v$$ guarda el peso de $$uv$$ si la arista
existe, e infinito si no». Una casilla sin arista no puede guardar $$0$$, porque una arista de peso $$0$$
existe: un tramo que no cuesta nada. Guarda un valor que ningún peso puede
tomar, $$\infty$$, que en Java es el entero más grande, `Integer.MAX_VALUE`.

public class WeightedMatrixGraph implements WeightedGraph {
    static final int INFINITY = Integer.MAX_VALUE;
    private final int[][] weight;
    private int E;

    public WeightedMatrixGraph(int V) {
        weight = new int[V][V];
        for (int[] row : weight) {
            Arrays.fill(row, INFINITY);
        }
    }

    public int V() { return weight.length; }

    public int E() { return E; }

    public Iterable<Edge> adj(int v) {
        List<Edge> edges = new ArrayList<>();
        for (int w = 0; w < weight.length; w++) {
            if (weight[v][w] != INFINITY) {
                edges.add(new Edge(w, weight[v][w]));
            }
        }
        return edges;
    }

    public void addEdge(int v, int w, int weight) {
        if (this.weight[v][w] == INFINITY) {
            E++;
        }
        this.weight[v][w] = weight;
        this.weight[w][v] = weight;
    }
}
```

`adj(v)` recorre la fila de `v` y arma un `Edge` por cada casilla que no
vale $$\infty$$. `addEdge` escribe el peso en las dos casillas y cuenta la
arista solo si no estaba.

public void addEdge(int v, int w, int weight) {
    lists.get(v).add(new Edge(w, weight));
    lists.get(w).add(new Edge(v, weight));
    E++;
}
```

La clase, `WeightedListGraph`, implementa `WeightedGraph` y cambia solo
esto: el constructor, `V()` y `E()` quedan como en las listas sin pesos.

</Slide>

## Costos y memoria

<Slide title="Costos de las dos implementaciones">
| Molde     | Operación          | Matriz                  | Listas                            | Invariante que restaura                          |
| --------- | ------------------ | ----------------------- | --------------------------------- | ------------------------------------------------ |
| crear     | `Graph(V)`         | $$\Theta(V^2)$$         | $$\Theta(V)$$                     | —                                                |
| consultar | `V()`, `E()`       | $$\Theta(1)$$           | $$\Theta(1)$$                     | Ninguna: no cambian nada                         |
| consultar | recorrer `adj(v)`  | $$\Theta(V)$$           | $$\Theta(\operatorname{grado}(v))$$ | Ninguna                                          |
| consultar | `hasEdge(v, w)`    | <span style={{ color: 'var(--color-keep)', fontWeight: 700 }}>$$\Theta(1)$$</span> | $$\Theta(\operatorname{grado}(v))$$ | Ninguna                                          |
| modificar | `addEdge(v, w)`    | $$\Theta(1)$$           | $$\Theta(1)$$                     | La arista queda en los dos lados y se cuenta una vez |

La matriz responde si hay una arista mirando una casilla, pero para dar los
vecinos de `v` recorre su fila completa, tenga `v` muchos o pocos. Las listas
entregan los vecinos sin mirar a nadie más, y pagan esa misma cuenta cuando se
les pregunta por una arista.

</Slide>

<Slide title="La memoria de las dos implementaciones">
- **La matriz** guarda $$V^2$$ casillas, haya las aristas que haya:
  $$\Theta(V^2)$$.
- **Las listas** guardan una lista por vértice y una entrada por extremo de
  arista: $$\Theta(V + E)$$.

Las entradas de las listas se cuentan con el lema del apretón de manos:

$$
\sum_{v} |\mathrm{adj}(v)| = \sum_{v} \operatorname{grado}(v) = 2E
$$

Se lee «la suma de los largos de las listas es la suma de los grados, que es
dos veces la cantidad de aristas». Cuál ocupa menos depende de cuántas aristas
tiene el grafo.

</Slide>

<Slide title="Grafos densos y dispersos">
En un grafo simple sin dirección, cada par de vértices tiene a lo más una
arista, así que

$$
E \le \frac{V(V - 1)}{2}
$$

Se lee «$$E$$ es a lo más $$V$$ por $$V - 1$$, dividido en dos», y un grafo
completo llega justo a ese máximo. Un grafo con cerca de ese máximo es
**denso**, y uno con muchas menos aristas, cerca de $$V$$, es **disperso**. En
las cuentas de costo, denso es $$E = \Theta(V^2)$$, y disperso, $$E = O(V)$$.

<Slide title="Recorrer todos los vecinos de todos los vértices">
Muchos problemas recorren los vecinos de cada vértice del grafo.

- **Con la matriz**, cada vértice recorre su fila: $$V$$ filas de $$V$$
  casillas, $$\Theta(V^2)$$.
- **Con listas**, cada vértice recorre su lista, y la suma de los largos de
  las listas es la suma de los grados, que es $$2E$$. Sumando la visita a cada
  vértice, $$\Theta(V + E)$$.

$$\Theta(V + E)$$ es lo que cuesta leer el grafo una vez: es **tiempo lineal**
en el tamaño del grafo, y ningún programa que mire cada arista puede hacerlo
en menos.

</Slide>

<Slide title="Matriz o listas">
Un grafo real casi siempre es disperso: en un mapa, cada esquina tiene unas
pocas calles; en una red social de millones de personas, cada una tiene unos
cientos de amigos. Una matriz para un millón de vértices tendría $$10^{12}$$
casillas, casi todas falsas.

- **La matriz** responde si dos vértices son vecinos en tiempo constante, y
  lo paga con $$\Theta(V^2)$$ de memoria y con recorrer filas completas.
  Conviene cuando el grafo es denso y chico.
- **Las listas** pagan $$\Theta(\operatorname{grado}(v))$$ para responder si
  dos vértices son vecinos, y a cambio ocupan $$\Theta(V + E)$$ y entregan los
  vecinos sin mirar a nadie más. Son la elección por omisión.

</Slide>

## Grafos que no se guardan

<Slide title="Un grafo implícito">
A veces no hace falta guardar el grafo, ni en una matriz ni en listas: sus

Una celda del borde tiene menos vecinas, porque algunos pasos salen de la

<Slide title="El código de las vecinas">
Las vecinas no se guardan: se calculan con dos arreglos de desplazamientos,
uno para la fila y otro para la columna. Cada posición `k` es un paso, y una
vecina cuenta solo si cae dentro de la grilla.

```java
static final int[] DR = {-1, 1, 0, 0};
static final int[] DC = {0, 0, -1, 1};

static List<int[]> neighbors(int r, int c, int rows, int cols) {
    List<int[]> result = new ArrayList<>();
    for (int k = 0; k < DR.length; k++) {
        int nr = r + DR[k];
        int nc = c + DC[k];
        if (nr >= 0 && nr < rows && nc >= 0 && nc < cols) {
            result.add(new int[] {nr, nc});
        }
    }
    return result;
}
```

En 8 direcciones cambian solo los arreglos; el método queda igual:

```java
static final int[] DR = {-1, -1, -1, 0, 0, 1, 1, 1};
static final int[] DC = {-1, 0, 1, -1, 1, -1, 0, 1};
```

<Slide title="Las rutas de una aerolínea">
Una aerolínea publica sus rutas como un texto, una ruta por línea: los
códigos de los dos aeropuertos que une. Cada ruta se vuela en los dos

```text

BOG MIA
LIM GRU
```

**Entrada.** Las rutas, a lo más $$10^5$$, sin repetir ninguna. $$R$$ es la
cantidad de rutas y $$A$$, la de aeropuertos.

**Salida.** El código del aeropuerto con más rutas —si hay empate, el que
aparece primero en el texto— y los códigos de sus destinos.

</Slide>

<Slide title="Rutas aéreas · el grafo">
Los aeropuertos son los vértices y cada ruta es una arista sin dirección,
porque se vuela en los dos sentidos. Las rutas no traen un número que el

Al leer cada línea, los dos códigos se traducen a números con `idOf`, y la

static void busiest(Scanner in) {
    List<int[]> routes = new ArrayList<>();
    while (in.hasNext()) {
        int v = idOf(in.next());
        int w = idOf(in.next());
        routes.add(new int[] {v, w});
    }
    Graph g = new AdjListGraph(names.size());
    for (int[] r : routes) {
        g.addEdge(r[0], r[1]);
    }
    int best = 0;
    int bestDegree = degree(g, 0);
    for (int v = 1; v < g.V(); v++) {
        int d = degree(g, v);
        if (d > bestDegree) {
            best = v;
            bestDegree = d;
        }
    }
    System.out.print(names.get(best) + ":");
    for (int w : g.adj(best)) {
        System.out.print(" " + names.get(w));
    }
    System.out.println();
}

apareció primero en el texto.

- **Memoria.** La lista de rutas, el `Map`, los nombres y el grafo:
  $$\Theta(A + R)$$.

Si el texto repitiera una ruta, el grafo la guardaría dos veces y la contaría
dos veces en el grado: el enunciado lo descarta.

<Slide title="Un solo trazo · la idea">
Probar todos los órdenes de los trazos funciona, pero $$E$$ trazos se pueden
ordenar de $$E!$$ maneras. El problema se reduce al camino euleriano, y la
regla de Euler responde sin probar ninguno: en un grafo conexo, lo deciden los
vértices de grado impar.

- **Ninguno**: cualquier punto sirve, y el trazo vuelve a él.
- **Dos**: hay que empezar en uno de los dos.
- **Más de dos**: no se puede.

Basta con calcular el grado de cada vértice y quedarse con los impares.

</Slide>

<Slide title="Un solo trazo · la solución">
```java
static int startOf(Graph g) {
    List<Integer> odd = new ArrayList<>();
    for (int v = 0; v < g.V(); v++) {
        if (degree(g, v) % 2 == 1) {
            odd.add(v);
        }
    }
    if (odd.isEmpty()) {
        return 0;
    }
    if (odd.size() == 2) {
        return odd.get(0);
    }
    return -1;
}
```

Sin vértices impares, cualquier punto sirve, y el método responde el $$0$$.
Con dos, el trazo empieza en el primero y termina en el segundo.

- **Tiempo.** El grado de cada vértice recorre su lista: $$\Theta(V + E)$$
  en total.
- **Memoria.** La lista de impares: $$O(V)$$.

La respuesta vale solo si el grafo es conexo, como dice el enunciado: dos
figuras separadas pueden tener sus grados pares y no dibujarse de un trazo.

</Slide>

```java
static int suggest(Graph g, int u) {
    boolean[] friend = new boolean[g.V()];
    for (int x : g.adj(u)) {
        friend[x] = true;
    }
    int[] common = new int[g.V()];
    for (int x : g.adj(u)) {
        for (int w : g.adj(x)) {
            if (w != u && !friend[w]) {
                common[w]++;
            }
        }
    }
    int best = -1;
    for (int w = 0; w < g.V(); w++) {
        if (common[w] > 0 && (best == -1 || common[w] > common[best])) {
            best = w;
        }
    }
    return best;
}
```

`friend` marca a los amigos de `u` para saltarlos en tiempo constante, sin
preguntar `hasEdge`, que en listas recorrería la lista de `u` cada vez.

</Slide>

<Slide title="Sugerir amigos · el costo">
- **Tiempo.** Recorrer los amigos de los amigos de `u` cuesta la suma de los
  grados de los amigos de `u`, a lo más $$2E$$. Crear los dos arreglos y
  buscar el mayor cuesta $$\Theta(V)$$. En total, $$O(V + E)$$, y casi siempre
  mucho menos que $$E$$ en el recorrido: solo se miran las personas a dos
  pasos de `u`.
- **Memoria.** Los dos arreglos: $$\Theta(V)$$.

Si `u` no tiene amigos, o sus amigos no tienen otros amigos, ningún contador
sube y el método retorna $$-1$$.

</Slide>

## Más allá de la matriz y las listas

<Slide title="Un Map de cada vértice a sus vecinos">
Cuando los vértices tienen nombre, un `Map` puede guardar el grafo sin
traducir nada: de cada nombre al **conjunto** de sus vecinos.

```java
Map<String, Set<String>> adj = new HashMap<>();

void addEdge(String v, String w) {
    if (!adj.containsKey(v)) {
        adj.put(v, new HashSet<>());
    }
    if (!adj.containsKey(w)) {
        adj.put(w, new HashSet<>());
    }
    adj.get(v).add(w);
    adj.get(w).add(v);
}
```

- **Lo que gana.** Los vértices se llaman como en el problema, y preguntar si
  hay una arista cuesta $$\Theta(1)$$ esperado, como en la matriz, con la
  memoria de las listas, $$\Theta(V + E)$$.
- **Lo que pierde.** Un conjunto no guarda dos veces el mismo vecino, así que
  no caben aristas paralelas, como los dos puentes entre la isla y una orilla.
  Un `HashSet` entrega los vecinos en un orden que nadie elige; un `TreeSet`
  los ordena, a cambio de $$O(\log V)$$ por operación. Y cada entrada pesa
  más que un entero en una lista.

</Slide>

<Slide title="Pasar una vez por cada vértice">
El juego de Euler pide pasar una vez por cada **arista**. Su gemelo pide pasar
una vez por cada **vértice** y volver al inicio: es un **ciclo hamiltoniano**,
un ciclo simple que pasa por todos los vértices, por William Hamilton, que lo
propuso como un juego en 1857.

Se parecen, y no se resuelven igual. Para Euler, contar grados basta. Para
Hamilton no se conoce ninguna regla así: probar todos los órdenes de los
vértices siempre responde, pero son $$V!$$, y no se conoce un algoritmo
eficiente que responda para cualquier grafo.

</Slide>

<Slide title="Los cuatro colores">
Pintar un mapa para que dos países con frontera tengan colores distintos es
un problema de grafos: cada país es un vértice, y cada frontera, una arista.
Pintar es dar a cada vértice un color distinto del de sus vecinos.

Los días de exámenes son el mismo problema: cada ramo es un vértice, dos
ramos con alumnos en común se unen con una arista, y cada color es un día.

Cuatro colores alcanzan para cualquier mapa dibujado en un plano: se demostró
en 1976, con la ayuda de un computador. Saber si **tres** alcanzan para un
mapa dado es otra cosa: no se conoce un algoritmo eficiente que lo responda.

## Lo que sigue

Con un grafo guardado, la pregunta siguiente es a dónde se llega desde un
vértice, la **alcanzabilidad**: si hay un camino entre dos esquinas, si el
barquero cruza el río, cuántas islas tiene un mapa,
por dónde se sale de un laberinto con menos pasos. Ninguna se responde
mirando un vértice y sus vecinos: hay que **recorrer** el grafo, de vecino en
vecino, sin perderse en sus ciclos.
