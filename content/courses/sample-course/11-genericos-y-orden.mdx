# Genéricos y orden

Ya escribiste una clase `Pair` que guarda dos enteros. Ahora la vas a hacer
crecer: primero para que sirva con **cualquier** combinación de tipos, después
para ordenarla, y al final para ordenarla de tres maneras distintas sin tocar
la clase. Todo el documento gira alrededor del mismo objeto: cambia lo que la
`Pair` puede hacer, no lo que la `Pair` es.

## Por qué generics existen

<Slide title="Genéricos y orden">
Este documento hace crecer la clase `Pair` que ya conocés hasta un punto en el
que sirva para cualquier combinación de tipos y se pueda ordenar de la manera
que quieras — sin duplicar la clase y sin apagar la verificación del
compilador.

El hilo es uno solo, el mismo objeto:

- **§1** una clase `Pair` distinta por cada combinación de tipos: el dolor
  que motiva todo lo demás.
- **§2 y §3** parámetros de tipo — un solo `Pair` que sirve para cualquier
  `A` y `B`.
- **§4** `Comparable`, con un bug que el aritmética entera esconde, y su
  arreglo.
- **§5** cotas sobre los parámetros (`extends Comparable`) para que la
  `Pair` genérica se pueda ordenar.
- **§6** comparadores como lambdas: ordenar el mismo arreglo de tres
  maneras distintas sin tocar la clase.

El código que vas a leer y escribir es Java 8 — el que el editor de esta
página corre.
</Slide>

<Slide title="Ya conocés el Pair — ¿cuántos Pairs necesitás?">
La clase `Pair` de enteros que escribiste guarda dos números. Sirve si lo que
querés emparejar son dos enteros. En cuanto aparece **otra** combinación —
dos textos, un número y un texto, una fecha y un texto — el camino conocido
es escribir otra clase, con el mismo cuerpo y los tipos cambiados. Tres
tipos ya son nueve pares. Cuatro son dieciséis.

Los tres pares más pedidos, escritos a mano:

<Slide title="¿Y si un solo Pair sirviera para cualquier combinación?">
Hay una salida intermedia que suele aparecer primero — un `Pair` cuyos campos
son `Object`, porque `Object` es el ancestro común de todo tipo por
referencia. Cualquier cosa entra. El problema es al **sacar**:

```java
class Pair {
    private Object first;
    private Object second;
    public Pair(Object a, Object b) { this.first = a; this.second = b; }
    public Object first()  { return first; }
    public Object second() { return second; }
}

Pair p = new Pair(20, "Ana");
int edad = (Integer) p.first();       // cast al leer
String s = (String) p.second();       // otra vez
```

Compila, pero cada uso pide un cast, y — peor — `(String) p.first()` sobre un
`Integer` compila sin quejarse y **revienta en runtime** con
`ClassCastException`. El error viaja del compilador al usuario, que es
justamente lo que Java trata de evitar.

Los **genéricos** son la tercera vía: una sola clase `Pair` cuyos tipos no se
fijan al escribir la clase, sino al **instanciarla**. Los tipos siguen ahí, y
el compilador los conoce — nada de casts, nada de sorpresas en runtime. En
las próximas secciones esa idea se vuelve concreta: primero con **un** hueco
(`Pair<T>`), después con **dos** (`Pair<A, B>`), y de ahí en adelante todo
sale del mismo objeto.
</Slide>

## Pair · T

<Slide title="Un parámetro de tipo — la sintaxis">
El primer paso es un solo hueco. La clase `Pair` declara un **parámetro de
tipo** — una letra entre `<...>` al lado del nombre — y lo usa como si fuera
un tipo cualquiera dentro del cuerpo:

```java
public class Pair<T> {
    private T first;
    private T second;

    public Pair(T first, T second) {
        this.first = first;
        this.second = second;
    }

    public T first()  { return first; }
    public T second() { return second; }
}
```

`T` no es un tipo — es una **variable** de tipo. Todavía no vale nada; es un
hueco. La regla del cuerpo es que en toda la clase esas cuatro `T` se
refieren al **mismo** tipo, cualquiera que termine siendo.

Este `Pair<T>` guarda dos cosas **del mismo tipo**: dos enteros, dos textos,
dos fechas — pero no un entero y un texto. Un solo parámetro es una
restricción de diseño: dos parámetros llegan en §3.
</Slide>

<Slide title="Instanciarlo: Pair de enteros, Pair de textos">
El hueco se rellena al instanciar. `new Pair<Integer>(20, 21)` ata `T` a
`Integer` **para ese objeto**; una instancia distinta puede atarlo a `String`
o a lo que necesites, y las dos coexisten sin conflicto:

<CodeEditor
  language="java"
  defaultValue={`class Pair<T> {

        int sumaEdades         = edades.first() + edades.second();

Fijate en dos cosas. La primera: **sin casts**. `edades.first() +
edades.second()` compila como suma de enteros porque el compilador sabe que
esa `T` es `Integer`. La segunda: intentá pasar `"hola"` a
`new Pair<Integer>(...)` — el compilador te frena en el editor, no cuando el
programa está corriendo.
</Slide>

<Slide title="T, E, K, V — convención de nombres">
La letra que se usa como parámetro de tipo es una convención, no una regla
del lenguaje. Podrías llamarla `MiTipoDeCosa` y funcionaría igual — pero
todo el mundo espera una letra mayúscula, corta, con un significado:

- **`T`** — «Type», el uso más común. Un contenedor cualquiera.
- **`E`** — «Element», habitual en colecciones (`List<E>`, `Set<E>`).
- **`K`, `V`** — «Key, Value», habitual en mapas (`Map<K, V>`).
- **`R`** — «Result», habitual en tipos que devuelven algo (`Function<T, R>`).

Cuando hay dos parámetros distintos, las opciones más frecuentes son `<A, B>`
o `<T, U>`. Este documento va a usar `<A, B>` desde §3 en adelante — no le da
a las letras un significado, así que dos letras contiguas del alfabeto son
la elección más honesta.

La letra no cambia lo que hace la clase; cambia cuánto trabajo le cuesta al
lector entender qué está guardando. En el JDK cada letra tiene su convención,
y tenerla en la cabeza abarata leer `HashMap<K, V>` sin ir a la
documentación.
</Slide>

## Pair · A, B

<Slide title="Dos parámetros de tipo">
La `Pair<T>` de §2 guarda dos cosas del **mismo** tipo. Basta con abrir el
paréntesis angular a dos letras para que guarde dos tipos **distintos**:

```java
public class Pair<A, B> {
    private A first;
    private B second;

    public Pair(A first, B second) {
        this.first = first;
        this.second = second;
    }

    public A first()  { return first; }
    public B second() { return second; }
}
```

`A` y `B` son dos parámetros **independientes**: cada uno se ata a su tipo al
instanciar, y no tienen por qué coincidir. El resto del cuerpo lee igual —
`first` es de tipo `A`, `second` es de tipo `B` — solo que ahora los dos
huecos son visibles.

El **orden** en el que declarás los parámetros importa: el primero es `A`, y
`first()` devuelve `A`. Reordenarlos a `<B, A>` no rompe la clase, pero cambia
lo que significa para el que la instancia. Ese es el trabajo del ejercicio de
esta sección.
</Slide>

<Slide title="Un par de entero y texto">
`Pair<Integer, String>` ata `A` a `Integer` y `B` a `String` para esa
instancia. Los métodos se leen sin cast — `first()` devuelve `Integer`,
`second()` devuelve `String` — y el compilador te frena antes de correr si te
equivocás de tipo al construir:

<CodeEditor

  defaultValue={`class Pair<A, B> {

Fijate en las dos instancias: son la **misma** clase (`Pair`), pero para el
compilador cada una es un tipo diferente. `Pair<Integer, String>` no es
`Pair<String, Integer>` — pasar una donde se espera la otra no compila. La
verificación que perdías con `Object` vuelve, sin costo de sintaxis.
</Slide>

<Slide title="Cuándo aparecen A y B, cuándo K y V">
Dos parámetros piden dos letras. La convención más neutra es `<A, B>`
—«primer parámetro», «segundo parámetro»—, y es la que este documento va a
usar cuando no haya nada más que decir. Cuando **sí** lo hay, dos letras
específicas dicen para qué sirve la clase:

- **`<K, V>`** — mapa (`HashMap<K, V>`, `Map.Entry<K, V>`): «Key, Value».
- **`<T, R>`** — función que transforma (`Function<T, R>`): «Type in, Result
  out».
- **`<T, U>`** — combinaciones que no son ni clave-valor ni entrada-salida
  (`BiFunction<T, U, R>` acumula las dos convenciones anteriores).

Elegir las letras es un gesto pequeño; el que lee la firma sabe en segundos
si el segundo hueco es un valor asociado a una clave, el resultado de una
operación, o simplemente otra cosa. Este documento se queda con `<A, B>`
porque un `Pair` no es un mapa ni una función: son dos cosas al lado, sin
significado especial.
</Slide>

## Comparable y el bug de resta

<Slide title="Ordenar necesita comparar">
Un arreglo `Pair<Integer, Integer>[]` no se ordena solo: `Arrays.sort` no
sabe qué significa que un par sea «menor» que otro — ¿por el primero? ¿por
el segundo? ¿por los dos? La decisión la toma la clase, y la manera estándar
de expresarla en Java es implementar la interfaz **`Comparable`**.

Todo lo que ya usás como ordenable — `Integer`, `String`, `Double` — la
implementa: por eso `Arrays.sort(new int[]{ 3, 1, 2 })` funciona sin más y
`Arrays.sort(new String[]{ "b", "a" })` los deja alfabéticamente. Para que
la `Pair` reciba el mismo trato, tenés que decir vos qué criterio usar.

El resto de esta sección construye ese criterio, con un desvío importante:
la forma más obvia de escribir `compareTo` tiene un bug que Java —y
prácticamente cualquier lenguaje con enteros de máquina— no puede detectar,
y que el código «funciona» hasta que un valor grande lo rompe. Lo vas a
predecir en vivo antes de arreglarlo.
</Slide>

<Slide title="La interfaz Comparable">
`Comparable<T>` declara un único método:

```java
public interface Comparable<T> {
    int compareTo(T other);
}
```

El contrato del `int` que devuelve es lo importante — no es «menor / mayor»,
son **tres regiones**:

- **negativo** — `this` va antes que `other`.
- **cero** — `this` y `other` empatan según este criterio.
- **positivo** — `this` va después que `other`.

Lo que importa es el **signo**, no la magnitud. `-1` y `-483` significan lo
mismo para `Arrays.sort`. Y hay una regla implícita que te va a doler en la
próxima slide: el resultado del `compareTo` tiene que ser un `int` válido —
sin desbordes, sin trampas de aritmética. Esa es la trampa.

Una clase que implementa `Comparable<Pair<Integer, Integer>>` declara que
sabe compararse con otro par de enteros, y `Arrays.sort` la acepta sin más.
</Slide>

<Slide title="Primer intento: restar los campos">
La manera más corta de escribir `compareTo` para ordenar por `second` es
restarlo — negativo si el mío es menor, positivo si es mayor, cero si son
iguales. Se lee natural y compila:

```java
public class Pair implements Comparable<Pair> {
    private String first;
    private int    second;

    public Pair(String first, int second) {
        this.first = first;
        this.second = second;
    }

    public int compareTo(Pair other) {
        return this.second - other.second;   // parece bien
    }
}
```

Sobre un arreglo con valores chicos —edades, notas, cantidades— ordena bien
y sigue ordenando bien durante mucho tiempo. Nadie te avisa nada. Después
llega un valor grande y el arreglo sale al revés.

En la próxima slide vas a **predecir** qué pasa cuando ese valor grande
aparece, sin verlo primero. Corré la predicción con lápiz — no en la cabeza —
y comparala con lo que imprime el runtime real.
</Slide>

el ordenamiento sale al revés porque el `int` se plegó.

<Slide title="Fix: Integer.compare + tie-breaking">
La regla es fácil de escribir y difícil de olvidar: **nunca compares por
resta**. `Integer.compare(a, b)` (y `Long.compare`, `Double.compare`,
`Character.compare`) hace exactamente lo que la resta prometía —negativo si
`a < b`, cero si son iguales, positivo si `a > b`— sin desbordarse, porque
por dentro compara y no resta.

Y si los `second` empatan, el arreglo tiene que decidir a mano cómo
desempata. Compararlos por el otro campo — el `first` — mantiene el orden
determinístico:

<CodeEditor
  language="java"
  defaultValue={`class Pair implements Comparable<Pair> {
    private String first;
    private int second;
    public Pair(String first, int second) {
        this.first = first;
        this.second = second;
    }
    public int compareTo(Pair other) {
        int porSecond = Integer.compare(this.second, other.second);
        if (porSecond != 0) return porSecond;
        return this.first.compareTo(other.first);   // desempate por nombre
    }
    public String toString() { return first + "=" + second; }
}

public class Main {
    public static void main(String[] args) {
        Pair a = new Pair("A", Integer.MAX_VALUE);
        Pair b = new Pair("B", -Integer.MAX_VALUE + 100);
        Pair c = new Pair("C", 0);
        Pair d = new Pair("D", 0);           // empate con c en el second

        Pair[] pares = { a, b, c, d };
        java.util.Arrays.sort(pares);
        for (Pair p : pares) System.out.println(p);
    }
}
`}
/>

Dos observaciones sobre el patrón. La primera: **guardá el resultado del
primer criterio en una variable y devuelvelo si es no-cero**. Es la misma
forma que después vas a leer con `.thenComparing`. La segunda: `String`
también implementa `Comparable`, así que `first.compareTo(other.first)`
funciona sin más — y no tiene el bug de resta, porque no hay resta detrás.
</Slide>

## Bounded types · T extends Comparable · T

<Slide title="El Pair no puede ordenarse todavía">
La `Pair` de §4 sirve para un caso concreto — `first` es `String`, `second`
es `int` —, y su `compareTo` está escrito a mano contra esos tipos. Ahora
querés que **cualquier** `Pair<A, B>` sea ordenable, siempre que sus dos
tipos sean ordenables. Volvés al `Pair<A, B>` genérico de §3 y probás:

```java
public class Pair<A, B> implements Comparable<Pair<A, B>> {
    private A first;
    private B second;
    public Pair(A first, B second) { this.first = first; this.second = second; }
    public A first()  { return first; }
    public B second() { return second; }

    public int compareTo(Pair<A, B> other) {
        return this.first.compareTo(other.first);   // ← ¡no compila!
    }
}
```

El compilador se detiene: `first` es del tipo `A`, y sobre un `A` cualquiera
no existe el método `compareTo`. `A` podría ser cualquier cosa — una clase
tuya sin nada implementado, un `Object` pelado. Java te pide que le prometas,
en la firma de la clase, que `A` sabe compararse.
</Slide>

<Slide title="La sintaxis: extends Comparable">
Un parámetro de tipo puede llevar una **cota** — la promesa de que solo
aceptará tipos que satisfagan una condición. La forma es `<T extends X>`, y
en el mundo de `Comparable` la cota que necesitás se repite bastante:
`<T extends Comparable<T>>` significa «cualquier `T` que sepa compararse con
otro `T`».

Con dos parámetros, se repite dos veces:

```java
public class Pair<A extends Comparable<A>, B extends Comparable<B>>
        implements Comparable<Pair<A, B>> {
    private A first;
    private B second;
    public Pair(A first, B second) { this.first = first; this.second = second; }
    public A first()  { return first; }
    public B second() { return second; }

    public int compareTo(Pair<A, B> other) {
        int porFirst = this.first.compareTo(other.first);
        if (porFirst != 0) return porFirst;
        return this.second.compareTo(other.second);
    }
}
```

Dos observaciones. Primero, **la palabra es `extends`** aunque `Comparable`
sea una interfaz — en la firma de un genérico, `extends` cubre las dos
cosas. Segundo, la cota afecta al **compilador**, no al runtime: el objeto
en el heap sigue siendo el mismo, la promesa vive en el sitio donde
instanciás la clase. `Pair<Integer, String>` compila porque `Integer` y
`String` implementan `Comparable`; `Pair<Object, String>` no compila, y el
error aparece donde escribís `Pair<Object, String>`, no dentro de la clase.
</Slide>

<Slide title="El mismo Pair, dos combinaciones ordenables">
La clase se escribió una sola vez y ordena cualquier combinación de tipos
que sepan compararse — `Pair<Integer, String>` y `Pair<String, Integer>`
funcionan sin tocar la clase, y `Arrays.sort` sabe qué hacer con las dos:

`}
/>

Fijate que la misma línea — `Arrays.sort(...)` — funciona sobre los dos
arreglos. El primer criterio es el `first`; cuando empatan, entra el
`second` a desempatar. Todo la clase lo escribió una sola vez.
</Slide>

## Comparator lambda

<Slide title="Ordenar sin tocar la clase">
La `Pair<A, B>` de §5 sabe ordenarse **de una** manera: por `first`, con
`second` como desempate. Eso vive en su `compareTo`, y `Arrays.sort` lo usa
automáticamente. Pero un mismo arreglo de pares se ordena a veces por
`first`, otras por `second`, otras por longitud del `first`, otras al revés
— y no querés reescribir la clase cada vez.

La segunda firma de `Arrays.sort` recibe un **`Comparator`** aparte: un
segundo argumento que decide, para esa llamada, cómo se comparan los pares.
La clase no se toca; el criterio va afuera y cambia cada vez.
</Slide>

<Slide title="Comparator como lambda">
`Comparator<T>` tiene un solo método — `int compare(T a, T b)` — con el
mismo contrato de tres regiones que `compareTo`. Al ser una interfaz de un
método, cualquier lambda del tipo `(a, b) -> int` la implementa
directamente. Escribir un criterio a mano es una línea:

```java
// Ordenar por el segundo campo, ascendente.
Arrays.sort(pares, (a, b) -> Integer.compare(a.second(), b.second()));

// Por longitud del nombre — que la clase no sabe hacer sola.
Arrays.sort(pares, (a, b) -> Integer.compare(a.first().length(), b.first().length()));
```

Regla de la lambda: **la que devuelve un `int` con la convención de
`compareTo`**. Negativo si `a` va antes que `b`, cero si empatan, positivo
si `a` va después. Y las mismas trampas que en §4: `Integer.compare` en vez
de resta.

Podrías, si querés, guardar la lambda en una variable de tipo
`Comparator<Pair<String, Integer>>` y reutilizarla — es útil cuando el
criterio se usa dos veces o cuando la próxima slide lo modifica en el sitio.
</Slide>

<Slide title="reversed() y thenComparing() — los atajos">
`Comparator` es una interfaz con **métodos default**: llamás `.reversed()` o
`.thenComparing(...)` sobre una lambda ya escrita, y obtenés otro
`Comparator`. Nada nuevo que memorizar, solo dos combinaciones que aparecen
a diario.

```java
Comparator<Pair<String, Integer>> porSecond =
    (a, b) -> Integer.compare(a.second(), b.second());

Arrays.sort(pares, porSecond);              // ascendente
Arrays.sort(pares, porSecond.reversed());   // descendente
```

`.thenComparing(otro)` encadena un segundo criterio como desempate — el
primero decide, y cuando devuelve `0`, el segundo entra:

```java
Comparator<Pair<String, Integer>> porFirst =
    (a, b) -> a.first().compareTo(b.first());

Comparator<Pair<String, Integer>> porFirstLuegoSecond =
    porFirst.thenComparing((a, b) -> Integer.compare(a.second(), b.second()));

Arrays.sort(pares, porFirstLuegoSecond);
```

Lo mismo que el `if (porFirst != 0) return porFirst; return porSecond;` de
§4 y §5, escrito como una composición en vez de a mano. La combinación con
`.reversed()` también funciona: `porFirst.thenComparing(porSecond).reversed()`
invierte el criterio compuesto.
</Slide>

<Slide title="Tres órdenes sobre el mismo arreglo">
Cinco pares `(nombre, edad)`, tres órdenes distintos sin tocar la clase:

<CodeEditor
  language="java"
  defaultValue={`import java.util.Arrays;
import java.util.Comparator;

class Pair<A, B> {
    private A first;
    private B second;
    public Pair(A first, B second) { this.first = first; this.second = second; }
    public A first()  { return first; }
    public B second() { return second; }
    public String toString() { return "(" + first + ", " + second + ")"; }
}

public class Main {
    public static void main(String[] args) {
        Pair<String, Integer>[] pares = new Pair[]{
            new Pair<String, Integer>("Ana",   30),
            new Pair<String, Integer>("Luis",  25),
            new Pair<String, Integer>("Bea",   30),
            new Pair<String, Integer>("Diego", 22),
            new Pair<String, Integer>("Cami",  25),
        };

        // 1) Por edad ascendente.
        Comparator<Pair<String, Integer>> porEdad =
            (a, b) -> Integer.compare(a.second(), b.second());
        Arrays.sort(pares, porEdad);
        System.out.println("Por edad ascendente:");
        for (Pair<String, Integer> p : pares) System.out.println("  " + p);

        // 2) Por edad descendente — la misma lambda invertida.
        Arrays.sort(pares, porEdad.reversed());
        System.out.println("Por edad descendente:");
        for (Pair<String, Integer> p : pares) System.out.println("  " + p);

        // 3) Por nombre; empate en nombre desempata por edad.
        Comparator<Pair<String, Integer>> porNombre =
            (a, b) -> a.first().compareTo(b.first());
        Arrays.sort(pares, porNombre.thenComparing(porEdad));
        System.out.println("Por nombre, desempate por edad:");
        for (Pair<String, Integer> p : pares) System.out.println("  " + p);
    }
}
`}
/>

Corré el programa: la misma clase `Pair`, el mismo arreglo, tres órdenes
distintos. Ninguno tocó la clase — todo el criterio vive en el segundo
argumento de `Arrays.sort`. Ese es el trato que `Comparator` te propone.
</Slide>

## Lo que sigue

Con genéricos ya escribís una sola clase `Pair` que sirve para cualquier
combinación de tipos, y con bounded types y comparators la ordenás de la
manera que necesites sin duplicar código y sin apagar la verificación del
compilador. El siguiente paso natural es abandonar el arreglo: dejar que
Java te dé las estructuras que ya vienen escritas —listas, conjuntos, mapas,
colas—, todas construidas encima de la misma idea de parámetros de tipo que
acabás de aprender.
