# Genéricos y orden

Ya escribiste una clase `Pair` que guarda dos enteros. Ahora la vas a hacer
crecer: primero para que sirva con **cualquier** combinación de tipos, después
para ordenarla, y al final para ordenarla de tres maneras distintas sin tocar
la clase. Todo el documento gira alrededor del mismo objeto: cambia lo que la
`Pair` puede hacer, no lo que la `Pair` es.

## Por qué generics existen

<Slide title="Genéricos y orden">
Este documento hace crecer la clase `Pair` que ya conocés hasta un punto en el
que sirva para cualquier combinación de tipos y se pueda ordenar de la manera
que quieras — sin duplicar la clase y sin apagar la verificación del
compilador.

El hilo es uno solo, el mismo objeto:

- **§1** una clase `Pair` distinta por cada combinación de tipos: el dolor
  que motiva todo lo demás.
- **§2 y §3** parámetros de tipo — un solo `Pair` que sirve para cualquier
  `A` y `B`.
- **§4** `Comparable`, con un bug que el aritmética entera esconde, y su
  arreglo.
- **§5** cotas sobre los parámetros (`extends Comparable`) para que la
  `Pair` genérica se pueda ordenar.
- **§6** comparadores como lambdas: ordenar el mismo arreglo de tres
  maneras distintas sin tocar la clase.

El código que vas a leer y escribir es Java 8 — el que el editor de esta
página corre.
</Slide>

<Slide title="Ya conocés el Pair — ¿cuántos Pairs necesitás?">
La clase `Pair` de enteros que escribiste guarda dos números. Sirve si lo que
querés emparejar son dos enteros. En cuanto aparece **otra** combinación —
dos textos, un número y un texto, una fecha y un texto — el camino conocido
es escribir otra clase, con el mismo cuerpo y los tipos cambiados. Tres
tipos ya son nueve pares. Cuatro son dieciséis.

Los tres pares más pedidos, escritos a mano:

<Slide title="¿Y si un solo Pair sirviera para cualquier combinación?">
Hay una salida intermedia que suele aparecer primero — un `Pair` cuyos campos
son `Object`, porque `Object` es el ancestro común de todo tipo por
referencia. Cualquier cosa entra. El problema es al **sacar**:

```java
class Pair {
    private Object first;
    private Object second;
    public Pair(Object a, Object b) { this.first = a; this.second = b; }
    public Object first()  { return first; }
    public Object second() { return second; }
}

Pair p = new Pair(20, "Ana");
int edad = (Integer) p.first();       // cast al leer
String s = (String) p.second();       // otra vez
```

Compila, pero cada uso pide un cast, y — peor — `(String) p.first()` sobre un
`Integer` compila sin quejarse y **revienta en runtime** con
`ClassCastException`. El error viaja del compilador al usuario, que es
justamente lo que Java trata de evitar.

Los **genéricos** son la tercera vía: una sola clase `Pair` cuyos tipos no se
fijan al escribir la clase, sino al **instanciarla**. Los tipos siguen ahí, y
el compilador los conoce — nada de casts, nada de sorpresas en runtime. En
las próximas secciones esa idea se vuelve concreta: primero con **un** hueco
(`Pair<T>`), después con **dos** (`Pair<A, B>`), y de ahí en adelante todo
sale del mismo objeto.
</Slide>

## Pair · T

<Slide title="Un parámetro de tipo — la sintaxis">
El primer paso es un solo hueco. La clase `Pair` declara un **parámetro de
tipo** — una letra entre `<...>` al lado del nombre — y lo usa como si fuera
un tipo cualquiera dentro del cuerpo:

```java
public class Pair<T> {
    private T first;
    private T second;

    public Pair(T first, T second) {
        this.first = first;
        this.second = second;
    }

    public T first()  { return first; }
    public T second() { return second; }
}
```

`T` no es un tipo — es una **variable** de tipo. Todavía no vale nada; es un
hueco. La regla del cuerpo es que en toda la clase esas cuatro `T` se
refieren al **mismo** tipo, cualquiera que termine siendo.

Este `Pair<T>` guarda dos cosas **del mismo tipo**: dos enteros, dos textos,
dos fechas — pero no un entero y un texto. Un solo parámetro es una
restricción de diseño: dos parámetros llegan en §3.
</Slide>

<Slide title="Instanciarlo: Pair de enteros, Pair de textos">
El hueco se rellena al instanciar. `new Pair<Integer>(20, 21)` ata `T` a
`Integer` **para ese objeto**; una instancia distinta puede atarlo a `String`
o a lo que necesites, y las dos coexisten sin conflicto:

<CodeEditor
  language="java"
  defaultValue={`class Pair<T> {
    private T first;
    private T second;
    public Pair(T first, T second) {
        this.first = first;
        this.second = second;
    }
    public T first()  { return first; }
    public T second() { return second; }
}

public class Main {
    public static void main(String[] args) {
        Pair<Integer> edades   = new Pair<Integer>(20, 21);
        Pair<String>  saludos  = new Pair<String>("hola", "chao");

        // El compilador ya sabe qué devuelve first() y second().
        int sumaEdades         = edades.first() + edades.second();
        String junto           = saludos.first() + " y " + saludos.second();

        System.out.println(sumaEdades);
        System.out.println(junto);
    }
}
`}
/>

Fijate en dos cosas. La primera: **sin casts**. `edades.first() +
edades.second()` compila como suma de enteros porque el compilador sabe que
esa `T` es `Integer`. La segunda: intentá pasar `"hola"` a
`new Pair<Integer>(...)` — el compilador te frena en el editor, no cuando el
programa está corriendo.
</Slide>

<Slide title="T, E, K, V — convención de nombres">
La letra que se usa como parámetro de tipo es una convención, no una regla
del lenguaje. Podrías llamarla `MiTipoDeCosa` y funcionaría igual — pero
todo el mundo espera una letra mayúscula, corta, con un significado:

- **`T`** — «Type», el uso más común. Un contenedor cualquiera.
- **`E`** — «Element», habitual en colecciones (`List<E>`, `Set<E>`).
- **`K`, `V`** — «Key, Value», habitual en mapas (`Map<K, V>`).
- **`R`** — «Result», habitual en tipos que devuelven algo (`Function<T, R>`).

Cuando hay dos parámetros distintos, las opciones más frecuentes son `<A, B>`
o `<T, U>`. Este documento va a usar `<A, B>` desde §3 en adelante — no le da
a las letras un significado, así que dos letras contiguas del alfabeto son
la elección más honesta.

La letra no cambia lo que hace la clase; cambia cuánto trabajo le cuesta al
lector entender qué está guardando. En el JDK cada letra tiene su convención,
y tenerla en la cabeza abarata leer `HashMap<K, V>` sin ir a la
documentación.
</Slide>
