# Genéricos y orden

La clase `Pair` que aparece en clases anteriores guarda dos enteros. El
material que sigue la hace crecer hasta un punto en el que sirva para
cualquier combinación de tipos y, además, se pueda ordenar por criterios
distintos sin modificar la clase. El objeto central no cambia; cambian las
capacidades que se le van agregando.

## El problema combinatorio

<Slide title="El punto de partida">
La clase `Pair` disponible guarda dos enteros. Funciona en el caso concreto
para el que se escribió: dos coordenadas, dos edades, dos cantidades. Basta
con que uno de los dos valores deje de ser un entero para que la clase
existente deje de aplicar y aparezca la pregunta que motiva todo el
material que sigue: **¿cuántas clases `Pair` son necesarias en total?**

La respuesta ingenua es una por combinación de tipos. Como un `Pair`
distingue el orden entre el primer y el segundo campo, cada par ordenado
`(A, B)` cuenta como una combinación distinta de cada `(B, A)`: con dos
tipos posibles hacen falta cuatro clases (`IntInt`, `StringString`,
`IntString`, `StringInt`); con tres tipos, nueve; con cuatro, dieciséis.
El crecimiento es cuadrático en la cantidad de tipos —$n^2$ para $n$
tipos disponibles—, y todas las clases comparten el mismo cuerpo: dos
campos, un constructor, dos getters. Lo único que cambia entre una clase
y la siguiente son los nombres de los tipos.
</Slide>

<Slide title="Una clase por combinación">
Escribir a mano las clases para las combinaciones más pedidas hace visible
el costo del enfoque:

Tres clases con la misma estructura y una única diferencia sintáctica: los
tipos de los campos. Cada combinación adicional exige una clase adicional,
y el bloque de código que las contiene crece con la misma proporción que la
cantidad de combinaciones cubiertas.
</Slide>

<Slide title="Object como salida · el precio del cast">
Una alternativa habitual es reducir todas las variantes a una sola clase
cuyos campos son de tipo `Object`, el ancestro común de todos los tipos por
referencia. La escritura de la clase se simplifica; la lectura de los
valores, no:

```java
class Pair {
    private Object first;
    private Object second;
    public Pair(Object a, Object b) { this.first = a; this.second = b; }
    public Object first()  { return first; }
    public Object second() { return second; }
}

Pair p = new Pair(20, "Ana");
int edad = (Integer) p.first();       // cast obligatorio al leer
String s = (String) p.second();       // otro cast, otro tipo
```

El costo aparece en dos frentes. Primero, cada uso obliga a un cast
explícito. Segundo, y de mayor gravedad, el compilador deja de rechazar
casts incorrectos: la expresión `(String) p.first()` sobre una instancia
cuyo primer campo es un `Integer` compila sin error y **falla en tiempo de
ejecución** con `ClassCastException`. La verificación del compilador queda
suspendida, y el error se traslada al usuario.

Los **genéricos** son la construcción del lenguaje que resuelve la misma
necesidad —una única clase para todas las combinaciones— sin renunciar a la
verificación estática. La clase se declara con **parámetros de tipo**, y
cada instanciación fija esos parámetros para ese objeto. Las siguientes
secciones desarrollan la mecánica: primero con un parámetro, después con
dos.
</Slide>

## Pair · T

<Slide title="Un parámetro de tipo">
El primer paso es una clase con **un** hueco para el tipo. La sintaxis
declara el parámetro entre `<...>` a continuación del nombre de la clase, y
lo emplea en el cuerpo como si fuera un tipo cualquiera:

```java
public class Pair<T> {
    private T first;
    private T second;

    public Pair(T first, T second) {
        this.first = first;
        this.second = second;
    }

    public T first()  { return first; }
    public T second() { return second; }
}
```

`T` no es un tipo concreto; es una **variable de tipo**, un placeholder.
Las cuatro apariciones de `T` en el cuerpo se refieren al mismo tipo,
cualquiera que resulte ser al instanciar la clase. Esta versión guarda dos
valores **del mismo tipo**: dos enteros, dos textos, dos fechas — pero no
un entero y un texto.
</Slide>

<Slide title="Instancias con distintos tipos">
El hueco se rellena en el momento de instanciar. La expresión
`new Pair<Integer>(20, 21)` liga `T` a `Integer` para esa instancia; una
instancia distinta puede ligarlo a otro tipo, y las dos coexisten:

<CodeEditor
  language="java"
  defaultValue={`class Pair<T> {
    private T first;
    private T second;
    public Pair(T first, T second) {
        this.first = first;
        this.second = second;
    }
    public T first()  { return first; }
    public T second() { return second; }
}

public class Main {
    public static void main(String[] args) {
        Pair<Integer> edades   = new Pair<Integer>(20, 21);
        Pair<String>  saludos  = new Pair<String>("hola", "chao");

        int sumaEdades         = edades.first() + edades.second();
        String junto           = saludos.first() + " y " + saludos.second();

        System.out.println(sumaEdades);
        System.out.println(junto);
    }
}
`}
/>

Dos consecuencias inmediatas. **La primera**: la lectura de los campos no
exige cast. La expresión `edades.first() + edades.second()` compila como
suma de enteros porque el compilador conoce la ligadura de `T` a `Integer`
para esa instancia. **La segunda**: pasar `"hola"` a `new Pair<Integer>(...)`
es rechazado en compilación, no en ejecución.

Un detalle del lenguaje que aparece por primera vez acá: el parámetro de
tipo sólo puede ligarse a tipos por referencia, no a primitivos. `T` no
puede ser `int`, sólo `Integer` (su versión objeto, la clase envoltorio).
Java realiza la conversión entre las dos formas de manera automática
—**autoboxing** al pasar un `int` donde se espera un `Integer`, **unboxing**
en el sentido inverso—, y por eso `new Pair<Integer>(20, 21)` funciona
con literales `int` y `edades.first() + edades.second()` se asigna a un
`int`.
</Slide>

## Pair · A, B

<Slide title="Dos parámetros de tipo">
La clase `Pair<T>` guarda dos valores del **mismo** tipo. Abrir el
paréntesis angular a dos letras permite guardar valores de tipos
**distintos**:

```java
public class Pair<A, B> {
    private A first;
    private B second;

    public Pair(A first, B second) {
        this.first = first;
        this.second = second;
    }

    public A first()  { return first; }
    public B second() { return second; }
}
```

`A` y `B` son parámetros **independientes**: cada uno se liga a su tipo al
instanciar, y no existe restricción alguna que obligue a que coincidan. El
cuerpo de la clase se lee igual — `first` es de tipo `A`, `second` es de
tipo `B` — con la única diferencia de que ahora los dos huecos son
visibles.

El **orden** de los parámetros es significativo: el primero es `A`, y
`first()` devuelve `A`. Reordenar la declaración a `<B, A>` no rompe la
clase, pero cambia la firma que sus usuarios ven.
</Slide>

<Slide title="Un par de entero y texto">
La instanciación `Pair<Integer, String>` liga `A` a `Integer` y `B` a
`String` para esa instancia. Los métodos se leen sin cast, y el compilador
rechaza construcciones con tipos incompatibles:

<CodeEditor
  language="java"
  defaultValue={`class Pair<A, B> {
    private A first;
    private B second;
    public Pair(A first, B second) {
        this.first = first;
        this.second = second;
    }
    public A first()  { return first; }
    public B second() { return second; }
}

        Pair<String, Integer> otra     = new Pair<String, Integer>("Luis", 67890);

        int rutEtiqueta    = etiqueta.first();
        String nombreOtra  = otra.first();

        System.out.println(etiqueta.second() + " tiene rut " + rutEtiqueta);
    }

/>

Las dos instancias pertenecen a la **misma** clase (`Pair`), pero para el
compilador constituyen tipos diferentes. `Pair<Integer, String>` no es
`Pair<String, Integer>`; pasar una donde la firma exige la otra no compila.
La verificación estática que se pierde con `Object` reaparece sin costo
sintáctico adicional. En este documento la clase `Pair` genérica utiliza
`<A, B>` como convención neutra: dos letras contiguas, sin significado
adicional, tal como se usan en el resto del material.
</Slide>

## Comparable

<Slide title="El ordenamiento como problema">
Dado un arreglo cualquiera, un **algoritmo de ordenamiento** reorganiza
sus elementos hasta dejarlos en un orden preestablecido — típicamente
ascendente. Las familias clásicas —bubble sort, insertion sort, selection
sort, merge sort, quicksort, heap sort— resuelven este problema con
distintas complejidades, y forman parte del programa de unidades
posteriores.

Aquí el foco es distinto. En lugar de escribir un algoritmo, este
documento se ocupa de cómo la biblioteca estándar de Java expone
ordenamientos listos para usar sobre arreglos de cualquier tipo, y qué
contrato exige del tipo para que la operación tenga sentido. Los detalles
del algoritmo interno de `Arrays.sort` no importan para este material; sí
importa el contrato con el que la función se comunica con los tipos que
ordena.
</Slide>

<Slide title="Arrays.sort · el contrato con el tipo">
La biblioteca estándar ofrece `Arrays.sort` para ordenar un arreglo. La
firma —simplificada— sobre arreglos de tipos por referencia es:

```java
// java.util.Arrays
public static void sort(Object[] a);
```

La firma recibe `Object[]`, no un parámetro de tipo: el algoritmo interno
no conoce el tipo concreto de los elementos. Lo que exige es que los
elementos del arreglo **sepan compararse entre sí**. Esa capacidad la
aportan los tipos que implementan la interfaz `Comparable`, y el
cumplimiento del contrato se verifica en **tiempo de ejecución**: si el
arreglo contiene elementos que no implementan `Comparable`, la llamada
lanza `ClassCastException`.

Los tipos habituales de la biblioteca —`Integer`, `String`, `Double`,
`LocalDate`— implementan `Comparable` de fábrica, y por eso llamadas como
`Arrays.sort(new Integer[]{3, 1, 2})` o
`Arrays.sort(new String[]{"b", "a"})` funcionan sin trabajo adicional del
programador. El algoritmo interno del `sort` está construido para operar
sobre cualquier tipo que respete el contrato de `Comparable`; el trabajo
del programador consiste en implementar `Comparable` en el tipo que
quiere ordenar.
</Slide>

<Slide title="El contrato de compareTo">
`Comparable<T>` declara un único método:

```java
public interface Comparable<T> {
    int compareTo(T other);
}
```

El `int` devuelto no representa dos valores («menor» o «mayor»); representa
**tres regiones**, definidas por el signo:

- **Negativo** — `this` va antes que `other`.
- **Cero** — `this` y `other` empatan según este criterio.
- **Positivo** — `this` va después que `other`.

Lo que importa es el **signo**, no la magnitud: `-1` y `-483` significan lo
mismo para `Arrays.sort`. El contrato añade una condición implícita: el
valor devuelto debe ser un `int` válido, sin desbordamientos silenciosos,
condición cuya violación —silenciosa— es una fuente conocida de defectos
en implementaciones de `compareTo`.
</Slide>

<Slide title="Un primer intento por resta">
La forma más corta de implementar `compareTo` para ordenar por el segundo
campo consiste en restarlo: el resultado es negativo cuando el `second`
propio es menor, positivo cuando es mayor y cero cuando coinciden. Se lee
natural y compila sin advertencias:

```java
public class Pair implements Comparable<Pair> {
    private String first;
    private int    second;

    public Pair(String first, int second) {
        this.first = first;
        this.second = second;
    }

    public int compareTo(Pair other) {
        return this.second - other.second;   // aparentemente correcto
    }
}
```

Sobre valores de magnitud moderada —edades, notas, cantidades pequeñas— el
método ordena correctamente y sigue ordenando correctamente durante un
tiempo largo. Ninguna herramienta emite alerta alguna. La aparición de un
valor cercano a los extremos del rango de `int` cambia el escenario.
</Slide>

<Slide title="Comparación segura con Integer.compare">
La resta `MAX_VALUE - (-MAX_VALUE + 100)` produce un valor que no cabe en
32 bits con signo. Java aplica aritmética modular sin emitir excepción:
el resultado se pliega, y el valor devuelto por `compareTo` **pierde la
garantía** de reflejar el orden real de los operandos — su signo puede
resultar contrario al esperado, ser cero, o coincidir por casualidad con
el correcto según los operandos concretos. El compilador y la máquina
virtual no dan aviso alguno.

La regla asociada a este fenómeno es directa: **la resta no es una
comparación segura**. La biblioteca estándar provee `Integer.compare(a, b)`
—junto con `Long.compare`, `Double.compare` y `Character.compare`— que
implementa la semántica prometida por la resta sin realizar la resta, y
por lo tanto sin exponerse al desbordamiento. Sustituir la resta por
`Integer.compare` es la corrección directa del método `compareTo`
mostrado en las slides previas:

<CodeEditor
  language="java"
  defaultValue={`class Pair implements Comparable<Pair> {

El orden que imprime el programa corresponde al criterio declarado —
ascendente por `second`— también sobre los valores cercanos a los
extremos del rango de `int`.
</Slide>

<Slide title="Desempate en cascada">
Un criterio de ordenación puede producir **empates**: dos elementos para
los cuales el criterio principal devuelve cero. Cuando eso ocurre, el
resultado del `sort` sobre esos elementos queda indefinido si el método
no declara qué hacer en el empate. Un `compareTo` bien construido
incorpora un criterio de **desempate**, aplicado únicamente cuando el
criterio principal devuelve cero:

<CodeEditor
  language="java"
  defaultValue={`class Pair implements Comparable<Pair> {
    private String first;
    private int second;
    public Pair(String first, int second) {
        this.first = first;
        this.second = second;
    }
    public int compareTo(Pair other) {
        int porSecond = Integer.compare(this.second, other.second);
        if (porSecond != 0) return porSecond;
        return this.first.compareTo(other.first);   // desempate por first
    }
    public String toString() { return first + "=" + second; }
}

public class Main {
    public static void main(String[] args) {
        Pair a = new Pair("A", 0);
        Pair b = new Pair("B", 0);   // empate en second con a
        Pair c = new Pair("C", 5);

        Pair[] pares = { c, b, a };
        java.util.Arrays.sort(pares);
        for (Pair p : pares) System.out.println(p);
    }
}
`}
/>

Dos observaciones sobre el patrón. Primero, `String.compareTo` es una
elección segura como criterio de desempate: su implementación interna
resta, sí, pero sobre `char` (entero sin signo de 16 bits) y sobre
longitudes no negativas, dos rangos donde la sustracción no desborda
un `int`. Segundo, la forma `guardar el resultado, devolverlo si es no
cero, comparar por el segundo criterio en caso contrario` es la
expresión estándar en Java de comparadores compuestos, y produce una
implementación **correcta**: el orden que declara es el que el programa
respeta ante cualquier arreglo.
</Slide>

## Tipos acotados

<Slide title="Ordenar un Pair genérico">
La versión de `Pair` con `Comparable` implementado sirve para un caso
concreto: `first` es `String`, `second` es `int`, y el método `compareTo`
está escrito a mano contra esos dos tipos. Extender la propiedad de ser
ordenable a **cualquier** `Pair<A, B>` requiere volver al `Pair` genérico
con dos parámetros y agregarle la interfaz:

```java
public class Pair<A, B> implements Comparable<Pair<A, B>> {
    private A first;
    private B second;
    public Pair(A first, B second) { this.first = first; this.second = second; }
    public A first()  { return first; }
    public B second() { return second; }

    public int compareTo(Pair<A, B> other) {
        return this.first.compareTo(other.first);   // no compila
    }
}
```

El compilador rechaza la expresión `this.first.compareTo(other.first)`. La
razón es directa: `first` es de tipo `A`, y sobre un `A` cualquiera no
existe garantía de que exista el método `compareTo`. `A` podría ligarse a
un tipo definido por el usuario sin interfaz alguna. Para que la operación
sea legítima, la declaración de la clase debe **prometer** al compilador
que `A` sabe compararse.
</Slide>

<Slide title="La cota extends Comparable">
Un parámetro de tipo puede llevar una **cota**: la promesa de que sólo
aceptará tipos que satisfagan una condición determinada. La sintaxis es
`<T extends X>`, donde `X` es un tipo que el parámetro debe respetar. Para
tipos ordenables, la cota que se repite con frecuencia es
`<T extends Comparable<T>>`, que se lee «cualquier `T` que sepa compararse
con otro `T`».

Con dos parámetros, la cota se repite dos veces:

```java
public class Pair<A extends Comparable<A>, B extends Comparable<B>>
        implements Comparable<Pair<A, B>> {
    private A first;
    private B second;
    public Pair(A first, B second) { this.first = first; this.second = second; }
    public A first()  { return first; }
    public B second() { return second; }

    public int compareTo(Pair<A, B> other) {
        int porFirst = this.first.compareTo(other.first);
        if (porFirst != 0) return porFirst;
        return this.second.compareTo(other.second);
    }
}
```

El `<T>` que aparece **dentro** de `Comparable<T>` no es decorativo.
Escribir la cota sin él —`<T extends Comparable>`, usando la interfaz
en su forma cruda— hace que `compareTo` reciba `Object` y no `T`, con
lo cual la expresión `this.first.compareTo(other.first)` compila pero
obliga a un cast interno y pierde la garantía estática de que `other`
es del mismo tipo que `this`. Escribir `Comparable<T>` es lo que le
comunica al compilador que la comparación es entre instancias del mismo
tipo, y es la razón por la cual la cota se declara con la letra que
repite el parámetro que la cota gobierna.

Dos observaciones sobre la sintaxis. Primero, la palabra clave es
`extends` aunque `Comparable` sea una interfaz — en las declaraciones
genéricas, `extends` cubre tanto clases como interfaces. Segundo, la cota
afecta al **compilador**, no al comportamiento en tiempo de ejecución: el
objeto en el heap no cambia, y la promesa se verifica en el sitio donde se
instancia la clase. `Pair<Integer, String>` compila porque tanto `Integer`
como `String` implementan `Comparable`; `Pair<Object, String>` no compila,
y el error aparece donde se escribe la instanciación.
</Slide>

<Slide title="Pair ordenable para cualquier tipo ordenable">
La clase se escribió una única vez y ordena cualquier combinación de
tipos que sepan compararse. `Pair<Integer, String>` y `Pair<String,
Integer>` funcionan sin modificar la clase; `Arrays.sort` opera sobre las
dos:

<CodeEditor
  language="java"
  defaultValue={`class Pair<A extends Comparable<A>, B extends Comparable<B>>
        implements Comparable<Pair<A, B>> {

    private B second;

    public A first()  { return first; }
    public B second() { return second; }

    public int compareTo(Pair<A, B> other) {
        int porFirst = this.first.compareTo(other.first);
        if (porFirst != 0) return porFirst;
        return this.second.compareTo(other.second);
    }
    public String toString() { return "(" + first + ", " + second + ")"; }
}

public class Main {
    public static void main(String[] args) {
        Pair<Integer, String>[] numerados = new Pair[]{
            new Pair<Integer, String>(3, "gamma"),
            new Pair<Integer, String>(1, "beta"),
            new Pair<Integer, String>(1, "alfa"),
        };
        java.util.Arrays.sort(numerados);
        for (Pair<Integer, String> p : numerados) System.out.println(p);

            new Pair<String, Integer>("alfa", 9),

/>

La misma línea —`Arrays.sort(...)`— opera sobre los dos arreglos. El
primer criterio es el `first`; ante empate, el `second` desempata. La
clase carga la definición del orden una sola vez, y la exhibe sobre
tantos tipos ordenables como el programa la instancie.
</Slide>

## Comparator

<Slide title="Ordenar sin modificar la clase">
La `Pair<A, B>` con la cota adecuada sabe ordenarse de **una** manera: por
`first`, con `second` como desempate. Esa lógica vive en su `compareTo`, y
`Arrays.sort` la usa automáticamente. Un mismo arreglo de pares, sin
embargo, admite ser ordenado por criterios distintos: por `second`
ascendente, por `second` descendente, por longitud del `first`. Modificar
la clase cada vez que aparece un criterio nuevo es una respuesta costosa y
frágil.

La segunda firma de `Arrays.sort` recibe un **`Comparator`** como segundo
argumento: un objeto que, para esa llamada, decide cómo comparar dos
elementos. La clase original queda intacta; el criterio se declara fuera y
puede cambiar en cada invocación.
</Slide>

<Slide title="Comparator como lambda">
`Comparator<T>` es una interfaz con un único método:

```java
public interface Comparator<T> {
    int compare(T a, T b);
}
```

El contrato del `int` devuelto es el mismo que el de `compareTo`: tres
regiones, definidas por el signo. Al ser una interfaz con un único
método abstracto —Java llama a esta forma **interfaz funcional**—
cualquier lambda cuya firma coincida con la del método (aquí,
`(T, T) -> int`) es una implementación válida de la interfaz: el
compilador construye por debajo una instancia anónima cuyo `compare`
tiene el cuerpo de la lambda. Escribir un criterio a mano ocupa una
única línea:

```java
// Orden por el segundo campo, ascendente.
Arrays.sort(pares, (a, b) -> Integer.compare(a.second(), b.second()));

// Orden por longitud del primer campo, ascendente.
Arrays.sort(pares, (a, b) -> Integer.compare(a.first().length(), b.first().length()));
```

Las mismas precauciones aplican: la resta como comparación produce el
desbordamiento descrito para `Comparable`, y `Integer.compare` la evita
por construcción.

La lambda puede guardarse en una variable de tipo
`Comparator<Pair<String, Integer>>` cuando el criterio se usa más de una
vez o cuando el comparador base sirve para derivar otros.
</Slide>

<Slide title="reversed y thenComparing">
`Comparator` provee dos métodos default que combinan comparadores ya
declarados. `.reversed()` invierte el signo devuelto por el comparador
base, produciendo el orden opuesto:

```java
Comparator<Pair<String, Integer>> porSecond =
    (a, b) -> Integer.compare(a.second(), b.second());

Arrays.sort(pares, porSecond);              // ascendente
Arrays.sort(pares, porSecond.reversed());   // descendente
```

`.thenComparing(otro)` encadena un segundo comparador que actúa como
desempate: cuando el comparador base devuelve cero, la decisión pasa al
segundo comparador:

```java
Comparator<Pair<String, Integer>> porFirst =
    (a, b) -> a.first().compareTo(b.first());

Comparator<Pair<String, Integer>> porFirstLuegoSecond =
    porFirst.thenComparing((a, b) -> Integer.compare(a.second(), b.second()));

Arrays.sort(pares, porFirstLuegoSecond);
```

La composición equivale al patrón `if (a != 0) return a; return b;` de un
`compareTo` con desempate, expresado como cadena de llamadas en lugar de
secuencia de declaraciones dentro del método.
</Slide>

<Slide title="Tres órdenes sobre un mismo arreglo">
Un mismo arreglo de cinco pares `(nombre, edad)` se ordena por tres
criterios distintos sin ninguna modificación de la clase `Pair`:

<CodeEditor
  language="java"
  defaultValue={`import java.util.Arrays;
import java.util.Comparator;

class Pair<A, B> {
    private A first;
    private B second;
    public Pair(A first, B second) { this.first = first; this.second = second; }
    public A first()  { return first; }
    public B second() { return second; }
    public String toString() { return "(" + first + ", " + second + ")"; }
}

public class Main {
    public static void main(String[] args) {
        Pair<String, Integer>[] pares = new Pair[]{
            new Pair<String, Integer>("Ana",   30),
            new Pair<String, Integer>("Luis",  25),
            new Pair<String, Integer>("Bea",   30),
            new Pair<String, Integer>("Diego", 22),
            new Pair<String, Integer>("Cami",  25),
        };

        Comparator<Pair<String, Integer>> porEdad =
            (a, b) -> Integer.compare(a.second(), b.second());
        Arrays.sort(pares, porEdad);
        System.out.println("Por edad ascendente:");
        for (Pair<String, Integer> p : pares) System.out.println("  " + p);

        Arrays.sort(pares, porEdad.reversed());
        System.out.println("Por edad descendente:");
        for (Pair<String, Integer> p : pares) System.out.println("  " + p);

        Comparator<Pair<String, Integer>> porNombre =
            (a, b) -> a.first().compareTo(b.first());
        Arrays.sort(pares, porNombre.thenComparing(porEdad));
        System.out.println("Por nombre, desempate por edad:");
        for (Pair<String, Integer> p : pares) System.out.println("  " + p);
    }

/>

La clase `Pair` se define una vez y el mismo arreglo se ordena tres
veces. El criterio vive en el segundo argumento de `Arrays.sort`, no en
la definición del tipo. Esta separación entre estructura de datos y
criterio de comparación es el objeto de estudio central de este bloque
del material.

`Arrays.sort` reorganiza el arreglo **in-place**: cada llamada reordena
el mismo objeto según su propio criterio, y el estado en que lo dejó la
llamada anterior no altera el resultado de la siguiente cuando el
criterio es un orden total sobre los elementos —como los tres empleados
acá—. La salida que imprime cada bloque corresponde exclusivamente al
criterio de ese `sort`.
</Slide>

<Slide title="Convenciones de nombres · T, E, K, V, R">
El material recorrió varias clases genéricas —`Pair<T>`, `Pair<A, B>`,
`Arrays`, `Comparator<T>`, `Comparator<Pair<String, Integer>>`— y en cada
una la letra del parámetro de tipo se eligió por convención, no por
regla del lenguaje. La convención del ecosistema Java asigna a cada letra
un uso preferente:

- **`T`** — «Type». Contenedor genérico sin significado adicional
  (`Comparable<T>`, `Comparator<T>`).
- **`E`** — «Element». Habitual en colecciones (`List<E>`, `Set<E>`).
- **`K`, `V`** — «Key, Value». Habitual en mapas
  (`Map<K, V>`, `HashMap<K, V>`).
- **`R`** — «Result». Aparece en tipos que devuelven algo
  (`Function<T, R>`: «Type in, Result out»).
- **`A, B`** o **`T, U`** — dos parámetros sin significado específico.

La letra no altera el comportamiento de la clase; sí altera cuánto
trabajo cuesta al lector reconocer, sin abrir la documentación, qué
guarda o produce el tipo. Un `HashMap<K, V>` se lee de un vistazo como
«clave-valor»; un `Function<T, R>` como «entrada, salida».
</Slide>

- [ ] Porque `this` y `other` deben ser del mismo tipo, y `A` no garantiza esa igualdad

</Question>

<Question id="sintaxis-bounded" anchor="tipos-acotados">

¿Cuál es la declaración correcta de una clase `Pair` cuyos dos parámetros
deben implementar `Comparable` sobre sí mismos?

- [x] `class Pair<A extends Comparable<A>, B extends Comparable<B>>`
- [ ] `class Pair<A implements Comparable<A>, B implements Comparable<B>>`
- [ ] `class Pair<A, B> where A extends Comparable, B extends Comparable`
- [ ] `class Pair<A: Comparable, B: Comparable>`

</Question>

<Question id="comparator-lambda" anchor="comparator">

`Comparator<T>` declara un único método abstracto, `int compare(T a, T b)`.
¿Qué relación tiene una lambda con esta interfaz?

- [x] Una lambda con firma `(T, T) -> int` es implementación válida de la interfaz: su cuerpo se usa como método `compare`
- [ ] Una lambda sólo puede implementar interfaces marcadas con `@FunctionalInterface`, anotación que `Comparator` no lleva
- [ ] El compilador rechaza asignar una lambda a una variable de tipo interfaz; se requiere una clase anónima
- [ ] Una lambda implementa `Comparator` únicamente si su cuerpo llama internamente a `Comparable.compareTo`

</Question>

<Question id="reversed-comparator" anchor="comparator">

Dado el comparador
`Comparator<Pair<String, Integer>> porSecond = (a, b) -> Integer.compare(a.second(), b.second());`,
¿qué produce la llamada `Arrays.sort(pares, porSecond.reversed())`?

- [x] El arreglo ordenado por `second` descendente
- [ ] El arreglo con los elementos en el orden inverso al que tenían antes de la llamada
- [ ] Una excepción, porque `.reversed()` sólo se puede aplicar a comparadores provenientes de `Comparator.comparing`
- [ ] Una copia del arreglo original, ordenada por `second` ascendente

</Question>

<Question id="thencomparing-desempate" anchor="comparator">

`porA.thenComparing(porB)` produce un comparador compuesto. ¿En qué caso
entra en acción `porB` sobre un par de elementos comparados?

- [x] Únicamente cuando `porA` devuelve cero para ese par
- [ ] En todas las comparaciones, sumando su resultado con el de `porA`
- [ ] Sólo cuando `porA` devuelve un valor positivo
- [ ] En ninguna: `thenComparing` es una marca sintáctica sin efecto en tiempo de ejecución

</Question>
