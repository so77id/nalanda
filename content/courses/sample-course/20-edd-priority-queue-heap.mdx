# Estructuras de Datos · Priority Queue y Heap

En una sala de urgencias no se atiende por orden de llegada: primero pasa
el paciente más grave. Una cola común no puede expresar esa regla, porque
sólo conoce el orden en que llegaron los elementos. Para eso existe la
**cola de prioridad**, un contrato en el que siempre sale el elemento de
mayor prioridad. Para implementarlo estudiaremos estructuras de datos que
ya hemos visto: cada una resulta rápida para insertar o para extraer, pero
no para ambas cosas. Y buscaremos una que no tenga que elegir.

<Slide title="Una cola de prioridad">
Una **cola de prioridad** es una colección donde cada elemento trae una
**prioridad**, y el que sale no es el que llegó primero sino el de
**prioridad más alta**.

La **prioridad** es el criterio que decide qué elemento es más importante
que otro. Puede ser cualquier cosa que se pueda comparar: la gravedad de un
paciente, la urgencia de una tarea, el instante en que ocurrirá un evento o
el tamaño de un archivo. Lo único que el contrato exige es que, dados dos
elementos, siempre se pueda decir cuál va primero.

En la mayoría de los ejemplos de esta clase, la prioridad la da el propio
valor de los datos que se guardan: por lo general, el elemento mayor es el de
mayor prioridad. Algunos ejemplos usan el orden inverso, y cuando ocurre se
indica explícitamente.

El orden de llegada deja de importar para decidir quién sale. Sólo decide
la prioridad, y lo único visible de la colección es su máximo.

</Slide>

<Slide title="Colas de prioridad en la vida real">
Una cola de prioridad aparece en cualquier lugar donde se atiende por
urgencia y no por turno.

- **El triage de una sala de urgencias.** Cada paciente recibe una
  categoría al llegar, y el médico atiende al más grave de los que esperan,
  no al que lleva más tiempo sentado.
- **El planificador de un sistema operativo.** Entre los procesos listos
  para ejecutarse, el procesador se entrega al de prioridad más alta.
- **La simulación por eventos.** Cada evento futuro se guarda con el
  instante en que ocurre, y la simulación avanza procesando siempre el más
  próximo. Aquí la prioridad más alta es el tiempo **menor**: el mismo
  contrato, con el orden invertido.
- **Los trabajos de una impresora compartida**, cuando un trabajo urgente
  puede pasar delante de los que ya estaban en espera.

Los cuatro necesitan lo mismo: agregar cuando llega algo nuevo y sacar el
más importante. Ese comportamiento está definido en un **tipo de dato
abstracto** (TDA) llamado **Priority Queue**.

</Slide>

<Slide title="El TDA Priority Queue">
La **Priority Queue** es una colección donde cada elemento tiene una
prioridad, y **sólo el elemento de mayor prioridad es visible**: es el único
que se puede consultar y el único que se puede sacar de la colección.

<Slide title="Las reglas del contrato Priority Queue">
Lo que distingue a esta colección de una Queue es la **regla de salida**.
En una Queue sale el elemento que lleva más tiempo esperando. En una
Priority Queue sale el de mayor prioridad, sin importar cuándo llegó: un
elemento recién insertado puede salir antes que todos los que ya estaban.

Qué elemento tiene la mayor prioridad lo decide quien implementa y usa el
TDA. A veces es el número mayor; otras, el menor, como el instante más
próximo de un evento; otras, una propiedad de los datos, como la gravedad
de un paciente. Por eso `max` y `extractMax` hablan de la **prioridad
máxima**, no del número más grande.

Hay una condición para usar el contrato: **`max()` y `extractMax()` sólo se
pueden llamar si la colección tiene al menos un elemento**, es decir, si
`isEmpty()` retorna falso. En una colección vacía no existe un elemento de
mayor prioridad que retornar.

</Slide>

<Slide title="Formas de implementar una cola de prioridad">
El contrato no dice dónde se guardan los elementos, así que hay que elegir
una estructura de datos. La primera candidata es la **lista enlazada**, y
admite dos maneras de usarla:

1. **Sin orden.** Los elementos se guardan en el orden en que llegan.
2. **Ordenada de mayor a menor prioridad.** Cada elemento nuevo se ubica en
   su lugar.

Las dos cumplen el mismo contrato. Encontrar el elemento de mayor prioridad
cuesta trabajo en ambas; lo que cambia es **cuándo se hace ese trabajo**: al
sacarlo, o al insertarlo.

</Slide>

<Slide title="La lista sin orden">
Si la lista no guarda ningún orden, insertar es inmediato: el elemento nuevo
se agrega al frente, sin mirar a los demás.

El precio aparece al consultar o sacar. Nada indica dónde está el elemento
de mayor prioridad, así que `max()` y `extractMax()` tienen que recorrer la
lista completa comparando cada elemento con el mayor visto hasta ese
momento.

| Molde     | Operación             | Peor caso     | Invariante que restaura                             |
| --------- | --------------------- | ------------- | --------------------------------------------------- |
| consultar | `max()`               | $$\Theta(N)$$ | Ninguna: recorre sin cambiar nada                   |
| consultar | `isEmpty()`, `size()` | $$\Theta(1)$$ | Ninguna                                             |
| modificar | <code style={{ color: 'var(--color-keep)' }}>insert(x)</code> | <span style={{ color: 'var(--color-keep)', fontWeight: 700 }}>$$\Theta(1)$$</span> | Ninguna que dependa del orden |
| modificar | `extractMax()`        | $$\Theta(N)$$ | La lista queda enlazada sin el elemento que salió   |

**Barato para entrar, caro para salir.** Todo el trabajo de encontrar el
elemento de mayor prioridad se posterga hasta que alguien lo pide.

</Slide>

<Slide title="La lista ordenada de mayor a menor">
La alternativa es hacer ese trabajo antes. Si la lista se mantiene ordenada
de mayor a menor prioridad, sostiene una invariante nueva:

1. **El valor de cada nodo es mayor o igual que el del siguiente.** Por eso
   el elemento de mayor prioridad está siempre en `head`.

Consultarlo o sacarlo ya no recorre nada. El trabajo se traslada a
`insert`, que tiene que avanzar por la lista hasta encontrar el lugar donde
el elemento nuevo conserva la invariante.

| Molde     | Operación             | Peor caso     | Invariante que restaura                                       |
| --------- | --------------------- | ------------- | ------------------------------------------------------------- |
| consultar | `max()`               | $$\Theta(1)$$ | Ninguna: lee `head`                                           |
| consultar | `isEmpty()`, `size()` | $$\Theta(1)$$ | Ninguna                                                       |
| modificar | `insert(x)`           | $$\Theta(N)$$ | Cada nodo mayor o igual que el siguiente, con `x` en su lugar |
| modificar | <code style={{ color: 'var(--color-keep)' }}>extractMax()</code> | <span style={{ color: 'var(--color-keep)', fontWeight: 700 }}>$$\Theta(1)$$</span> | El orden se conserva: sacar el primero no desordena el resto |

**Caro para entrar, barato para salir.** El trabajo no desapareció: se
movió de `extractMax` a `insert`.

</Slide>

<Slide title="Un dilema entre insertar y extraer">
Puestas lado a lado, cada implementación es rápida exactamente donde la otra
es lenta:

| Implementación  | `insert(x)`   | `extractMax()` | `max()`       |
| --------------- | ------------- | -------------- | ------------- |
| Lista sin orden | $$\Theta(1)$$ | $$\Theta(N)$$  | $$\Theta(N)$$ |
| Lista ordenada  | $$\Theta(N)$$ | $$\Theta(1)$$  | $$\Theta(1)$$ |
| ¿?              | ¿?            | ¿?             | ¿?            |

Una cola de prioridad no hace una sola operación: recibe muchas. Si entran
$$N$$ elementos y después se sacan todos, con la lista sin orden cada
extracción recorre los que quedan: la primera mira $$N$$, la segunda
$$N - 1$$, y así hasta 1. En total son

$$
N + (N - 1) + \dots + 1 = \frac{N(N + 1)}{2} \in \Theta(N^2)
$$

pasos. Con la lista ordenada la suma es la misma, pero se paga al insertar:
el elemento número $$k$$ puede recorrer los $$k - 1$$ que ya están. Con un
millón de elementos son unos quinientos mil millones de pasos. Ni postergar
el trabajo ni adelantarlo lo hace desaparecer.

**¿Existe una forma de hacerlo mejor?**

</Slide>

<Slide title="Un orden que sólo garantiza dónde está el máximo">
La lista ordenada paga caro al insertar porque mantiene **todos** los
elementos en orden. Con 10, 8, 7, 4, 3, 2, 1 sabe que el 10 es el primero,
pero también que el 8 va antes que el 7, el 7 antes que el 4, y así hasta
el 1. El contrato, en cambio, sólo deja ver un elemento: el de mayor
prioridad. Que el 8 vaya antes que el 7 no le sirve a ninguna operación.

La idea es guardar sólo el orden necesario para saber cuál es el mayor. Por
ejemplo, en una jerarquía: el 10 arriba, y debajo de él dos grupos, cada
uno con su propio mayor arriba.

<HeapPicture values={[10, 7, 8, 1, 3, 2, 4]} view="tree" label="Los mismos siete valores en una jerarquía: el 10 arriba; debajo, el 7 y el 8; debajo del 7, el 1 y el 3; y debajo del 8, el 2 y el 4. Cada valor es mayor o igual que los que tiene debajo." />

La única invariante es que **cada elemento sea mayor o igual que los que
tiene debajo**. Con eso el mayor de todos queda siempre arriba, y nadie compara
al 7 con el 8, porque están en ramas distintas. Hay mucho menos orden que
mantener, y por eso insertar y extraer pueden ser baratos a la vez: los dos
cuestan $$O(\log N)$$.

Esta jerarquía es un árbol, y la estructura que la guarda se llama
**heap**.

</Slide>

{/* HeapPicture — a static drawing of one heap, as the tree, as the array, or both with the correspondence drawn between them. */}
{/* File-local on purpose (add-a-course-document.md §6e-quater): one consumer, no catalog entry, not registered. The second document that wants it promotes it. */}
{/* Same geometry as the heap-max recipe of <SequenceStepper> (sequenceStepperHeapLayout.ts), so a static figure and the widget beside it draw the same tree. */}

export function HeapPicture({
  values = [],
  n = values.length,
  view = 'both',
  hot = [],
  marked = [],
  levelBrackets = false,
  levelLines = false,
  levelColors = false,
  edgeArrows,
  arcs,
  parentArcs = false,
  zeroBased = false,
  childBrackets = false,
  nextSlot = false,
  brokenEdges = [],
  minLevels = 1,
  capacity,
  reserveCells,
  staleTail = false,
  heightRuler = false,
  idPrefix = 'heap-pic',
  label,
}) {
  const r = 17;
  const pitch = 46;
  const levelH = 54;
  const pad = 14;
  const box = 40;
  // A null value is a HOLE: a position the numbering reserves and nobody occupies.
  const present = (k) => values[k - 1] !== null && values[k - 1] !== undefined;
  const LEVEL = ['var(--color-accent)', 'var(--color-keep)', 'var(--color-focus)', 'var(--color-mark)'];
  // One colour per PARENT, so the two arrows leaving one node read as a pair.
  const PAIR = ['var(--color-accent)', 'var(--color-keep)', 'var(--color-focus)', 'var(--color-mark)'];
  const pairColor = (parent) => PAIR[(parent - 1) % 4];
  const arcMode = arcs ?? (parentArcs ? 'parent' : undefined);
  const levelOf = (k) => Math.floor(Math.log2(k));
  // The next free position, n + 1, is drawn dashed when asked for.
  const total = values.length + (nextSlot ? 1 : 0);
  // minLevels lets two pictures side by side reserve the same canvas, so
  // their nodes come out the same size.
  const levels = Math.max(total === 0 ? 1 : levelOf(total) + 1, minLevels);
  const leaves = 2 ** (levels - 1);
  const labelW = levelLines ? 58 : 0;
  // A vertical ruler from the root's level to the last one, left of the
  // level labels: the height of the tree, written as floor(log2 n).
  const rulerW = heightRuler ? 40 : 0;
  const treeW = rulerW + labelW + 2 * pad + leaves * pitch;
  const treeH = view === 'array' ? 0 : 2 * pad + 2 * r + (levels - 1) * levelH;
  // Zero-based storage has no unused slot: the root sits in data[0].
  const lead = zeroBased ? 0 : 1;
  // capacity is data.length: the empty cells past the last element are
  // drawn too, so a full block and a grown one can be compared.
  const cells = Math.max(total + lead, capacity ?? 0);
  // reserveCells widens the canvas without drawing cells, left-aligned, so
  // a small block lines up cell by cell with a larger one drawn below it.
  const arrayW = Math.max(cells, reserveCells ?? 0) * box;
  const width = Math.max(view === 'array' ? 0 : treeW, view === 'tree' ? 0 : arrayW + 8);
  const treeX = (width - treeW) / 2;
  const arrayX = (width - arrayW) / 2;
  const arcSpace = arcMode ? 74 : 0;
  const arrayY = treeH + (view === 'both' ? 26 : 6) + arcSpace;
  // Parent arcs alternate sides by parent — those landing on 1 and 3 above
  // the array, those landing on 2 below it — so the pairs do not overlap.
  const arcAbove = (parent) => parent % 2 === 1;
  const belowArcs = arcMode !== undefined && values.length >= 4;
  // Brackets sit under everything else: one row lower when arcs run below.
  const bracketY = arrayY + box + (belowArcs ? 92 : 40);
  const height =
    view === 'tree' ? treeH : (levelBrackets || childBrackets ? bracketY + 26 : arrayY + box + (belowArcs ? 84 : 40));
  const at = (k) => {
    const level = levelOf(k);
    const span = leaves / 2 ** level;
    return { cx: treeX + rulerW + labelW + pad + (k - 2 ** level + 0.5) * span * pitch, cy: pad + r + level * levelH };
  };
  // Past n: heapsort's sorted tail (keep), or with staleTail a copy nobody
  // reads any more — what extractMax leaves behind in data[n + 1].
  const stroke = (k) =>
    hot.includes(k) ? 'var(--color-accent)' : marked.includes(k) ? 'var(--color-mark)' : k > n ? (staleTail ? 'var(--color-rule)' : 'var(--color-keep)') : levelColors ? LEVEL[levelOf(k) % 4] : 'var(--color-rule-strong)';
  const fill = (k) => (marked.includes(k) ? 'var(--color-mark-soft)' : k > n ? (staleTail ? 'var(--color-sunk)' : 'var(--color-keep-soft)') : 'var(--color-surface)');
  const weight = (k) => (hot.includes(k) ? 2.8 : marked.includes(k) || levelColors ? 2 : 1.4);
  const ks = values.map((_, i) => i + 1);
  // The number a reader sees: the node's position, from 1 or from 0.
  const shown = (k) => k - 1 + lead;
  const cellLeft = (k) => arrayX + (k - 1 + lead) * box;
  const cellX = (k) => cellLeft(k) + box / 2;
  const linked = (k) => k > 1 && k <= n && present(k) && present(Math.floor(k / 2));
  return (
    <svg
      viewBox={`0 0 ${width} ${height}`}
      style={{ width: '100%', maxWidth: `${Math.round(width * 1.45)}px`, height: 'auto', display: 'block', margin: '1rem auto' }}
      role="img"
      aria-label={label}
    >
      <defs>
        {PAIR.map((c, i) => (
          <marker key={i} id={`${idPrefix}-tip${i}`} markerWidth="7" markerHeight="7" refX="6" refY="3.5" orient="auto">
            <path d="M0,0 L7,3.5 L0,7 z" style={{ fill: c }} />
          </marker>
        ))}
        <marker id={`${idPrefix}-arc`} markerWidth="7" markerHeight="7" refX="6" refY="3.5" orient="auto">
          <path d="M0,0 L7,3.5 L0,7 z" style={{ fill: 'var(--color-ink-soft)' }} />
        </marker>
      </defs>
      {view !== 'array' && heightRuler ? (() => {
        const x = treeX + 16;
        const y1 = pad + r;
        const y2 = pad + r + (levels - 1) * levelH;
        return (
          <g>
            {/* From the top of the root to the bottom of the last level, no tips. */}
            <line x1={x} y1={y1 - r} x2={x} y2={y2 + r} style={{ stroke: 'var(--color-ink)' }} strokeWidth="1.6" />
            <text x={x - 6} y={(y1 + y2) / 2} textAnchor="middle" fontSize="11" fontWeight="700" transform={`rotate(-90 ${x - 6} ${(y1 + y2) / 2})`} style={{ fill: 'var(--color-ink)' }}>altura = ⌊log₂ n⌋</text>
          </g>
        );
      })() : null}
      {view !== 'array' && levelLines ? Array.from({ length: levels }, (_, d) => {
        const y = pad + r + d * levelH;
        return (
          <g key={`ll${d}`}>
            <line x1={treeX + rulerW + 4} y1={y} x2={treeX + treeW - 4} y2={y} style={{ stroke: levelColors ? LEVEL[d % 4] : 'var(--color-rule)' }} strokeWidth="1" strokeDasharray="4 4" opacity="0.7" />
            <text x={treeX + rulerW + 4} y={y - 6} fontSize="11" fontWeight="600" style={{ fill: levelColors ? LEVEL[d % 4] : 'var(--color-ink-faint)' }}>{`nivel ${d}`}</text>
          </g>
        );
      }) : null}
      {view === 'array' ? null : ks.filter((k) => k > 1 && k <= n && (!present(k) || !present(Math.floor(k / 2)))).map((k) => {
        // An edge touching a hole: the position exists, nobody occupies it.
        const p = at(Math.floor(k / 2));
        const c = at(k);
        return <line key={`h${k}`} x1={p.cx} y1={p.cy} x2={c.cx} y2={c.cy} style={{ stroke: 'var(--color-rule)' }} strokeWidth="1.2" strokeDasharray="3 4" />;
      })}
      {view === 'array' ? null : ks.filter(linked).map((k) => {
        const parent = Math.floor(k / 2);
        const p = at(parent);
        const c = at(k);
        const hotEdge = hot.includes(k) && hot.includes(parent);
        if (edgeArrows) {
          // Rim to rim, so the arrowhead lands on the node's edge, not under it.
          const dx = c.cx - p.cx;
          const dy = c.cy - p.cy;
          const len = Math.hypot(dx, dy);
          const ux = dx / len;
          const uy = dy / len;
          const down = edgeArrows === 'down';
          const [x1, y1, x2, y2] = down
            ? [p.cx + ux * r, p.cy + uy * r, c.cx - ux * (r + 2), c.cy - uy * (r + 2)]
            : [c.cx - ux * r, c.cy - uy * r, p.cx + ux * (r + 2), p.cy + uy * (r + 2)];
          return <line key={`e${k}`} x1={x1} y1={y1} x2={x2} y2={y2} style={{ stroke: pairColor(parent) }} strokeWidth="1.8" markerEnd={`url(#${idPrefix}-tip${(parent - 1) % 4})`} />;
        }
        if (brokenEdges.includes(k)) {
          // A broken invariant: red AND dashed, so colour is not the only signal.
          return <line key={`e${k}`} x1={p.cx} y1={p.cy} x2={c.cx} y2={c.cy} style={{ stroke: 'var(--color-flag)' }} strokeWidth="2.8" strokeDasharray="6 4" />;
        }
        return <line key={`e${k}`} x1={p.cx} y1={p.cy} x2={c.cx} y2={c.cy} style={{ stroke: hotEdge ? 'var(--color-accent)' : 'var(--color-rule-strong)' }} strokeWidth={hotEdge ? 2.8 : 1.2} />;
      })}
      {view !== 'array' && nextSlot && present(Math.floor(total / 2)) ? (() => {
        const p = at(Math.floor(total / 2));
        const c = at(total);
        return (
          <g>
            <line x1={p.cx} y1={p.cy} x2={c.cx} y2={c.cy} style={{ stroke: 'var(--color-mark)' }} strokeWidth="1.4" strokeDasharray="4 4" />
            <circle cx={c.cx} cy={c.cy} r={r} style={{ fill: 'var(--color-mark-soft)', stroke: 'var(--color-mark)' }} strokeWidth="1.8" strokeDasharray="4 3" />
            <text x={c.cx} y={c.cy + 4} textAnchor="middle" fontSize="10" fontWeight="700" style={{ fill: 'var(--color-mark)' }}>n + 1</text>
            <text x={c.cx} y={c.cy + r + 13} textAnchor="middle" fontSize="11" fontWeight="600" style={{ fill: 'var(--color-ink-soft)' }}>{shown(total)}</text>
          </g>
        );
      })() : null}
      {view === 'array' ? null : ks.filter((k) => k <= n).map((k) => {
        const c = at(k);
        if (!present(k)) {
          return (
            <g key={`n${k}`}>
              <circle cx={c.cx} cy={c.cy} r={r} style={{ fill: 'var(--color-sunk)', stroke: 'var(--color-flag)' }} strokeWidth="1.6" strokeDasharray="4 3" />
              <text x={c.cx} y={c.cy + 3} textAnchor="middle" fontSize="8" fontWeight="600" style={{ fill: 'var(--color-flag)' }}>hueco</text>
              <text x={c.cx} y={c.cy + r + 13} textAnchor="middle" fontSize="11" fontWeight="600" style={{ fill: 'var(--color-ink-soft)' }}>{shown(k)}</text>
            </g>
          );
        }
        return (
          <g key={`n${k}`}>
            <circle cx={c.cx} cy={c.cy} r={r} style={{ fill: fill(k), stroke: stroke(k) }} strokeWidth={weight(k)} />
            <text x={c.cx} y={c.cy + 5} textAnchor="middle" fontSize="14" fontWeight="600" style={{ fill: 'var(--color-ink)' }}>{values[k - 1]}</text>
            <text x={c.cx} y={c.cy + r + 13} textAnchor="middle" fontSize="11" fontWeight="600" style={{ fill: 'var(--color-ink-soft)' }}>{shown(k)}</text>
          </g>
        );
      })}
      {view === 'tree' ? null : (
        <g>
          {arcMode === 'parent' ? ks.filter(linked).map((k) => {
            // A left child (even k) lands on the left half of its parent, a
            // right child on the right half, so two arrows never share a tip.
            // Coloured by parent, like the tree's arrows.
            const parent = Math.floor(k / 2);
            const from = cellX(k);
            const to = cellX(parent) + (k % 2 === 0 ? -8 : 8);
            const lift = 16 + (from - to) * 0.3;
            const style = { fill: 'none', stroke: pairColor(parent) };
            const tip = `url(#${idPrefix}-tip${(parent - 1) % 4})`;
            if (arcAbove(parent)) {
              return <path key={`arc${k}`} d={`M ${from} ${arrayY - 2} C ${from} ${arrayY - lift}, ${to} ${arrayY - lift}, ${to} ${arrayY - 4}`} style={style} strokeWidth="1.6" markerEnd={tip} />;
            }
            // Below, under the index rail, so the numbers stay readable.
            const base = arrayY + box + 20;
            return <path key={`arc${k}`} d={`M ${from} ${base} C ${from} ${base + lift}, ${to} ${base + lift}, ${to} ${base + 2}`} style={style} strokeWidth="1.6" markerEnd={tip} />;
          }) : null}
          {arcMode === 'children' ? ks.filter(linked).map((k) => {
            // Both arrows of a pair leave the SAME point of the parent's cell
            // and land on their own child, on the side the parent's pair uses
            // (1 and 3 above, 2 below), coloured by parent like the tree.
            const parent = Math.floor(k / 2);
            const from = cellX(parent);
            const to = cellX(k);
            const lift = 16 + (to - from) * 0.3;
            const style = { fill: 'none', stroke: pairColor(parent) };
            const tip = `url(#${idPrefix}-tip${(parent - 1) % 4})`;
            if (arcAbove(parent)) {
              return <path key={`arc${k}`} d={`M ${from} ${arrayY - 2} C ${from} ${arrayY - lift}, ${to} ${arrayY - lift}, ${to} ${arrayY - 4}`} style={style} strokeWidth="1.6" markerEnd={tip} />;
            }
            const base = arrayY + box + 20;
            return <path key={`arc${k}`} d={`M ${from} ${base} C ${from} ${base + lift}, ${to} ${base + lift}, ${to} ${base + 2}`} style={style} strokeWidth="1.6" markerEnd={tip} />;
          }) : null}
          {zeroBased ? null : (
            <g>
              <rect x={arrayX} y={arrayY} width={box} height={box} rx="3" style={{ fill: 'var(--color-sunk)', stroke: 'var(--color-rule)' }} strokeWidth="1.2" strokeDasharray="3 3" />
              <text x={arrayX + box / 2} y={arrayY + box + 14} textAnchor="middle" fontSize="10" style={{ fill: 'var(--color-ink-faint)' }}>0</text>
              <text x={arrayX} y={arrayY + box + 30} fontSize="9" style={{ fill: 'var(--color-ink-soft)' }}>no se usa</text>
            </g>
          )}
          {levelBrackets ? Array.from({ length: levels }, (_, d) => {
            const first = 2 ** d;
            const last = Math.min(2 ** (d + 1) - 1, values.length);
            const x1 = cellLeft(first) + 3;
            const x2 = cellLeft(last) + box - 3;
            const y = bracketY;
            const color = levelColors ? LEVEL[d % 4] : 'var(--color-accent)';
            return (
              <g key={`lv${d}`}>
                <path d={`M ${x1} ${y - 6} L ${x1} ${y} L ${x2} ${y} L ${x2} ${y - 6}`} style={{ fill: 'none', stroke: color }} strokeWidth="1.4" />
                <text x={(x1 + x2) / 2} y={y + 15} textAnchor="middle" fontSize="10" fontWeight="600" style={{ fill: color }}>{`nivel ${d}`}</text>
              </g>
            );
          }) : null}
          {childBrackets ? ks.filter((k) => k <= Math.floor(n / 2) && 2 * k <= n).map((k) => {
            // The two children of node k sit side by side, in data[2k] and
            // data[2k + 1]: one bracket per pair, in the parent's colour.
            const last = Math.min(2 * k + 1, n);
            const x1 = cellLeft(2 * k) + 3;
            const x2 = cellLeft(last) + box - 3;
            const y = bracketY;
            return (
              <g key={`cb${k}`}>
                <path d={`M ${x1} ${y - 6} L ${x1} ${y} L ${x2} ${y} L ${x2} ${y - 6}`} style={{ fill: 'none', stroke: pairColor(k) }} strokeWidth="1.6" />
                <text x={(x1 + x2) / 2} y={y + 15} textAnchor="middle" fontSize="10" fontWeight="600" style={{ fill: pairColor(k) }}>{`hijos de ${shown(k)}`}</text>
              </g>
            );
          }) : null}
          {capacity ? Array.from({ length: Math.max(capacity - lead - total, 0) }, (_, i) => {
            const k = total + 1 + i;
            return (
              <g key={`free${k}`}>
                <rect x={cellLeft(k)} y={arrayY} width={box} height={box} rx="3" style={{ fill: 'var(--color-sunk)', stroke: 'var(--color-rule)' }} strokeWidth="1.2" strokeDasharray="3 3" />
                <text x={cellX(k)} y={arrayY + box + 14} textAnchor="middle" fontSize="10" style={{ fill: 'var(--color-ink-faint)' }}>{shown(k)}</text>
              </g>
            );
          }) : null}
          {nextSlot ? (
            <g>
              <rect x={cellLeft(total) + 2} y={arrayY + 2} width={box - 4} height={box - 4} rx="3" style={{ fill: 'var(--color-mark-soft)', stroke: 'var(--color-mark)' }} strokeWidth="1.8" strokeDasharray="4 3" />
              <text x={cellX(total)} y={arrayY + box / 2 + 4} textAnchor="middle" fontSize="10" fontWeight="700" style={{ fill: 'var(--color-mark)' }}>n + 1</text>
              <text x={cellX(total)} y={arrayY + box + 14} textAnchor="middle" fontSize="10" style={{ fill: 'var(--color-ink-faint)' }}>{shown(total)}</text>
            </g>
          ) : null}
          {ks.map((k) => (
            <g key={`a${k}`}>
              {present(k) ? (
                <rect x={cellLeft(k)} y={arrayY} width={box} height={box} rx="3" style={{ fill: fill(k), stroke: stroke(k) }} strokeWidth={weight(k)} strokeDasharray={staleTail && k > n && !hot.includes(k) ? '3 3' : undefined} />
              ) : (
                <rect x={cellLeft(k) + 2} y={arrayY + 2} width={box - 4} height={box - 4} rx="3" style={{ fill: 'var(--color-sunk)', stroke: 'var(--color-flag)' }} strokeWidth="1.6" strokeDasharray="4 3" />
              )}
              {present(k) ? (
                <text x={cellX(k)} y={arrayY + box / 2 + 5} textAnchor="middle" fontSize="14" fontWeight="600" style={{ fill: staleTail && k > n ? 'var(--color-ink-faint)' : 'var(--color-ink)' }}>{values[k - 1]}</text>
              ) : (
                <text x={cellX(k)} y={arrayY + box / 2 + 4} textAnchor="middle" fontSize="9" fontWeight="600" style={{ fill: 'var(--color-flag)' }}>vacía</text>
              )}
              <text x={cellX(k)} y={arrayY + box + 14} textAnchor="middle" fontSize="10" style={{ fill: 'var(--color-ink-faint)' }}>{shown(k)}</text>
            </g>
          ))}
        </g>
      )}
    </svg>
  );
}

## El heap binario

<Slide title="Un árbol binario con orden de heap">
Un **árbol binario** es una jerarquía donde cada elemento, llamado
**nodo**, tiene a lo más dos nodos debajo: sus **hijos**, izquierdo y
derecho. El de arriba de todo, que no es hijo de nadie, es la **raíz**. Un
árbol binario tiene **orden de heap** cuando cumple esta **invariante**:

> **el valor de cada nodo es mayor o igual que los valores de sus dos
> hijos.**

<HeapPicture values={[10, 7, 8, 1, 3, 2, 4]} view="tree" label="Un árbol binario con orden de heap. La raíz es 10; sus hijos son 7 y 8; los hijos de 7 son 1 y 3, y los de 8 son 2 y 4. Cada nodo es mayor o igual que sus hijos." />

Si partimos de cualquier nodo y subimos hacia la raíz, cada paso llega a un
valor mayor o igual: desde el 1, el camino es 1, 7, 10; desde el 4, es 4, 8,
10. Todos los caminos terminan en la raíz, así que **el valor más grande del
árbol está siempre en la raíz**. Es lo único que el contrato necesita saber.

Esta invariante, en cambio, no dice nada entre nodos que no son padre e hijo. El 7
y el 8 están en ramas distintas y nunca se comparan; el 3 y el 4 tampoco.
Por eso es un orden más débil que el de una lista ordenada: alcanza para
saber cuál es el mayor, pero no ordena a los demás.

Cuando cada nodo es mayor o igual que sus hijos, en la raíz queda el
elemento mayor, y el árbol se llama **max-heap**. Si la invariante se
invierte —cada nodo menor o igual que sus hijos—, en la raíz queda el menor, y el
árbol se llama **min-heap**.

</Slide>

<Slide title="Un árbol binario completo">
Un heap exige una segunda **invariante**, sobre la **forma** del árbol y no sobre
sus valores: el árbol es **completo**. Todos sus niveles están llenos,
salvo quizás el último, que se llena **de izquierda a derecha**, sin
huecos.

El de la izquierda cumple las dos invariantes. El de la derecha cumple la
invariante de orden de heap y rompe la de forma completa: el último nivel
tiene un hueco antes de su primer nodo.

En resumen, las dos **invariantes del heap** son:

1. **Orden de heap: cada nodo es mayor o igual que sus hijos.** Es la que
   pone el máximo en la raíz, y la que cada operación que la rompe tiene que
   restaurar.
2. **Forma completa: los niveles se llenan de izquierda a derecha, sin
   huecos.** Es la que mantiene al árbol bajo —con $$N$$ nodos tiene
   $$\lfloor \log_2 N \rfloor + 1$$ niveles— y la que permite guardarlo sin
   punteros.

La segunda es la invariante que decide el costo. Un árbol con huecos puede
degenerar en una fila de $$N$$ niveles, y cualquier camino de la raíz a una
hoja se vuelve tan largo como la lista.

Funciona, pero guarda información que el heap ya conoce. La invariante de
**forma completa** dice exactamente dónde está cada nodo: los niveles se
llenan de izquierda a derecha, sin huecos. Si la posición de cada nodo
está determinada por la invariante, las dos referencias de cada nodo son
datos que se podrían calcular. Y cuando hay que insertar en la primera hoja
libre, la que mantiene la invariante de forma completa, las referencias no
dicen dónde está: hay que recorrer el árbol para encontrarla.

</Slide>

<Slide title="Numerar los nodos del árbol">
La invariante de forma completa permite darle a cada **nodo** un número, sin
ambigüedad. La raíz recibe el **1**. Después se recorre el árbol nivel por
nivel, de arriba hacia abajo, y dentro de cada nivel de izquierda a derecha:
el 7 recibe el 2, el 8 el 3, y así hasta el último nodo.

<HeapPicture values={[10, 7, 8, 1, 3, 2, 4]} view="tree" levelLines levelColors label="El heap 10, 7, 8, 1, 3, 2, 4 dibujado como árbol, con una línea punteada por cada nivel. El nivel 0 tiene la raíz, numerada 1; el nivel 1 tiene el 7 y el 8, numerados 2 y 3; el nivel 2 tiene el 1, el 3, el 2 y el 4, numerados del 4 al 7." />

Los números de los nodos son los que aparecen debajo de cada uno. Los
**niveles** se cuentan aparte, desde 0. Cada nivel lleno tiene el doble de
nodos que el anterior —1, 2, 4—, así que el **nivel $$d$$ tiene $$2^d$$
nodos, numerados del $$2^d$$ al $$2^{d+1} - 1$$**: el nivel 1 va del 2 al
3, y el nivel 2 del 4 al 7.

Como la invariante de forma completa no deja huecos, la numeración **no
salta ningún número**: un árbol de $$n$$ nodos usa exactamente los números
del 1 al $$n$$, y el próximo nodo recibe el $$n + 1$$. Aquí, del 1 al 7, y
el siguiente será el 8.

</Slide>

<Slide title="Los niveles, uno detrás del otro">
Si se ponen los niveles uno detrás del otro, la numeración se convierte en
los índices de un arreglo: **el nodo número `k` se guarda en `data[k]`**.

<HeapPicture values={[10, 7, 8, 1, 3, 2, 4]} levelLines levelColors levelBrackets label="El mismo heap como árbol y como arreglo, con los niveles marcados por color. El nivel 0, la raíz 10, ocupa data[1]. El nivel 1, el 7 y el 8, ocupa data[2] y data[3]. El nivel 2, el 1, el 3, el 2 y el 4, ocupa data[4] a data[7]. La casilla data[0] está vacía y rotulada no se usa." />

Cada nivel ocupa un tramo seguido del arreglo, en el mismo orden en que se
lee de izquierda a derecha. El arreglo `data` guarda el heap en
`data[1..n]`, donde `n` es la cantidad de elementos, y **`data[0]` queda
sin usar a propósito**: empezar en 1 hace más simple la aritmética entre
padres e hijos.

Ya no hay referencias. El árbol es el modelo para pensar y el arreglo es lo
que el programa guarda: son el mismo objeto con dos representaciones, y
cualquier cambio en una es un cambio en la otra.

</Slide>

<Slide title="Un árbol con huecos en el arreglo">
El arreglo funciona **porque** el árbol cumple la invariante de forma
completa. Un árbol con un hueco —aquí falta el hijo izquierdo del 7— igual
tendría que reservarle su número a esa posición, y el arreglo quedaría con
una casilla vacía en medio:

<HeapPicture values={[10, 7, 8, null, 3, 2, 4]} levelLines label="Un árbol que rompe la invariante de forma completa: falta el hijo izquierdo del 7, en la posición 4. En el arreglo, data[4] queda vacía entre data[3], que guarda 8, y data[5], que guarda 3." />

Con huecos, los elementos ya no ocuparían exactamente `data[1..n]`: `n` no
diría cuántos hay, y la primera posición libre no sería `data[n + 1]`. Por
eso la invariante de forma completa se lee directamente en el arreglo:
**los elementos ocupan `data[1..n]`, sin casillas vacías entre medio**. Y
mantenerla al insertar es fácil: el elemento nuevo va siempre a
`data[n + 1]`.

</Slide>

<Slide title="Los hijos de un nodo">
En el árbol numerado, cada nodo apunta a sus dos hijos. Como el nodo `k`
vive en `data[k]`, las mismas flechas unen casillas del arreglo, y los dos
hijos de cada nodo quedan en casillas seguidas:

<HeapPicture values={[10, 7, 8, 1, 3, 2, 4]} edgeArrows="down" arcs="children" childBrackets idPrefix="pq-hijos" label="El heap 10, 7, 8, 1, 3, 2, 4 como árbol y como arreglo. En el árbol, flechas de cada nodo a sus dos hijos, con un color por padre: del nodo 1 a los nodos 2 y 3, del nodo 2 a los nodos 4 y 5, y del nodo 3 a los nodos 6 y 7. En el arreglo, las mismas flechas y los mismos colores salen de la casilla de cada padre hacia las de sus hijos: las del 1 y del 3 por arriba, las del 2 por abajo. Más abajo, corchetes del mismo color agrupan cada par de hermanos: data[2] y data[3] son los hijos de 1, data[4] y data[5] los hijos de 2, data[6] y data[7] los hijos de 3." />

| Nodo `k`              | 1     | 2     | 3     |
| --------------------- | ----- | ----- | ----- |
| Hijos (izq., der.)    | 2, 3  | 4, 5  | 6, 7  |

El hijo izquierdo de cada nodo tiene el doble de su número, y el derecho, el
siguiente: **los hijos del nodo `k` son `2k` y `2k + 1`**.

</Slide>

<Slide title="Por qué los hijos de k son 2k y 2k + 1">
El patrón no es una casualidad del ejemplo: sale de numerar por niveles.
Tomemos el nodo 3.

<HeapPicture values={[10, 7, 8, 1, 3, 2, 4]} view="tree" levelLines hot={[3, 6, 7]} marked={[2, 4, 5]} label="El árbol numerado por niveles. El nodo 3 y sus hijos, los nodos 6 y 7, resaltados. El nodo 2, a la izquierda del 3 en el nivel 1, y sus hijos, los nodos 4 y 5, marcados aparte: ocupan los dos primeros números del nivel 2." />

- El nodo 3 está en el nivel 1, y sus hijos están en el nivel 2, que empieza
  en el número $$2^2 = 4$$.
- Los hijos se numeran en el mismo orden que sus padres. A la izquierda del
  3, en su nivel, sólo está el nodo 2, y sus dos hijos ocupan el 4 y el 5.
- El siguiente número libre es el 6: ahí va el hijo izquierdo del 3, y el
  derecho en el 7.

En general, el nodo $$k$$ del nivel $$d$$ tiene $$k - 2^d$$ nodos a su
izquierda en su nivel, y cada uno ocupa dos lugares del nivel siguiente, que
empieza en $$2^{d+1}$$. El hijo izquierdo de $$k$$ queda en

$$
2^{d+1} + 2\,(k - 2^d) = 2k
$$

y el derecho, en el siguiente: $$2k + 1$$.

</Slide>

<Slide title="El padre de un nodo">
Si los hijos del nodo $$p$$ son $$2p$$ y $$2p + 1$$, ir de un hijo a su
padre es deshacer esa cuenta: dividir por 2. Con división entera el resto se
descarta, así que los dos hijos llegan al mismo padre.

<HeapPicture values={[10, 7, 8, 1, 3, 2, 4]} edgeArrows="up" arcs="parent" idPrefix="pq-padre" label="El heap como árbol y como arreglo, con flechas de cada nodo a su padre: los nodos 2 y 3 apuntan al 1, los nodos 4 y 5 al 2, y los nodos 6 y 7 al 3. En el arreglo, las mismas flechas, con los mismos colores, van de cada casilla a la de su padre: las que llegan a las casillas 1 y 3 por arriba, y las que llegan a la casilla 2 por abajo." />

| Nodo `k` | 2   | 3   | 4   | 5   | 6   | 7   |
| -------- | --- | --- | --- | --- | --- | --- |
| `k / 2`  | 1   | 1   | 2   | 2   | 3   | 3   |

**El padre del nodo `k` es `k / 2`**, con la división entera de Java. La
raíz, el nodo 1, no tiene padre: `1 / 2` da 0, justo la casilla que no se
usa.

</Slide>

<Slide title="Si el arreglo empezara en 0">
El mismo árbol se puede numerar desde 0. La raíz va en `data[0]` y no queda
ninguna casilla sin usar.

<HeapPicture values={[10, 7, 8, 1, 3, 2, 4]} view="tree" zeroBased label="El mismo heap numerado desde 0: la raíz es el nodo 0, sus hijos los nodos 1 y 2, y el último nivel los nodos 3 a 6." />
</div>
</div>

|                        | Desde 1         | Desde 0               |
| ---------------------- | --------------- | --------------------- |
| Hijos de `k`           | `2k`, `2k + 1`  | `2k + 1`, `2k + 2`    |
| Padre de `k`           | `k / 2`         | `(k - 1) / 2`         |
| El nivel `d` empieza en | $$2^d$$        | $$2^d - 1$$           |
| Casillas sin usar      | `data[0]`       | ninguna               |

Las dos numeraciones funcionan. Empezar en 0 ahorra una casilla, y a cambio
cada fórmula carga un $$\pm 1$$, que es justo donde se cometen los errores.
Aquí el heap se guarda desde 1; `java.util.PriorityQueue` lo guarda desde 0.
Es una decisión de diseño, no una regla.

</Slide>

<Slide title="Las funciones `parent`, `left` y `right`">
Las tres fórmulas, escritas como funciones. La división entera de `k / 2` es la que
hace que los dos hijos de un nodo lleguen al mismo padre:

```java
int parent(int k) {
    return k / 2;
}

int left(int k) {
    return 2 * k;
}

int right(int k) {
    return 2 * k + 1;
}
```

Ninguna recorre nada: moverse entre un nodo y su padre o sus hijos cuesta
una operación aritmética, $$\Theta(1)$$, sin referencias que seguir.

</Slide>


<Slide title="Las dos invariantes leídas en el arreglo">
Con la aritmética de índices, las dos invariantes del heap se pueden
comprobar sobre el arreglo, sin dibujar el árbol.

<HeapPicture values={[10, 7, 8, 1, 3, 2, 4]} view="array" parentArcs idPrefix="pq-inv-arr" label="El arreglo del heap, data[1] a data[7] = 10, 7, 8, 1, 3, 2, 4. Sobre él, una flecha va de cada casilla k a la casilla k dividido 2, su padre: de data[2] y data[3] a data[1]; de data[4] y data[5] a data[2]; de data[6] y data[7] a data[3]. En todas, el valor de llegada es mayor o igual." />

1. **Forma completa: los elementos ocupan `data[1..n]`, sin casillas vacías
   entre medio.** Aquí son los 7, de `data[1]` a `data[7]`.
2. **Orden de heap: para cada `k` entre 2 y `n`,
   `data[parent(k)] >= data[k]`.**
   Cada flecha va de una casilla a la de su padre, y en todas el valor de
   llegada es mayor o igual: `data[5] = 3` apunta a `data[2] = 7`, y
   `data[7] = 4` apunta a `data[3] = 8`.

Las operaciones del heap trabajan sobre el arreglo, y las dos invariantes
son lo que cada una tiene que dejar cumplido al terminar.

</Slide>

## Las operaciones del heap

<Slide title="La clase MaxHeap">
El heap se guarda en un arreglo `data` y un entero `n`: los elementos
ocupan `data[1..n]`, y `data[0]` no se usa.

```java
class MaxHeap {
    private int[] data = new int[2];
    private int n = 0;
}
```

Un heap vacío arranca como el arreglo dinámico, con una sola casilla útil,
`data[1]`, más la casilla 0. Cuando se llena crece con el mismo `resize`,
que reserva un bloque del doble y copia los elementos, aquí los de
`data[1..n]`. Las funciones `parent`, `left`, `right` y las que siguen son
métodos de esta clase.

Construir el heap vacío —el `build()` del contrato— cuesta $$\Theta(1)$$, y
el heap vacío cumple las dos invariantes.

</Slide>

<Slide title="Las dos invariantes al modificar el heap">
Insertar o sacar un elemento cambia el heap, y después del cambio las dos
invariantes tienen que seguir cumpliéndose. Las dos operaciones lo logran
de la misma manera: primero cuidan la forma y después el orden.

**La invariante de forma completa no deja elegir el lugar.** Para que el
árbol siga sin huecos, un elemento nuevo sólo puede ocupar la primera
posición libre, `data[n + 1]`, y el único que puede salir sin dejar un hueco
es el último, `data[n]`.

**La invariante de orden de heap se repara después.** El lugar obligado no
mira los valores. Al insertar, el nuevo puede quedar debajo de un padre
menor que él; al sacar, el que pasa a la raíz puede quedar encima de hijos
mayores. La invariante queda rota, pero en un solo punto. Repararla es
mover ese elemento,
intercambio a intercambio, por el único camino que une ese punto con la
raíz. Cada intercambio cuesta $$\Theta(1)$$, así que el costo de la
operación lo decide el largo de ese camino, que a lo más es la altura del
árbol.

</Slide>

<Slide title="Las consultas max, isEmpty y size">
Las tres consultas del contrato sólo leen. La invariante de orden de heap
pone el elemento de mayor prioridad en la raíz, y la raíz es `data[1]`:

```java
int max() {
    if (n == 0) {
        throw new NoSuchElementException();
    }
    return data[1];
}

boolean isEmpty() {
    return n == 0;
}

int size() {
    return n;
}
```

Ninguna recorre ni cambia nada, así que ninguna puede romper una invariante:

| Molde     | Operación             | Peor caso     | Invariante que restaura               |
| --------- | --------------------- | ------------- | ------------------------------------- |
| crear     | `build()`             | $$\Theta(1)$$ | Ninguna: el heap vacío cumple las dos |
| consultar | `max()`               | $$\Theta(1)$$ | Ninguna: lee `data[1]`                |
| consultar | `isEmpty()`, `size()` | $$\Theta(1)$$ | Ninguna                               |

</Slide>

<Slide title="Hacer espacio para un elemento nuevo">
Un elemento nuevo necesita la casilla `data[n + 1]`. Si el arreglo está
lleno —`n == data.length - 1`, porque `data[0]` no se usa—, esa casilla
todavía no existe. Antes de escribir hay que agrandar el arreglo con el
`resize` del arreglo dinámico: reserva un bloque del doble y copia
`data[1..n]`. Si el arreglo tiene espacio, este paso no ocurre.

<Slide title="Dónde entra un elemento nuevo">
Con espacio en el arreglo, la invariante de forma completa fija el lugar:
el elemento nuevo ocupa la posición `n + 1`, la que sigue a la última del
último nivel. Cualquier otro lugar dejaría un hueco.

<div style={{ fontSize: '0.85rem', fontWeight: 600, color: 'var(--color-ink-soft)', textAlign: 'center' }}>n = 7: el 9 entra en data[8], hijo del nodo parent(8) = 4</div>
<HeapPicture values={[10, 7, 8, 1, 3, 2, 4, 9]} hot={[8]} label="El heap de ejemplo con un 9 escrito en data[8]: en el árbol, el hijo izquierdo del nodo 4, que guarda el 1, en el último nivel." />

En el arreglo, `n + 1` es la casilla que sigue al último elemento. En el
árbol, es un hijo del nodo `parent(n + 1)`: el elemento nuevo siempre entra
como hoja. Después de escribirlo, `n` crece en uno.

</Slide>

<Slide title="La invariante que el nuevo puede romper">
Escribir en la posición `n + 1` mantiene la invariante de forma completa,
pero puede romper la de orden de heap. Y sólo en un lugar: **la arista entre
el elemento nuevo y su padre**. El nuevo es una hoja, así que no tiene hijos
con los que compararse, y ninguna otra arista cambió.

<div style={{ fontSize: '0.85rem', fontWeight: 600, color: 'var(--color-ink-soft)', textAlign: 'center' }}>el 9 es mayor que su padre, el 1: esa arista rompe la invariante</div>
<HeapPicture values={[10, 7, 8, 1, 3, 2, 4, 9]} hot={[8]} brokenEdges={[8]} label="El mismo heap con el 9 en data[8]. Si el padre es mayor o igual que el nuevo, la invariante se cumple y no hay
nada que reparar. Si es menor, hay que intercambiarlos.

</Slide>

<Slide title="Subir sin romper otra arista">
Intercambiar el elemento con su padre restaura la invariante en esa arista,
y no la rompe en ninguna de abajo:

- **El padre baja**, y queda arriba de nodos que ya estaban debajo de él
  antes de la inserción: ya era mayor o igual que ellos.
- **El elemento sube**, y queda arriba de su antiguo padre y del otro hijo
  de ese padre. Es mayor que su antiguo padre, y ese padre ya era mayor o
  igual que su otro hijo.

La única arista que puede quedar rota es la de arriba, entre el que subió y
su nuevo padre. Por eso el intercambio se repite subiendo, hasta que la
invariante se cumple o el elemento llega a la raíz.

</Slide>

<Slide title="La función auxiliar swim">
Repetir el intercambio hacia arriba es una función auxiliar, `swim`. Recibe
la posición del elemento que puede estar rompiendo la invariante de orden
de heap con su padre:

```java
void swim(int k) {
    while (k > 1 && data[parent(k)] < data[k]) {
        swap(parent(k), k);
        k = parent(k);
    }
}

void swap(int i, int j) {
    int t = data[i];
    data[i] = data[j];
    data[j] = t;
}
```

Mientras `k` no sea la raíz y su padre sea menor, los intercambia y sube con
`k = parent(k)`. Se detiene en la raíz, o en cuanto la invariante se cumple.
`swap` no lleva ninguna idea: intercambia dos casillas del arreglo.

</Slide>

<Slide title="La operación insert">
Con `swim` escrita, insertar son tres líneas, y cada una atiende una
invariante:

```java
void insert(int x) {
    if (n == data.length - 1) {
        resize(2 * data.length);
    }
    data[++n] = x;
    swim(n);
}
```

- **`resize`**: si `data[1..n]` ocupa todo el arreglo, se reserva uno del
  doble, como en el arreglo dinámico. El arreglo está lleno con
  `n == data.length - 1`, porque `data[0]` no se usa.
- **`data[++n] = x`**: el nuevo va a la primera hoja libre y `n` crece. La
  invariante de forma completa se mantiene.
- **`swim(n)`**: restaura la invariante de orden de heap desde la hoja nueva.

</Slide>

</Slide>

<Slide title="El costo de insert">
Escribir en `data[n + 1]` cuesta $$\Theta(1)$$, y `swim` sube a lo más un
nivel por vuelta. ¿Cuántos niveles puede subir? Un árbol completo duplica
sus nodos en cada nivel lleno —1, 2, 4, 8—, así que con $$N$$ nodos tiene
$$\lfloor \log_2 N \rfloor + 1$$ niveles, y el camino de una hoja a la raíz
recorre a lo más $$\lfloor \log_2 N \rfloor$$ aristas: 2 en el heap de
ejemplo, 20 en uno de un millón.

| --------- | ----------- | ------------- | ------------- | ---------------------------------------------------------- |
| modificar | <code style={{ color: 'var(--color-keep)' }}>insert(x)</code> | $$\Theta(N)$$ | <span style={{ color: 'var(--color-keep)', fontWeight: 700 }}>$$O(\log N)$$</span> | Forma completa: entra en `data[n + 1]`. Orden de heap: `swim` |

El peor caso es $$\Theta(N)$$ sólo cuando toca `resize`, que copia los
$$N$$ elementos. Repartido entre las inserciones que llenaron el arreglo,
como en el arreglo dinámico, `insert` cuesta $$O(\log N)$$ amortizado.

</Slide>

<Slide title="Por dónde sale el máximo">

invariante de forma completa. El único elemento que puede salir sin dejar
un hueco es el último, `data[n]`. Por eso son dos pasos: **se intercambia la
raíz con el último**, y después **`n` baja en uno**. El máximo queda fuera
del heap, en `data[n + 1]`, y el árbol sigue completo.

<Slide title="La invariante que el que sube puede romper">
El intercambio mantiene la invariante de forma completa, pero el elemento
que llega a la raíz viene de una hoja y suele ser chico. Puede romper la
invariante de orden de heap, y sólo en un lugar: **las aristas entre la
raíz y sus hijos**. Debajo de ellos no cambió nada.

<div style={{ fontSize: '0.85rem', fontWeight: 600, color: 'var(--color-ink-soft)', textAlign: 'center' }}>el 1 en la raíz es menor que sus dos hijos, el 9 y el 8</div>

Si la raíz es mayor o igual que sus dos hijos, la invariante se cumple y no
hay nada que reparar. Si no, hay que bajarla, intercambiándola con uno de
sus hijos.

</Slide>

<Slide title="Bajar por el hijo mayor">
¿Con cuál de los dos hijos? Con el **mayor**. El hijo que sube pasa a ser
el padre de su hermano:

- **Si sube el mayor**, queda arriba de su hermano, que es menor o igual. La
  invariante se cumple en esa arista, y sólo puede seguir rota abajo, donde
  bajó el elemento.
- **Si sube el menor**, queda arriba de un hermano mayor que él, y la
  invariante se rompe en una arista que antes no estaba rota. Bajar nunca la
  repara, porque está arriba.

<Slide title="Achicar el arreglo cuando sobra espacio">
Después de sacar, el arreglo puede quedar con demasiadas casillas vacías.
Lo resuelve `shrinkIfSparse`, la misma del arreglo dinámico, con la
implementación que tiene en la clase de arreglos: si `n` llega a un cuarto
de `data.length`, reserva un bloque de la mitad y copia `data[1..n]`. Lo que
quedaba fuera del heap no se copia. Si el arreglo sigue con suficiente uso,
este paso no ocurre.

<Slide title="La función auxiliar sink">
Repetir el intercambio hacia abajo es otra función auxiliar, `sink`. Recibe
la posición del elemento que puede estar rompiendo la invariante de orden
de heap con sus hijos:

```java
void sink(int k) {
    while (left(k) <= n) {
        int j = left(k);
        if (right(k) <= n && data[right(k)] > data[j]) {
            j = right(k);
        }
        if (data[k] >= data[j]) break;
        swap(k, j);
        k = j;
    }
}
```

Mientras `k` tenga al menos un hijo, `left(k) <= n`, la variable `j` apunta
al hijo mayor: el izquierdo, o el derecho si existe y es mayor. Si
`data[k]` ya es mayor o igual que ese hijo, la invariante se cumple y
termina. Si no, los intercambia y baja con `k = j`.

</Slide>

<Slide title="La operación extractMax">
Con `sink` escrita, cada línea de `extractMax` atiende una invariante:

```java
int extractMax() {
    if (n == 0) {
        throw new NoSuchElementException();
    }
    int max = data[1];
    swap(1, n);
    n--;
    sink(1);
    shrinkIfSparse();
    return max;
}
```

- **`swap(1, n)` y `n--`**: el máximo sale por la última hoja. La invariante
  de forma completa se mantiene.
- **`sink(1)`**: restaura la invariante de orden de heap desde la raíz.
- **`shrinkIfSparse()`**: la misma función del arreglo dinámico, con la
  implementación que tiene en la clase de arreglos. Si `n` llega a un
  cuarto de `data.length`, el arreglo se achica a la mitad, y así nunca
  ocupa más de cuatro veces el espacio que necesita.

Sobre un heap vacío no hay máximo que sacar, y la guarda lo dice con
`NoSuchElementException`.

</Slide>

</Slide>

El heap que dejó la inserción del 9 entrega su máximo, el 10. La última
hoja, el 1, sube a la raíz y baja dos niveles por el camino de los hijos

<Slide title="Una seguidilla de extracciones">
El mismo heap entrega sus ocho elementos, del mayor al menor. Cuando `n`

</Slide>

<Slide title="El costo de extractMax">
El intercambio de la raíz con la última hoja y el `n--` cuestan
$$\Theta(1)$$. Después, `sink` baja a lo más un nivel por vuelta, y en cada
nivel hace una cantidad constante de trabajo: elegir el hijo mayor,
compararlo y, si hace falta, intercambiar.

<div style={{ fontSize: '0.85rem', fontWeight: 600, color: 'var(--color-ink-soft)', textAlign: 'center' }}>el 1 bajó de la raíz a una hoja: 2 aristas, la altura ⌊log₂ 7⌋ = 2</div>
<HeapPicture values={[9, 7, 8, 1, 3, 2, 4]} view="tree" levelLines levelColors heightRuler idPrefix="pq-alt-ext" hot={[1, 2, 4]} label="A la izquierda, una línea de la raíz al último nivel rotulada altura = piso de logaritmo en base 2 de n. El heap después de extraer el 10, con sus tres niveles marcados. El camino que recorrió el 1, de la raíz a la posición 4, resaltado: dos aristas, una por nivel." />

¿Cuántos niveles puede bajar? En un árbol completo de $$N$$ nodos, el
camino de la raíz a una hoja tiene a lo más $$\lfloor \log_2 N \rfloor$$
aristas, así que `sink` cuesta $$O(\log N)$$.

Queda `shrinkIfSparse`. Cuando achica, copia los $$N$$ elementos, y esa
extracción cuesta $$\Theta(N)$$; repartido entre las extracciones que
dejaron vacíos tres cuartos del arreglo, como en el arreglo dinámico,
cuesta $$\Theta(1)$$ amortizado. En total, `extractMax` cuesta
$$\Theta(N)$$ en el peor caso y $$O(\log N)$$ amortizado.

</Slide>

<Slide title="Costos de las operaciones del heap">
Las operaciones del contrato sobre el heap, cada una con la invariante que
restaura:

| Molde     | Operación             | Peor caso     | Amortizado    | Invariante que restaura                                         |
| --------- | --------------------- | ------------- | ------------- | --------------------------------------------------------------- |
| crear     | `build()`             | $$\Theta(1)$$ | $$\Theta(1)$$ | Ninguna: el heap vacío cumple las dos                           |
| consultar | `max()`               | $$\Theta(1)$$ | $$\Theta(1)$$ | Ninguna: lee `data[1]`                                          |
| consultar | `isEmpty()`, `size()` | $$\Theta(1)$$ | $$\Theta(1)$$ | Ninguna                                                         |
| modificar | <code style={{ color: 'var(--color-keep)' }}>insert(x)</code> | $$\Theta(N)$$ | <span style={{ color: 'var(--color-keep)', fontWeight: 700 }}>$$O(\log N)$$</span> | Forma completa: entra en `data[n + 1]`. Orden de heap: `swim` |
| modificar | <code style={{ color: 'var(--color-keep)' }}>extractMax()</code> | $$\Theta(N)$$ | <span style={{ color: 'var(--color-keep)', fontWeight: 700 }}>$$O(\log N)$$</span> | Forma completa: sale `data[n]`. Orden de heap: `sink` |

Las consultas no cambian nada. Las dos operaciones que modifican el heap
mantienen la invariante de forma completa por donde entran y salen, y
restauran la de orden de heap recorriendo un solo camino.

</Slide>

<Slide title="El heap frente a las dos listas">
Las dos listas obligaban a elegir qué operación sería lenta. El heap no
elige:

| Implementación  | `insert(x)`   | `extractMax()` | `max()`       |
| --------------- | ------------- | -------------- | ------------- |
| Lista sin orden | $$\Theta(1)$$ | $$\Theta(N)$$  | $$\Theta(N)$$ |
| Lista ordenada  | $$\Theta(N)$$ | $$\Theta(1)$$  | $$\Theta(1)$$ |
| **Heap**        | <span style={{ color: 'var(--color-keep)', fontWeight: 700 }}>$$O(\log N)$$</span> | <span style={{ color: 'var(--color-keep)', fontWeight: 700 }}>$$O(\log N)$$</span> | $$\Theta(1)$$ |

El heap no es el más rápido en ninguna columna por separado:

- la lista sin orden inserta más rápido, en $$\Theta(1)$$;
- la lista ordenada extrae más rápido, también en $$\Theta(1)$$.

</Slide>

<Slide title="Muchas operaciones mezcladas">
Una cola de prioridad no hace una sola operación: mezcla inserciones y
extracciones. Con $$N$$ de cada una, el costo total es:

| Implementación  | Costo total         | Con un millón de cada una |
| --------------- | ------------------- | ------------------------- |
| Lista sin orden | $$\Theta(N^2)$$     | unos 500 000 millones de pasos |
| Lista ordenada  | $$\Theta(N^2)$$     | unos 500 000 millones de pasos |
| **Heap**        | <span style={{ color: 'var(--color-keep)', fontWeight: 700 }}>$$O(N \log N)$$</span> | <span style={{ color: 'var(--color-keep)', fontWeight: 700 }}>unos 40 millones de pasos</span> |

Ahí gana el heap: ninguna de sus operaciones es lenta.

</Slide>

## El min-heap

<Slide title="La invariante de orden de heap invertida">
Un **min-heap** es un heap con la primera invariante dada vuelta: **el valor
de cada nodo es menor o igual que los valores de sus hijos.** Siguiendo
cualquier camino hacia arriba los valores nunca suben, así que en la raíz
queda el **mínimo**.

<HeapPicture values={[2, 5, 3, 9, 6]} view="tree" label="Un min-heap de cinco nodos. La raíz es 2; sus hijos son 5 y 3; los hijos de 5 son 9 y 6. Cada nodo es menor o igual que sus hijos." />

Todo lo demás es idéntico: la invariante de forma completa, el arreglo desde 1, la
aritmética de índices, `swim` y `sink`. Lo único que cambia es el sentido
de las tres comparaciones que deciden si un nodo sube o baja:

```java
data[k / 2] > data[k]     // swim: sube mientras el padre sea mayor
data[j] > data[j + 1]     // sink: j pasa al hijo menor
data[k] <= data[j]        // sink: se detiene si k ya es menor o igual
```

El contrato cambia de nombre y no de forma: `min()` y `extractMin()` en
lugar de `max()` y `extractMax()`, con los mismos costos.

</Slide>

<Slide title="Un min-heap para una simulación por eventos">
Una simulación por eventos guarda cada evento futuro con el instante en que
ocurre, y avanza siempre procesando **el más próximo**. La prioridad más
alta es el tiempo **menor**, y eso es un min-heap.

Si los eventos pendientes ocurren en los instantes 9, 2, 6, 3 y 5, el heap
los guarda así:

<HeapPicture values={[2, 3, 6, 9, 5]} label="Un min-heap de instantes: 2 en la raíz, 3 y 6 como sus hijos, 9 y 5 como hijos del 3. En el arreglo, data[1] a data[5] guardan 2, 3, 6, 9 y 5, y data[0] no se usa." />

`extractMin()` entrega el 2, el evento que ocurre primero. Procesarlo suele
crear eventos nuevos, más adelante en el tiempo, y cada uno entra con
`insert` en $$O(\log N)$$. La simulación nunca ordena la lista entera de
eventos: sólo necesita saber, en cada momento, cuál viene.

</Slide>

## PriorityQueue en Java

<Slide title="La clase PriorityQueue">
Java trae una cola de prioridad en `java.util.PriorityQueue`: un heap
binario guardado en un arreglo. Tiene una diferencia que sorprende la
primera vez: **es un min-heap**. Sin más indicación, `poll()` devuelve el
menor.

```java
PriorityQueue<Integer> pq = new PriorityQueue<>();
pq.add(5);
pq.add(1);
pq.add(8);

int first = pq.poll();   // 1: el menor, no el primero que entró
```

Los nombres del TDA en la clase de Java:

| TDA            | `PriorityQueue`     |
| -------------- | ------------------- |
| `insert(x)`    | `add(x)`            |
| `min()`        | `peek()`            |
| `extractMin()` | `poll()`            |
| `isEmpty()`    | `isEmpty()`         |
| `size()`       | `size()`            |

Sobre una cola vacía, `peek()` y `poll()` **no** lanzan una excepción:
devuelven `null`. Con `Integer`, guardar ese `null` en un `int` sí la lanza,
así que preguntar `isEmpty()` antes sigue siendo trabajo de quien usa la
cola.

</Slide>

<Slide title="Un max-heap con Comparator.reverseOrder">
Para que `poll()` devuelva el mayor, el constructor recibe un
**`Comparator`** que invierte el orden natural:

```java
PriorityQueue<Integer> pq =
    new PriorityQueue<>(Comparator.reverseOrder());
pq.add(5);
pq.add(1);
pq.add(8);

int first = pq.poll();   // 8: ahora sale el mayor
```

La clase no cambia. `PriorityQueue` siempre saca el que el comparador
considera menor, y `reverseOrder()` hace que el mayor de los enteros sea
el menor para el comparador. Es la misma idea que el min-heap: el heap es
uno solo, lo que se invierte es la comparación.

</Slide>

<Slide title="Prioridad según un criterio propio">
Los elementos de una cola de prioridad casi nunca son números sueltos. Son
objetos, y la prioridad es uno de sus campos. El comparador dice cuál de
los campos, y en qué sentido:

```java
class Task {
    String name;
    int urgency;

    Task(String name, int urgency) {
        this.name = name;
        this.urgency = urgency;
    }
}

PriorityQueue<Task> tasks = new PriorityQueue<>(
    (a, b) -> Integer.compare(b.urgency, a.urgency));
tasks.add(new Task("respaldo", 2));
tasks.add(new Task("caída del servidor", 9));
tasks.add(new Task("informe", 5));

Task next = tasks.poll();   // la de urgencia 9
```

Comparar `b` con `a`, y no `a` con `b`, es lo que convierte al min-heap de
Java en un max-heap por urgencia. Más ejemplos de comparadores sobre
`PriorityQueue`, en
[este gist](https://gist.github.com/so77id/b78952de9dc850446ab7d1507692cb18).

</Slide>

<Slide title="Costos de PriorityQueue">
La documentación de `PriorityQueue` da los mismos costos que el heap de esta
clase, porque es el mismo heap:

| Operación                | Costo          |
| ------------------------ | -------------- |
| `add(x)`, `poll()`       | $$O(\log N)$$  |
| `peek()`, `size()`       | $$\Theta(1)$$  |
| `contains(x)`, `remove(x)` | $$\Theta(N)$$ |

La última fila es la que el orden débil cobra. Buscar un elemento cualquiera
no tiene atajo, porque el heap sólo sabe dónde está el mínimo: el resto del
arreglo hay que recorrerlo.

Por la misma razón, **imprimir una `PriorityQueue` no la muestra ordenada**.
`System.out.println(pq)` recorre el arreglo en el orden en que está guardado,
que sólo cumple la invariante de orden de heap. Lo único garantizado es que el
primero es el menor.

</Slide>

## HeapSort

<Slide title="Ordenar con un heap">
Si a un max-heap se le pide `extractMax` $$N$$ veces, los elementos salen
del mayor al menor: es un algoritmo de ordenamiento. Cada extracción cuesta
$$O(\log N)$$, así que ordenar cuesta $$O(N \log N)$$.

Lo que lo vuelve interesante es **dónde queda cada máximo**. `extractMax`
lo intercambia con `data[n]` y baja `n`: el máximo queda justo después del
heap, en una casilla que el heap ya no usa. Esa casilla es exactamente la
que le corresponde en el arreglo ordenado de menor a mayor. Repetido, el
arreglo se parte en dos zonas, el heap al frente y la parte ordenada al
final, y la segunda crece mientras la primera se achica.

Por eso **HeapSort** ordena el arreglo **en su lugar**, sin un segundo
arreglo, en dos fases: primero convierte el arreglo desordenado en un heap,
y después extrae hasta vaciarlo.

</Slide>

<Slide title="La fase de construcción">
La primera fase convierte `data[1..n]` en un heap. Las hojas ya lo son,
porque un nodo sin hijos cumple la invariante de orden de heap. Basta entonces con
aplicar `sink` a cada nodo que tiene hijos, desde el último de ellos,
`n / 2`, hasta la raíz:

```java
for (int k = n / 2; k >= 1; k--) {
    sink(k);
}
```

Recorrer de abajo hacia arriba es lo que hace funcionar el ciclo: cuando
`sink(k)` corre, los dos subárboles de `k` ya son heaps, y sólo falta ubicar
a `k`. Sobre 5, 2, 9, 1, 7, 3, 8, 4:

<Slide title="La fase de ordenamiento">
La segunda fase es `extractMax` sin devolver nada. El máximo se intercambia
con `data[n]`, `n` baja, y la nueva raíz se hunde:

```java
while (n > 1) {
    swap(1, n);
    n--;
    sink(1);
}
```

Cada vuelta deja un elemento más en su lugar definitivo, al final del
arreglo. Cuando `n` llega a 1, el único que queda en el heap es el menor, y
también está en su lugar.

<HeapPicture values={[9, 7, 8, 4, 2, 3, 5, 1]} view="array" label="El heap entero: data[1..8] = 9, 7, 8, 4, 2, 3, 5, 1. Nada ordenado todavía." />
<HeapPicture values={[8, 7, 5, 4, 2, 3, 1, 9]} n={7} view="array" label="Tras una vuelta: el 9 quedó en data[8], ordenado, y data[1..7] = 8, 7, 5, 4, 2, 3, 1 es de nuevo un heap." />
<HeapPicture values={[7, 4, 5, 1, 2, 3, 8, 9]} n={6} view="array" label="Tras dos vueltas: 8 y 9 ordenados al final, y data[1..6] = 7, 4, 5, 1, 2, 3 es un heap." />
<HeapPicture values={[1, 2, 3, 4, 5, 7, 8, 9]} n={0} view="array" label="Al terminar: el arreglo completo 1, 2, 3, 4, 5, 7, 8, 9, ordenado de menor a mayor." />

La zona ordenada crece desde el final, y siempre contiene los
mayores: cada valor que entra ahí es el máximo de lo que quedaba en el
heap.

</Slide>

<Slide title="HeapSort paso a paso">
Las dos fases sobre 5, 2, 9, 1, 7, 3, 8, 4: el árbol pierde una hoja por
vuelta y el arreglo conserva todas sus casillas.

<SequenceStepper eda="heap-max" operation="heapsort" values={[5, 2, 9, 1, 7, 3, 8, 4]} />

</Slide>

El listado es un método del heap: usa su `n` y su `sink`, el mismo `sink`
de `extractMax`. La versión de biblioteca recibe el arreglo como parámetro y
hace exactamente lo mismo.


<Slide title="El costo de HeapSort">
Las dos fases cuestan distinto.

- **Construcción: $$O(N)$$.** Es menos de lo que sugiere contar $$N/2$$
  llamadas a `sink` de costo $$O(\log N)$$: la mayoría de los nodos está
  cerca de las hojas y baja muy poco. Sedgewick demuestra que la
  construcción hace menos de $$2N$$ comparaciones; aquí lo usamos sin
  demostrarlo.
- **Ordenamiento: $$O(N \log N)$$.** Son $$N - 1$$ vueltas, y cada `sink`
  desde la raíz recorre a lo más la altura, $$\lfloor \log_2 N \rfloor$$
  niveles.

En total, **$$O(N \log N)$$ en el peor caso**, sin excepciones. Quicksort
es más rápido en promedio, pero su peor caso es $$\Theta(N^2)$$; HeapSort no
tiene entrada que lo lleve ahí.

La memoria extra es $$\Theta(1)$$: una variable para el intercambio y los
índices. El heap vive dentro del mismo arreglo que se ordena.

</Slide>

<Slide title="HeapSort y mergesort">
Los dos ordenan en $$O(N \log N)$$ en el peor caso. Se diferencian en lo que
cobran por eso:

| Propiedad                 | HeapSort          | Mergesort                  |
| ------------------------- | ----------------- | -------------------------- |
| Peor caso                 | $$O(N \log N)$$   | $$O(N \log N)$$            |
| Memoria extra             | $$\Theta(1)$$     | $$\Theta(N)$$              |
| Estable                   | no                | sí                         |

HeapSort no necesita un segundo arreglo. Mergesort sí, y a cambio es
**estable**: dos elementos iguales salen en el orden en que entraron.
HeapSort no lo garantiza, porque `sink` y el intercambio con `data[n]`
mueven elementos a lo largo de todo el arreglo sin mirar su posición
original. Cuando los elementos son registros ordenados por un campo, esa
diferencia decide cuál usar.

</Slide>

<Slide title="Lo que el orden débil no responde">
El heap es rápido para una sola pregunta, cuál es el máximo, y lo es porque
guarda el orden más débil que la responde. Cualquier otra pregunta sobre el
orden le sale cara: **buscar un valor cualquiera es $$\Theta(N)$$**, y
recorrer los elementos de menor a mayor exige desarmarlo.

La causa es la invariante de **forma completa**. Obliga a que cada valor quede donde toca
llenar el árbol, no donde lo ubicaría su valor, y por eso dos hermanos
nunca se comparan.

¿Qué pasa si se abandona? Un árbol binario que acomoda cada nodo según su
valor —los menores hacia un lado, los mayores hacia el otro— puede
**buscar** bajando por un solo camino, y recorrer sus valores en orden sin
destruirlo. El precio es la altura: sin la invariante de forma completa nada garantiza
$$\lfloor \log_2 N \rfloor$$ niveles, y el árbol puede degenerar en una
fila tan larga como la lista. Tampoco cabe ya en un arreglo sin huecos:
necesita punteros entre nodos.

Esa es la estructura general de la que el heap es un caso particular: el
**árbol binario**.

</Slide>

## Ejercicios

<Slide title="Problemas resueltos y propuestos">
Dos problemas resueltos completos, cada uno en cinco pasos: el problema, por
qué no es trivial, la idea, el código y dónde falla.

- **Top-K de una secuencia**: los $$K$$ mayores de una secuencia larga, sin
  guardarla entera.
- **Un planificador de tareas**: atender por urgencia sin perder el orden de
  llegada entre tareas igual de urgentes.

Después, en el libro, dos problemas propuestos con su solución: el
**k-ésimo mayor** de un arreglo y la **verificación de un max-heap**.

</Slide>

<Slide title="Los K mayores de una secuencia">
Un servidor registra el tiempo de respuesta de cada solicitud, millones al
día, y al final del día hay que informar los $$K$$ más lentos. Los tiempos
llegan de a uno y no se pueden volver a pedir.

El programa recibe $$K$$ y la secuencia, y devuelve los $$K$$ valores
mayores ordenados de mayor a menor:

```java
int[] topK(int k, int[] stream)
```

**Entrada.** `k`, mayor que cero; `stream`, con a lo más 10⁶ números. Los
valores se pueden repetir.

**Salida.** Los `k` mayores de `stream`, de mayor a menor. Si `stream` tiene
menos de `k` números, todos ellos, de mayor a menor.

| `k` | `stream`              | resultado |
| --- | --------------------- | --------- |
| `3` | `5 1 9 3 7 2 8`       | `9 8 7`   |
| `2` | `6 6 1`               | `6 6`     |
| `2` | `4`                   | `4`       |
| `1` | (vacío)               | (vacío)   |

</Slide>

<Slide title="Ordenar la secuencia entera">
Lo primero que se piensa es guardar todos los números, ordenarlos y tomar
los primeros $$K$$. Da el resultado correcto, y cobra dos cosas que el
problema no necesita.

Cuesta $$\Theta(N \log N)$$, cuando sólo interesan $$K$$ posiciones del
orden. Y ocupa $$\Theta(N)$$ de memoria: con un millón de tiempos por día
hay que tener el millón guardado al mismo tiempo, para quedarse con tres.

Guardar todo en un max-heap y extraer $$K$$ veces mejora el tiempo pero no
la memoria: el heap también tiene los $$N$$ adentro.

</Slide>

<Slide title="El peor de los K mejores">
Basta con recordar, en cada momento, **los $$K$$ mejores vistos hasta
ahora**. Cuando llega un número nuevo, la única pregunta es si merece entrar
entre ellos, y eso depende de un solo valor: **el peor de los $$K$$**. Si el
nuevo es mayor que ese peor, lo reemplaza; si no, se descarta sin mirar a
los otros.

Lo que hay que tener a mano es entonces el **mínimo** de un grupo de $$K$$
números que cambia a cada rato: sacarlo, agregar otro, y volver a saber cuál
es el mínimo. Eso es un **min-heap de tamaño $$K$$**.

A mano, con $$K = 3$$ sobre `5 1 9 3 7 2 8`: los tres primeros entran sin
preguntar, `{1, 5, 9}`. Llega 3, mayor que el peor, 1: sale 1, entra 3. Llega
7, mayor que 3: sale 3, entra 7, y queda `{5, 7, 9}`. Llega 2, menor que 5:
se descarta. Llega 8, mayor que 5: queda `{7, 8, 9}`.

</Slide>

<Slide title="Top-K · la solución">
`PriorityQueue` sin comparador es el min-heap que la idea pide, y `peek()`
es su peor elemento. Al final, el heap guarda los $$K$$ mayores y los
entrega del menor al mayor, así que se escriben en el arreglo de atrás hacia
adelante.

<Slide title="Las secuencias más cortas que K">
Si la secuencia tiene menos de $$K$$ números, la primera rama es la única que
corre: todos entran, ninguno se compara, y el resultado tiene el largo del
heap, no $$K$$. Con `k = 2` sobre `4` devuelve `4`; sobre la secuencia vacía
devuelve un arreglo vacío. Los repetidos no necesitan un caso aparte: con
`6 6 1` el segundo 6 entra por la primera rama y el 1 no supera al peor.

Con `k` en cero el heap nunca tendría dónde guardar el primer número, y
`peek()` devolvería `null` sobre un heap vacío. La función lo rechaza de
entrada con `IllegalArgumentException`.

Cada número cuesta un `peek()`, $$\Theta(1)$$, y a lo más un `poll()` y un
`add()` sobre un heap de $$K$$, $$O(\log K)$$: **$$O(N \log K)$$** en total.
El heap nunca guarda más de $$K$$ números, así que la memoria es
**$$\Theta(K)$$**, sin importar cuán larga sea la secuencia.

</Slide>

<Slide title="Un planificador de tareas">
Un sistema recibe tareas con un nombre y una **urgencia**, un entero donde
más es más urgente, y las atiende de a una. La regla del sistema tiene dos
partes: primero la más urgente, y **entre dos igual de urgentes, la que
llegó antes**.

El programa recibe las tareas en el orden en que llegaron y devuelve el
orden en que se atienden:

```java
String[] schedule(String[] names, int[] urgency)
```

**Entrada.** Dos arreglos del mismo largo, a lo más 10⁵: `names[i]` y
`urgency[i]` son la tarea que llegó en el lugar `i`.

**Salida.** Los nombres en el orden de atención.

| `names`                                          | `urgency`   | resultado                                       |
| ------------------------------------------------ | ----------- | ----------------------------------------------- |
| `respaldo caída informe correo parche`           | `2 9 5 5 9` | `caída parche informe correo respaldo`          |
| `a b`                                            | `1 1`       | `a b`                                           |
| (vacío)                                          | (vacío)     | (vacío)                                         |

</Slide>

<Slide title="Comparar sólo por urgencia">
Lo primero que se piensa es la `PriorityQueue` de tareas con un comparador
por urgencia, la de mayor primero. Atiende bien a las urgentes, y falla en
los empates.

Sobre `respaldo caída informe correo parche`, con urgencias `2 9 5 5 9`,
`java.util.PriorityQueue` entrega:

```
caída  parche  correo  informe  respaldo
```

`informe` y `correo` tienen la misma urgencia, e `informe` llegó antes. El
heap los entregó al revés. No es un error de Java: el comparador dice que
son iguales, y un heap **no es estable**. `sink` y los intercambios con la
última hoja mueven elementos sin mirar cuándo llegaron, así que entre dos
iguales cualquiera de los dos puede salir primero.

</Slide>

<Slide title="El orden de llegada como desempate">
Si dos tareas empatan en urgencia, lo que las distingue es **cuándo
llegaron**, y eso ya está en los datos: es su posición en la entrada. Basta
con que el comparador lo use como segundo criterio. Primero la urgencia, de
mayor a menor; si empatan, el número de llegada, de menor a mayor.

Con ese comparador ya no hay dos tareas iguales: cada una tiene un número de
llegada distinto. El heap sigue sin ser estable, pero ya no tiene empates
que desordenar.

A mano, sobre el ejemplo: `caída` y `parche` empatan en 9 y `caída` llegó
en el lugar 1, antes que `parche`, en el 4; `informe` y `correo` empatan en 5
y llegaron en los lugares 2 y 3. El orden es `caída parche informe correo
respaldo`.

</Slide>

<Slide title="Planificador · la solución">
El heap guarda **números de llegada**, no tareas. El índice `i` es a la vez
el número de llegada y la posición de la tarea en los dos arreglos, así que
el comparador lee la urgencia desde ahí.

```java
static String[] schedule(String[] names, int[] urgency) {
    if (names.length != urgency.length) {
        throw new IllegalArgumentException();
    }
    PriorityQueue<Integer> pending = new PriorityQueue<>(
        (a, b) -> urgency[a] != urgency[b]
            ? Integer.compare(urgency[b], urgency[a])
            : Integer.compare(a, b));
    for (int i = 0; i < names.length; i++) {
        pending.add(i);
    }
    String[] order = new String[names.length];
    for (int t = 0; t < order.length; t++) {
        order[t] = names[pending.poll()];
    }
    return order;
}
```

`Integer.compare(urgency[b], urgency[a])`, con `b` primero, ordena de mayor
a menor; `Integer.compare(a, b)` desempata de menor a mayor. Sobre el
ejemplo, los números de llegada salen 1, 4, 2, 3, 0, que son `caída`,
`parche`, `informe`, `correo` y `respaldo`.

</Slide>

<Slide title="Los empates y la entrada vacía">
El caso que el primer intento rompía es el que el desempate cubre: con
`a b` y urgencias `1 1`, los dos empatan en urgencia y `a` llegó en el
lugar 0, así que sale primero. Sin el desempate, cuál sale primero dependería
de cómo quedó armado el heap.

Con la entrada vacía ningún ciclo corre y se devuelve un arreglo vacío. Con
arreglos de distinto largo no hay una tarea `i` bien definida, y la función
lo rechaza con `IllegalArgumentException`.

Cada una de las $$N$$ tareas entra y sale del heap una vez, a
$$O(\log N)$$ cada operación: **$$O(N \log N)$$** en total. El heap guarda
los $$N$$ números de llegada, y el resultado $$N$$ nombres: **$$\Theta(N)$$**
de memoria.

</Slide>

```java solution
import java.util.PriorityQueue;

class Solution {

    static int kthLargest(int k, int[] data) {
        if (k < 1 || k > data.length) {
            throw new IllegalArgumentException();
        }
        PriorityQueue<Integer> best = new PriorityQueue<>();
        for (int x : data) {
            if (best.size() < k) {
                best.add(x);
            } else if (x > best.peek()) {
                best.poll();
                best.add(x);
            }
        }
        return best.peek();
    }
}
```

<Exercise title="La verificación de un max-heap">

La función recibe un arreglo guardado como heap desde 1 —`data[0]` sin usar
y los elementos en `data[1..n]`— y decide si cumple el orden de max-heap.

```java
boolean isMaxHeap(int[] data, int n)
```

`n` está entre 0 y `data.length - 1`. Un heap con cero o un elemento
siempre cumple el orden. No hace falta comparar cada nodo con sus dos hijos:
alcanza con comparar cada posición `k`, de 2 a `n`, con su padre `k / 2`.
El costo esperado es $$\Theta(n)$$.

```java starter
class Solution {

    static boolean isMaxHeap(int[] data, int n) {
        return false;
    }
}
```

```java test

check(Solution.isMaxHeap(new int[] {0, 10, 7, 8, 1, 9}, 5), false);
```

```java solution
class Solution {

    static boolean isMaxHeap(int[] data, int n) {
        for (int k = 2; k <= n; k++) {
            if (data[k / 2] < data[k]) {
                return false;
            }
        }
        return true;
    }
}
```

## Lo que sigue

El heap es un **árbol binario** con dos invariantes: la forma completa y el
orden de heap. Gracias a ellas cabe en un arreglo y encuentra su máximo sin
buscarlo; por ellas mismas no sirve para ninguna otra pregunta sobre el
orden.

La próxima clase estudia el árbol binario sin esas restricciones, como
estructura general: nodos enlazados con punteros a sus hijos, las formas de
recorrerlo —preorden, inorden, postorden— y cuánto puede crecer su altura
cuando nada la controla. Es la base de los árboles de búsqueda, que ordenan
los valores de izquierda a derecha para poder encontrar cualquiera de ellos,
no sólo el máximo.
