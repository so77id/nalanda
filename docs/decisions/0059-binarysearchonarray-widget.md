# ADR-0059: `<BinarySearchOnArray>` — the binary-search visualiser

**Status:** Accepted
**Date:** 2026-08-31
**Decision-makers:** Miguel Rodriguez
**Covers:** the introduction of `<BinarySearchOnArray>`, the widget that
traces the classical binary-search algorithm step by step on a sorted array
authored inline in a course document · the layout choice (code panel on top,
array visualisation below, controls at the foot — one column) · the decision
to compose `<CodeStepper>` for the code panel rather than reimplement code
highlighting from scratch · the outcome panel that emphasises the STEP COUNT
in both found and not-found paths, because the pedagogical point is that
they take the same number of comparisons
**Source:** Issue #266 — Course document "Diseño de Algoritmos · Divide y
Conquista". Block 2 of the deck introduces binary search as the first D&C
example and needs a widget that shows the algorithm running on a specific
array with `lo`, `mid`, `hi` visible on the cells and the corresponding code
line highlighted as each iteration decides.

## Context

Binary search is the deck's simplest D&C example: one recursive subcall per
call, constant combine work, `Θ(log n)` closed form. The `<RecursionTree
Divide recipe="binary-search">` widget already draws the recursion tree and
the cost breakdown. What is missing is the *other* half of the story — what
the algorithm *does* on a real array. A reader looking at the tree learns
why the cost is logarithmic; a reader looking at the trace learns how the
loop actually shrinks the range at every step.

The class also uses this widget to make a subtler point: binary search
takes the same number of comparisons whether the target is present or
absent — the loop runs until `lo > hi`, and the outcome is decided by
which branch the last comparison took. Emphasising this in the outcome
panel matters because students, before they see it, will assume "not
found" costs more.

The repository already has `<CodeStepper>` (CodeMirror in read-only mode
with a `highlightLines` prop) — the primitive `<CallStack>`, `<FibMemoSteps>`,
`<HanoiPlayground>` all compose. Reimplementing code highlighting for this
widget would duplicate a known-good primitive and diverge on the first
convention change (dim-line policy, hover behaviour, active-line paint).

## Decision

**1. One widget, one layout: code on top, array below, controls at the foot.**
The code panel is the reader's anchor — it names what each step is doing.
The array visualisation shows the effect (lo/mid/hi over the cells, the
range in-focus painted). The panel between them narrates the current step
in Spanish prose (`a[mid] = 19 < 22 → lo = mid + 1`). The controls sit
under everything: Atrás | Paso | Play/Pausa | Reset.

**2. Compose `<CodeStepper>` for the code panel** — do not reimplement.
This is the same choice `<CallStack>`, `<HanoiPlayground>` and the three
`<Fib*Steps>` widgets made in Peli 2. The listing is `int busquedaBinaria
(int[] a, int t)` in the classical form, hardcoded in the component (not
authorable), because the pedagogical narration is tied to specific line
numbers.

**3. The widget is lazy.** Composing `<CodeStepper>` pulls CodeMirror +
`useGrammar('java')`. The MDX map is evaluated eagerly, so a
`LazyBinarySearchOnArray.tsx` wrapper is registered instead of the real
component, and a per-name architecture-test case guards that no other
importer reaches the real component (same shape as the other lazy widgets
in this feature).

**4. Trace is generated by a pure function `tracesBinarySearch(values,
target)`.** Exported so a suite test can pin the trace shape without the
DOM, and so a future reuse (e.g. a `<PredictOutput>` seeded with the trace)
can share the same events. The step list carries `lo`, `mid`, `hi`,
`comparison`, `description` and the `highlightLines` for the code panel
per step — one shape for playback, one shape for the outcome.

**5. Outcome panel emphasises the step count in both branches.**

- Found: `✓ 22 encontrado en índice 5 — buscar 22 tomó 3 pasos.`
- Not found: `✗ 20 no está en el arreglo — buscar 20 requirió 3 pasos igual
  que un caso encontrado.`

The wording of the not-found path deliberately says *"igual que un caso
encontrado"*: the equivalence is the point the deck wants to land. A
student who tries a target absent from the array walks away with the
observation, not the assumption.

**6. Author-facing errors before render.** `values` must be a strictly
increasing non-empty array of integers; a repeat or a descent is refused
with the offending pair called out. `target` must be an integer. The
widget renders no UI until both preconditions are met, so a document that
mistyped a value gets an authoring message rather than a wrong trace.

**7. Play does not loop.** Single pass — the widget stops on the last
step so the outcome panel is what the reader sees. If Play is pressed when
the trace has already finished, the widget rewinds to step 0 first, then
plays. Matches the `<CallStack>` and `<HanoiPlayground>` playback
convention.

**8. Playback speed is 0.5× / 1× / 2× (default 1×).** The `speed` prop is
public and MDX-authorable. Tuning the exact speed is a deck-side decision
Miguel iterates on in S7.

## Alternatives considered

**Reimplement the code panel with a plain `<pre>` and a manual per-line
highlight.** Rejected on the same grounds as ADR-0054's `<CallStack>`
composed `<CodeStepper>` and ADR-0055's `<HanoiPlayground>` did: the code
panel a course reader sees must read the same everywhere — the java
grammar, the theme-keyed line background, the active-line data attribute
— and reimplementing it would let those diverge. The lazy cost is
shared across the family.

**Author-supplied code listing.** Rejected: the widget's narration is tied
to specific line numbers (`if (a[mid] == t) return mid;` is line 5). An
author-supplied listing would either force the author to know those line
numbers, or force the widget to search for anchor patterns in the source
— either way, the coupling is stronger, not weaker, than a hardcoded
listing.

**Show only the current step's decision on the array (no lo/mid/hi
markers).** Rejected: without the markers, the mid=(lo+hi)/2 arithmetic
is invisible on the cells, and the reader has to cross-reference the code
panel every step to know what index the algorithm just looked at. The
markers make each iteration self-contained.

**Auto-play loop.** Rejected: the outcome panel is what the reader needs
to see at the end. A loop would erase it every 3-4 seconds; a reader who
looked away would miss it. Single pass is what the whole widget family
(CallStack, HanoiPlayground) does, and for the same reason.

**Show target hit-count and iteration index only.** Rejected: the widget
was born to show that BS runs in `O(log n)` on real data. Removing the
visualisation collapses it to a text-only demo which the prose already
does better.

## Consequences

**Widget count for issue #266.** This is the second of five new widgets;
five ADRs (0058-0062). Same shape as the axis widget: five new files
(`.tsx`, `.test.tsx`, `.catalog.tsx`, `lazy*.tsx`, and this ADR).

**Reader payload.** BS visualiser pulls CodeMirror + java grammar the
first time a page mounts it — same weight already paid by any page using
`<CodeEditor>`, `<CallStack>`, `<FibMemoSteps>`, `<HanoiPlayground>` or a
Java fence. Pages that never mount one pay nothing (the lazy wrapper +
architecture-test guard is the whole point).

**Test coverage.** Three groups of tests:
- The pure engine (`tracesBinarySearch`): classical trace, not-found
  trace, off-by-one at both ends of the array.
- Interactive behaviour: initial state, step advance, rewind, reset,
  outcome for found + not-found. `<CodeStepper>` is stubbed (jsdom paints
  no syntax highlighting) so the widget's ask ("highlight lines X, Y")
  is verifiable via `data-highlight-lines`.
- Authoring errors: missing `values`, non-monotone `values`, missing
  `target`.

Colour and the theme-keyed active-line paint are the S7 browser check's
job (same shape `<CodeStepper>` earned in ADR-0054).

**No package.json change.** Widget lives entirely in
`apps/web/src/components/interactive/`; no new dependency (lucide-react
and CodeMirror already ship for the sibling widgets).
