## Problem

Per decision I, the only way a student becomes a Nalanda user is via admin pre-enrollment: the admin pastes a list of emails + chooses a course version, the backend creates `users` rows for any unknown email, creates `enrollments` rows, and sends an invite email per new enrollment. Without this endpoint, S4.1's tables stay empty and no student can log in via S4.2. This spec closes that loop with both backend handler and a minimal frontend admin UI.

## Goals

- Backend endpoint `POST /api/admin/enrollments` accepting `{course_version_id, emails: [...]}`. For each email: find-or-create user with `role='student'` and `display_name=NULL`, create enrollment (idempotent), enqueue invite email via S4.3.
- Response details per-email outcome: `created`, `already_enrolled`, `email_failed`. Whole request is best-effort partial-success (one bad email does not abort the rest).
- The endpoint is gated by `auth.RequireRole("admin")` from S4.2.
- Minimal frontend admin UI at `/admin/enrollments`: a `<textarea>` for emails (one per line or comma-separated), a course-version selector (placeholder — in MVP this is a free-text UUID input since no `/api/admin/course-versions` endpoint exists yet; documented as a known gap), a "Send invites" button, a result table showing per-email status.
- The admin UI is itself gated by `useRequireAuth('admin')` (from S4.5 — soft dependency: this spec can ship the route + the API call, and S4.5 wires the auth check).

## Non-goals

- CSV file upload parsing (deferred — pasting into a textarea is enough for MVP; CSV is a small follow-up in E9 along with the proper course-version selector).
- Bulk operations beyond invite (delete enrollment, edit role, change email) — E9.
- Email re-send button (deferred; admin re-submits the same email to re-enqueue the invite).
- Audit log of admin actions (deferred to E9).
- Course-version listing/picker UI (depends on Material Domain endpoints from E2; for now the admin enters the UUID directly).

## Design

### Backend

Files:
- `apps/backend/internal/admin/enrollments.go` — request/response types + handler `CreateEnrollments`.
- `apps/backend/internal/admin/enrollments_test.go` — unit tests with a `RecordingMailer` + an in-memory or real test DB.
- `apps/backend/cmd/server/main.go` — mount `POST /api/admin/enrollments` behind `auth.RequireRole("admin")`.

Request shape:

```json
{
  "course_version_id": "11111111-1111-1111-1111-111111111111",
  "emails": ["alice@example.edu", "bob@example.edu"]
}
```

Response shape (always 200 with per-email results; only returns 4xx on whole-request validation errors):

```json
{
  "results": [
    { "email": "alice@example.edu", "status": "created",          "user_id": "..." },
    { "email": "bob@example.edu",   "status": "already_enrolled", "user_id": "..." },
    { "email": "x@oops",            "status": "email_failed",     "error": "send failed: 502" }
  ]
}
```

Status values:
- `created` — new user row + new enrollment row + invite email sent successfully.
- `already_enrolled` — user existed, enrollment already existed (no email re-sent).
- `enrolled` — user existed but was not yet enrolled in this course; enrollment created + invite email sent.
- `email_failed` — user + enrollment created (or already existed and we tried re-invite), but email send failed. The DB state is still consistent.

Handler logic (per email):
1. Normalise email to lowercase + trim.
2. Validate format (simple regex; reject obviously malformed early into a 4xx for that one entry — `status: "invalid_email"`).
3. Begin per-email transaction:
   a. `FindUserByEmail(email)` → `user` (or `nil`).
   b. If `nil`: `CreateUser(email, 'student', NULL)` → `user`.
   c. `EnrollmentExists(user.id, course_version_id)`:
      - true → status = `already_enrolled`, commit, do not send email.
      - false → `CreateEnrollment(user.id, course_version_id)`, commit, send email.
4. If email send fails after enrollment commit → record `email_failed` but keep the DB write (it's the right semantic: the user is enrolled; the email is a notification, retriable).

Whole-request validation:
- `course_version_id` must parse as UUID → else 400 `{error: "bad_course_version_id"}`.
- `emails` must be non-empty array, max 500 entries (DOS guard) → else 400 `{error: "too_many_emails"}` or `{error: "no_emails"}`.

### Frontend

Files:
- `apps/frontend/src/routes/admin/enrollments.jsx` — page component.
- `apps/frontend/src/routes/admin/EnrollmentsForm.jsx` — textarea + course-version UUID input + submit button.
- `apps/frontend/src/routes/admin/EnrollmentsResultTable.jsx` — renders per-email status with color coding.
- `apps/frontend/src/api/admin.js` — `submitEnrollments({course_version_id, emails})` calling the API via `fetch` with `credentials: 'include'`. (Long-term this is replaced by the generated TS client from S4.6, but for the initial slice a hand-rolled fetch is acceptable to unblock parallel work.)
- Route entry mounted under whatever routing is established by E2 (or a placeholder route if E2 hasn't landed yet).

The form parses the textarea on submit: split on newline or comma, trim, dedupe, filter empties.

### Environment variables introduced

None beyond what S4.1, S4.2, S4.3 already require.

## Acceptance criteria

- [ ] AC1: `POST /api/admin/enrollments` without an `admin` JWT returns 403 (verified via curl + RequireRole behavior from S4.2).
- [ ] AC2: With an admin JWT, posting `{course_version_id: <uuid>, emails: ["new@example.com"]}` against a fresh DB returns `{results: [{email, status: "created", user_id}]}`, creates one row in `users` (role='student'), one row in `enrollments`, and RecordingMailer captures one email with the right subject + body.
- [ ] AC3: Re-posting the same payload returns `status: "already_enrolled"` and no new email is sent.
- [ ] AC4: Posting a payload with an unknown email **and** a known email returns `status: "created"` for the unknown and `status: "already_enrolled"` for the known (mixed results in one request work).
- [ ] AC5: If the mailer returns an error (forced in test via a `FailingMailer`), the user + enrollment rows are still committed and the response shows `status: "email_failed"`.
- [ ] AC6: Posting `{emails: []}` returns 400.
- [ ] AC7: Frontend page `/admin/enrollments` renders the form, accepts input, submits, and displays the result table. Manual verification in browser.
- [ ] AC8: `go vet ./...`, `go test ./internal/admin/...`, lint clean. ESLint clean on the new frontend files.

## Slices (1 slice = 1 commit)

- [ ] Slice 1: Backend handler skeleton with request/response types, validation, mounted behind `RequireRole("admin")`. No DB writes yet; returns stub `results` with `status: "stub"`.
- [ ] Slice 2: Implement DB logic (find-or-create user, enrollment create, idempotency) with `RecordingMailer` for tests. Comprehensive tests in `enrollments_test.go`.
- [ ] Slice 3: Wire actual mailer (`SendEnrollmentInvite`) into the handler; add the failure-mode test (`FailingMailer`).
- [ ] Slice 4: Frontend admin page (route, form, result table, API client). Manual smoke against a running backend + admin user.

## Test plan

- Backend tests: `go test ./internal/admin/...` for all status branches (created, already_enrolled, email_failed, invalid_email, mixed batches).
- Smoke test `smoke-test-admin-enrollments.mjs` (puppeteer): with a logged-in admin (test fixture sets cookie directly), navigate to `/admin/enrollments`, paste an email, submit, assert the success row.
- Manual verification:
  - `make migrate-up` + bootstrap an `admin` user.
  - Log in as that admin via S4.2 in the browser.
  - Visit `/admin/enrollments`, paste a test email, submit, observe result table.
  - Check DB: `SELECT * FROM users WHERE role='student'` shows the new row; `SELECT * FROM enrollments` shows the new enrollment.
  - Check the dev console (NoopMailer logs the would-have-sent email).
- Lint + build pass.

## Notes

- Domain: **Administration Domain** (ADR-0002). 100% of traffic is gated by `RequireRole("admin")`.
- The textarea-only UI is intentionally minimal — proper CSV upload + course picker is E9.
- Soft dependency on S4.5 for the route guard. If S4.5 is not yet merged, the admin UI route is reachable by URL but the API call still requires the admin JWT, so it's safe — just sub-optimal UX for non-admins.
