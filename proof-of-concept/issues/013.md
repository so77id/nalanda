## Problem

The pilot course is "Estructuras de Datos en Java". Today the `CodeEditor` widget supports C++ (via `browsercc` + WASI) and Python (via Pyodide). Java is missing. Without Java compilation/execution in the browser, no Java content can be authored or run interactively.

Per ADR-0003, we use **CheerpJ 3.0 in browser only** (no server-side compilation). The runtime integrates with the existing `useRuntime` pattern by adding `java.js` (metadata) + `java.worker.js` (worker), exactly parallel to how `cpp.js`/`cpp.worker.js` and `python.js`/`python.worker.js` work today.

## Goals

- License verification of CheerpJ for non-commercial / Chilean university use — documented in S3.1 (or escalated to a new ADR if pivot to server-side is required).
- New runtime files following the existing pattern: `apps/frontend/src/widgets/code-editor/runtimes/java.js` + `java.worker.js`.
- CheerpJ lazy-loaded inside the worker (no impact on first paint when Java isn't selected).
- `LanguageContext` extended to expose `'java'`; UI language picker shows Java as an option.
- All `CodeEditor` variants (snippet, read, exercise, lab) work with `language="java"`.
- `smoke-test-java.mjs` covering: compile a simple program, run it, capture stdout, supply stdin, surface compile errors.

## Non-goals

- Server-side compilation as a fallback or hybrid (deferred — would only be added if license check fails OR for high-stakes autograder validation, which is post-MVP per ADR-0003).
- `RemoteRuntime` abstraction (Fase B, post-junio per L decision).
- New CodeEditor UI features; this epic adds a runtime, not UI surface.
