## Problem

The platform needs a backend service (per ADR-0001) to support auth, sessions, submissions, and admin features that cannot run in a static frontend. This spec lands the minimum Go backend skeleton: a build-able, runnable HTTP server with a single `/healthz` endpoint, structured logging, and the project layout that subsequent E4 specs will extend with database, OAuth, and feature handlers.

The skeleton must follow the stack decided in the plan (G): `net/http` + `chi`, with the structure prepared so that `sqlc`-generated code, `goose` migrations, and `oapi-codegen` stubs (S1.3) can land in their conventional locations without rework.

## Goals

- Create `apps/backend/` as a self-contained Go module compiling to a single binary.
- Expose `GET /healthz` returning `200 OK` with a small JSON body (`{"status":"ok","version":"..."}`).
- Structured logging via `log/slog` (stdlib) with JSON output to stderr, level configurable via `LOG_LEVEL` env var.
- Graceful shutdown on `SIGINT`/`SIGTERM`.
- Project layout that anticipates future additions: `cmd/server/`, `internal/`, `migrations/` (empty), and a placeholder for sqlc/codegen targets.
- `go build`, `go vet`, and `go test ./...` all green from a fresh clone.
- README inside `apps/backend/` documenting how to run the server locally.

## Non-goals

- Database connection (DB lives in `apps/backend/` but the `db.Open` call comes in E4's first spec when the `users` migration lands).
- Any business endpoint beyond `/healthz`.
- OpenAPI codegen wiring (that's S1.3 — this spec only leaves a directory + comment placeholder).
- Authentication / OAuth (E4).
- Dockerfile (deferred to S1.6 where docker-compose is introduced; backend Dockerfile can land then or in an E4 spec, decision documented in S1.6).
- CI workflow (S1.5).
- Goose migration command wiring beyond creating the empty `migrations/` directory (real migrations arrive in E4 specs).

## Design

**Reference decisions:** G (Go + chi + sqlc + goose), G' (OpenAPI contracts), and ADR-0001.

**Module name:** `github.com/so77id/nalanda/apps/backend` (matches the repo path so import paths are stable when packages reference each other within the backend).

**Layout:**

```
apps/backend/
├── go.mod
├── go.sum
├── README.md
├── cmd/
│   └── server/
│       └── main.go             # entrypoint: load config, build router, ListenAndServe + graceful shutdown
├── internal/
│   ├── config/
│   │   └── config.go           # env-var loader (PORT, LOG_LEVEL, etc.) — small, no third-party deps
│   ├── httpserver/
│   │   ├── router.go           # chi router builder + middleware stack
│   │   └── health.go           # /healthz handler
│   └── logging/
│       └── logging.go          # slog setup (JSON handler, level from env)
├── migrations/
│   └── .gitkeep                # goose migrations will live here from E4 onward
└── api/
    └── .gitkeep                # oapi-codegen output target (filled in by S1.3 codegen)
```

**Dependencies (added via `go get`):**

- `github.com/go-chi/chi/v5` — router.
- `github.com/go-chi/chi/v5/middleware` — request ID, recoverer, real-IP.

No other third-party deps in this spec. `slog` is stdlib. Config is parsed by hand from env vars (no `viper`).

**`main.go` outline:**

```go
package main

import (
    "context"
    "errors"
    "net/http"
    "os"
    "os/signal"
    "syscall"
    "time"

    "github.com/so77id/nalanda/apps/backend/internal/config"
    "github.com/so77id/nalanda/apps/backend/internal/httpserver"
    "github.com/so77id/nalanda/apps/backend/internal/logging"
)

func main() {
    cfg := config.Load()
    logger := logging.New(cfg.LogLevel)
    router := httpserver.New(logger)
    srv := &http.Server{
        Addr:    ":" + cfg.Port,
        Handler: router,
    }
    // start server in goroutine
    // wait for SIGINT/SIGTERM
    // call srv.Shutdown with 10s timeout
}
```

**`/healthz` response:**

```json
{"status":"ok","version":"dev"}
```

Version comes from a `-ldflags "-X main.version=..."` injected at build time. Default `"dev"` when unset. The handler is tested with `httptest`.

**Middleware stack (chi):** `middleware.RequestID`, `middleware.Recoverer`, custom `logging.RequestLogger` that emits one structured log per request (`method`, `path`, `status`, `duration_ms`, `request_id`).

**Tests:**

- `internal/httpserver/health_test.go`: spin up router via `httptest.NewServer`, assert `GET /healthz` returns 200 + correct JSON body.
- `internal/config/config_test.go`: cover defaults + env-var overrides.

**Config defaults:**

| Env var | Default | Notes |
|---|---|---|
| `PORT` | `8080` | HTTP listen port |
| `LOG_LEVEL` | `info` | `debug` / `info` / `warn` / `error` |

**TODO at implementation time:** confirm whether the team prefers `go-chi/httplog` over a hand-rolled slog middleware for request logging. The decision is small and reversible; if going hand-rolled, keep the middleware tiny (≤30 lines).

## Acceptance criteria

- [ ] AC1: `cd apps/backend && go build ./...` succeeds with no warnings.
- [ ] AC2: `cd apps/backend && go vet ./...` exits 0.
- [ ] AC3: `cd apps/backend && go test ./...` runs and all tests pass.
- [ ] AC4: `cd apps/backend && go run ./cmd/server` listens on `:8080` (or `$PORT`) and `curl -s localhost:8080/healthz` returns `{"status":"ok","version":"dev"}` with HTTP 200.
- [ ] AC5: Sending `SIGINT` to the process triggers a graceful shutdown log line and the process exits 0 within 10 seconds.
- [ ] AC6: With `LOG_LEVEL=debug` set, request logs appear in stderr as one-line JSON.
- [ ] AC7: `apps/backend/README.md` documents the run command and `/healthz` example.

## Slices (1 slice = 1 commit in the PR)

- [ ] Slice 1: `go mod init github.com/so77id/nalanda/apps/backend`, add chi dependency, create empty layout (cmd/server/, internal/, migrations/.gitkeep, api/.gitkeep, README stub).
- [ ] Slice 2: Implement `internal/logging/logging.go` (slog JSON handler) + `internal/config/config.go` (env-var loader with defaults) + unit tests for config.
- [ ] Slice 3: Implement `internal/httpserver/router.go` (chi + middleware stack) + `internal/httpserver/health.go` (/healthz handler) + test for the handler.
- [ ] Slice 4: Wire `cmd/server/main.go` (start server, graceful shutdown on SIGINT/SIGTERM, version ldflag). Update `apps/backend/README.md` with run instructions and `/healthz` curl example.

Dependencies between slices: linear (each builds on the previous).

## Test plan

- Go tests: added under `internal/`, run via `go test ./...`.
- Manual verification:
  1. `cd apps/backend && go run ./cmd/server` — confirm log line `server listening` on `:8080`.
  2. `curl -i localhost:8080/healthz` — confirm `200 OK` and JSON body.
  3. `curl -i localhost:8080/does-not-exist` — confirm `404` (chi's default) and one structured log line.
  4. `Ctrl-C` — confirm graceful shutdown log line and clean exit.
- Lint: project-level lint is N/A for Go (use `go vet`). Document this in the PR.
- Smoke tests: no frontend smoke tests apply. Future Go smoke tests will arrive with E4's auth flow.

## Notes

- Stack decided in plan file (G): chi + sqlc + goose. This spec lands chi only; sqlc and goose are added by E4 specs along with their first migration.
- `slog` (stdlib) is chosen over `zap`/`zerolog` to keep dependencies minimal during the skeleton phase. Easy to swap later.
- Dockerfile for the backend lands in S1.6 (docker-compose) or its own follow-up — explicitly out of scope here.
- Module path `github.com/so77id/nalanda/apps/backend` keeps imports stable even though the repo also contains non-Go directories. The Go tooling only cares about paths inside the module.
