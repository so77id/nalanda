## Problem

After S3.2 adds the Java runtime files, the runtime is technically usable via `runtimeList` (because `LanguagePicker` in `CodeEditor.jsx` already iterates `runtimeList` from `runtimes/index.js`), but two integration points need explicit verification and possibly a small extension:

1. `LanguageContext.jsx` initializes with `defaultLanguage = 'cpp'`. The context itself stores any string id, so it already supports `'java'` mechanically. But we should confirm — and document — that the context handles `'java'` correctly, that any consumers that switch on language id don't have C++/Python-only branches, and that `defaultLanguage` can be set to `'java'` at the provider level for Java-first courses.
2. `CodeEditor.jsx` renders a `<LanguagePicker>` that maps over `runtimeList`. Once S3.2 registers Java in `runtimes/index.js`, Java appears automatically. We must verify this works visually with all four variants (`snippet`, `read`, `exercise`, `lab`) and that the per-language code state in `CodeEditor` (the `codeByLang` map seeded from `runtimeList`) correctly carries Java samples between language switches.

This spec is the **integration** + **verification** layer for Java in the UI, not a big refactor.

## Goals

- Verify `LanguageContext.jsx` works with `'java'` as a language id (including being passed as `defaultLanguage`). If any consumer code (e.g. comments, type hints, defensive guards) implicitly assumes only `'cpp'`/`'python'`, fix it.
- Verify `CodeEditor.jsx`'s `LanguagePicker` shows Java as an option, with the correct label from `meta.label` (likely "Java 8").
- Verify all variant presets work with `language="java"`:
  - `snippet` — read-only code block with header.
  - `read` — read-only with line numbers.
  - `exercise` — runnable, expanded mode available.
  - `lab` — full UX (stdin, diagnostics, fullscreen).
- Verify the `codeByLang` per-language state in `CodeEditor` correctly initializes a Java entry from `samples.java ?? defaultValue ?? meta.defaultCode`.
- Verify the diagnostics panel label (`runtime?.meta.id === 'cpp' ? 'diagnósticos' : 'errores'`) — Java falls through to `'errores'` which is correct; just confirm.
- (Optional) Add a Java sample to whatever demo page currently shows cpp/python editors (likely `src/App.jsx` or a content section), so a visual smoke test is possible and so S3.4's puppeteer test has a target.

## Non-goals

- Adding new variants or chrome panels (out of scope; this epic is about runtime, not UI).
- Translating the picker labels (UI labels stay as-is — `meta.label` is "Java 8" or whatever S3.2 chose).
- Server-side runtime (deferred per ADR-0003).
- Modifying the `LanguagePicker` styling.
- Adding language-version selection within Java (Java 8 vs 11 vs 17) — CheerpJ 3.0 supports one bytecode level; we expose what it provides.

## Design

**Files to touch:**

- `src/widgets/code-editor/LanguageContext.jsx`:
  - Audit: the file is already language-agnostic (it stores any string id via `useState`). No mechanical change required for Java to "work".
  - Consider: changing the default initializer from `defaultLanguage = 'cpp'` to a list-aware default — but per CLAUDE.md "Never modify ... without discussing first" applies to config files, not to widget files. Leave `defaultLanguage = 'cpp'` as the prop default; callers can pass `defaultLanguage="java"`. Document this in a JSDoc comment if not already clear.
  - Defensive: if any later assertion (e.g. validating that the id is a known runtime) lands here, ensure it permits 'java'. Currently there's none, so this is a documentation pass.

- `src/widgets/code-editor/CodeEditor.jsx`:
  - The `LanguagePicker` iterates `runtimeList` — once S3.2 registers Java, the option appears automatically. **Verify, do not modify.**
  - The `codeByLang` state (line 180 in current file) seeds itself from `runtimeList` — Java is included automatically once registered. **Verify, do not modify.**
  - The diagnostics label (line ~463) reads `runtime?.meta.id === 'cpp' ? 'diagnósticos' : 'errores'`. Java falls through to `'errores'` (correct — Java compiler errors are surfaced via the same `compileLog` channel as Python's runtime errors). **No change needed**, but document the rationale in a one-line comment if helpful.
  - If the implementer discovers ANY branching on `activeLang === 'cpp'` / `activeLang === 'python'` in `CodeEditor.jsx` or its sub-components that would exclude Java, fix it.

- Demo wiring (likely `src/App.jsx` or a section file):
  - Add a `<CodeEditor language="java" variant="lab" />` (or equivalent) to whatever demo page currently shows cpp/python editors, with a small Java sample. This is the surface S3.4's puppeteer smoke test targets.
  - If the demo already has multiple editors (one per language), simply add a third for Java.

- [ ] AC2: Switching the LanguagePicker from cpp → java → python and back preserves each language's code separately (the `codeByLang` map keeps Java edits isolated from cpp/python edits).
- [ ] AC3: `<CodeEditor language="java" variant="snippet" />`, `variant="read"`, `variant="exercise"`, `variant="lab"` all render without console errors. Read-only variants stay read-only.
- [ ] AC4: The diagnostics panel for Java is labelled `errores` (consistent with python).
- [ ] AC5: Passing `<LanguageProvider defaultLanguage="java">` initializes the global language as `'java'` correctly. (Test by wrapping a sub-tree in dev.)
- [ ] AC6: A Java sample is reachable from a dev URL so S3.4's smoke test can find it.
- [ ] AC7: Lint passes (`npm run lint`).
- [ ] AC8: Build passes (`npm run build`).
- [ ] AC9: Manual browser verification in all four variants — output captured as screenshots in the PR description.

  - `npm run dev`, open `http://localhost:5173/`.
  - For each variant (snippet, read, exercise, lab):
    - Mount `<CodeEditor language="java" variant="...">` on the dev page.

- Build: `npm run build`.
