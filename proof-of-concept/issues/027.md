## Problem

Once MDX renders (S2.1), we need a stable abstraction for *how content is loaded* so the rest of the app (routing, TOC, presentation) doesn't depend on the storage mechanism. In phase 1, content lives in the repo and is bundled by Vite via glob imports (decision **O**). In phase 2+ (post-junio, when the editor and multi-professor system arrive), content may move to Postgres TEXT or R2 (decision **O'** — deferred). The hook contract must be stable enough that swapping the backend is a one-file change.

This spec defines the `SectionLoader` interface and the `useSection` hook. Both consume MDX files via `import.meta.glob` (Vite-native). Frontmatter (title, order, slug, chapter) is parsed via `gray-matter` so the loader can return rich metadata without coupling to a specific backend.

## Goals

- Define a `SectionLoader` JS contract (informal — JS, not TS — but documented in JSDoc) with methods: `loadSection(courseSlug, chapter, section)`, `listSections(courseSlug)`, `listCourses()`. All return Promises that resolve to plain objects.
- Implement `viteGlobLoader` that uses `import.meta.glob('/src/content/courses/**/*.mdx', { eager: false })` to enumerate and dynamically import MDX files.
- Implement `useSection(courseSlug, chapter, section)` React hook backed by the loader (uses `useState` + `useEffect` for now; TanStack Query integration is a separate concern for E4+).
- Frontmatter: every MDX file has YAML frontmatter `{ title, order, chapter, slug }`. Parser uses `gray-matter` (already a transitive dep of many MDX setups; install if needed).
- Loader returns: `{ Component, frontmatter, raw, path }`. `Component` is the MDX-compiled React component. `frontmatter` is the parsed YAML. `raw` is the original source (used by S2.5 parser).
- Export from `src/content/index.js` as the public API.

## Non-goals

- Backend-backed loader (phase 2+).
- Search functionality.
- TanStack Query integration (kept simple with `useState`+`useEffect` for now; can be upgraded later without changing the hook signature).
- Frontmatter validation against a schema (just consume what's there; missing fields fall back to derived values like slug-from-path).
- Course inheritance / overrides (M decision, deferred).

## Design

**Approach:** Vite's `import.meta.glob` with `{ eager: false }` returns a record `{ '/src/content/.../intro.mdx': () => import('...') }`. The loader builds an index from the path structure (`courses/<slug>/<chapter>/<section>.mdx`), and `loadSection` looks up + dynamically imports the matching file.

**Architecture decisions consumed:**
- **O** — Phase 1 storage: MDX files in repo, glob-imported by Vite at build time.
- **X** — Material Domain: this loader serves content only. Stateless, no auth, cacheable.

**Files to create / modify:**
- `src/content/loader.js` — implements `viteGlobLoader`. Exports `loadSection`, `listSections`, `listCourses`.
- `src/content/useSection.js` — React hook wrapping the loader. Signature: `useSection({ courseSlug, chapter, section }) => { Component, frontmatter, loading, error }`.
- `src/content/index.js` — re-exports the public API.
- `src/content/README.md` — documents the contract (so future spec authors writing course files know the file layout + frontmatter shape).
- Sample file from S2.1 gets frontmatter added (`title:`, `order:`, etc.) to match the new contract.
- `package.json` — add `gray-matter` if used for frontmatter parsing. (Alternative: MDX itself can extract frontmatter via `remark-frontmatter` + `remark-mdx-frontmatter` — leaner. **TODO**: pick during slice 1 based on which is simpler to wire.)

**Contract (documented in JSDoc):**

```js
/**
 * @typedef {Object} Section
 * @property {React.ComponentType} Component - The MDX-compiled component.
 * @property {Object} frontmatter - { title, order, chapter, slug, ... }
 * @property {string} path - Source path, e.g. 'courses/data-structures-java/chapter-01/intro.mdx'
 *
 * @typedef {Object} SectionLoader
 * @property {(slug: string, chapter: string, section: string) => Promise<Section>} loadSection
 * @property {(slug: string) => Promise<Array<{frontmatter, path}>>} listSections
 * @property {() => Promise<Array<{slug, title}>>} listCourses
 */
```

The hook is the consumer-facing API; the loader is internal.

- [ ] AC1: `src/content/loader.js` exists, uses `import.meta.glob`, exposes the three functions.
- [ ] AC2: `useSection` returns `{ Component, frontmatter, loading: true }` on mount, then `{ Component, frontmatter, loading: false }` after the dynamic import resolves.

## Notes

- **TODO**: pick `gray-matter` vs `remark-frontmatter` + `remark-mdx-frontmatter` during slice 1. Document the choice in `src/content/README.md`.
- **Future-proofing**: the hook signature `useSection({ courseSlug, chapter, section })` is intentionally object-shaped so adding params (e.g. `language`, `version`) doesn't break callers.
- Domain: **Material Domain** (per ADR-0002). The loader can be swapped to call `/api/content/...` later without consumers noticing.
- The interface shape mirrors the future Go-side `SectionRepository` interface documented in the plan file (O' decision), so frontend↔backend types align when the migration happens.
