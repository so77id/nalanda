## Problem

The POC has zero routing — `src/App.jsx` directly renders one lesson. To support a multi-section, multi-course platform we need URLs that map to chapters/sections so users can bookmark, share, and navigate via browser back/forward. Per decision **C**, the choice is React Router v6 (already cemented; not up for re-discussion).

This spec introduces the routing skeleton: a landing page that lists courses, course-overview pages, and a section page. Section content rendering still uses what S2.1/S2.2 deliver (sample MDX). The POC remains accessible during the transition so we never break the live site.

## Goals

- Install `react-router-dom@^6`.
- Define three routes:
  - `/` — landing page. Lists all courses (via `listCourses()` from S2.2). One card per course with title + short description, click → `/courses/:slug`.
  - `/courses/:slug` — course overview. Shows course title + chapter list with section links. Click a section → `/courses/:slug/:chapter/:section`.
  - `/courses/:slug/:chapter/:section` — section page. Renders the MDX section using `useSection({ courseSlug, chapter, section })` from S2.2.
- A 404 catch-all route (`*`) renders a friendly "section not found" page.
- `src/App.jsx` switches from rendering the POC lesson directly to mounting `<BrowserRouter>` + `<Routes>`. The POC content is still reachable temporarily at `/legacy` (a route that renders the old `<Presentation>` JSX) — this fallback is removed in S2.7.
- Landing page lists the sample course (from S2.1/S2.2) plus a placeholder card for "Data Structures in Java" (which gets real content in S2.7).

## Non-goals

- TOC sidebar / breadcrumbs — that is S2.4 (this spec only delivers the route skeleton; S2.4 wraps it in a layout shell).
- Authenticated routes / protected routes — that is E4.
- Course inheritance — deferred (M).
- Localization / i18n routing — out of scope.
- Animation/transition between routes — out of scope (can be a polish ticket later).

## Design

**Approach:** Standard React Router v6 setup. Use `createBrowserRouter` + `RouterProvider` (the v6.4+ data-router API). The router config is a flat array of routes; nested layouts come in S2.4 via `<Outlet/>`.

**Architecture decisions consumed:**
- **C** — React Router v6.
- **X** — Material Domain: all routes here are content-only, no auth gate.

**Files to create / modify:**
- `src/App.jsx` — replaces the current direct-render with `<RouterProvider router={router} />`. The legacy POC view is preserved at `/legacy` temporarily.
- `src/routes/router.jsx` — defines the router config (`createBrowserRouter([...])`).
- `src/routes/LandingPage.jsx` — lists courses. Uses `listCourses()` from S2.2.
- `src/routes/CourseOverview.jsx` — params: `:slug`. Uses `listSections(slug)` to render chapter+section index.
- `src/routes/SectionPage.jsx` — params: `:slug`, `:chapter`, `:section`. Uses `useSection(...)` and renders the resolved `Component`.
- `src/routes/NotFound.jsx` — 404 catch-all.
- `package.json` — add `react-router-dom`. (Requires confirmation per CLAUDE.md; this issue is that confirmation.)
- `vite.config.js` — verify GitHub Pages SPA fallback works (or use `base: '/nalanda/'` if needed for Pages routing). May need a `public/404.html` redirect-to-index trick if hosted on Pages. **TODO**: confirm GH Pages SPA strategy during slice 1.
- `smoke-test-routing.mjs` — new puppeteer test that navigates `/`, `/courses/:slug`, `/courses/:slug/:chapter/:section`, and a bad URL → asserts each renders the right page.

**Landing page UI sketch:**
- Header (reuse `Appbar`).
- Grid of course cards. Each card: course title, short description from frontmatter, click → navigate.
- Empty-state if `listCourses()` returns nothing.

**Course overview UI sketch:**
- Course title at top.
- For each chapter (grouped by frontmatter `chapter`): chapter heading + ordered list of sections, each a link.

## Notes

- **TODO (slice 5)**: GitHub Pages does NOT serve SPA fallback by default. Common workarounds: `public/404.html` that mirrors `index.html`; or hash-based routing; or switch to `createHashRouter`. Pick during slice 5 based on what the user prefers — hash routing is ugly but bulletproof; the 404.html trick is cleaner but a bit hacky. The plan file leans toward Cloudflare Pages eventually (decision T) which handles SPA fallback natively, so a temporary 404.html trick is fine.
- Domain: **Material Domain** — all routes are public-content-only. Auth gates come later (E4) on `/study/*` and `/admin/*` routes.
- Sequencing: this spec can run in parallel with S2.1 (different concerns), but S2.3 needs S2.2 done before SectionPage is fully wired. Slice 1 (router skeleton with stubs) is independent.
