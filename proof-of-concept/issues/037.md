## Problem

The platform's production hosting (decision T) spans four providers: Cloudflare Pages (frontend), Fly.io (Go backend), Neon (PostgreSQL), and Cloudflare R2 (assets). Today none of these are provisioned. Doing it click-by-click in each provider's dashboard is error-prone and undocumented: a year from now nobody will remember which DNS record points where, which environment variable was set on Fly.io, or how to recreate the stack if a provider revokes the free tier.

Decision T' commits to Terraform from the start. This spec creates the `infra/` directory with one module per provider plus a `prod` environment that wires them together. The first `terraform plan` is the goal here — actually applying it (`terraform apply`) is a manual operator step the user runs once they're ready, NOT something CI does in this spec (CI for infra lands in S1.5 with `plan` on PRs and gated `apply` on main).

## Goals

- Create `infra/` with Terraform modules for the four providers and a `prod` environment.
- Each module is self-contained: declares its required providers, accepts variables, exposes outputs.
- The `prod` environment composes the four modules with concrete inputs (app names, region, etc.) and stitches outputs between them where needed (e.g., Neon connection string → Fly.io secret).
- `terraform init` and `terraform plan` succeed locally and in CI given the right provider tokens (set as env vars).
- Document required env vars / GitHub secrets in `infra/README.md`.
- Terraform state stored remotely from day one — Terraform Cloud free tier or an S3-compatible backend in R2.

## Non-goals

- Running `terraform apply` against real providers in this spec (manual operator step, post-merge).
- `staging` environment (deferred per plan; can be added post-junio when needed).
- DNS record automation for nalanda.xx domain — module exists but inputs left as TODO if the domain isn't registered yet at implementation time.
- Cloudflare Workers, D1, or other CF products (we chose T1: CF Pages + Fly.io + Neon + R2, not T4).
- Database schema or migrations — those live in `apps/backend/migrations/` and arrive with E4 specs.
- Secret management beyond "tokens via env vars / GitHub Actions secrets" — no Vault, no SOPS at this stage.

## Design

**Reference decisions:** T (hosting: CF Pages + Fly.io + Neon + R2), T' (Terraform from start), plan-file section "Grupo 8 — Deployment".

**Layout:**

```
infra/
├── README.md
├── modules/
│   ├── cf-pages/
│   │   ├── main.tf         # cloudflare_pages_project + build config
│   │   ├── variables.tf
│   │   └── outputs.tf
│   ├── fly/
│   │   ├── main.tf         # fly_app + fly_machine + fly_volume (if needed)
│   │   ├── variables.tf
│   │   └── outputs.tf
│   ├── neon/
│   │   ├── main.tf         # neon_project + neon_branch + neon_role + neon_database
│   │   ├── variables.tf
│   │   └── outputs.tf
│   └── r2/
│       ├── main.tf         # cloudflare_r2_bucket (assets)
│       ├── variables.tf
│       └── outputs.tf
├── environments/
│   └── prod/
│       ├── main.tf         # provider configs + module composition
│       ├── variables.tf    # var inputs (app names, regions, domain, etc.)
│       ├── outputs.tf
│       ├── backend.tf      # remote state config
│       └── terraform.tfvars.example  # documented placeholder values
└── .gitignore              # ignore .terraform/, *.tfstate, *.tfstate.backup, .terraform.lock.hcl is committed
```

**Providers:**

- `cloudflare/cloudflare` — for CF Pages, R2, optionally DNS.
- `fly-apps/fly` — for Fly.io apps and machines.
- `kislerdm/neon` — for Neon Postgres projects (community provider, listed in plan).

**Module: `cf-pages`** — creates a `cloudflare_pages_project` named `nalanda-frontend` with:
- Build config: `build_command = "cd apps/frontend && npm install && npm run build"`, `destination_dir = "apps/frontend/dist"`, `root_dir = ""` (repo root).
- Production branch `main`, preview deployments for PRs.
- Inputs: `account_id`, `project_name`, `repo_name`, `production_branch`.
- Outputs: `subdomain` (`<project>.pages.dev`).

**Module: `fly`** — creates a `fly_app` named `nalanda-backend` with:
- One `fly_machine` in `scl` (Santiago) or `mia` (closest free-tier region — confirm at implementation time).
- 256MB RAM, shared CPU (free tier).
- Inputs: `app_name`, `region`, `image` (default `nalanda-backend:latest` — built via fly deploy later, not by Terraform here), `env` (map), `secrets` (map, marked sensitive).
- Outputs: `app_hostname` (`<app>.fly.dev`).
- TODO at implementation time: confirm whether `fly_machine` resource is the right one for free-tier deployment vs `fly_machine` + `fly_volume`. If a volume is needed for migrations, add it; if backend is stateless (DB lives in Neon), no volume.

**Module: `neon`** — creates `neon_project` `nalanda` with:
- Region matching Fly.io (or closest available).
- Default branch `main` with a `nalanda` database and a `app` role.
- Inputs: `project_name`, `region`, `database_name`, `role_name`.
- Outputs: `connection_uri` (sensitive — passed as Fly secret), `host`, `database`.

**Module: `r2`** — creates `cloudflare_r2_bucket` `nalanda-assets` with:
- Inputs: `account_id`, `bucket_name`.
- Outputs: `bucket_name`, `endpoint`.

**`environments/prod/main.tf` composition:**

```hcl
provider "cloudflare" { api_token = var.cloudflare_api_token }
provider "fly"        { fly_api_token = var.fly_api_token }
provider "neon"       { api_key = var.neon_api_key }

module "neon" {
  source         = "../../modules/neon"
  project_name   = "nalanda"
  region         = var.neon_region
  database_name  = "nalanda"
  role_name      = "app"
}

module "fly" {
  source   = "../../modules/fly"
  app_name = "nalanda-backend"
  region   = var.fly_region
  secrets  = {
    DATABASE_URL = module.neon.connection_uri
  }
}

module "cf_pages" {
  source           = "../../modules/cf-pages"
  account_id       = var.cloudflare_account_id
  project_name     = "nalanda-frontend"
  repo_name        = "so77id/nalanda"
  production_branch = "main"
}

module "r2" {
  source     = "../../modules/r2"
  account_id = var.cloudflare_account_id
  bucket_name = "nalanda-assets"
}
```

**Remote state (`backend.tf`):**

Two viable options — pick at implementation time:

- **Option A (recommended):** Terraform Cloud free tier (5 users free, remote state + run history). Backend block: `terraform { cloud { organization = "..." workspaces { name = "nalanda-prod" } } }`.
- **Option B:** R2 bucket as S3-compatible backend. Cheaper if Terraform Cloud's quota is restrictive, but chicken-and-egg (you need R2 before you can store TF state in R2; bootstrap with a local state apply for r2 module first).

**TODO at implementation time:** pick A unless there's a reason. Document the choice in `infra/README.md`.

**Required env vars for `terraform plan`:**

- `CLOUDFLARE_API_TOKEN` — Cloudflare API token with Pages + R2 permissions.
- `CLOUDFLARE_ACCOUNT_ID` — CF account ID.
- `FLY_API_TOKEN` — Fly.io personal access token.
- `NEON_API_KEY` — Neon API key.
- `TF_CLOUD_TOKEN` (if using Option A backend).

These map 1:1 to GitHub Actions secrets in S1.5.

**TODO at implementation time:** confirm region availability for Fly.io free tier (Santiago `scl` may not be free; `mia` or `gru` are likely fallbacks). Confirm Neon region matches.

## Acceptance criteria

- [ ] AC1: `cd infra/environments/prod && terraform init` succeeds with required provider tokens set as env vars.
- [ ] AC2: `terraform validate` exits 0 in `environments/prod` AND in each `modules/<name>/`.
- [ ] AC3: `terraform fmt -check -recursive infra/` exits 0 (all `.tf` files are formatted).
- [ ] AC4: `terraform plan -out plan.tfplan` runs in `environments/prod` and produces a non-empty plan (creating the four resources). No errors.
- [ ] AC5: `infra/README.md` documents: required env vars, how to authenticate each provider, how to run `init` / `plan` / `apply`, the chosen remote state backend, and the explicit warning that `apply` is a manual operator step.
- [ ] AC6: `terraform.tfvars.example` lists every variable with a placeholder and an inline comment explaining its origin (e.g., `cloudflare_account_id = "REPLACE_ME" # found at dash.cloudflare.com/<account> → URL`).
- [ ] AC7: Each module's `outputs.tf` declares at least the outputs consumed by `environments/prod/main.tf`.

## Slices (1 slice = 1 commit in the PR)

- [ ] Slice 1: Create `infra/` skeleton (README, `.gitignore`, empty `modules/` and `environments/prod/`). Add a top-level note that `apply` is a manual step.
- [ ] Slice 2: Author `modules/neon/` (variables, main, outputs). Validate with `terraform init && terraform validate` standalone.
- [ ] Slice 3: Author `modules/fly/` and `modules/r2/`. Validate each standalone.
- [ ] Slice 4: Author `modules/cf-pages/`. Validate standalone.
- [ ] Slice 5: Author `environments/prod/` (main, variables, outputs, backend, tfvars.example). Run `terraform init && terraform validate && terraform plan` against real provider tokens (use a throwaway TF Cloud workspace or local state for plan-only). Capture plan output in PR.
- [ ] Slice 6: Finalize `infra/README.md` with: required tokens, how to bootstrap, what the plan creates, how to rollback, link to ADRs and the plan file.

Dependencies between slices: Slices 2-4 are independent (each module standalone). Slice 5 depends on all of them. Slice 6 is documentation, last.

## Test plan

- `terraform fmt -check -recursive infra/` — passes.
- `terraform validate` in each module + in `environments/prod` — passes.
- `terraform plan` in `environments/prod` — produces a non-error plan that shows the four resources to be created. Plan output is pasted into the PR as evidence.
- Manual verification: NOT applying to real providers in this spec. The user reviews the plan output and applies manually after merge (or in a follow-up where they're ready to spend the time on provider sign-up flows).
- Lint/format: `terraform fmt -recursive infra/` passes.
- Smoke tests: none (infra has no frontend behavior to smoke-test).

## Notes

- This spec lands the plumbing only. `terraform apply` is a deliberate manual step — provisioning real cloud resources outside the agent's loop reduces blast radius if something is misconfigured.
- The state backend choice (TF Cloud vs R2 S3-compat) is documented as a TODO. Either works; the spec author at implementation time picks one.
- The Fly.io region in the plan-file recommendation is `scl` (Santiago, closest to the user's likely audience). Free tier coverage of `scl` is not guaranteed — confirm at implementation time and fall back to `mia` or `gru` if needed.
- DNS automation (mapping `nalanda.xx` to Pages + Fly) is intentionally a stub — domain decisions live outside this spec.
- Per CLAUDE.md, no secrets are committed. All tokens come from env vars / GitHub Actions secrets.
