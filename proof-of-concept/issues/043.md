## Problem

The POC's entire lesson lives hardcoded in `src/App.jsx` as a JSX literal: prose, headings, embedded widgets (`<LinkedListViz />`, `<CodeEditor />`, etc.), all wrapped in `<Presentation>`. This is the final step of E2 — migrate that content into the new MDX-based structure so the app no longer ships content in source files. After this spec, `src/App.jsx` (or its `apps/frontend/` equivalent) contains only application setup: providers, router, no course content.

This spec is the integration test for all of E2. If S2.1 through S2.6 work, this migration is mechanical.

- Create `src/content/courses/data-structures-java/course.json` (or equivalent metadata file — see TODO) with `{ slug: 'data-structures-java', title: 'Estructuras de Datos en Java', description: '...' }`. (The course is "Java" per the broader plan, even though the POC content was C++/Python — adopting the Java name now signals direction.)
- Move POC content into `src/content/courses/data-structures-java/chapter-01/`:
  - `01-introduction.mdx` — "¿Qué es una lista enlazada?" + LinkedListViz + LINKED_LIST CodeEditor.
  - `02-stacks.mdx` — "Stacks — el primo LIFO" + StackViz.
  - `03-queues.mdx` — "Queues — FIFO" + QueueViz.

  - `05-recursion.mdx` — "Recursión: Fibonacci" + Fibonacci CodeEditor.

- `src/App.jsx` final state: provider stack (`LanguageProvider`, `MDXProvider`, `PresentationModeProvider` if appropriate) + `<RouterProvider router={router}/>`. Nothing else.

## Non-goals

- Adding new pedagogical content (this is migration, not authoring).
- Using slide markers (`<Slide>`, `<BookOnly>`, etc.) — the migration preserves current h2-based slide boundaries to keep the diff focused on structure, not pedagogy. Markers will be applied to specific sections in E6 (Course Content Authoring) when content is properly written.
- Translating content to English (course material may stay in Spanish per CLAUDE.md).
- Java code samples — the POC samples are C++/Python; keep them as-is. Java content is the responsibility of E3 (Java Runtime) + E6 (Course Authoring).
- New widgets or behavior changes.

## Design

**Approach:** Mechanical extract-and-move. Each h2 section in current `App.jsx` becomes one .mdx file. Embedded widget JSX moves verbatim. Sample constants get their own files. The `<Presentation>` wrapper moves from `App.jsx` into the `SectionPage` route (S2.3/S2.4 wraps section content in presentation chrome when appropriate) OR each MDX file gets wrapped automatically by the section renderer. **TODO during slice 1**: decide whether each section IS its own presentation, or whether the whole chapter is one presentation. Current POC = one presentation for the whole lesson; the new structure points toward "one presentation per section" (cleaner URL semantics, smaller cognitive load). Going with **one presentation per section** as the default unless this turns out to break the UX.

- **D** — MDX format.
- **E** — h2 fallback (preserved here; markers come later).
