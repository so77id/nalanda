## Problem

A monorepo with two languages (TS frontend + Go backend), generated contracts, and Terraform infra has very different CI needs per piece. Running every job on every PR is wasteful and slow; missing a job because path filters were misconfigured is a silent quality regression.

Decision U commits to four GitHub Actions workflows with path filters and independent triggers — each app/package owns its own pipeline. This spec lands all four. Deploy steps are wired but gated: frontend deploys to Cloudflare Pages on merge to `main`, backend deploys to Fly.io on merge to `main`, infra changes require a manual approval before `terraform apply`. Contracts CI is verification-only (no deploy).

## Goals

- Author `.github/workflows/frontend-ci.yml`: lint + build + smoke (Puppeteer) on PR; deploy to CF Pages on merge to `main`.
- Author `.github/workflows/backend-ci.yml`: `go vet` + `go test` + `go build` on PR; deploy to Fly.io on merge to `main`.
- Author `.github/workflows/contracts-ci.yml`: lint OpenAPI + run codegen + verify no drift on PR; no deploy step.
- Author `.github/workflows/infra-ci.yml`: `terraform fmt -check` + `terraform validate` + `terraform plan` on PR; `terraform apply` on merge to `main` gated by manual `environment` approval.
- Path filters wired so each workflow only triggers on relevant changes. A PR touching only `apps/frontend/` does NOT trigger backend-ci.
- A shared dependency: changes in `packages/shared-contracts/` trigger BOTH frontend-ci and backend-ci (the consumers need to revalidate).
- Document required GitHub Actions secrets in `.github/workflows/README.md` (and link from `infra/README.md`).

## Non-goals

- Caching strategy beyond `actions/setup-node` and `actions/setup-go` defaults (those already cache by `package-lock.json` and `go.sum`).
- Multi-environment deploys (`staging` is post-junio).
- Required status checks branch protection rules (those are repo settings, configured manually by the user).
- Test parallelization, matrix builds (single OS, single language version each).
- Notifications (Slack, Discord, etc.) — out of scope.
- Performance budgets, bundle-size checks (those belong to E8 Polish & Stability).
- Container image building for the backend — `flyctl deploy` builds and pushes the image as part of the deploy step; standalone `docker build` in CI is out of scope.

## Design

**Reference decisions:** U (GitHub Actions with path filters, independent pipelines), T (hosting providers), T' (Terraform).

**Workflow layout:**

```
.github/
├── workflows/
│   ├── frontend-ci.yml
│   ├── backend-ci.yml
│   ├── contracts-ci.yml
│   ├── infra-ci.yml
│   └── README.md         # docs: required secrets, how each pipeline is triggered
```

**Triggers — shared pattern:**

Every workflow:

```yaml
on:
  pull_request:
    paths:
      - <relevant paths>
  push:
    branches: [main]
    paths:
      - <relevant paths>
```

**`frontend-ci.yml`:**

- Paths: `apps/frontend/**`, `packages/shared-contracts/**`, `.github/workflows/frontend-ci.yml`.
- Jobs:
  - `ci` (always): checkout, setup-node 20, `cd apps/frontend && npm ci && npm run lint && npm run build`. Then run one Puppeteer smoke test against the build (e.g., `node smoke-test.mjs` after `npm run preview &`).
  - `deploy` (only on `push` to `main`, depends on `ci`): use `cloudflare/pages-action@v1` or `wrangler` CLI to deploy `apps/frontend/dist/`. Requires `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` secrets.

**`backend-ci.yml`:**

- Paths: `apps/backend/**`, `packages/shared-contracts/**`, `.github/workflows/backend-ci.yml`.
- Jobs:
  - `ci` (always): checkout, setup-go 1.22, `cd apps/backend && go vet ./... && go test ./... && go build ./cmd/server`.
  - `deploy` (only on `push` to `main`, depends on `ci`): use `superfly/flyctl-actions/setup-flyctl@master` then `flyctl deploy --remote-only`. Requires `FLY_API_TOKEN` secret.

**`contracts-ci.yml`:**

- Paths: `packages/shared-contracts/**`, `.github/workflows/contracts-ci.yml`.
- Jobs:
  - `ci` (always): setup-node + setup-go (Go needed because gen-go shells out to `oapi-codegen` via `go run`). `cd packages/shared-contracts && npm ci && npm run lint && npm run generate && npm run verify-no-drift`. Fails if committed generated files differ from a fresh regeneration.
- No deploy step.

**`infra-ci.yml`:**

- Paths: `infra/**`, `.github/workflows/infra-ci.yml`.
- Jobs:
  - `ci` (always): setup-terraform, `cd infra && terraform fmt -check -recursive`, then for each module + `environments/prod`: `terraform init && terraform validate`.
  - `plan` (only on `pull_request`): `cd infra/environments/prod && terraform init && terraform plan -out plan.tfplan`. Upload `plan.tfplan` as artifact. Post a sanitized summary as a PR comment (use `terraform show -json` + a small parser, or rely on `actions/github-script`).
  - `apply` (only on `push` to `main`, depends on `ci` + `plan`): protected by an `environment: prod` block that requires manual approval. `terraform apply -auto-approve`.

**Required GitHub Actions secrets (documented in `.github/workflows/README.md`):**

| Secret | Used by | Source |
|---|---|---|
| `CLOUDFLARE_API_TOKEN` | frontend-ci, infra-ci | CF dashboard → API tokens |
| `CLOUDFLARE_ACCOUNT_ID` | frontend-ci, infra-ci | CF dashboard URL |
| `FLY_API_TOKEN` | backend-ci, infra-ci | `flyctl auth token` |
| `NEON_API_KEY` | infra-ci | Neon console → API keys |
| `TF_CLOUD_TOKEN` | infra-ci (if Option A backend) | Terraform Cloud user settings |

**`environment: prod`:** GitHub Actions environments support required reviewers — the user configures this manually in repo settings to enforce that `terraform apply` and (optionally) production deploys require an approval click.

## Acceptance criteria

- [ ] AC1: A PR that touches only `apps/frontend/src/App.jsx` triggers `frontend-ci` and NOT `backend-ci`, `contracts-ci`, or `infra-ci`. (Verified by opening a test PR or by `gh run list` after pushing.)
- [ ] AC2: A PR that touches only `apps/backend/cmd/server/main.go` triggers `backend-ci` and NOT the others.
- [ ] AC3: A PR that touches `packages/shared-contracts/openapi.yaml` triggers BOTH `frontend-ci` AND `backend-ci` AND `contracts-ci`.
- [ ] AC4: A PR that touches `infra/modules/fly/main.tf` triggers `infra-ci` with a passing `plan` job.
- [ ] AC5: `frontend-ci` succeeds end-to-end on a representative PR (lint, build, at least one smoke step or a documented downgrade).
- [ ] AC6: `backend-ci` succeeds end-to-end (vet, test, build).
- [ ] AC7: `contracts-ci` succeeds and would fail if generated files were out-of-sync with `openapi.yaml` (manually verified by perturbing the committed types and observing red CI).
- [ ] AC8: `infra-ci` `plan` step succeeds on a PR (using repo secrets) and uploads a plan artifact.
- [ ] AC9: `.github/workflows/README.md` lists all required secrets, what each workflow does, and how `environment: prod` is configured.

## Slices (1 slice = 1 commit in the PR)

- [ ] Slice 1: `frontend-ci.yml` — lint + build + smoke job (no deploy step yet). Push to a test branch + open a draft PR to verify the workflow triggers correctly.
- [ ] Slice 2: `backend-ci.yml` — vet + test + build job. Verify it triggers on backend changes only.
- [ ] Slice 3: `contracts-ci.yml` — lint + generate + verify-no-drift. Verify it triggers on contracts changes and fails on drift (manual test).
- [ ] Slice 4: `infra-ci.yml` — fmt + validate + plan. Skip the apply job here. Verify plan runs on a test PR.
- [ ] Slice 5: Add deploy job to `frontend-ci.yml` (Cloudflare Pages action, gated on push to main).
- [ ] Slice 6: Add deploy job to `backend-ci.yml` (flyctl, gated on push to main).
- [ ] Slice 7: Add apply job to `infra-ci.yml` with `environment: prod` gate. Document the manual approval step in README.
- [ ] Slice 8: Write `.github/workflows/README.md` documenting all secrets, triggers, and gates.

Dependencies between slices: Slices 1-4 are independent (different workflow files). Slices 5-7 depend on their respective CI workflow existing. Slice 8 last.

## Test plan

- Manual verification (via test PRs against `chore/migrate-claude-workflow` or a throwaway branch):
  1. Push a no-op change to `apps/frontend/README.md` — confirm only `frontend-ci` runs.
  2. Push a no-op change to `apps/backend/README.md` — confirm only `backend-ci` runs.
  3. Push a one-character whitespace change to `packages/shared-contracts/openapi.yaml` — confirm `contracts-ci`, `frontend-ci`, AND `backend-ci` all run.
  4. Push a no-op comment change to `infra/modules/fly/main.tf` — confirm only `infra-ci` runs and the `plan` job succeeds.
  5. Intentionally break the contracts (edit `apps/frontend/src/gen/api-types.ts` to mismatch `openapi.yaml`) — confirm `contracts-ci` fails.
- Lint: workflow files validated by `actionlint` locally if available (not required but encouraged).
- Smoke tests: existing Puppeteer smoke tests reused; one runs inside `frontend-ci`.

## Notes

- Required status checks (which workflows must pass before merge) are set in repo branch protection — NOT in this spec. User configures them after the workflows are stable.
- The `environment: prod` gate is a GitHub-native primitive that pauses the deploy job until a configured reviewer clicks approve. Documented in README; configured manually in repo settings.
- Backend deploy via `flyctl deploy --remote-only` builds the container image on Fly's builders, no Docker registry needed.
- If puppeteer smoke tests turn out to be flaky in CI (Chromium download time, headless issues), it's acceptable to mark them as `continue-on-error: true` for a follow-up — but lint + build must remain hard requirements.
- Per CLAUDE.md and `docs/conventions.md`: all PRs must be squash-merged; CI does not auto-merge.
