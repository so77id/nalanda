## Problem

The pilot course is "Estructuras de Datos en Java" but `CodeEditor` only supports C++ (`browsercc` + WASI) and Python (Pyodide). We need a Java runtime that follows the exact same worker pattern so a `language="java"` editor compiles + runs Java code in the browser with no server dependency. Per ADR-0003 we use CheerpJ 3.0, lazy-loaded inside a Web Worker, exposing the same postMessage contract as `cpp.worker.js` and `python.worker.js`.

This spec is blocked by **S3.1** (license verification). It must NOT start until S3.1 lands with verdict **OK**.

## Goals

- Add `runtimes/java.js` (metadata + factory) following the exact shape of `runtimes/cpp.js` and `runtimes/python.js`.
- Add `runtimes/java.worker.js` that:
  - Lazy-loads CheerpJ 3.0 from the official CDN (no eager import — first paint when Java is not selected must be unaffected).
  - Warms up on instantiation (posts `{type: 'warm', stats: {...}}` exactly like cpp/python workers).
  - Accepts `{id, source, stdin}` messages and replies with `{id, type: 'result', compileLog, output, exitCode, compileMs, runMs}` matching the existing contract that `useRuntime.js` consumes.
  - Surfaces compile errors via `compileLog` (non-empty when compilation fails, `output` empty, `exitCode` null).
  - Captures stdout AND stderr (merged into `output`, matching the cpp/python convention).
  - Honors `stdin` (CheerpJ accepts a `System.in` stream; the worker must wire the given string in).
- Register the runtime in `runtimes/index.js` so `runtimeList` and `getRuntime('java')` work.
- Honor any attribution requirements recorded in S3.1's ADR follow-up.

## Non-goals

- Touching `LanguageContext.jsx` or any UI (that's S3.3).
- Smoke test (that's S3.4).
- Server-side fallback (deferred per ADR-0003).
- `RemoteRuntime` abstraction (Fase B per decision L; this spec stays in Fase A).
- Optimizing bundle size beyond "lazy import inside the worker".
- Adding Java-specific features that don't exist for cpp/python (e.g. dependency resolution, multi-file projects).

## Design

**Files to create** (paths assume current layout `src/widgets/code-editor/...`; if E1/S1.1 monorepo reorg has landed first, paths become `apps/frontend/src/widgets/code-editor/...`):

- `src/widgets/code-editor/runtimes/java.js` — metadata + worker factory, mirror of `cpp.js`/`python.js`:
  ```js
  import { java } from '@codemirror/lang-java' // add as dep if not present
  export const meta = {
    id: 'java',
    label: 'Java 8',                // version exposed by CheerpJ 3.0
    fileName: 'Main.java',
    codeMirrorLanguage: java(),
    defaultCode: `public class Main {
  public static void main(String[] args) {
    System.out.println("hello");
  }
}
`,
    statsLabel: (stats) => `cheerpj ${stats.loadMs}ms · init ${stats.initMs}ms`,
  }
  export function createWorker() {
    return new Worker(new URL('./java.worker.js', import.meta.url), { type: 'module' })
  }
  ```
- `src/widgets/code-editor/runtimes/java.worker.js` — worker that:
  1. On module load, calls `warmUp()` which:
     - Dynamic `import('https://cjrtnc.leaningtech.com/3.0/loader.js')` (or the canonical CheerpJ 3.0 ESM URL confirmed in S3.1 — pin a version).
     - Calls `await cheerpjInit({ /* options as recommended by CheerpJ docs, e.g. clean classloader */ })`.
     - Posts `{ type: 'warm', stats: { loadMs, initMs } }`.
  2. On `message {id, source, stdin}`:
     - Writes `source` to a virtual FS path expected by CheerpJ (e.g. `/files/Main.java`).
     - Invokes `cheerpjRunMain('com.sun.tools.javac.Main', '/app/tools.jar:/files', '-d', '/files', '/files/Main.java')` (or the equivalent CheerpJ API for compiling — confirmed in CheerpJ 3.0 docs; pin the exact entrypoint in implementation).
     - If compile exit code is non-zero, capture compiler output → return `{compileLog, output: '', exitCode: null, compileMs, runMs: null}`.
     - Otherwise, invoke `cheerpjRunMain('Main', '/files', ...args)` with stdin wired via `cheerpjAddStringFile('/str/stdin.txt', stdin || '')` and redirecting `System.in` (consult CheerpJ stdin API — there's a documented mechanism).
     - Capture stdout/stderr via the CheerpJ display/console API (post-MVP we can pipe to a virtual console; consult docs in implementation).
     - Return `{compileLog: '', output, exitCode, compileMs, runMs}`.
  3. On any thrown error: post `{id, type: 'error', message}` — same as cpp/python workers.

  Pseudocode anchor (the **shape** is mandated; CheerpJ API names are confirmed at implementation time against CheerpJ 3.0 docs):
  ```js
  let cheerpjReady = null
  async function warmUp() {
    const t0 = performance.now()
    await import(/* @vite-ignore */ 'https://cjrtnc.leaningtech.com/3.0/loader.js')
    const loadMs = performance.now() - t0
    const tI = performance.now()
    await globalThis.cheerpjInit({ /* ... */ })
    const initMs = performance.now() - tI
    postMessage({ type: 'warm', stats: { loadMs: Math.round(loadMs), initMs: Math.round(initMs) } })
  }
  const warmPromise = warmUp()
  addEventListener('message', async (e) => {
    const { id, source, stdin } = e.data
    try {
      await warmPromise
      // ... compile, run, capture, post {id, type:'result', ...}
    } catch (err) {
      postMessage({ id, type: 'error', message: err.message ?? String(err) })
    }
  })
  ```

**Files to modify:**

- `src/widgets/code-editor/runtimes/index.js` — add `import * as javaRuntime from './java.js'` and include `java: javaRuntime` in the `runtimes` map. This single edit makes Java appear in `runtimeList` (which `LanguagePicker` iterates) and makes `getRuntime('java')` work.

## Acceptance criteria

- [ ] AC1: `runtimes/java.js` exports `meta` (id 'java', label, fileName 'Main.java', codeMirrorLanguage, defaultCode, statsLabel) and `createWorker()` — same shape as cpp.js/python.js.
- [ ] AC2: `runtimes/java.worker.js` lazy-loads CheerpJ via dynamic import inside `warmUp()` — no top-level static import that would force a load even when Java isn't selected.
- [ ] AC3: Worker accepts `{id, source, stdin}` and replies with `{id, type: 'result', compileLog, output, exitCode, compileMs, runMs}` — verified by writing a tiny scratch HTML/JS during development that instantiates the worker directly and posts a message. (Smoke test is S3.4, but a developer sanity check is required here.)
- [ ] AC4: A program that compiles and prints `Hello, World!` returns `output: 'Hello, World!
'` and `exitCode: 0`.
- [ ] AC5: A program with a compile error returns non-empty `compileLog`, `output: ''`, `exitCode: null`.
- [ ] AC6: A program that reads stdin and echoes it produces the correct output when the worker is called with a non-empty `stdin`.
- [ ] AC7: `runtimes/index.js` exposes Java via `runtimeList` (`getRuntime('java')` returns the module).
- [ ] AC8: Bundle analysis (manual via `npm run build` + checking dist size) shows CheerpJ is NOT loaded when only cpp/python editors are on the page. Java should only load when the worker is instantiated.
- [ ] AC9: Lint passes (`npm run lint`).
- [ ] AC10: Build passes (`npm run build`).
- [ ] AC11: Attribution requirements from S3.1 are honored (or N/A if S3.1 said none).

## Test plan

- Smoke tests: deferred to S3.4 (`smoke-test-java.mjs`).
- Manual verification: in `npm run dev`, open a page that mounts `<CodeEditor language="java" variant="lab" />`, wait for the "● listo" chip, click Ejecutar with the default code. Output should include `hello`. Then change source to invalid Java (e.g. missing semicolon), Ejecutar — `diagnostics` panel shows the compile error. Add stdin and a program that reads it (e.g. `BufferedReader`), verify output reflects stdin.
- Lint: `npm run lint`.
- Build: `npm run build` — confirm dist builds; manually inspect the dist for evidence that CheerpJ is not in the main bundle (should be in a separately chunked worker file or fetched at runtime from CDN).
